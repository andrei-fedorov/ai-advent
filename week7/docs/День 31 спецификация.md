# Неделя 7 — спецификация дня 31

Тема: ассистент разработчика. Неделя 7 — это серия небольших продуктов, каждый день свой: ассистент разработчика (день 31), AI-ревью PR (день 32), поддержка пользователей (день 33) и дальше по заданиям. Все они живут в каталоге `week7/` этого репозитория, со своими зависимостями и своим окружением, и **ничего не импортируют из `src/`**, чтобы `week7/` можно было вынести в отдельный репозиторий без правок. Продукт, вокруг которого они работают всю неделю, — сам TooManyRules: его README и спецификации — документация, его ветки и PR — материал для ревью, его сбои — материал для поддержки.

Продукт дня 31 — **`devhelp`**: ассистент в терминале, который отвечает на вопросы разработчика о проекте по команде `/help <вопрос>`. Перед ответом он ищет выдержки в документации проекта (README и `docs/`, RAG на локальной модели эмбеддингов с реранкером) и узнаёт текущую git-ветку у своего MCP-сервера `git_server.py`. Ещё три инструмента сервера — статус рабочего дерева, последние коммиты и diff — модель вызывает сама, если вопрос про них. Ответ — со ссылками `[N]` на выдержки; список источников с путём и строкой файла пишет код.

### 2.1. Схема

```
./week7/run.sh index ── README.md, docs/*.md, week7/README.md, week7/docs/*.md
                         │ md_chunks.py: разделы по заголовкам → куски
                         │ embedder.py: e5-base (ONNX, fastembed)

./week7/run.sh help
   /help <вопрос>
     1. search.py: 20 ближайших кусков → реранкер → 5 выдержек

     3. llm.py: системный промпт + ветка + выдержки + вопрос, инструменты git_status/git_log/git_diff
            └─ модель вызывает инструменты (через тот же MCP-сервер) → финальный ответ
     4. devhelp.py: ответ + «Источники: [N] путь:строка · раздел · день» + «Git: …»
```

### 2.2. Подготовка (делает человек)

1. `uv` установлен (`uv --version`).
2. `week7/.env` с `LLM_API_KEY=<ключ DeepSeek>` (тот же ключ, что `DEEPSEEK_API_KEY` в `src/.env`). Файл не коммитится.
3. `./week7/run.sh index` — первый запуск скачивает модели (≈1,7 ГБ, один раз, в `week7/data/models/`) и строит индекс.
4. `./week7/run.sh help`.

### 2.3. Корпус

По умолчанию (`settings.DOCS_GLOBS`, пути — от корня `--repo`):

- `README.md` — подпись «текущее состояние»;
- `docs/*.md` — спецификации, сравнения и проверки дней TooManyRules (день — из имени файла, `День (\d+)`), спецификация проекта, архитектура недели 2 и **архитектура кода TooManyRules** (`docs/TooManyRules — архитектура кода.md`, подпись «текущее состояние»);
- `week7/README.md`, `week7/docs/*.md` — продукты недели 7.

Шаблон, который ничего не нашёл, — строка предупреждения, не отказ; не нашёл ничего ни один шаблон — отказ (код 2).

**Архитектура кода индексируется, инструкции агентам — нет.** 14.10.2026 корневой `CLAUDE.md` разделён: общие правила для агентов — `AGENTS.md` (+ `CLAUDE.md` — символьная ссылка на него), устройство кода TooManyRules и решения дней 6–30 — `docs/TooManyRules — архитектура кода.md` (≈330 КБ). Архитектура — лучшее описание текущего кода, и как файл `docs/` она входит в корпус с подписью «текущее состояние» (список таких файлов — `settings.CURRENT_DOCS`). `AGENTS.md` и `CLAUDE.md` — инструкции агентам, а не документация проекта: в корпус не входят. Проверка до реализации (§2.4) шла **до** разделения — без архитектуры; с ней корпус больше примерно на десятую часть, а ответы на вопросы об устройстве кода (В1, В3) вероятно придут из неё — это видно на прогоне §12.

**Сравнения и проверки индексируются.** Они — часть `docs/`, задание называет папку целиком. Это крупнейшие файлы корпуса (сравнения дней 28 и 29 — около 0,5 МБ каждое, всего ≈35 % объёма) с дословными ответами модели о правилах игры; на проверке до реализации (§2.4) они спецификации из выдачи не вытеснили, но стоят треть времени полной сборки. Исключить — решение автора (шаблон-исключение `DOCS_EXCLUDE` в `settings.py`, по умолчанию пуст).

### 2.4. Проверка до реализации (14.10.2026)

Прототип нарезки и поиска на `fastembed` (scratchpad, не в репозитории), корпус по §2.3 без `week7/`:

- `fastembed` 0.9.0 и `onnxruntime` 1.31.0 ставятся на Python 3.14 (macOS arm64) без сборки; зависимости — 28 пакетов, без `torch`.
- Встроенных моделей `multilingual-e5-base` у `fastembed` нет (есть `-large`, 2,24 ГБ). e5-base подключается как своя модель (`TextEmbedding.add_custom_model`: `onnx/model.onnx` из `intfloat/multilingual-e5-base`, 1,1 ГБ, среднее по токенам, нормирование).
- Реранкеры `fastembed` с русским: `BAAI/bge-reranker-v2-m3` (2,27 ГБ), **`BAAI/bge-reranker-v2-m3-int8`** (0,57 ГБ, Apache 2.0), `jinaai/jina-reranker-v2-base-multilingual` (1,11 ГБ, **CC BY-NC 4.0** — только некоммерческое использование; для инструмента, который может пойти в компанию, отклонён).
- Корпус: 44 файла, 3 284 куска до 1 200 символов (в среднем 810).
- Скачивание: e5-base ONNX — 81 с, реранкер int8 — около 70 с (≈4 МБ/с). Загрузка из кэша: эмбеддер 1,5 с, реранкер 0,9 с.
- **Скорость на CPU — главная находка**: эмбеддинги всего корпуса — **762 с** (≈4,3 куска/с, ≈5 ядер); на 53 кусках — 5,0 куска/с. Реранк 20 пар — **4–5,7 с** на вопрос. Вывод: полная пересборка на каждую правку документа недопустима — **индекс пересчитывает только изменённые файлы** (§4.3).
- Оценка реранкера — **логиты**, не 0..1: на пробных вопросах от −4,2 до 6,8. Порога на дне 31 нет (§5.2).

### 2.5. Устаревшие факты

Спецификации — живые документы своего дня: спецификация дня N описывает проект на день N, и следующие дни её не переписывают. Поэтому на вопрос «сколько значений возвращает `_view()`» в корпусе есть ответы 31, 34, 37, 40, 41, 42 и 43. Поиск находит их все одинаково уверенно.

Что делает день:

- **подпись выдержки называет день**: `[2] docs/TooManyRules — День 14 спецификация.md:418 · 9. Технические требования · день 14`; у README и архитектуры кода (`CURRENT_DOCS`) — `· текущее состояние`; у остальных файлов без дня в имени — без пометки;
- **инструкция** (§5.1): документация копилась по дням; если выдержки расходятся, верна более поздняя; README и архитектура кода — текущее состояние; если в выдержках только старый день, сказать, к какому дню относится факт;
- поиск **не** поднимает поздние дни в выдаче и не отбрасывает ранние: это подгонка под один вид вопроса («как сейчас»), а вопрос «как было на дне 13» законен.

Покажет ли это достаточно — результат прогона (§12, вопрос В3).

### 3.1. `run.sh`

```

Без аргумента или с неизвестным — список команд и код 2. Ключ LLM `run.sh` не проверяет (его проверяет `devhelp.py`: индексу ключ не нужен).

## 4. Индекс: `md_chunks.py`, `embedder.py`, `docs_index.py`

### 4.1. `md_chunks.py` — нарезка (чистые функции)

Ни диска, ни модели, ни логов; вход — текст и имя файла, выход — список кусков.

- `Chunk`: `doc` (путь от корня репозитория), `section` (путь заголовков через « › », пусто — текст до первого заголовка), `part`/`parts` (часть длинного раздела, 1/1 у короткого), `line` (номер первой строки куска в файле, с 1), `text`.
- **Заголовок** — строка `#`…`######` с пробелом после решёток **вне** ограждённого блока кода (` ``` ` или `~~~`). Строка `# комментарий` внутри блока кода — не заголовок.
- **Раздел** — текст между заголовком и следующим заголовком любого уровня. Путь — стек заголовков: `### 3.4` под `## 3.` под `# …` даёт «Заголовок файла › 3. … › 3.4. …». Заголовок файла (единственный `#`) в путь входит: он называет документ.
- **Длинный раздел** (больше `CHUNK_MAX_CHARS` = 1 200) делится по пустым строкам (абзац, таблица, блок кода — целиком, пока помещаются); абзац длиннее предела — по строкам; строка длиннее предела — по пробелу. Блок кода между частями не разрывается, если помещается в предел целиком.
- Раздел из одного заголовка без текста куска не даёт.
- **Текст для эмбеддинга** — `<doc> · <section>\n<text>`: имя файла и путь заголовков помогают поиску («день 30», «Технические требования»). Модели в запросе уходит `text` с подписью отдельно (§5.1), без повтора.

### 4.2. `embedder.py` — модели (единственный импорт `fastembed`)

- `Embedder(model_name, cache_dir)`: регистрирует e5-base как свою модель (§2.4), если её нет во встроенных; `embed_passages(texts)` и `embed_query(text)` — **префиксы `passage: ` и `query: ` ставит только он**; векторы `float32`, нормированные. `count_tokens(text)` — токенизатором модели с префиксом (для отчёта индекса).
- `Reranker(model_name, cache_dir)`: `score(query, texts) → list[float]` — логиты, как отдаёт `fastembed` (§2.4); сигмоиду не применять: порога на дне 31 нет (§5.2), а порядок от неё не меняется.
- Провайдер ONNX — только `CPUExecutionProvider` (явно): CoreML на e5 убивает процесс (§2.4).
- Загрузка ленивая. `load(allow_download)`: индекс качает (`allow_download=True`), `devhelp` — нет: модели нет в кэше → `ModelMissing` с текстом «модели нет в кэше — запустите ./week7/run.sh index». Как именно `fastembed` запрещает скачивание (`local_files_only` или проверка файлов в `cache_dir`), — решение исполнителя по версии 0.9; результат — нет сетевых запросов у `devhelp`.
- `cache_dir` — `week7/data/models/` (`settings.MODELS_DIR`), **не** каталог по умолчанию `fastembed` (он во временном каталоге системы и чистится).

### 4.3. `docs_index.py` — программа индексации

`./week7/run.sh index [--repo <путь>] [--db <путь>] [--full] [--probe]`

1. Проверки (отказ — код 2, до загрузки модели): `--repo` существует и это корень git-репозитория (`git -C <repo> rev-parse --show-toplevel` совпадает); шаблоны §2.3 нашли хотя бы один файл; файл по `--db`, если есть, — свой индекс (ниже).
2. **Что пересчитывать.** Прежний индекс по `--db` есть, свой, и у него те же `schema`, `embed_model`, `chunk_max_chars` и `repo`, и нет `--full` — файл корпуса с тем же SHA-256, что в таблице `files`, берёт свои куски и векторы из прежнего индекса как есть; новый и изменённый файл нарезается и считается заново; файл, которого больше нет в корпусе, в новый индекс не попадает. Иначе — всё с нуля (строка лога с причиной: «другая модель», «`--full`», «индекса нет»…). Новый индекс пишется целиком в любом случае (ниже) — «пересчитать» значит не звать модель, а не править файл на месте.
3. Нарезка и эмбеддинги пакетами (прогресс — строкой раз в 10 с: «N из M кусков, ≈S с осталось»), запись.
4. Отчёт в stdout (`[Индекс]`): файлов (взято из прежнего индекса / пересчитано / удалено), кусков, по пересчитанным файлам (кусков, символов), длины кусков (средн., макс.), **токены** (макс. и сколько кусков длиннее 512 — модель такие обрезает молча; ожидается 0 при 1 200 символах, иначе строка предупреждения с файлами), время нарезки, загрузки модели, эмбеддингов, записи; HEAD репозитория.
4. `--probe` — без пересборки: пробные вопросы `settings.PROBE_QUESTIONS` → 20 ближайших → реранкер → печать 5 лучших с близостью и оценкой. Качает реранкер, если его нет (так индекс готовит обе модели для `devhelp`).

**Файл индекса** — SQLite, схема версии 1 (`PRAGMA user_version`):

- `meta(key, value)`: `schema`, `embed_model`, `dim`, `repo` (абсолютный путь), `globs`, `head` (sha HEAD на момент сборки), `built_at` (ISO), `chunk_max_chars`;
- `files(doc, sha256, size, chunks)` — по строке на файл корпуса;
- `chunks(id, doc, day, kind, section, part, parts, line, text, tokens, vec)` — `kind`: `current` (файл из `CURRENT_DOCS`) / `docs`; `day` — число или NULL; `vec` — `float32` байтами.

Запись — в `<db>.tmp` одной транзакцией и `os.replace()`. Чужой файл по пути (не SQLite, другая версия, версия 0 с таблицами, версия 1 без наших таблиц) не затирается — отказ, код 2 (правило дня 21). Инкрементальной сборки нет: индекс пересобирается целиком.

Коды: 0 — собран; 2 — отказ до работы; 1 — сбой посреди (файл по `--db` не тронут); 130 — Ctrl+C (не тронут).

### 5.2. `search.py` — поиск

`DocsIndex(db_path, models_dir)`: читает индекс целиком в память (строки + матрица), модели — из `meta` индекса, загрузка при первом вопросе без скачивания. `search(question) → SearchResult`:

### 5.3. `git_server.py` — MCP-сервер git

Отдельная программа, stdio, SDK v2 `MCPServer`, процесс на вопрос (его запускает `mcp_client` для каждого `/help`). Аргумент `--repo` (обязателен; `mcp_client` передаёт путь `devhelp`). Логи — только stderr, префикс `[git-сервер]`: stdout — канал JSON-RPC.

| Инструмент | Аргументы | Что отдаёт |
| --- | --- | --- |
| `git_branch` | — | имя ветки (или «detached HEAD at <sha>»), upstream и «впереди/позади на N/M», если upstream есть |
| `git_status` | — | изменённые файлы: индекс, рабочее дерево, неотслеживаемые; по строке на файл, не больше `STATUS_MAX_LINES` = 100 (остаток — «и ещё N») |
| `git_log` | `limit` 1..30, по умолчанию 10 | коммиты: короткий sha, дата, автор, тема, теги |
| `git_diff` | `staged` (bool), `path` (необязательно) | `--stat`, затем diff; не больше `DIFF_MAX_CHARS` = 12 000 символов, обрезка по границе строки с пометкой «обрезано: показано N из M» |

**Только чтение, фиксированные командные строки.** Каждая команда — список аргументов без оболочки: `git -C <repo> --no-pager <команда> <фиксированные флаги>`; от модели в командную строку попадают только `limit` (число из схемы) и `path` — после проверки, что путь относительный, без `..` и внутри репозитория (иначе `ToolError`), и всегда после `--`. Окружение процесса git — `GIT_OPTIONAL_LOCKS=0` (`git status` не обновляет индекс и не берёт `index.lock` — урок общего репозитория с автором), `GIT_TERMINAL_PROMPT=0`, `LC_ALL=C` для разбора. Потолок каждой команды — `GIT_TIMEOUT_S` = 10 с. Ошибка git (не репозиторий, нет коммитов) — `ToolError` с текстом stderr git: только текст `ToolError` доходит до клиента (урок дня 17).

**Описания инструментов — это промпт** (урок дня 17): по-русски, когда вызывать («что изменено сейчас», «над чем работали», «покажи изменения в файле»). Правки описаний по прогону — строкой в комментарии у константы описания.

Инструментов записи нет и не будет: ни `commit`, ни `checkout`, ни `reset`, ни `add`.

### 5.4. `mcp_client.py` — MCP-клиент

Единственное место, где импортируется клиентская часть SDK `mcp`. Асинхронный контекстный менеджер `McpSession(command, args, env, timeout_s)`: запускает сервер по stdio (`Client(StdioServerParameters(...))`, SDK v2), отдаёт `tools()` (все страницы `tools/list`) и `call(name, arguments) → ToolCall` (`ok`, `text`, `elapsed`, `error`). Сбои не бросает, возвращает со стадией (`запуск` / `соединение` / `вызов`) — правило дня 16. Окружение сервера — белый список SDK, без ключа LLM.

Одно подключение на один `/help`: ветка, каталог и все вызовы модели идут через него, затем процесс сервера закрывается. Проверка: после ответа `pgrep -fl git_server` пуст.

### 5.5. `llm.py` — вызов модели

Единственное место, где импортируется `openai`. `AsyncOpenAI(base_url, api_key)`. `answer(messages, tools, call_tool, params) → LlmResult`:

- цикл раундов function calling: модель → вызовы → результаты `tool` на каждый `tool_call_id` → модель; не больше `LLM_MAX_TOOL_ROUNDS` = 4 раундов с вызовами, затем финальный с `tool_choice="none"`; имя вне каталога и неразобранные аргументы на сервер не уходят (ответ `tool` с ошибкой); результат длиннее `TOOL_RESULT_MAX_CHARS` = 16 000 обрезается;
- `reasoning_content` раунда с `tool_calls` уходит обратно внутри хода (правило DeepSeek, урок дня 17);
- `LlmResult`: `text`, `finish_reason`, `rounds` (по раунду: время, токены, `finish_reason`, вызовы), суммы токенов, `cost_usd` (`None` для модели вне `PRICES`), `answered_model` (поле `model` ответа);
- ошибка API — `LlmResult(ok=False, error=…)`, без исключения наружу.

**Лог каждого раунда** (паттерн TooManyRules): модель, раунд, `finish_reason`, время, `prompt`/`completion`/кэш, стоимость, вызовы инструментов с аргументами. Цены — `settings.PRICES` ($ за 1M, `deepseek-flash` 0,15/0,60 — копия, не импорт).
