# Неделя 7 — спецификация дня 34

Тема: ассистент, который работает с файлами проекта. Неделя 7 — серия небольших продуктов в каталоге `week7/` (правила — `week7/AGENTS.md`): ассистент разработчика (день 31), AI-ревью PR (день 32), поддержка пользователей (день 33), работа с файлами (день 34). Демо-проект — TooManyRules из корня этого репозитория вместе с самим `week7/`.

Продукт дня 34 — **не новая программа, а расширение `help` дня 31**. Ассистент разработчика получает инструменты файлов. Он сам ищет и читает файлы проекта и предлагает правки Markdown-документов. Цель задаётся словами («проверь правило X», «обнови документацию под изменения кода»), а не «открой файл X». Правки ассистента — это **черновик и diff**, файлы на диске не меняются. Применяет их разработчик: на странице — кнопкой «Применить» у каждого файла, в CLI — флагом `--apply`. Каждый ответ с правками сохраняет `.diff`: его можно посмотреть и применить вручную через `git apply`. У `help` появляется **веб-страница** (`help --web`); CLI дня 31 остаётся.

## 2. Что делаем конкретно

### 2.1. Схема

```text
разработчик ──цель──► devhelp (CLI или --web через local_web)
                         ├─► search: выдержки current/docs (как день 31)
                         ├─► llm.answer: раунды function calling
                         │     ├─► MCP git_server: git_status, git_log, git_diff,
                         │     │                   project_files, project_grep, project_read
                         │     └─► локально: propose_edit, propose_file ──► file_changes: черновик
                         ├─► file_changes: unified diff ──► data/changes/<время>-<id>.diff
                         └─► ответ + diff по файлам
«Применить» (страница) / --apply (CLI) ──► MCP project_path_status ──► file_changes.apply(path)
```

Модель ничего не пишет на диск. Она видит только список инструментов из `DEVHELP_TOOLS` (§7). `project_path_status` вызывает код: перед принятием предложения и перед записью.

## 4. `git_server.py` — инструменты файлов

Сервер остаётся программой без импортов проекта: логи только в stderr, ожидаемый сбой — `ToolError`. Все вызовы git идут через существующую функцию `git()` (`--literal-pathspecs`, таймаут, `LC_ALL=C`). Константы — в начале файла, рядом с текущими.

**Список файлов проекта** — общая функция `project_list()`:

- `git ls-files -co --exclude-standard -z`: отслеживаемые и новые файлы, без игнорируемых;
- удалённые из рабочего дерева файлы отбрасываются;
- символьные ссылки остаются в списке и помечаются: их можно читать, но не править.

Glob-фильтр применяется в Python (`fnmatch` к относительному пути), потому что `--literal-pathspecs` отключает glob у git.

| Инструмент | Аргументы | Что возвращает | Ограничения |
| --- | --- | --- | --- |
| `project_files` | `glob: str \| None` | Пути по одному на строку, в конце «всего N» | `FILES_MAX = 300`, сверх — «и ещё N» |
| `project_grep` | `pattern: str`, `glob: str \| None`, `fixed: bool = False` | `путь:строка: текст` | `git grep -n -I --null --no-color --untracked` (`-F` при `fixed`, иначе `-E`), пути — отфильтрованный список после `--`. `GREP_MAX_MATCHES = 100`, строка обрезается до `GREP_LINE_MAX_CHARS = 200`. Нет совпадений — «совпадений нет», а не ошибка (код git 1) |
| `project_read` | `path`, `start_line = 1`, `end_line = None` | Шапка `путь, строки A–B из N`, затем строки с номерами `N│текст` | Путь — `validate_path` и наличие в `project_list()`. Только UTF-8 без `\0`. `READ_MAX_LINES = 300`, `READ_MAX_CHARS = 12000` (меньше `TOOL_RESULT_MAX_CHARS = 16000`, иначе `llm.py` обрежет ответ без пометки о продолжении). Пометка «обрезано», как у `git_show_file` |
| `project_path_status` (только для кода) | `path` | JSON: `{"status": "tracked" \| "untracked" \| "ignored" \| "absent", "symlink": bool}` | `git ls-files --error-unmatch`, `git check-ignore -q`, `os.lstat` на каждом компоненте пути. Модели не показывается (§7) |

`project_read` читает **рабочее дерево**, а `git_show_file` — ревизию. Описания у них разные, чтобы модель не путала, что вызывать.

Описания инструментов — это промпт. Тексты:

- `project_files`: «Список файлов проекта: отслеживаемые git и новые, без игнорируемых. glob — шаблон пути, например `week7/src/*.py` или `*.md`; без него — все файлы. Вызывай, чтобы узнать, какие файлы есть.»
- `project_grep`: «Найти строки в файлах проекта: путь, номер строки, текст. pattern — регулярное выражение, fixed=true — точная строка; glob — в каких файлах искать. Вызывай, чтобы найти все места использования имени, импорта, константы. Показывает до 100 совпадений.»
- `project_read`: «Прочитать файл проекта из рабочего дерева целиком или диапазоном строк, с номерами строк. Ответ ограничен 300 строками и 12000 символами; продолжение читай следующим диапазоном. Номера строк — не часть файла.»

Строки `project_grep` и `project_read` делятся только по `\n` (как `git grep`), завершающий `\r` у CRLF-строк не показывается. Если первая строка диапазона длиннее потолка ответа, `project_read` отдаёт её начало с пометкой «строка обрезана: N симв.», а не пустой ответ.

Лог сервера — как у остальных инструментов: имя подкоманды git и время.

## 5. `file_changes.py` — черновик, diff, применение

Лист: стандартная библиотека (`difflib`, `hashlib`, `os`, `pathlib`). Не вызывает git и не знает про MCP. Статус пути ему передаёт `devhelp` (результат `project_path_status`).

### 5.1. Проверки пути (общие для предложения и применения)

- Путь относительный, без `..` и `\0`, после `resolve()` внутри `--repo`.
- Расширение `.md` без учёта регистра. Иначе — «менять можно только Markdown (.md)».
- Ни один компонент пути не является символьной ссылкой. Иначе — «путь — символьная ссылка; правь файл, на который она указывает».
- Служебный каталог `.git` запрещён без учёта регистра: на macOS `.GIT/x.md` ведёт в `.git/`.
- Правка: статус `tracked` или `untracked`. Новый файл: `absent`, родительский каталог существует (каталоги не создаются) и путь не попадает под `.gitignore` (`check-ignore`). Статус `ignored` — всегда отказ.
- Текст — UTF-8. Концы строк файла сохраняются как есть (чтение и запись через `newline=""`).

### 5.2. Черновик одного ответа

`Draft` создаётся на каждый ответ: `id` — 8 hex-символов, `goal`, `files: dict[path, FileDraft]`. В `FileDraft` хранятся `kind` (`edit`/`new`), `original_sha256` (`None` для нового), `original_text` и `new_text`.

- `propose_edit(path, old, new)`. При первом обращении к файлу читается диск и запоминается SHA-256. Дальше правки применяются к тексту черновика по очереди. `old` должен встретиться **ровно один раз**, иначе ошибка модели: «фрагмент не найден» или «фрагмент встречается N раз — добавь соседние строки». `old == new` — ошибка. Удалять текст можно (`new` пустой).
- `propose_file(path, content)`. Если путь уже есть в черновике как новый, содержимое заменяется. Ограничение — `DEVHELP_NEW_FILE_MAX_CHARS`.
- `propose_edit` по пути, который в черновике уже новый файл, отвечает «для нового файла используй propose_file» до проверки диска (иначе было бы «файл не найден»).
- Больше `DEVHELP_MAX_CHANGED_FILES` файлов в черновике — отказ.
- Ответ инструмента модели — короткий: «правка принята: week7/README.md, +1 −1 (на диске не изменён)». Ошибки возвращаются текстом через `ToolCall(ok=False, …)`, как у MCP: модель может исправиться в следующем раунде.

### 5.3. Diff и файл `.diff`

- По каждому файлу строится `difflib.unified_diff` с 3 строками контекста. Заголовки — как у git, чтобы `git apply` их принял: `diff --git a/<путь> b/<путь>`, `new file mode 100644` и `--- /dev/null` для нового файла, `--- a/<путь>` / `+++ b/<путь>`. Пути пишутся без кавычек, в UTF-8. Если в файле нет перевода строки в конце — строка `\ No newline at end of file`.
- `write_patch(draft, out_dir, header)` пишет `<out>/<ГГГГММДД-ЧЧММСС>-<id>.diff`. До первой строки `diff --git` идёт шапка из строк, начинающихся с `#`: цель, репозиторий, HEAD, модель, раунды, инструменты по порядку, дата. `git apply` текст до первого заголовка пропускает. Файл создаётся, только если в черновике есть файлы.
- Для страницы и CLI по каждому файлу: путь, вид, `+N −M` и текст diff.

### 5.4. Применение одного файла

`apply(draft, path, status)` повторяет проверки §5.1. Затем:

- правка: текущий SHA-256 на диске совпадает с `original_sha256`, иначе отказ «файл изменился после предложения — попроси правку заново»;
- новый файл: файла всё ещё нет.

Запись: `<путь>.<id>.tmp` в том же каталоге, затем `os.replace`; права существующего файла сохраняются. Результат — `записан` / `отказ: <причина>`; файл помечается применённым. Повторное «Применить» того же файла — «уже применён». Отменять применение код не умеет: для этого есть `git`.

### 6.2. Один ответ — `async def ask(goal, repo, index, params, out_dir) -> Answer`

Порядок дня 31 сохраняется:

1. Поиск `current`/`docs` (в веб-режиме — `asyncio.to_thread`, как в `support_desk`).
2. Сессия MCP, `git_branch`, каталог инструментов.
3. Сообщения модели.
4. `llm.answer`.

Новое:

- В каталог модели идут MCP-инструменты из `DEVHELP_TOOLS` и две локальные схемы `DEVHELP_LOCAL_TOOLS` из `settings.py`.
- `call_tool` в замыкании: `propose_*` → `project_path_status` через ту же сессию → `file_changes`; остальное → `session.call`. Возвращается `ToolCall`; `llm.py` обрабатывает ошибки формата и завершение черновика (§15, исправление DSML).
- Параметры модели для `help` — свои (`DEVHELP_MAX_TOKENS`, `DEVHELP_MAX_TOOL_ROUNDS`, `DEVHELP_FINAL_TOOL_ROUNDS`, `DEVHELP_TOOL_TEXT_RETRIES`); `support` и `review` остаются на прежних.
- `llm.answer` получает необязательные `final_tools`, `final_tool_rounds` и `tool_text_retries`: после основного лимита `help` идёт стадия черновика (только `propose_*`), затем текстовый ответ без каталога инструментов; разметка DSML в `content` не исполняется и исправляется ограниченным числом повторов (§15).
- После ответа: если черновик не пуст — `write_patch`. Служебные вызовы кода (`git_branch`, `project_path_status`, `git_log` для HEAD) помечаются в `details.calls` полем `service` и в строку `# инструменты` шапки `.diff` не попадают.

`Answer` (dataclass) содержит:

- текст;
- источники (`citations.source_lines`);
- ветку;
- вызовы инструментов: имя, аргументы, время, размер ответа, ошибка, признак служебного вызова;
- `LlmResult`;
- черновик и путь к `.diff`.

Из него печатает CLI и собирает JSON сервер.

### 6.3. CLI

### 6.4. Страница (`--web`)

Сервер — `local_web` (§8), адрес `http://127.0.0.1:8834`. Черновики хранятся в памяти процесса, последние `DEVHELP_KEPT_DRAFTS` = 20. Старые удаляются, их `.diff` остаются на диске.

- `POST /api/chat` `{"goal": "…"}` → `{"answer", "sources", "branch", "change": {"id", "diff_path", "files": [{"path", "kind", "added", "removed", "diff", "applied"}]} | null, "details": {"query", "hits": [{"label", "sim", "score"}], "calls": [{"name", "arguments", "elapsed", "size", "error", "service"}], "rounds", "prompt_tokens", "completion_tokens", "cost_usd", "finish_reason"}}`. `devhelp_page.html` — один файл без внешних зависимостей, только `textContent` (никакого `innerHTML` для данных):

- Лента ответов. Каждый ответ независим, страница истории не отправляет.

  - источники `[N]`;
  - блок «Правки»: по файлу — путь, «новый»/«правка», `+N −M`, свёрнутый diff (строки `+`/`−` подсвечены классами), кнопка «Применить» и статус рядом с ней;

17.10.2026, реализация и ручные проверки:

- `git check-ignore` отвергает глобальный `--literal-pathspecs` («pathspec magic not supported … literal»). Только для этой подкоманды общая функция `git()` опускает флаг; перед путём остаётся `--`. Остальные команды сохраняют прежние параметры. `git grep` принимает код 1 как отсутствие совпадений, ошибки выражения возвращаются модели.
- Для новых файлов дополнительно запрещён служебный каталог `.git`, а в путях diff — переводы строк и табуляция. Чтение символьной ссылки допустимо, только если её цель тоже входит в список проекта: ссылка не открывает игнорируемые данные.
- Если последовательные правки вернули исходный текст, файл убирается из черновика: пустой diff не сохраняется как патч. Уникальность `old` проверяется также для перекрывающихся вхождений.
- Заголовки `---` / `+++` завершаются табуляцией перед переводом строки: так `git apply` однозначно разбирает UTF-8-пути с пробелами. Пустой новый файл описывается git-заголовком с хешем пустого blob.
- На первом реальном прогоне проверка правила и создание CHANGELOG исчерпали 10 раундов: финальный ответ содержал разметку незапущенных вызовов. Лимит `DEVHELP_MAX_TOOL_ROUNDS` поднят до 14. Промпт уточнён: независимые поиски и чтения объединять в раунде, не повторять поиск без причины, при недоступных инструментах завершать ответ по собранным данным.
- После второй попытки обновления порта модель также исчерпала 14 раундов, читая спецификацию и файл настроек подряд по частям. Промпт дополнен порядком действий: diff → поиск изменённых значений → правила и найденные фрагменты → предложения; исторические спецификации в этом сценарии не открывать. Для нового обзора — история, README и начала спецификаций. Повтор цели обновления порта завершился за 5 раундов с двумя предложениями.
- Первый прогон обновления порта предложил правки также в спецификации дня 33. Промпт уточнён: при синхронизации с текущим кодом исторические спецификации не переписываются; правила читаются в корне и каталогах правок. Это инструкция модели, а не проверка правил кодом.
- В итоговом тексте цели обновления порта модель написала «Обновил» до применения, вопреки промпту. Код не трактует эту фразу как запись: оба файла на странице оставались «на диске не изменён» до кнопок. Это наблюдение для автора, не оценка качества ответа.
- Проверки выполнены на клонах HEAD `3c5a303` (`day33`), с отдельной копией моделей и `--out`, своими портами 18844/18845. Четыре цели прогнаны с реальным API (разрешение автора 17.10.2026); замеры и последовательности — в `settings.py`. Проверки CLI/отказов/HTTP/CRM проводились также на стенде без LLM; поддержка использовала реальный MCP CRM, ответ модели был заменён стендом.
- Если LLM не завершила ответ после предложений, `.diff` всё равно сохраняется и доступен странице, но CLI с `--apply` не применяет неполученный ответ и возвращает 1.

17.10.2026, правки по ревью (Claude, по просьбе автора):

- `project_grep` и `project_read` делят текст только по `\n`, как `git grep`. Раньше `splitlines()` резал и по `\f`, `\v`, `\x1c–\x1e`, `\x85`, ` `: grep падал без пояснения на строке с таким символом, а номера строк `project_read` расходились с номерами grep. Завершающий `\r` у CRLF-строк в выводе не показывается.
- `project_read`: строка длиннее потолка ответа показывается началом с пометкой «строка обрезана: N симв.». Раньше ответ был пустым и звал читать с той же строки — модель зацикливалась.
- Запрет каталога `.git` для правок не зависит от регистра: на macOS `.GIT/x.md` вёл в `.git/`.
- `propose_edit` по пути, который в черновике уже новый файл, отвечает «для нового файла используй propose_file» до проверки диска (раньше — «файл не найден»).
- Вызовы, которые делает код (`git_branch`, `project_path_status`, `git_log` для HEAD в шапке `.diff`), помечаются в `details.calls` полем `"service": true` и на странице — «служебный». Строка `# инструменты` шапки `.diff` перечисляет только вызовы модели.
- Подсветка diff на странице различает заголовок и тело файла: удалённая строка `---` (`----` в diff) подсвечивается как удалённая.

## 17. Что сознательно НЕ делаем на этом шаге

- **Правку кода, конфигураций и любых не-`.md` файлов**: только чтение. Если цель требует кода — модель описывает правку словами.
- **Удаление, переименование файлов и создание каталогов.**
- **Инструмент записи у модели**: запись — только по кнопке или `--apply`.
- **«Применить всё» одной кнопкой** и отмену применённой правки: отменяет `git`.
- **Память разговора**: ни на странице, ни в CLI цель не видит прошлых ответов.
- **Коммит, ветку, push и PR** от ассистента.
- **Отдельный MCP-сервер файлов** и чтение файлов вне `git ls-files`.
- **Свой индекс кода для поиска мест использования** и разбор кода парсером: только `git grep`.
- **Проверку правил кодом**: правила читает модель из документов проекта, код их не знает и находки не оценивает.
- **Изменение `review`, `support` и индекса** сверх переименования веб-модуля.
- **Доступ к странице по сети, ключи и вход**: только `127.0.0.1`, как на дне 33.
