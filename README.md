# TooManyRules — день 13

Ассистент по правилам настольной игры Too Many Bones (Chip Theory Games).
Без RAG (он появится на неделе 5) — модель отвечает из общих знаний,
чтобы позже наглядно сравнить с версией, которая читает реальные правила.

С дня 6 вся работа с LLM вынесена в отдельную сущность — **агента**.
Агент владеет конфигом (системный промпт, модель, режим рассуждения,
температура, лимиты), сам ведёт стек сообщений, сам ходит в API, считает
токены и стоимость и пишет лог. Интерфейс — только вид на его состояние:
содержимое чата на каждом шаге рендерится из `agent.history`, своей копии
переписки Gradio не ведёт.

С дня 7 диалог переживает перезапуск приложения: история лежит на диске
по файлу на сессию, и при старте процесса агенты поднимаются из этих
файлов. Открытая страница сразу показывает тот же диалог — кнопки
«восстановить» в интерфейсе нет.

С дня 8 агент считает токены **до** запроса, а не только после: видно, из
чего складывается запрос, сколько это от контекстного окна модели и как
токены со стоимостью растут по ходам. Партия в Too Many Bones идёт несколько
часов, и каждый следующий вопрос тащит в модель весь предыдущий разговор —
день 8 показывает цену этого свойства в токенах и деньгах.

С дня 9 агент этой ценой **управляет**. Последние N сообщений уходят в модель
как есть, всё, что старше, сворачивается в короткую сводку — отдельным
служебным вызовом модели, который виден в панели и оплачен по той же таблице
цен. Стратегия переключается на живом диалоге, и это ключевое: стек сообщений
и файл сессии всегда остаются полными, сжимается **запрос, а не память**.
Поэтому один и тот же разговор можно отправить несколькими способами и
сравнить ответы.

День 10 добавляет ещё два способа собрать запрос и один способ разветвить
сам диалог:

- **«Скользящее окно»** — в модель уходят только последние N сообщений,
  всё старше отбрасывается из запроса без замены. Ни одного служебного
  вызова, запрос не растёт — плата идёт деталями, которые выпали из окна,
  а не токенами.
- **«Факты + последние N»** — отдельный блок «ключ — значение»
  (`цель`, `состав`, `коробки`, `герои`, `тиран`, `договорённости`,
  `поправки игрока` и т.д.), который служебный вызов обновляет **перед
  каждым ответом**. Дороже сводки по числу вызовов (два вызова на каждый
  ход вместо одного раз в несколько ходов), но не пересказывает, а хранит
  факты — и не размывается пересказом того, что уже не изменится.
- **Checkpoint и ветка диалога** — не пункт списка стратегий (у веток
  расходится сама история, а не способ её отправить), а отдельная сессия:
  «Сохранить checkpoint» фиксирует конец текущего диалога вместе со снимком
  памяти всех стратегий, «Ветка от checkpoint'а» порождает от этой точки
  новый независимый диалог со своим файлом, своей стратегией и своими
  счётчиками. От одного checkpoint'а можно завести сколько угодно веток —
  например, чтобы сравнить «а что, если бы мы выбрали другого тирана»,
  не смешивая варианты партии в одном разговоре.

Сравнение всех четырёх стратегий на одном сценарии — в
[`docs/TooManyRules — День 10 сравнение стратегий.md`](docs/TooManyRules%20—%20День%2010%20сравнение%20стратегий.md).

День 11 открывает неделю 3 и даёт агенту **модель памяти из трёх слоёв**,
разведённых по времени жизни. Партия заканчивается, игрок остаётся: коллекция
коробок, «отвечай коротко, я с телефона» и домашнее «спорное — в пользу
игроков» верны неделями, а герои, тиран и «в 21:00 надо закончить» — один вечер.

- **Краткосрочная** — разговор этой сессии: стек сообщений и стратегии
  дней 9-10. Лежит в файле сессии, уходит по «Сбросить диалог».
- **Рабочая** — данные текущей партии (цель, состав, герои, тиран,
  ограничения, договорённости партии, открытые вопросы). Перед каждым ответом
  её пополняет служебный вызов «разбор памяти»; лежит в том же файле сессии,
  в `context.working`, копируется в ветку и уходит со сбросом.
- **Долговременная** — игрок вообще: окружение (коллекция, игровая группа),
  решения (домашние правила) и знания (что игрок сообщил о правилах как
  проверенное). Лежит в отдельном файле `src/data/memory/long_term.json`,
  общем для всех сессий и агентов, и пишется **только с согласия человека**:
  разбор предлагает кандидатов, сохраняет их кнопка.

Какой ключ в какой слой — решает не модель, а **карта памяти** в
`presets.py`; переключатель «Слои памяти в запросе» меняет то, что уходит в
модель, а не то, что агент помнит. Проверка слоёв на сценарии из двух
сессий — в
[`docs/TooManyRules — День 11 проверка слоёв памяти.md`](docs/TooManyRules%20—%20День%2011%20проверка%20слоёв%20памяти.md).

День 12 добавляет ещё одну сущность — **профиль пользователя**, и это ни
пресет, ни память. Пресет выбирает разработчик — это параметры вызова модели
(роль, температура, лимиты). Профиль пишет сам пользователь в редакторе — это
как с ним работать: обращение, язык, уровень, ограничения и **режимы** под
задачу («За столом», «Учу новичка», «Разбор после партии»). Память выводится
из разговора и предлагается моделью; профиль модель не пишет и не предлагает
править никогда. Подробности — в разделе
[«Профиль пользователя» ниже](#профиль-пользователя-не-память-и-не-пресет-день-12).

День 13 даёт агенту **состояние задачи** — конечный автомат с этапом
(`планирование → выполнение → проверка → готово`), текущим шагом, ожидаемым
действием и планом с отметками. Партия — это данные («герои Patches и
Picket, тиран Drellen»), задача — это ход работы («шаг 3 из 5, шаги 1-2
выполнены, ждём подтверждения»), и ни одно в другое не пишется: рабочая
память (день 11) помнит первое, состояние задачи — второе.

- **Этап и шаг меняет только таблица переходов** (`task_state.TRANSITIONS`),
  а не модель: событие для перехода называет **трекер** — служебный вызов
  перед ответом — по разговору, или человек кнопками; допустим ли переход,
  решает код.
- **Пауза — не этап, а флаг** на любом из трёх активных этапов. Ставится и
  снимается словами (трекер понимает «давай прервёмся» и «мы вернулись») или
  кнопками «⏸ Пауза»/«▶ Продолжить». На паузе трекеру доступно только
  «продолжить», вопросы задачу не двигают.
- **Задачу начинает и отменяет только человек** — кнопками «Начать задачу с
  этим сообщением» и «Отменить задачу»; одна задача на сессию.
- **Блок состояния уходит в запрос сразу за рабочей памятью**, поэтому пауза
  и продолжение не зависят от того, что осталось в окне контекста —
  проверено на «Скользящем окне» намеренно тесным (см. документ проверки).
  Отказ трекера этого хода тоже попадает в блок, чтобы ассистент объяснил
  его пользователю, а не сделал вид, что переход состоялся.

Состояние и журнал переходов лежат в `context.task` файла сессии, переживают
перезапуск, копируются в ветку из снимка checkpoint'а и очищаются сбросом —
тем же приёмом, что рабочая память дня 11. Проверка паузы на каждом этапе и
продолжения с блоком и без него — в
[`docs/TooManyRules — День 13 проверка состояния задачи.md`](docs/TooManyRules%20—%20День%2013%20проверка%20состояния%20задачи.md).

## Что видно в приложении

Один экран без вкладок:

- **Слева — чат.** Многоходовый диалог: второй вопрос отвечает с учётом
  первого, потому что стек сообщений держит агент. Кнопка «Сбросить диалог»
  очищает стек и удаляет файл сессии, не сбрасывая счётчики агента (а с
  дня 10 — и checkpoint'ы с происхождением ветки, если они были); кнопка
  «Новый агент» поднимает ещё один экземпляр с текущим пресетом, а «Удалить
  агент» убирает активного из процесса вместе с его файлом (интерфейс
  переходит на оставшегося).
- **Сверху — выпадающий список пресетов.** Смена пресета создаёт **нового
  агента** с другим конфигом и пустым стеком — в том же процессе.
- **Под ним — переключатель стратегии контекста**, теперь на четыре пункта:
  «Вся история», «Сводка + последние N» (день 9), «Скользящее окно» и
  «Факты + последние N» (день 10). Соседний список с другой семантикой, и
  это подписано прямым текстом: пресет создаёт нового агента, а стратегия
  нового агента **не** создаёт и стек **не** трогает — меняется только то,
  что из истории уходит в модель начиная со следующего вопроса.
- **Ещё ниже — «Ветка диалога»** (день 10): третий переключатель с третьей
  семантикой — не новый агент, не другой запрос у того же агента, а **другая
  история**. Показывает исходный диалог и все его ветки; переключение меняет
  и стек, и файл, и стратегию, и счётчики на те, что у выбранной сессии.
- **Ещё ниже — «Слои памяти в запросе»** (день 11): флажки «долговременная»
  и «рабочая». Выключенный слой не уходит в модель, но продолжает
  записываться — разбор памяти идёт при любом положении, и включённый обратно
  слой сразу полон. Нового агента переключатель не создаёт и ничего не пишет
  на диск; краткосрочную память урезает стратегия.
- **Ещё ниже — «Профиль в запросе»** (день 12): `авто` (режим на этот ход
  выбирает роутер — служебный вызов модели), название режима (в запрос
  всегда уходит он) или `выключен` (профиль в запрос не уходит, сам профиль
  не трогается). Переключатель не создаёт агента и ничего не пишет — меняет
  запрос, а не профиль; у нового, восстановленного агента и у ветки всегда
  `авто`.
- **Ещё ниже — «Состояние задачи в запросе»** (день 13): выключенный блок не
  уходит в модель, но трекер продолжает вести задачу, и включённый обратно
  блок сразу актуален. Начинают и завершают задачу не этим переключателем, а
  кнопками под чатом.
- **Под кнопками «Отправить / Сбросить диалог / Новый агент / Удалить
  агент» — ряд кнопок задачи** (день 13): «Начать задачу с этим сообщением»
  (текст поля ввода становится целью), «⏸ Пауза», «▶ Продолжить», «Отменить
  задачу». Кнопки активны всегда — недопустимое нажатие отклоняет автомат, и
  в статусе видно почему.
- **Под строкой статуса — редактор профиля**, закрытый аккордеон: общая
  часть («как обращаться», «язык», «уровень», «ограничения») и режим для
  правки с полями «когда», «стиль», «формат», «ограничения», «порядок
  ответа». Единственная форма в интерфейсе — её поля не входят в общий вид
  на состояние агента, иначе любое действие затирало бы несохранённую
  правку. Кнопка «Сохранить профиль» проверяет профиль и пишет его в файл,
  общий для всех агентов и сессий; примеры «А · опытный игрок» / «Б ·
  новичок» заполняют общую часть одним кликом.
- **Под кнопками чата — ряд checkpoint'ов** (день 10): «Сохранить
  checkpoint» фиксирует конец текущей истории вместе со снимком памяти всех
  стратегий (с дня 11 — и рабочей памяти), список «Checkpoint» показывает
  checkpoint'ы активной сессии, а «Ветка от checkpoint'а» создаёт от
  выбранного новую сессию с копией общего начала истории — она сразу
  становится активной.
- **Под ним — ряд кандидатов** (день 11): «Кандидаты в долговременную
  память» с кнопками «Сохранить в долговременную» и «Отклонить». Пункт —
  ключ, предложенное значение и что было раньше; по умолчанию не отмечено
  ничего. Когда кандидаты есть, статус хода начинается с них: человеку есть
  что решить.
- **Справа — дебаг-панель:** конфиг агента (`AgentConfig`), стек сообщений
  (растёт на 2 за ход), метрики последнего вызова (время, `finish_reason`,
  токены, стоимость, оценка против факта, кэш промпта, служебный вызов этого
  хода — свёртка или обновление фактов, в зависимости от стратегии, разбор
  памяти с дня 11, роутер профиля с дня 12 и трекер задачи с дня 13),
  **«Профиль»** (день 12: где
  лежит файл, положение переключателя у этого агента, режим прошлого хода
  и режим следующего запроса с размером блока, общая часть и все режимы с
  пометкой активного и размером блока каждого), **«Слои памяти»** (день 11:
  по слою — что в нём лежит, где, в запросе ли он; рабочая память по
  ключам, долговременная по разделам «окружение / решения / знания» с
  сессией и временем записи, кандидаты, ждущие решения, и ключи вне карты
  последнего разбора), **«Состояние задачи»** (день 13: цель, этап на пути
  `планирование → выполнение → проверка → готово` с пометкой паузы, текущий
  шаг, ожидаемое действие, план с отметками ✓/→, допустимые сейчас события
  отдельно для человека и трекера, последний переход и последний отказ,
  размер блока в следующем запросе и полный журнал переходов; таблица
  автомата — в соседнем аккордеоне, закрытом по умолчанию), **«Контекст: что
  уходит в модель»** (стратегия,
  состав запроса, что осталось за бортом и чем заменено, экономия и итог
  «сэкономлено против потрачено на служебные вызовы»), **«Память
  стратегии»** (сводка или факты текстом — подпись зависит от активной
  стратегии), **бюджет контекста** (с дня 12 — отдельной строкой корзина
  профиля, с дня 13 — корзина задачи), **рост по ходам** (таблица ходов
  агента, с дня 10 — со временем ответа и служебного вызова, с дня 12 —
  режим хода, корзина профиля и токены/время роутера, с дня 13 — этап и шаг
  после хода, событие перехода, корзина и время трекера), **«Агенты
  процесса»** (день 10: расход по
  состоявшимся ходам каждого агента реестра рядом, без подсветки «лучшего»;
  с дня 12 — ещё и положение переключателя профиля и токены роутера, с
  дня 13 — этап/шаг задачи и токены трекера),
  накопленное агентом за время жизни (с дня 12 — отдельной строкой роутер
  профиля, с дня 13 — трекер задачи) и счётчики процесса.
  `reasoning_content` показывается свёрнутым блоком, когда модель его вернула.
  Выше переключателя агентов — блок **«Ветки диалога»** (день 10): что это
  за сессия (исходный диалог или чья-то ветка, жива ли связь с родителем),
  какие у неё checkpoint'ы и какие ветки от них уже созданы, и всё семейство
  сессий целиком. Под стеком сообщений — блок **«Хранилище»** (сессия, путь
  к файлу, сколько сообщений восстановлено при создании агента), **сырое
  содержимое файла сессии** и рядом с ним — **файла долговременной памяти**
  (день 11) и **файла профиля** (день 12): рабочая память лежит в первом,
  долговременная — во втором, профиль — в третьем, и три файла рядом и есть
  «профиль, пресет и память — три разные вещи».
- **Переключатель агентов** над стеком сообщений: в нём все агенты, поднятые
  с момента старта процесса (в том числе восстановленные из файлов) и ещё не
  удалённые. Выбор агента делает его активным: переключаются чат,
  стек, конфиг и метрики, и следующий вопрос уходит ему. Так видно, что
  инстансов действительно несколько и переписка у каждого своя; с дня 10
  подпись агента-ветки дополнена происхождением (`#6 · Базовый · s006 ·
  ветка от s005 · 14 сообщ.`).
- **Под чатом — пять блоков примеров.** Три вопроса дня 6, одиннадцать
  сообщений сценария сравнения стратегий (день 10: шаги 1-6, контрольные
  вопросы К1-К3, вторая ветка В2 и общий вопрос КВ), одиннадцать сообщений
  сценария проверки слоёв памяти (день 11: первая партия С1-С6 и К1-К3,
  следующая партия Н1 и Н3; Н2 — это К2), девять сообщений сценария
  проверки профиля (день 12: вопрос В1 для сравнения профилей и режимов,
  сообщения Р1-Р8 для роутера) и семнадцать сообщений сценария проверки
  состояния задачи (день 13: З1-З9, В1-В6, Г и Д) — клик кладёт текст в поле
  ввода, отправляет человек (З1 — кнопкой «Начать задачу с этим сообщением»).

Каждый вызов дополнительно логируется в stdout с номером агента, именем
пресета и сессией (`[#2 Базовый · s002]`) — терминал, где запущен `run.sh`,
остаётся основным инструментом отладки. Туда же идёт каждое обращение к
диску: `сохранено s002: 4 сообщ. → src/data/sessions/s002.json`.

### Пресеты

Один и тот же агент, разные конфиги — то, что на неделе 1 было разными
кусками кода:

| Пресет | Конфиг | Откуда |
| --- | --- | --- |
| Базовый | `SYSTEM_PROMPT`, `deepseek-flash`, thinking off | день 1 |
| Строгий JSON | промпт с требованием JSON, `max_tokens=350`, `stop=["###END###"]` | день 2 |
| Креативный | `SYSTEM_PROMPT`, `temperature=1.2` | день 4 |
| Флагман + thinking | `SYSTEM_PROMPT`, `deepseek-v4-pro`, thinking on | день 5 |

## История диалогов на диске

Одна сессия — один файл `src/data/sessions/sNNN.json`:

```json
{
  "version": 2,
  "session_id": "s001",
  "preset": "Базовый",
  "created_at": "2026-09-09T14:15:30",
  "updated_at": "2026-09-09T14:22:07",
  "context": {
    "strategy": "Сводка + последние N",
    "memory": {
      "Сводка + последние N": {
        "summary": "Играем базовой коробкой вдвоём, герои Пэтч и Тантрум…",
        "covered": 12,
        "updated_turns": 2
      }
    }
  },
  "messages": [
    {"role": "user", "content": "Из каких фаз состоит ход игрока?"},
    {"role": "assistant", "content": "Ход игрока состоит из..."}
  ]
}
```

Формат версии **2** с дня 9: рядом с историей на диск едет память стратегии.
Файлы версии 1 читаются как есть — нет ключа `context`, значит пустая память
и стратегия по умолчанию; миграций нет, первая же запись делает файл вторым.

**Формат не растёт и на дне 10.** Checkpoint'ы и происхождение ветки едут в
тот же непрозрачный блок `context` — новыми ключами `checkpoints` (у сессии,
где сохраняли checkpoint) и `branch` (у сессии, которая сама является
веткой), только непустые:

```json
"context": {
  "strategy": "Факты + последние N",
  "memory": { "Факты + последние N": {"facts": {"тиран": "Drellen"}, "covered": 14, "updated_turns": 8} },
  "checkpoints": [
    {"id": "cp1", "messages": 12, "strategy": "Факты + последние N", "memory": {"…": "снимок памяти на момент сохранения"}, "created_at": "2026-09-13T19:35:03"}
  ]
}
```

```json
"context": {
  "strategy": "Вся история",
  "memory": {},
  "branch": {"parent": "s005", "checkpoint": "cp1", "messages": 10, "created_at": "2026-09-13T19:35:03"}
}
```

**Не растёт формат и на дне 11.** Рабочая память — состояние сессии и едет
в тот же блок `context` ключом `working` (только непустая), а в каждый
checkpoint — своим снимком `working`:

```json
"context": {
  "strategy": "Скользящее окно",
  "memory": {},
  "working": {
    "entries": {"цель": "подготовиться к сегодняшней партии", "состав партии": "вдвоём с женой", "тиран": "Drellen"},
    "covered": 16,
    "updated_turns": 9
  }
}
```

Долговременная память с сессиями не связана, поэтому лежит **не в файле
сессии**, а отдельно — `src/data/memory/long_term.json`, сосед каталога
сессий. У каждой записи — сессия и время, когда человек её сохранил:

```json
{
  "version": 1,
  "updated_at": "2026-09-16T01:12:06",
  "entries": {
    "коллекция": {"value": "дома только базовая коробка, Undertow не наш — он у друга", "session_id": "s003", "updated_at": "2026-09-16T01:11:44"},
    "домашние правила": {"value": "спорное место в правилах всегда трактуем в пользу игроков", "session_id": "s003", "updated_at": "2026-09-16T01:10:45"}
  }
}
```

Файлы дня 10 кодом дня 11 читаются без предупреждений (ключа `working` нет —
рабочая память пуста). Кандидатов в долговременную память и положения
переключателя слоёв нет ни в одном файле.

Что важно знать:

- **Файл появляется с первой записью.** У обычной сессии это первый
  успешный ответ; у ветки (день 10) — момент создания, вместе с уже
  скопированной историей. Исчезает по «Сбросить диалог»: пустых файлов
  сессий не бывает — нет контекста, нет и сессии. Запись атомарная
  (временный файл рядом плюс `os.replace`), файл каждый раз переписывается
  целиком.
- **При старте процесса** приложение читает каталог и поднимает по агенту на
  каждую сессию — по возрастанию `session_id`, то есть в порядке создания.
  Сколько восстановлено, видно в логе старта и в строке статуса на странице.
- **На диск едут только история и имя пресета.** Системный промпт, модель и
  параметры остаются в коде (`presets.py`) и подтягиваются по имени пресета:
  правка промпта доезжает до восстановленных агентов. Имени нет в наборе —
  берётся пресет по умолчанию, приложение не падает.
- **Каталог данных не коммитится** (`src/.gitignore`): переписка и
  долговременная память — локальные данные. Путь переопределяется переменной
  окружения `TOOMANYRULES_DATA_DIR` — так поднимается второй экземпляр
  приложения, не перемешивая свою историю с рабочей. Долговременная память
  такого экземпляра ложится рядом с его каталогом сессий
  (`<каталог>/memory/`) и в память автора не пишет:

  ```bash
  TOOMANYRULES_DATA_DIR=/tmp/tmr-test GRADIO_SERVER_PORT=7861 python app.py
  ```

- **Приложение поднимается при любом состоянии каталога:** каталога нет, он
  пуст, в нём битый JSON или посторонний файл. Нечитаемая сессия пропускается
  с предупреждением в лог, её файл не перезаписывается, остальные
  восстанавливаются. Агент, не прочитавший свою историю, выключает себе
  запись — чтобы не затереть файл, который сегодня не прочитался.
- **Сбой записи не роняет ход:** ответ отдаётся как обычно, причина видна в
  логе и в блоке «Хранилище», а на следующем ходе запись повторяется.
- Метрики и счётчики на диск **не** сохраняются: восстанавливается контекст
  диалога, а не бухгалтерия — «потрачено» относится к запуску приложения.
  Сводка на диск едет именно потому, что она контекст: после перезапуска она
  на месте, и повторной свёртки не происходит. А журнал ходов и «сэкономлено»
  начинаются заново — это бухгалтерия. С дня 11 так же ведут себя рабочая и
  долговременная память (память, на месте после перезапуска) и кандидаты
  (вопрос к человеку в этом процессе, после перезапуска их нет).
- **Битый файл долговременной памяти не затирается:** память стартует
  пустой, запись в неё выключается, причина видна в логе и в панели. Сбой
  записи оставляет кандидатов ждать решения.

## Токены: оценка до запроса и факт после

С дня 5 токены считались только **после** вызова и только за один вызов — из
`usage` в ответе API. День 8 добавляет вторую сторону: сколько уйдёт в модель
**до** того, как мы туда сходим, из чего это складывается и сколько от лимита
модели уже занято.

- **Оценка и факт стоят рядом, и это принципиально.** Точное число до запроса
  дал бы только тот же токенизатор, что стоит на сервере модели: он
  раздаётся демо-зипом и тянет `transformers` — сотни мегабайт в проект с
  тремя строчками в `requirements.txt`, а `tiktoken` считает по правилам
  OpenAI, то есть не то, за что выставят счёт. Поэтому в `tokens.py` —
  эвристика по классам символов (кириллица / латиница / прочее; пробельные не
  считаются вовсе), а рядом всегда показан факт из `usage`.
- **Калибровка по собственному трафику.** У нас есть то, чего нет у
  токенизатора: после каждого вызова известно, сколько сервер насчитал ровно
  за ту строку, которую мы отправили. Агент копит отношение «факт / оценка» и
  применяет его к бюджету; первые же ходы подтягивают оценку к факту. На
  живом диалоге из 8 ходов на русском стартовые коэффициенты дали +6.7%
  расхождения (замер записан комментарием в `tokens.py`), калибровка снимает
  и это.
- **Бюджет контекста.** Окно модели берётся из таблицы `CONTEXT_WINDOW_TOKENS`
  и уменьшается на резерв под ответ (`max_tokens` из конфига, иначе
  константа): «занято 100%» не должно означать, что ответу места уже не
  осталось. Уровни занятости — `ok` / `warn` / `danger` / `over`, полоса и
  предупреждение в панели. Модели нет в таблице (локальная модель недели 6) —
  «н/д», без процентов и без падений, ровно как `estimate_cost_usd()`.
- **Рост по ходам.** Агент ведёт журнал успешных ходов, и панель показывает
  его таблицей: ход, стек до хода, оценка, `prompt`/`completion`/`total`,
  расхождение оценки с фактом, стоимость хода и накопительно; с дня 9 —
  стратегия хода, сколько сообщений ушло в модель, сколько ушло бы со всей
  историей и служебные токены, с дня 10 — время ответа и время служебного
  вызова. Главное, что
  видно — `prompt` растёт от хода к ходу, хотя вопросы одинаково короткие:
  n-й ход тащит в модель все предыдущие. Журнал ведёт себя как счётчики агента, а не
  как стек сообщений: «Сбросить диалог» его не чистит, на диск он не едет и
  после перезапуска пуст, хотя история восстановлена.

### Что происходит при переполнении

У поломки два конца, и в проекте есть оба:

- **на выходе** — `max_tokens` обрывает ответ на полуслове с
  `finish_reason=length`; это живёт в пресете «Строгий JSON» с дня 2;
- **на входе** — контекстное окно. С API это не «модель забудет начало
  диалога», а **отказ целиком**: ответа нет, ход не состоялся, стек сообщений
  и файл сессии не изменились, счётчик ошибок вырос.

Агент отправляет запрос, даже когда сам считает, что тот не влезет:
предупреждение в панели и в логе есть, предохранителя нет — и день 9 его не
добавил. Сжатие это способ до переполнения **не доходить**, а не проверка
перед вызовом.

Достать переполнение вручную нельзя — окно моделей V4 больше миллиона
токенов, столько не наговорить. Для этого в панели есть кнопка **«Набить
контекст»**: она кладёт в поле вопроса текст-заполнитель нужного размера и
ничего не отправляет — отправляет человек обычной кнопкой «Отправить».
Заполнитель, который **прошёл** в модель, остаётся в истории и дорожает с
каждым следующим ходом, так что после эксперимента диалог сбрасывается.

Размер окна — внешний факт, и он сверен с сервером: документация DeepSeek
говорит «1M», а переполненный запрос возвращает `400` с текстом
`This model's maximum context length is 1048576 tokens`. В таблице стоит
число из ошибки, а не из документации.

## Управление контекстом: четыре стратегии и одна ветка

День 8 показал проблему и ничего не починил: каждый ход тащит в модель весь
предыдущий разговор. День 9 эту кривую ломает первым способом — сводкой; день
10 добавляет ещё два способа собрать запрос («Скользящее окно», «Факты +
последние N») и один способ разветвить саму историю (checkpoint и ветка). Все
четыре стратегии сборки запроса и переключатель между ними в интерфейсе живы
на живом диалоге — и честно показывают, чем за приём платят.

### Сводка + последние N (день 9)

Как это работает:

- Параметры — константы `presets.py`: последние **6** сообщений уходят как
  есть, свёртка наступает, когда несвёрнутого хвоста набралось ещё на **6**
  сообщений сверх них (то есть впервые — на 12 сообщениях, дальше каждые
  3 хода). Длину сводки держит просьба в промпте — не длиннее **150** слов, а
  потолок служебного вызова (**800** токенов) — только страховка от обрыва на
  полуслове. Лимит в предложениях длину не держал: модель соблюдала число
  предложений и растягивала каждое.
- **Свёртка — отдельный вызов модели.** Сворачиваемые сообщения уходят текстом
  внутри одного `user`-сообщения (иначе модель отвечает на последний вопрос
  игрока вместо того, чтобы сворачивать диалог), с собственным системным
  промптом и всегда выключенным thinking. Предыдущая сводка — часть входа: на
  выходе получается **одна** сводка, покрывающая и её, и новые сообщения.
- **В запрос сводка встаёт ведущим `system`-сообщением** сразу после
  системного промпта и помечена как пересказ. Дальше идёт весь несвёрнутый
  хвост — `history[covered:]`, а не «последние 6»: сообщение не может выпасть
  из запроса, не попав перед этим в сводку.
- **Сводка хранит то, чего модель не знает.** Не пересказ формулировок
  правил, а какая игра и дополнение, каким составом играют, какие правила
  разобраны и **к чему пришли**, о чём договорились. Выводы обязательны:
  книги правил у модели нет до недели 5, Too Many Bones она знает плохо, и
  поправка игрока — ровно то, чего в её весах нет.
- **История не режется ни в стеке, ни в файле.** Сводка живёт отдельным полем
  рядом с полной перепиской.

### Скользящее окно (день 10)

Самая простая стратегия: в модель уходят только последние **6** сообщений
истории, всё старше отбрасывается из запроса **без замены** — ни служебного
вызова, ни пересказа. Плата — деталями: на прогоне сравнения к контрольному
вопросу о времени партии второе сообщение, где оно было названо, уже выпало
из окна, и модель назвала своё («примерно 2–3 часа» вместо «в 21:00 надо
закончить»), а на вопрос о договорённости из третьего сообщения ответила, что
договорённостей не было. Зато ни одного лишнего вызова, и запрос перестаёт
расти, как только диалог длиннее окна.

### Факты + последние N (день 10)

Отдельный блок «ключ — значение» (`цель`, `состав`, `коробки`, `герои`,
`тиран`, `договорённости`, `поправки игрока`, `открытые вопросы` и т.д.),
который служебный вызов обновляет **перед каждым ответом** — не пересказ, а
выжимка того, что понадобится, когда исходных сообщений в контексте уже не
будет.

- **Источник факта — только игрок.** Утверждения ассистента о правилах
  фактами не становятся, пока игрок их не подтвердил: книги правил у модели
  нет, Too Many Bones она знает плохо, и собственная ошибка, записанная в
  факты, подтверждала бы сама себя в каждом следующем запросе. Это главное
  правило промпта фактов. Остальные формулировки промпта подобраны на живом
  сценарии, и какой сбой закрывает каждая, записано в комментарии у
  `FACTS_PROMPT` в `presets.py`; замер итогового промпта — у
  `FACTS_MAX_TOKENS`.
- **Ответ модели — только изменения**, разбираются построчно в `context.py`:
  `ключ: значение` — новый или изменившийся факт, `ключ: удалить` — отмена,
  `нет изменений` — успешное обновление без правок. Поправка игрока — это
  новое значение ключа, а не удаление. Слияние, а не замена: факт, который
  модель забыла повторить, не теряется. Разбор прощает оформление: выделение
  и кавычки вокруг строки, ключа или значения срезаются, «нет изменений» с
  пояснением тоже понимается — иначе «**тиран**» встал бы отдельным ключом
  рядом с «тиран».
- **Платит служебным вызовом на каждом ходе** — дороже сводки по числу
  вызовов, но исправление (поправка игрока) обновляет тот же ключ на месте,
  а не тонет в пересказе шестью ходами позже.

### Checkpoint и ветка диалога (день 10)

Ветка — **не пункт списка стратегий**, а отдельная сессия: у веток расходится
сама история, а не способ её отправить, и внутри любой ветки работает любая
из четырёх стратегий.

- **«Сохранить checkpoint»** фиксирует конец текущей истории вместе со
  снимком памяти всех стратегий. Сами сообщения не копируются — история от
  checkpoint'а не укорачивается, а снимок памяти согласован с историей только
  в момент сохранения.
- **«Ветка от checkpoint'а»** порождает новый агент с новой сессией: история —
  копия префикса до checkpoint'а, память стратегий и активная стратегия — из
  снимка. Файл ветки пишется сразу, не после первого ответа: история у неё
  уже есть.
- **Копия, а не ссылка.** Сброс или удаление исходного диалога ветку не
  ломает — панель честно пишет, что связь с родителем потеряна. От одного
  checkpoint'а можно завести сколько угодно веток, и они не видят решений
  друг друга: на прогоне сравнения ни одна из двух веток не упомянула выбор
  соседней. Оговорка того же прогона: ветка с Drellen этого тирана не
  приняла и сама подставила Nom, так что на общий контрольный вопрос обе
  ветки назвали одного тирана (документ сравнения, §5).
- **Checkpoint не опережает историю.** Нажатый во время ответа, он
  дожидается конца хода: иначе в снимок попала бы память, уже обновлённая по
  вопросу, которого в истории ещё нет.

### Чем платит каждая стратегия

- **Сводка** — оплачивается сразу, а экономится потом. На коротком диалоге
  сжатие дороже, чем его отсутствие, и панель пишет это прямым текстом.
- **Окно** — платит деталями: что выпало из окна, модели узнать неоткуда.
- **Факты** — платят вызовом на каждом ходе, и это видно в журнале ходов
  числом (не только словом): в «Росте по ходам» у каждого хода две последние
  колонки — время ответа и время служебного вызова.
- **Ветки** — платят ручным управлением: сами по себе они ничего не сжимают,
  а checkpoint и ветку создаёт человек.
- **Служебный вызов считается наравне с обычными** — те же счётчики агента и
  процесса, та же оценка стоимости, та же строка в логе. Но это не ход: в
  стек сообщений он не пишет, строку журнала ходов не создаёт и метрики
  последнего вызова не затирает — там остаётся ответ игроку.
- **Сбой служебного вызова хода не отменяет.** Память не двигается, ответ
  приходит, причина видна в панели и в логе, а запрос собирается тем, что
  есть: деградация идёт в сторону «без сжатия», а не в сторону потерянного
  контекста. Обновление остаётся назревшим и повторится на следующем ходе.
- **Обрезанный ответ не проходит молча.** Если служебный вызов упёрся в
  потолок (`finish_reason=length`), результат применяется — иначе задача
  повторялась бы каждый ход за деньги, — но в логе предупреждение, а в панели
  и статусе хода пометка.

В логе служебный вызов виден одной строкой, и по ней понятно, что она дала —
формат общий для сводки и фактов, слова приходят от стратегии:

```
[#3 Базовый · s003] служебный вызов — свёртка сообщений #0-#5 (6 шт.) в сводку: учтено ≈1 436 токенов истории → сводка ≈257 токенов (сводка переписана, учитывает 6 сообщ.); 2.50s, tokens=2096/270/2366, cost=$0.000476
[#1 Базовый · s001] служебный вызов — обновление фактов по сообщениям #6-#7 (2 шт.) и новому сообщению: учтено ≈289 токенов истории → факты ≈192 токенов (~коробки; +открытые вопросы); 1.10s, tokens=1356/48/1404, cost=$0.000232
[#5 Базовый · s005] checkpoint cp1: 10 сообщ., стратегия «Вся история», снимок памяти стратегий: нет памяти
[#6 Базовый · s006] агент создан как ветка от s005 · cp1: общий префикс 10 сообщ., стратегия «Вся история», память стратегий из снимка checkpoint'а; живых агентов: 6
```

Заполнитель дня 8 при этом остаётся обычным сообщением истории и попадает под
общие правила стратегии — тяжёлое сообщение либо схлопывается в сводку, либо
выпадает из окна, либо превращается в несколько строк фактов.

Реальный прогон сценария на всех четырёх стратегиях и на ветках — числа,
дословные ответы и содержимое файлов — в
[`docs/TooManyRules — День 10 сравнение стратегий.md`](docs/TooManyRules%20—%20День%2010%20сравнение%20стратегий.md).

## Модель памяти: три слоя (день 11)

До дня 11 память агента была устроена по одному признаку — что отправить в
модель из разговора, — и вся исчезала вместе с разговором. День 11 разводит её
**по времени жизни**: разговор, партия, игрок.

| | Краткосрочная | Рабочая | Долговременная |
| --- | --- | --- | --- |
| Что это | разговор этой сессии | данные текущей партии | игрок вообще: окружение, решения, знания |
| Живёт | сессию | сессию — она же партия | не зависит от сессий и агентов |
| Где лежит | `src/data/sessions/sNNN.json` → `messages` | тот же файл → `context.working` | `src/data/memory/long_term.json` |
| Кто пишет | агент, каждым ходом | разбор памяти, сразу | разбор предлагает кандидата, записывает человек |
| В запросе | стратегия контекста | ведущим `system`-блоком | ведущим `system`-блоком, первым после системного промпта |

Сводка и факты дней 9-10 — не отдельный слой, а способ отправить краткосрочную
память короче.

### Карта памяти: слой выбирает не модель

`MEMORY_MAP` в `presets.py` — закрытый список ключей, у каждого слой, раздел и
описание:

- **рабочая часть** («партия»): `цель`, `состав партии`, `герои`, `тиран`,
  `сложность`, `ограничения`, `договорённости партии`, `открытые вопросы`;
- **долговременная часть**: `коллекция`, `игровая группа` (окружение),
  `домашние правила` (решения), `знания о правилах` (знания). Ключ `формат
  ответов` был здесь до дня 12 — как отвечать теперь профиль пользователя,
  а не память (подробности ниже).

Граница между слоями — «верно для этой партии» против «верно для игрока
вообще», а не тема: «договорённости партии» и «домашние правила», «состав
партии» и «игровая группа» — в разных слоях. Модель по описанию выбирает
**ключ**, слой ключа берётся из карты, ключ вне карты отклоняется и виден в
логе и панели.

### Разбор памяти

Перед каждым ответом — ещё один служебный вызов модели: на входе рабочая и
долговременная память, ждущие решения кандидаты, новые сообщения и новое
сообщение игрока; на выходе — только изменения в формате фактов дня 10
(`ключ: значение`, `ключ: удалить`, `нет изменений`), разбор строк общий с
фактами. Рабочие ключи сливаются в рабочую память сразу, долговременные
становятся кандидатами. Источник записи — только игрок: утверждения ассистента
о правилах записью не являются; какой сбой на живом сценарии закрывает каждое
правило промпта, записано у `MEMORY_PROMPT`. Разбор идёт при любом положении
«слоёв в запросе», считается в счётчиках агента и процесса, но **не** в
служебных вызовах стратегий — он ничего не экономит, он добавляет; в панели и
журнале ходов у него свои строки и колонки. Сбой разбора ход не отменяет:
память не двигается, разбор повторится на следующем ходе.

### Долговременная запись — только с подтверждения

Ошибка в рабочей памяти живёт до конца партии; ошибка в долговременной уходит
в каждый запрос каждой будущей сессии. Поэтому в долговременную память
попадает только то, что человек отметил в ряду кандидатов и сохранил кнопкой.
Кандидат — не память, а вопрос к человеку: в запрос не уходит, на диск не
пишется, в ветку не копируется, перезапуск не переживает; сказанное игроком
от отклонения не теряется — оно в истории разговора. На прогоне проверки
разбор один раз предложил в `знания о правилах` собственный вывод о правилах,
которого игрок не говорил, — кнопка «Отклонить» не пустила его в память
(документ проверки, §2).

### Слои в запросе, ветки и сброс

- **Переключатель «Слои памяти в запросе» меняет запрос, а не память** — тем
  же правилом, что стратегии дня 9. Положение переключателя — состояние
  агента, но не диалога: на диск не едет, у нового, восстановленного агента и
  у ветки оба слоя включены.
- **В запросе слои стоят от устойчивого к изменчивому:** системный промпт,
  долговременная память, рабочая, память стратегии, хвост истории, вопрос. В
  бюджете контекста и журнале ходов у слоёв свои корзины, а экономия стратегии
  считается без них.
- **Ветка** получает копию рабочей памяти из снимка checkpoint'а и ту же
  долговременную память; **сброс** чистит краткосрочную и рабочую, а
  долговременную не трогает; **удаление агента** уносит его разговор и
  рабочую память вместе с файлом сессии.

В логе слои видны теми же строками с номером агента и сессией:

```
[#3 Базовый · s003] разбор памяти по сообщениям #8-#9 (2 шт.) и новому сообщению: рабочая: без изменений; ждут подтверждения: коллекция, знания о правилах; вне карты: нет; finish_reason=stop 1.42s, tokens=1 896/51/1 947, cost=$0.000315; ответ: '…'
[#3 Базовый · s003] кандидат в долговременную память: коллекция = «дома только базовая коробка, Undertow не наш — он у друга» (было: «дома есть базовая коробка и Undertow») — ждёт решения
[#3 Базовый · s003] долговременная память: отклонено — знания о правилах = «Patches и Picket доступны в базовой коробке, для игры без Undertow подходят» (раньше ключа не было); в память не попало, сказанное осталось в истории разговора
[#3 Базовый · s003] долговременная память: сохранено 1 — коллекция; решение человека → src/data/memory/long_term.json
[#2 Базовый · s002] слои в запросе: рабочая → нет; стек и память не тронуты
```

Проверка слоёв на сценарии из двух сессий (первая партия со слоями и без,
следующая партия с долговременной памятью и без неё, ветка и сброс) — числа,
дословные ответы и оба файла — в
[`docs/TooManyRules — День 11 проверка слоёв памяти.md`](docs/TooManyRules%20—%20День%2011%20проверка%20слоёв%20памяти.md).

## Профиль пользователя: не память и не пресет (день 12)

После дня 11 агент знает мир игрока, но нигде не записано **как ему
отвечать**: во время боя нужен вердикт в пять строк, когда игрок объясняет
игру новичку — шаги и пример, после партии — разбор подробно. День 12 даёт
агенту профиль — явные настройки, которые пользователь пишет сам, а не
выводит модель.

| | Пресет | Профиль | Долговременная память |
| --- | --- | --- | --- |
| Кто задаёт | разработчик, в `presets.py` | пользователь, в редакторе | модель предлагает, человек подтверждает |
| Что описывает | как вызывать модель: роль, температура, лимиты, формат ответа | как работать с этим пользователем: обращение, уровень, режимы под задачу | что верно о мире пользователя: коллекция, домашние правила, знания |
| Где лежит | в коде; на диск едет только имя | `src/data/profile/profile.json` | `src/data/memory/long_term.json` |
| Как меняется | правкой кода; смена — новый агент | кнопкой «Сохранить профиль»; действует со следующего хода у всех агентов | кнопкой «Сохранить в долговременную» |
| Может ли изменить модель | нет | нет | только предложить |
| В запросе | системный промпт | блок сразу за системным промптом | блок после профиля |

### Общая часть и режимы

Профиль состоит из двух уровней. **Общая часть** верна для любой задачи:
обращение, язык ответов и названий, уровень в игре, ограничения во всех
ответах — все поля необязательные. **Режим** — профиль под одну задачу:
название, когда он нужен (по этому описанию выбирает роутер), стиль,
формат, ограничения и **порядок ответа** — шаги, из которых складывается
ответ. В запрос уходят общая часть и **один** режим, выбранный на этот
ход, — не все режимы сразу: иначе указания разных режимов конфликтовали бы
в одном запросе, а какой режим сработал, не было бы видно ни в логе, ни в
панели.

Профиль по умолчанию — три режима задачи игрока:

| Режим | Когда | Формат ответа |
| --- | --- | --- |
| **За столом** | партия идёт, нужен быстрый ответ по ситуации | не больше пяти пунктов, вердикт первым |
| **Учу новичка** | объясняете игру тому, кто не играл | пошагово, нумерованным списком, с примером |
| **Разбор после партии** | партия закончилась, есть время разобрать подробно | связный текст с подзаголовками |

Формат режима «За столом» — это бывший ключ памяти `формат ответов` дня 11,
перенесённый туда, где ему место: это настройка профиля, а не то, что агент
узнал о мире игрока.

### Кто выбирает режим

Переключатель **«Профиль в запросе»** у каждого агента:

- **`авто`** — режим на каждое сообщение выбирает **роутер**: служебный
  вызов модели перед ответом, на входе — режимы с описанием «когда», режим
  прошлого хода, последний обмен и новое сообщение, на выходе — одно
  название. Ключевые слова здесь не работают: «А если у меня дальняя
  атака?» после вопроса о бое — это продолжение «За столом», а «А что
  значат цифры на жетонах?» после объяснения новичку — продолжение «Учу
  новичка», хотя по словам оба вопроса игровые;
- **режим** — в запрос всегда уходит он, роутер не вызывается;
- **`выключен`** — профиль в запрос не уходит, роутер не вызывается,
  профиль при этом не стирается.

Роутер не вызывается, если выбирать не из чего (меньше двух режимов) или не
нужно (режим выбран вручную или выключен, вопрос пуст). Сбой роутера, пустой
или неразобранный ответ дают запасной режим — режим прошлого хода, если он
ещё есть в профиле, иначе первый режим списка; ход это не отменяет, как и
любой другой служебный вызов.

### Приоритеты в запросе

1. **Системный промпт пресета** — роль и технический формат ответа: JSON у
   пресета «Строгий JSON» профиль отменить не может.
2. **Текущий разговор** — «давай подробнее» важнее формата режима «За
   столом».
3. **Профиль** — явные настройки пользователя.
4. **Долговременная память** — выученное из прошлых разговоров.

Порядок блоков в запросе: системный промпт → **профиль** → долговременная
память → рабочая память → память стратегии → хвост истории → новый вопрос.

### Редактор — форма, а не вид

Интерфейс всюду остаётся видом на состояние агента, кроме одного места:
редактор профиля — это форма ввода, и её поля не входят в общий вид на
состояние агента. Иначе отправка вопроса или смена стратегии затирали бы
несохранённую правку. «Сохранить профиль» разбирает форму, проверяет
(в профиле должен быть хотя бы один режим, у каждого — непустое название,
без повторов и зарезервированных слов `авто`/`выключен`; при двух режимах и
больше — непустое «когда» у каждого) и пишет файл, только если что-то
изменилось. Файл общий для всех агентов и сессий процесса.

### Файл профиля на диске

```json
{
  "version": 1,
  "updated_at": "2026-09-16T22:58:38",
  "profile": {
    "address": "Саша, на «ты»",
    "language": "по-русски; названия героев — по-английски, как на коробке",
    "level": "играю больше года, базовые правила знаю — азы не объясняй",
    "constraints": "не предлагай хоум-рулы, пока я сам не попросил",
    "modes": [
      {"name": "За столом", "when": "…", "style": "…", "format": "…", "constraints": "…", "steps": ["…", "…"]}
    ]
  }
}
```

Нет файла — действует профиль по умолчанию из `presets.py`; после первого
сохранения источник — файл, и правка кода в него уже не доезжает (в отличие
от пресетов, где на диск едет только имя): профиль — данные пользователя, а
не промпт разработчика. Битый файл не затирается: профиль по умолчанию,
запись выключена, причина в логе и в панели.

### Что осталось от дня 11

Ключ `формат ответов` удалён из карты памяти — как отвечать теперь профиль,
а не то, что агент выучил; раздел долговременной памяти `профиль` у
`коллекция`/`игровая группа` переименован в `окружение`, чтобы не путаться с
новым блоком «Профиль пользователя» в запросе. В промпт разбора памяти
добавлено правило: просьбы о том, как отвечать (длина, формат, тон,
обращение, язык), — не запись памяти ни в какой ключ. Старая запись `формат
ответов` в уже существующем `long_term.json` не мигрирует и не удаляется —
она показывается в панели как «в файле, не используется» и не уходит ни в
запрос, ни во вход разбора; перенести её текст в профиль можно вручную, в
редакторе.

## Состояние задачи: конечный автомат (день 13)

Рабочая память (день 11) помнит **что** известно о партии; состояние задачи
помнит **где мы в работе** и чего ждём: этап, текущий шаг, ожидаемое
действие, план с отметками и журнал переходов. Ни одно в другое не пишется.

### Этапы, пауза и таблица переходов

Основной путь — `планирование → выполнение → проверка → готово`; вне него —
`отменена` (только по кнопке человека). **Пауза — не этап, а флаг** на любом
из трёх активных этапов.

| Этап | Ожидается от пользователя | Что делает ассистент |
| --- | --- | --- |
| планирование | утвердить план или сказать, что поправить | предлагает план — шаги и отдельно проверки |
| выполнение | сделать шаг N и сказать, что готово | объясняет только текущий шаг |
| проверка | подтвердить проверку N | проводит текущую проверку |
| готово / отменена | ничего | один раз подводит итог / подтверждает отмену |

Всё допустимое — таблица `task_state.TRANSITIONS`: событие, кто может его
вызвать (человек и/или трекер), из каких этапов, при каком флаге паузы, куда
ведёт переход и условие. Переход, которого в таблице нет для текущего
этапа/паузы/источника, — **отклоняется** с причиной, видной в логе, в панели
и — если отказал трекер — в блоке следующего запроса, чтобы ассистент
объяснил его пользователю. Этап и номер шага модель не пишет никогда —
только код, по таблице.

### Кто двигает автомат

- **Человек — кнопками**: «Начать задачу с этим сообщением», «⏸ Пауза»,
  «▶ Продолжить», «Отменить задачу».
- **Трекер — служебный вызов перед ответом**, четвёртый вокруг того же
  `_call_service_model()`, что свёртка/факты, разбор памяти и роутер
  профиля. На вход — состояние задачи и только допустимые сейчас события,
  на выход — одно событие (или «нет»). Не вызывается без задачи, на
  конечном этапе, на ходе «Начать задачу» и повторно на месте истории, где
  его переход уже применён.
- **Основная модель — никогда**: видит состояние в блоке запроса и ведёт
  разговор по нему, но переходов не объявляет.

Сбой трекера, как и любого служебного вызова, ход не отменяет. Исключение —
**обрезанный ответ не применяется вовсе** (в отличие от сводки, фактов и
разбора памяти): оборванный ответ трекера — это оборванный план, а
утверждённый план с потерянными шагами пользователь не заметит до этапа
проверки.

### Блок в запросе

Порядок блоков: системный промпт → профиль → долговременная память →
рабочая память → **состояние задачи** → память стратегии → хвост истории →
новый вопрос. На активном этапе (в том числе на паузе) блок уходит всегда;
на «готово»/«отменена» — только ходом сразу после перехода, дальше
завершённая задача в запрос не уходит, но остаётся в панели и в файле.
Переключатель «Состояние задачи в запросе» меняет это; трекер работает при
любом его положении.

### Где лежит и сколько живёт

Состояние и журнал переходов — в `context.task` файла сессии, тем же
приёмом, что рабочая память дня 11: переживают перезапуск, копируются в
ветку из снимка checkpoint'а, очищаются «Сбросить диалог». Переключатель
блока, последний отказ и расход трекера на диск не едут — это инструмент
проверки и бухгалтерия, а не диалог. Одна задача на сессию: начать новую
можно только когда задачи нет или она на этапе «готово»/«отменена».

Проверка паузы на каждом активном этапе и продолжения с блоком состояния и
без него (в ветке с выключенным переключателем, на «Скользящем окне» —
намеренно тесном, чтобы цель и план выпадали из окна) — в
[`docs/TooManyRules — День 13 проверка состояния задачи.md`](docs/TooManyRules%20—%20День%2013%20проверка%20состояния%20задачи.md).
На живом прогоне блок без окна восстанавливает номер шага по общим знаниям,
но путает его содержание и пересказывает шаги, которых просили не
пересказывать, — там же цитаты.

интерфейс.

Модель памяти и хранилище долговременной памяти (день 11), профиль и роутер
(день 12), автомат задачи (день 13) — пять необязательных зависимостей
агента, как хранилище истории и стратегии: без них агент ведёт себя ровно
как на дне 10 (без первых двух), как на дне 11 (без следующих двух) или как
на дне 12 (без автомата). Экземпляр модели памяти, роутера и автомата свой у
каждого агента (`presets.make_memory()`, `presets.make_router()`,
`presets.make_task_machine()`) — рабочая память, положение переключателя и
задача относятся к конкретному агенту; хранилища долговременной памяти и
профиля — по одному на процесс.

Стратегия подключена к агенту третьей зависимостью после конфига и хранилища
и, как хранилище, необязательна: без неё агент ведёт себя ровно как на дне 8.
Она — **состояние агента, а не поле `AgentConfig`**: конфиг заморожен и
описывает вызов модели, а стратегию переключают на живом агенте, не теряя
диалог. Протокол `ContextStrategy` объявлен в самом `context.py` (в отличие от
`HistoryStore`), потому что стратегия обменивается с агентом своими типами —
`ContextTask` и `StrategyState`; иначе `context.py` пришлось бы импортировать
`agent.py` и лист графа перестал бы быть листом.

Хранилище подключено к агенту через протокол `HistoryStore` (`load`/`save` по
`session_id`), объявленный в `agent.py` ещё на дне 6: день 7 подставил в эту
точку реализацию, не меняя публичный контракт агента. Туда же встанет SQLite,
когда появится VPS и несколько пользователей.

**Checkpoint и ветка (день 10)** — операция над самой историей, а не
стратегия и не зависимость агента: `Agent.save_checkpoint()` и `Agent.fork()`
работают со стеком сообщений и реестром напрямую. Ветка собирается через
параметр `seed` конструктора — тем же кодом (`_normalize_messages()`,
`_load_context()`), которым агент читает файл сессии, — чтобы в реестр не
попал недособранный агент (правило дня 6: регистрация последним шагом
конструктора). `branch_family()`/`branch_parent()` в `agent.py` вычисляют
семейство веток по происхождению агентов в реестре, а не по ссылкам,
хранимым у родителя.

## Запуск локально

```bash
./run.sh
```

Скрипт сам создаёт `src/.venv` (если его ещё нет), ставит зависимости и
запускает `src/app.py` на http://127.0.0.1:7860

Перед первым запуском нужно один раз положить API-ключ в `src/.env` — см.
шаг 2 ниже; без него приложение запустится, но на первый же вопрос ответит
понятной ошибкой вместо ответа модели.

### Пошагово вручную

Все команды выполняются из папки `src/` — код и виртуальное окружение
находятся там, а не в корне репозитория.

1. Перейти в `src/` и установить зависимости (Python 3.12+, проверено на 3.14):

   ```bash
   cd src
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

   Если системный Python старый, свежий ставится одной командой через [uv](https://docs.astral.sh/uv/):
   `uv python install 3.14 --default`.

2. Получить API-ключ DeepSeek на https://platform.deepseek.com
   и положить его в файл `.env` внутри `src/`:

   ```bash
   echo 'DEEPSEEK_API_KEY=...' > .env
   ```

   `.env` не коммитится в репозиторий (см. `src/.gitignore`).

3. Запустить (из папки `src/`, с активированным `.venv`):

   ```bash
   python app.py
   ```

   и открыть в браузере http://127.0.0.1:7860
