# TooManyRules — день 9

Ассистент по правилам настольной игры Too Many Bones (Chip Theory Games).
Без RAG (он появится на неделе 5) — модель отвечает из общих знаний,
чтобы позже наглядно сравнить с версией, которая читает реальные правила.

С дня 6 вся работа с LLM вынесена в отдельную сущность — **агента**.
Агент владеет конфигом (системный промпт, модель, режим рассуждения,
температура, лимиты), сам ведёт стек сообщений, сам ходит в API, считает
токены и стоимость и пишет лог. Интерфейс — только вид на его состояние:
содержимое чата на каждом шаге рендерится из `agent.history`, своей копии
переписки Gradio не ведёт.

С дня 7 диалог переживает перезапуск приложения: история лежит на диске
по файлу на сессию, и при старте процесса агенты поднимаются из этих
файлов. Открытая страница сразу показывает тот же диалог — кнопки
«восстановить» в интерфейсе нет.

С дня 8 агент считает токены **до** запроса, а не только после: видно, из
чего складывается запрос, сколько это от контекстного окна модели и как
токены со стоимостью растут по ходам. Партия в Too Many Bones идёт несколько
часов, и каждый следующий вопрос тащит в модель весь предыдущий разговор —
день 8 показывает цену этого свойства в токенах и деньгах.

С дня 9 агент этой ценой **управляет**. Последние N сообщений уходят в модель
как есть, всё, что старше, сворачивается в короткую сводку — отдельным
служебным вызовом модели, который виден в панели и оплачен по той же таблице
цен. Стратегия переключается на живом диалоге, и это ключевое: стек сообщений
и файл сессии всегда остаются полными, сжимается **запрос, а не память**.
Поэтому один и тот же разговор можно отправить обоими способами и сравнить
ответы.

## Что видно в приложении

Один экран без вкладок:

- **Слева — чат.** Многоходовый диалог: второй вопрос отвечает с учётом
  первого, потому что стек сообщений держит агент. Кнопка «Сбросить диалог»
  очищает стек и удаляет файл сессии, не сбрасывая счётчики агента; кнопка
  «Новый агент» поднимает ещё один экземпляр с текущим пресетом, а «Удалить
  агент» убирает активного из процесса вместе с его файлом (интерфейс
  переходит на оставшегося).
- **Сверху — выпадающий список пресетов.** Смена пресета создаёт **нового
  агента** с другим конфигом и пустым стеком — в том же процессе.
- **Под ним — переключатель стратегии контекста.** Соседний список с другой
  семантикой, и это подписано прямым текстом: пресет создаёт нового агента,
  а стратегия нового агента **не** создаёт и стек **не** трогает — меняется
  только то, что из истории уходит в модель начиная со следующего вопроса.
- **Справа — дебаг-панель:** конфиг агента (`AgentConfig`), стек сообщений
  (растёт на 2 за ход), метрики последнего вызова (время, `finish_reason`,
  токены, стоимость, оценка против факта, кэш промпта, свёртка этого хода),
  **«Контекст: что уходит в модель»** (стратегия, состав запроса, что осталось
  за бортом, экономия и итог «сэкономлено против потрачено на свёртки»),
  **«Память стратегии»** (сама сводка текстом), **бюджет контекста**,
  **рост по ходам** (таблица ходов агента), накопленное агентом за время
  жизни и счётчики процесса (сколько агентов создано, сколько потрачено
  суммарно).
  `reasoning_content` показывается свёрнутым блоком, когда модель его вернула.
  Под стеком сообщений — блок **«Хранилище»** (сессия, путь к файлу, сколько
  сообщений восстановлено при создании агента) и **сырое содержимое файла
  сессии**: одна и та же переписка, показанная в памяти и на диске.
- **Переключатель агентов** над стеком сообщений: в нём все агенты, поднятые
  с момента старта процесса (в том числе восстановленные из файлов) и ещё не
  удалённые. Выбор агента делает его активным: переключаются чат,
  стек, конфиг и метрики, и следующий вопрос уходит ему. Так видно, что
  инстансов действительно несколько и переписка у каждого своя.

Каждый вызов дополнительно логируется в stdout с номером агента, именем
пресета и сессией (`[#2 Базовый · s002]`) — терминал, где запущен `run.sh`,
остаётся основным инструментом отладки. Туда же идёт каждое обращение к
диску: `сохранено s002: 4 сообщ. → src/data/sessions/s002.json`.

### Пресеты

Один и тот же агент, разные конфиги — то, что на неделе 1 было разными
кусками кода:

| Пресет | Конфиг | Откуда |
| --- | --- | --- |
| Базовый | `SYSTEM_PROMPT`, `deepseek-flash`, thinking off | день 1 |
| Строгий JSON | промпт с требованием JSON, `max_tokens=350`, `stop=["###END###"]` | день 2 |

| Флагман + thinking | `SYSTEM_PROMPT`, `deepseek-v4-pro`, thinking on | день 5 |

## История диалогов на диске

Одна сессия — один файл `src/data/sessions/sNNN.json`:

```json
{
  "version": 2,
  "session_id": "s001",
  "preset": "Базовый",
  "created_at": "2026-09-09T14:15:30",
  "updated_at": "2026-09-09T14:22:07",
  "context": {
    "strategy": "Сводка + последние N",
    "memory": {
      "Сводка + последние N": {
        "summary": "Играем базовой коробкой вдвоём, герои Пэтч и Тантрум…",
        "covered": 12,
        "updated_turns": 2
      }
    }
  },
  "messages": [
    {"role": "user", "content": "Из каких фаз состоит ход игрока?"},
    {"role": "assistant", "content": "Ход игрока состоит из..."}
  ]
}
```

Формат версии **2** с дня 9: рядом с историей на диск едет память стратегии.
Файлы версии 1 читаются как есть — нет ключа `context`, значит пустая память
и стратегия по умолчанию; миграций нет, первая же запись делает файл вторым.

Что важно знать:

- **Файл появляется после первого успешного ответа** и исчезает по «Сбросить
  диалог»: пустых файлов сессий не бывает — нет контекста, нет и сессии.
  Запись атомарная (временный файл рядом плюс `os.replace`), файл каждый раз
  переписывается целиком.
- **При старте процесса** приложение читает каталог и поднимает по агенту на
  каждую сессию — по возрастанию `session_id`, то есть в порядке создания.
  Сколько восстановлено, видно в логе старта и в строке статуса на странице.
- **На диск едут только история и имя пресета.** Системный промпт, модель и
  параметры остаются в коде (`presets.py`) и подтягиваются по имени пресета:
  правка промпта доезжает до восстановленных агентов. Имени нет в наборе —
  берётся пресет по умолчанию, приложение не падает.
- **Каталог данных не коммитится** (`src/.gitignore`): переписка — локальные
  данные. Путь переопределяется переменной окружения `TOOMANYRULES_DATA_DIR` —
  так поднимается второй экземпляр приложения, не перемешивая свою историю с
  рабочей:

  ```bash
  TOOMANYRULES_DATA_DIR=/tmp/tmr-test GRADIO_SERVER_PORT=7861 python app.py
  ```

- **Приложение поднимается при любом состоянии каталога:** каталога нет, он
  пуст, в нём битый JSON или посторонний файл. Нечитаемая сессия пропускается
  с предупреждением в лог, её файл не перезаписывается, остальные
  восстанавливаются. Агент, не прочитавший свою историю, выключает себе
  запись — чтобы не затереть файл, который сегодня не прочитался.
- **Сбой записи не роняет ход:** ответ отдаётся как обычно, причина видна в
  логе и в блоке «Хранилище», а на следующем ходе запись повторяется.
- Метрики и счётчики на диск **не** сохраняются: восстанавливается контекст
  диалога, а не бухгалтерия — «потрачено» относится к запуску приложения.
  Сводка на диск едет именно потому, что она контекст: после перезапуска она
  на месте, и повторной свёртки не происходит. А журнал ходов и «сэкономлено»
  начинаются заново — это бухгалтерия.

## Токены: оценка до запроса и факт после

С дня 5 токены считались только **после** вызова и только за один вызов — из
`usage` в ответе API. День 8 добавляет вторую сторону: сколько уйдёт в модель
**до** того, как мы туда сходим, из чего это складывается и сколько от лимита
модели уже занято.

- **Оценка и факт стоят рядом, и это принципиально.** Точное число до запроса
  дал бы только тот же токенизатор, что стоит на сервере модели: он
  раздаётся демо-зипом и тянет `transformers` — сотни мегабайт в проект с
  тремя строчками в `requirements.txt`, а `tiktoken` считает по правилам
  OpenAI, то есть не то, за что выставят счёт. Поэтому в `tokens.py` —
  эвристика по классам символов (кириллица / латиница / прочее; пробельные не
  считаются вовсе), а рядом всегда показан факт из `usage`.
- **Калибровка по собственному трафику.** У нас есть то, чего нет у
  токенизатора: после каждого вызова известно, сколько сервер насчитал ровно
  за ту строку, которую мы отправили. Агент копит отношение «факт / оценка» и
  применяет его к бюджету; первые же ходы подтягивают оценку к факту. На
  живом диалоге из 8 ходов на русском стартовые коэффициенты дали +6.7%
  расхождения (замер записан комментарием в `tokens.py`), калибровка снимает
  и это.
- **Бюджет контекста.** Окно модели берётся из таблицы `CONTEXT_WINDOW_TOKENS`
  и уменьшается на резерв под ответ (`max_tokens` из конфига, иначе
  константа): «занято 100%» не должно означать, что ответу места уже не
  осталось. Уровни занятости — `ok` / `warn` / `danger` / `over`, полоса и
  предупреждение в панели. Модели нет в таблице (локальная модель недели 6) —
  «н/д», без процентов и без падений, ровно как `estimate_cost_usd()`.
- **Рост по ходам.** Агент ведёт журнал успешных ходов, и панель показывает
  его таблицей: ход, стек до хода, оценка, `prompt`/`completion`/`total`,
  расхождение оценки с фактом, стоимость хода и накопительно. Главное, что
  видно — `prompt` растёт от хода к ходу, хотя вопросы одинаково короткие:
  n-й ход тащит в модель все предыдущие. Журнал ведёт себя как счётчики агента, а не
  как стек сообщений: «Сбросить диалог» его не чистит, на диск он не едет и
  после перезапуска пуст, хотя история восстановлена.

### Что происходит при переполнении

У поломки два конца, и в проекте есть оба:

- **на выходе** — `max_tokens` обрывает ответ на полуслове с
  `finish_reason=length`; это живёт в пресете «Строгий JSON» с дня 2;
- **на входе** — контекстное окно. С API это не «модель забудет начало
  диалога», а **отказ целиком**: ответа нет, ход не состоялся, стек сообщений
  и файл сессии не изменились, счётчик ошибок вырос.

Агент отправляет запрос, даже когда сам считает, что тот не влезет:
предупреждение в панели и в логе есть, предохранителя нет — и день 9 его не
добавил. Сжатие это способ до переполнения **не доходить**, а не проверка
перед вызовом.

Достать переполнение вручную нельзя — окно моделей V4 больше миллиона
токенов, столько не наговорить. Для этого в панели есть кнопка **«Набить
контекст»**: она кладёт в поле вопроса текст-заполнитель нужного размера и
ничего не отправляет — отправляет человек обычной кнопкой «Отправить».
Заполнитель, который **прошёл** в модель, остаётся в истории и дорожает с
каждым следующим ходом, так что после эксперимента диалог сбрасывается.

Размер окна — внешний факт, и он сверен с сервером: документация DeepSeek
говорит «1M», а переполненный запрос возвращает `400` с текстом
`This model's maximum context length is 1048576 tokens`. В таблице стоит
число из ошибки, а не из документации.

## Управление контекстом: сводка вместо старой части истории

День 8 показал проблему и ничего не починил: каждый ход тащит в модель весь
предыдущий разговор. День 9 эту кривую ломает — и честно показывает, чем за
это платят.

Как это работает:

- **Две стратегии в переключателе.** «Вся история» — поведение дней 6-8 и база
  для сравнения; «Сводка + последние N» — сегодняшняя. Параметры — константы
  `presets.py`: последние **6** сообщений уходят как есть, свёртка наступает,
  когда несвёрнутого хвоста набралось ещё на **6** сообщений сверх них
  (то есть впервые — на 12 сообщениях, дальше каждые 3 хода), потолок сводки —
  **400** токенов. Крутилок в интерфейсе нет намеренно.
- **Свёртка — отдельный вызов модели.** Сворачиваемые сообщения уходят текстом
  внутри одного `user`-сообщения (иначе модель отвечает на последний вопрос
  игрока вместо того, чтобы сворачивать диалог), с собственным системным
  промптом и всегда выключенным thinking. Предыдущая сводка — часть входа: на
  выходе получается **одна** сводка, покрывающая и её, и новые сообщения.
- **В запрос сводка встаёт ведущим `system`-сообщением** сразу после
  системного промпта и помечена как пересказ. Дальше идёт весь несвёрнутый
  хвост — `history[covered:]`, а не «последние 6»: сообщение не может выпасть
  из запроса, не попав перед этим в сводку.
- **Сводка хранит то, чего модель не знает.** Не пересказ правил (их модель
  знает и без нас), а какая игра и дополнение, каким составом играют, какие
  темы разобраны и о чём договорились: «спорные места решаем по официальному
  FAQ, тренировочный режим не используем». Ровно это и нужно на тридцатом
  вопросе от пятого хода.
- **История не режется ни в стеке, ни в файле.** Сводка живёт отдельным полем
  рядом с полной перепиской. Поэтому переключение стратегии обратимо, сравнить
  «со сжатием / без сжатия» можно на одном и том же диалоге, а неудачная
  сводка стоит одного служебного вызова, а не разговора.

Чем платим:

- **Свёртка оплачивается сразу, а экономится потом** — на каждом следующем
  ходе. На коротком диалоге сжатие дороже, чем его отсутствие, и панель
  пишет это прямым текстом: рядом с «сэкономлено ≈N токенов» всегда стоит
  «потрачено на свёртки M токенов». Итог может быть отрицательным.
- **Служебный вызов считается наравне с обычными** — те же счётчики агента и
  процесса, та же оценка стоимости, та же строка в логе. Но это не ход: в стек
  сообщений он не пишет, строку журнала ходов не создаёт и метрики последнего
  вызова не затирает — там остаётся ответ игроку.
- **Сводка теряет детали.** Что именно потерялось, код не знает и знать не
  может: оценка качества в проекте всегда ручная. Задача кода — дать
  инструмент для сравнения: одна и та же история, два способа её отправить.
- **Сбой свёртки хода не отменяет.** Память не двигается, ответ приходит,
  причина видна в панели и в логе, а запрос собирается тем, что есть:
  деградация идёт в сторону «без сжатия», а не в сторону потерянного
  контекста.

В логе свёртка видна одной строкой, и по ней понятно, что она дала:

```
[#2 Базовый · s003] свёртка: сообщения #0-#5 (6 шт., ≈3 119 токенов) → сводка ≈67 токенов; служебный вызов 2.24s, tokens=3489/67/3556, cost=$0.000564
[#2 Базовый · s003] стратегия «Сводка + последние N»: в запросе 6 сообщ. из 12, ≈1 184 вместо ≈2 015 (−41%)
```

Заполнитель дня 8 при этом остаётся обычным сообщением истории и
сворачивается на общих основаниях — тяжёлое сообщение схлопывается в пару
строк сводки.

## Структура кода

| Файл | Назначение |
| --- | --- |
| `src/agent.py` | `AgentConfig`, `AgentReply`, `TurnStats`, `ServiceCall`, `ContextView`, `Agent`, протокол `HistoryStore`, счётчики процесса. **Единственное место, где вызывается LLM API** — с дня 9 в двух точках: основной вызов и служебный (свёртка). Не знает ни про Gradio, ни про Too Many Bones |
| `src/tokens.py` | Оценка токенов без обращения к API, разложение запроса по частям, таблица контекстных окон, бюджет контекста и генератор заполнителя. Чистые функции: ни сети, ни состояния, ни импортов из проекта |
| `src/context.py` | Стратегии управления контекстом: что из истории уходит в модель. Протокол `ContextStrategy`, «Вся история» и «Сводка + последние N». `prepare()` и `build()` чистые — их зовёт панель на каждый рендер; память меняет только `apply()`. Ни сети, ни Gradio, ни Too Many Bones, ни импортов из проекта |
| `src/presets.py` | Системный промпт проекта, набор конфигов агентов, промпт свёртки и реестр стратегий |
| `src/storage.py` | `JsonHistoryStore` — реализация протокола `HistoryStore` на JSON-файлах плюс каталог сессий. Не знает ни про Gradio, ни про Too Many Bones |
| `src/app.py` | Только интерфейс на Gradio: чат + дебаг-панель, LLM-логики не содержит |
| `src/app_week1.py` | Замороженный артефакт недели 1 (дни 1-5), вне графа импортов нового кода |

Направление зависимостей одностороннее: `app.py` → `presets.py` → `agent.py`
→ `tokens.py` и `context.py`, плюс `app.py` → `storage.py` и `app.py` →
`tokens.py` (оттуда интерфейс берёт только генератор заполнителя и оценку его
размера). Из проекта `agent.py` импортирует только листья графа, которые сами
не импортируют ничего. Благодаря этому агента можно позже поднять за HTTP или
переключить на локальную модель (`AgentConfig.base_url`), не трогая интерфейс.

Стратегия подключена к агенту третьей зависимостью после конфига и хранилища
и, как хранилище, необязательна: без неё агент ведёт себя ровно как на дне 8.
Она — **состояние агента, а не поле `AgentConfig`**: конфиг заморожен и
описывает вызов модели, а стратегию переключают на живом агенте, не теряя
диалог. Протокол `ContextStrategy` объявлен в самом `context.py` (в отличие от
`HistoryStore`), потому что стратегия обменивается с агентом своими типами —
`ContextTask` и `StrategyState`; иначе `context.py` пришлось бы импортировать
`agent.py` и лист графа перестал бы быть листом.

Хранилище подключено к агенту через протокол `HistoryStore` (`load`/`save` по
`session_id`), объявленный в `agent.py` ещё на дне 6: день 7 подставил в эту
точку реализацию, не меняя публичный контракт агента. Туда же встанет SQLite,
когда появится VPS и несколько пользователей.

Спецификации и промпты исполнителю лежат в `docs/` и `prompts/`
(`docs/TooManyRules — День 9 спецификация.md`,
`docs/TooManyRules — Неделя 2 архитектура.md`, `prompts/day9-prompt.md`).

## Запуск локально

```bash
./run.sh
```

Скрипт сам создаёт `src/.venv` (если его ещё нет), ставит зависимости и
запускает `src/app.py` на http://127.0.0.1:7860

Перед первым запуском нужно один раз положить API-ключ в `src/.env` — см.
шаг 2 ниже; без него приложение запустится, но на первый же вопрос ответит
понятной ошибкой вместо ответа модели.

### Пошагово вручную

Все команды выполняются из папки `src/` — код и виртуальное окружение
находятся там, а не в корне репозитория.

1. Перейти в `src/` и установить зависимости (Python 3.12+, проверено на 3.14):

   ```bash
   cd src
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

   Если системный Python старый, свежий ставится одной командой через [uv](https://docs.astral.sh/uv/):
   `uv python install 3.14 --default`.

2. Получить API-ключ DeepSeek на https://platform.deepseek.com
   и положить его в файл `.env` внутри `src/`:

   ```bash
   echo 'DEEPSEEK_API_KEY=...' > .env
   ```

   `.env` не коммитится в репозиторий (см. `src/.gitignore`).

3. Запустить (из папки `src/`, с активированным `.venv`):

   ```bash
   python app.py
   ```

   и открыть в браузере http://127.0.0.1:7860

## Неделя 1 — `app_week1.py`

Дни 1-5 были сравнительными экспериментами (A vs B, четыре способа
рассуждения, три температуры × три повтора, матрица «модель × thinking»),
и каждый жил своей вкладкой. Этот код заморожен отдельным запускаемым
артефактом и больше не редактируется:

```bash
./run.sh week1
```

Запускается тот же интерфейс с пятью вкладками, что и на теге `day05`.
Артефакт самодостаточен: он ничего не импортирует из нового кода и ничего
ему не отдаёт — поэтому дублирование системного промпта, констант DeepSeek
и таблицы цен между ним и `agent.py`/`presets.py` оставлено намеренно.
