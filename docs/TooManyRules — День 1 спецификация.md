# TooManyRules — спецификация дня 1

Тема: Первый запрос к LLM через API

Эта спецификация — техническое задание для AI\-ассистента, который будет писать код.

## 1\. Задание челленджа (день 1)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git\-репозитории): `tasks/AI Advent Challenge_01.txt`.

## 2\. Что делаем конкретно для TooManyRules

Минимальный веб\-чат на Gradio, который отправляет вопрос пользователя в DeepSeek API с системным промптом «ты ассистент по правилам настольной игры Too Many Bones» и показывает ответ. **Без RAG, без базы знаний, без сохранения истории между сессиями** — это всё будущие недели (см. общую спецификацию проекта). Ответ на этом этапе полностью полагается на общие знания модели о Too Many Bones — это осознанно, чтобы позже сравнить с версией, использующей RAG.

Многоходовый диалог в рамках одной открытой вкладки — это встроенное поведение стандартного `gr.ChatInterface` в Gradio и не требует отдельной реализации; специально управлять памятью/контекстом за пределами этого дня не нужно.

## 3\. Системный промпт (черновик)

```
Ты — TooManyRules, ассистент по правилам настольной игры Too Many Bones
(издательство Chip Theory Games) и её дополнений (Undertow, Age of Tyranny,
Splice & Dice, Unbreakable и другие).

Отвечай точно и по делу, ориентируясь на официальные правила игры.
Если не уверен в ответе — так и скажи, не выдумывай правила.
Отвечай на том языке, на котором задан вопрос (русский или английский).

Если вопрос не связан с Too Many Bones и настольными играми Chip Theory
Games — вежливо сообщи, что можешь помочь только с вопросами по правилам
этих игр.
```

Уточнение для ассистента\-разработчика: этот промпт — стартовая версия для дня 1, где ещё нет RAG. Смело оставляй его как константу в коде (не нужно выносить в конфиг/UI на этом этапе) — редактировать его по ходу следующих дней (2 и 3) будем отдельными задачами.

## 4\. Технические требования

- Язык: Python 3.
- Интерфейс: Gradio, компонент `gr.ChatInterface`.
- LLM\-провайдер: DeepSeek API (OpenAI\-совместимый REST API — можно использовать официальный SDK `openai` с изменённым `base_url`, либо прямые HTTP\-запросы через `requests`— на усмотрение ассистента\-разработчика, но предпочтителен вариант через `openai` SDK с `base_url` DeepSeek, это меньше кода).
- API\-ключ DeepSeek — только через переменную окружения (`.env` файл, не коммитить в репозиторий). Приложить `.env.example` с именем переменной без значения.
- Никаких внешних баз данных, файлов с правилами, векторных хранилищ — их нет ни в коде, ни в зависимостях на этом этапе.

## 5\. Структура репозитория (предложение)

```
too-many-rules/
├── app.py              # точка входа: запуск Gradio-приложения
├── requirements.txt    # gradio, openai (или requests), python-dotenv
├── .env.example        # DEEPSEEK_API_KEY=
├── .gitignore           # .env, __pycache__, venv и т.п.
└── README.md            # как запустить локально
```

`README.md` должен содержать: команду установки зависимостей, команду запуска, где взять и куда положить API\-ключ.

## 6\. Что должно быть видно в видео (день 1)

1. Запуск приложения (`python app.py`), открытие Gradio\-интерфейса в браузере.
2. 2\-3 вопроса по правилам Too Many Bones, например:
   - «Что такое Adrenaline и как она работает?»
   - «Можно ли использовать Fated Card после того, как атака уже объявлена?»
   - «What happens when a Baddie dies during the Adrenaline phase?»
3. Кратко показать код `app.py` — где формируется системный промпт и где происходит вызов DeepSeek API.

Видео не обязано быть длинным — 1\-2 минуты достаточно, задача организатора — увидеть, что запрос реально уходит во внешний API и возвращается ответ.

## 7\. Критерии приёмки

- Приложение запускается одной командой после установки зависимостей.
- Реальный вызов DeepSeek API происходит (не заглушка/не захардкоженный ответ).
- Системный промпт из раздела 3 задан в коде.
- Ключ API не закоммичен в репозиторий.
- Ответы модели релевантны вопросам про Too Many Bones (при этом не обязаны быть фактически точными — это ожидаемо на этом этапе, без RAG; сравнение с точным вариантом будет позже).

## 8\. Что сознательно НЕ делаем на этом шаге

- RAG / базу правил — неделя 5.
- Ограничение формата и длины ответа, стоп\-условия — день 2.
- Множественные стратегии рассуждения / «консилиум экспертов» — день 3.
- Управление памятью/состоянием между сессиями (не вкладками) — недели 2\-3.
- MCP\-интеграции — неделя 4.

Явно не расширяй объём задания сверх этого списка — цель дня 1 узкая и по заданию организатора минимальная.
