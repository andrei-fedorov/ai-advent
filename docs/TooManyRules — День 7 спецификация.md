# TooManyRules — спецификация дня 7

Тема: Сохранение контекста (история диалога на диске, восстановление при перезапуске)

## 1. Задание челленджа (день 7)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_07.txt`.

Ключевое из задания: история диалога (`messages`) хранится в JSON или SQLite; при перезапуске агента история загружается обратно; диалог продолжается так, **как будто агент не выключался**. Проверка практикой прописана в самом задании: начать диалог → перезапустить приложение → продолжить и убедиться, что агент помнит прошлые сообщения. Формат сдачи — видео + код.

Общие решения недели 2 (заморозка недели 1, отказ от вкладок, раскладка модулей, конвенции) описаны в `docs/TooManyRules — Неделя 2 архитектура.md`, контракт агента и устройство интерфейса — в `docs/TooManyRules — День 6 спецификация.md`. Этот документ их не повторяет и опирается на них.

## 2. Что делаем конкретно для TooManyRules

День 6 закончился ровно на границе сегодняшнего задания: в `agent.py` объявлен протокол `HistoryStore` (`load`/`save` по `session_id`), агент принимает `session_id` и необязательный `store`, но реализаций хранилища в проекте нет и `store` всегда `None`. Сегодня в эту точку подставляется реальное хранилище — и доводится до конца всё, что из этого следует:

1. **Новый модуль `src/storage.py`** — `JsonHistoryStore`: реализация протокола на JSON-файлах (по файлу на сессию) плюс каталог сессий (перечислить, удалить, дать путь и содержимое файла).
2. **Минимальные правки `src/agent.py`** — сколько сообщений пришло из хранилища при создании агента и что сбой хранилища не роняет `ask()`. **Публичный контракт агента не меняется**: ни сигнатур, ни протокола, ни порядка вызовов. В этом и был смысл задела дня 6, и сегодня он проверяется на практике.
3. **`src/app.py`** — агенты восстанавливаются из файлов один раз при старте процесса, открытая страница сразу показывает восстановленный диалог, дебаг-панель показывает файл на диске рядом со стеком в памяти.

Продуктовый смысл для TooManyRules: партия в Too Many Bones идёт несколько часов и переживает и закрытую вкладку, и перезапуск приложения. Вопрос «а если в этой фазе выпал Encounter?» должен продолжать тот же разговор, а не начинать новый.

### 2.1. Почему JSON, а не SQLite

Задание допускает и то, и другое; общая спецификация проекта (§3) фиксирует JSON на локальном старте и SQLite — с появлением VPS и нескольких сессий/пользователей. Архитектурный документ недели 2 держал этот выбор открытым до сегодняшнего дня (§7). Фиксируем JSON:

- один локальный пользователь и десятки сообщений — SQLite здесь решал бы несуществующую проблему;
- **файл видно**: на видео открывается `sNNN.json` рядом с приложением, и в нём те же самые `messages`, что в дебаг-панели. С таблицей SQLite этот кадр не снимается;
- замена реализации ничего не стоит: агент знает только протокол `HistoryStore`, и SQLite-реализация подставится в ту же точку без правок агента и интерфейса. Ровно это сегодня и демонстрируется — день 6 объявил интерфейс, день 7 подставил реализацию.

Открытое решение из `docs/TooManyRules — Неделя 2 архитектура.md` (§7) считается закрытым этим разделом.

## 3. Формат хранения

Каталог данных: `src/data/sessions/`. Создаётся при первой записи, в git не попадает (см. §7). Путь переопределяется переменной окружения `TOOMANYRULES_DATA_DIR` — нужно, чтобы поднять второй экземпляр приложения, не перемешав его историю с рабочей.

Одна сессия — один файл `<session_id>.json`. `session_id` вида `s001`, `s002`, … — порядковый номер с ведущими нулями: файлы сортируются по возрастанию в порядке создания, и в логах сессия читается глазом.

```json
{
  "version": 1,
  "session_id": "s003",
  "preset": "Флагман + thinking",
  "created_at": "2026-09-09T14:15:30",
  "updated_at": "2026-09-09T14:22:07",
  "messages": [
    {"role": "user", "content": "Из каких фаз состоит ход игрока?"},
    {"role": "assistant", "content": "Ход игрока состоит из..."}
  ]
}
```

Требования к формату:

- **`json.dump(..., ensure_ascii=False, indent=2)`, кодировка UTF-8.** Русский текст в файле должен читаться как русский текст, а не как `\u0425\u043e\u0434` — иначе главный кадр видео («вот он, диалог на диске») не работает.
- **На диск едет история и имя пресета, но не сам конфиг.** Системный промпт, модель и параметры остаются в коде (`presets.py`) и подтягиваются по имени пресета при восстановлении: правка промпта в коде должна доезжать до восстановленных агентов, а не оставаться перекрытой копией годичной давности.
- `version` — задел на дни 8-10: сжатие контекста, скорее всего, добавит в файл сводку. Миграций сейчас не пишем, поле нужно, чтобы старый файл можно было опознать.
- `reasoning_content` в файл не пишется — его нет и в стеке агента (день 6, API не принимает рассуждение обратно в контекст).
- В `messages` только пары `{"role": "user"|"assistant", "content": str}` — тот же вид, в котором стек ведёт агент.

## 4. Модуль `src/storage.py`

Реализация протокола `HistoryStore` плюс то, что нужно интерфейсу для работы с каталогом сессий. Модуль **не знает ни про Gradio, ни про Too Many Bones** и **не импортирует `presets.py`**: направление зависимостей `app.py` → `storage.py` → `agent.py` (за протоколом; импорт из `agent.py` допустим только ради `HistoryStore`, и без него можно обойтись — протокол структурный).

```python
DATA_DIR: Path            # src/data/sessions, переопределяется TOOMANYRULES_DATA_DIR

class StorageError(Exception):
    """Файл сессии не прочитался или не записался."""

@dataclass(frozen=True)
class SessionInfo:
    session_id: str
    preset: str | None        # None, если в файле его нет
    messages: int             # сколько сообщений в файле
    created_at: str
    updated_at: str
    path: str

class JsonHistoryStore:
    def __init__(self, data_dir: Path | None = None) -> None: ...

    # --- протокол HistoryStore (объявлен на дне 6, не меняется) ---
    def load(self, session_id: str) -> list[dict]: ...
    def save(self, session_id: str, messages: list[dict]) -> None: ...

    # --- каталог сессий: этим пользуется только app.py ---
    def create_session(self, preset: str) -> str: ...   # выдать новый session_id
    def sessions(self) -> list[SessionInfo]: ...        # по возрастанию session_id
    def delete_session(self, session_id: str) -> bool: ...
    def path_for(self, session_id: str) -> Path: ...
    def read_file(self, session_id: str) -> dict | None: ...  # сырое содержимое для панели
```

Требования к поведению:

- **`load`**: файла нет → пустой список (это нормальная ситуация, а не ошибка). Файл не читается или в нём не JSON нужной формы → `StorageError`. Отдельные битые записи внутри `messages` (нет `role`/`content`, роль не `user`/`assistant`, не строка) — **отбрасываются с предупреждением в лог**, остальные возвращаются: одна испорченная строка не должна стоить всего диалога.
- **`save`**: файл переписывается целиком и **атомарно** — запись во временный файл рядом плюс `os.replace`, чтобы падение посреди записи не оставило половину диалога. Инкрементальной дозаписи нет: файл маленький, а простота здесь дороже.
- **`save` с пустым списком удаляет файл**, если он есть, и не создаёт, если его нет. Отсюда правило: **пустых файлов сессий не бывает**. Файл появляется после первого успешного ответа и исчезает по «Сбросить диалог» — нет контекста, нет и сессии. Иначе каталог за пару дней зарастает пустышками, а после перезапуска в переключателе висят агенты без единого сообщения.
- **`create_session`** выдаёт следующий свободный номер и **файла не создаёт** — только резервирует `session_id` и запоминает имя пресета в памяти процесса (оно понадобится первой записи). Номер берётся как максимум по файлам на диске и по всем номерам, выданным за этот запуск: **номера сессий в пределах процесса не переиспользуются** — по той же причине, что и номера агентов на дне 6. Иначе новый агент мог бы получить `session_id` живого агента, у которого файл только что удалили сбросом, и они начали бы писать в один файл.
- **Прочитанные метаданные кэшируются**: имя пресета, увиденное в `sessions()`/`load()`, запоминается в памяти — если файл восстановленной сессии исчез (сброс диалога), следующая запись восстановит его с правильным пресетом, а не с пустым.
- **`sessions()` не бросает исключений**: нечитаемый или чужой файл в каталоге пропускается с предупреждением в лог. Приложение обязано подниматься при любом содержимом каталога данных.
- **Логируется каждое обращение к диску** — тем же паттерном, что вызовы агента: `загружено s003: 6 сообщ.`, `сохранено s003: 8 сообщ. → src/data/sessions/s003.json`, `файл сессии s003 удалён`. Логи в этом проекте — основной инструмент отладки, и «дошло ли до диска» должно быть видно в терминале, а не только в панели.
- **Один `Lock` на выдачу номеров и кэш метаданных**: Gradio обрабатывает запросы в пуле потоков (то же обоснование, что у реестра агентов на дне 6). Разные сессии пишут в разные файлы, поэтому сериализовать сами записи не требуется.
- Экземпляр хранилища в приложении **один** на процесс и общий для всех агентов: `session_id` разводит их по файлам.

## 5. Что меняется в `src/agent.py`

Правки минимальные и все — про «хранилище есть, но агент от него не зависит». Сигнатуры `__init__`/`ask`/`reset`/`history`, протокол `HistoryStore` и порядок вызовов (`load` в конструкторе, `save` после успешного хода и после `reset`) **остаются как есть**.

- **`restored_messages`** — свойство и поле в `debug_state()`: сколько сообщений пришло из хранилища при создании агента. Нужно панели: после первого же хода `len(history)` растёт и «сколько было восстановлено» иначе не показать.
- **Сбой хранилища не выходит наружу.** `ask()` по контракту дня 6 не бросает исключений, а `_persist()` вызывается внутри него — значит вызовы `store.load`/`store.save` заворачиваются в `try/except`:
  - **ошибка на загрузке (конструктор)** → агент стартует с пустым стеком, **запись для него выключается**, причина кладётся в `store_error`. Это не перестраховка: агент с выключенной записью не затрёт файл, который сегодня не прочитался, а завтра, возможно, ещё починится;
  - **ошибка на записи** → ход состоялся, ответ пользователю отдаётся как обычно, причина кладётся в `store_error` и в лог (уровень `warning`), запись при следующем ходе повторяется — разовый сбой диска не должен переводить агента в режим «только память» навсегда;
  - успешная запись `store_error` очищает.
- **`debug_state()`** дополняется полями `restored_messages` и `store_error`; `store` (имя класса хранилища) и `session_id` там уже есть с дня 6 — теперь в `store` будет `JsonHistoryStore` вместо `None`.
- **Префикс логов агента** становится `[#3 Базовый · s003]`: в дне, где у каждого агента появился файл, номер процесса и имя сессии нужны в логе рядом.

Ничего другого в `agent.py` не трогаем. В частности, сборка сообщений (`_build_messages`) остаётся точкой дня 8 и сегодня не меняется: в модель уходит вся восстановленная история целиком.

## 6. Что меняется в `src/app.py`

Интерфейс остаётся видом на состояние агента; своей копии переписки Gradio по-прежнему не ведёт.

- **Хранилище создаётся один раз** на модуле: `STORE = JsonHistoryStore()`.
- **Восстановление агентов — один раз при старте процесса**, до `demo.launch()`, а не в `demo.load`: `demo.load` срабатывает на каждую открытую вкладку браузера и плодил бы копии. Порядок — по возрастанию `session_id` (он же порядок создания), поэтому восстановленные агенты получают номера процесса `#1..#N` в том же порядке, в каком сессии заводились.
- **Пресет восстанавливается по имени** из `PRESETS`. Имени нет в наборе (пресет переименовали или убрали) → берётся `DEFAULT_PRESET`, факт пишется в лог и в строку статуса. Падать из-за этого приложение не должно.
- **Открытие страницы больше не создаёт агента, если в реестре кто-то есть.** `on_load` берёт активным последнего агента реестра (сессию с наибольшим номером — она же последняя заведённая) и только при пустом реестре поднимает нового. Ровно так же уже ведёт себя «Удалить агент» на дне 6. Угадывать «последнюю активную» сессию по времени не нужно: остальные агенты никуда не делись и берутся одним кликом в переключателе. Это прямое следствие задания: после перезапуска пользователь открывает страницу и **видит свой диалог**, а не пустой чат рядом с восстановленными агентами в переключателе. День 6 на каждое открытие страницы поднимал нового агента — это поведение меняется сознательно.
- **Строка статуса при открытии страницы** говорит, что произошло: `Восстановлено 3 агента из src/data/sessions. Активен #3 «Базовый» · s003: 6 сообщ. из файла.` Если восстанавливать было нечего — привычное «Поднят агент … с пустым стеком».
- **«Новый агент» и смена пресета** заводят сессию через `STORE.create_session(preset)` и передают агенту `session_id` и `store`. Файла до первого ответа не появляется.
- **«Сбросить диалог»** — как и раньше, `agent.reset()`; теперь тот же вызов удаляет и файл сессии (следствие правила «пустой список — удалить файл»). Счётчики агента, как и на дне 6, сохраняются.
- **«Удалить агент»** дополнительно удаляет файл сессии: `agent.delete_agent(number)` **и** `STORE.delete_session(agent.session_id)`. Иначе «удалённый» агент возвращался бы из файла на следующем запуске. Счётчики процесса, как и на дне 6, не откатываются.
- **Дебаг-панель** получает два новых блока — под стеком сообщений, чтобы «в памяти» и «на диске» были в кадре рядом:
  - **«Хранилище»** (`gr.Markdown`): класс хранилища и каталог данных; `session_id` активного агента и путь к его файлу; сколько сообщений восстановлено при создании агента; сколько сообщений сейчас в файле и когда он обновлён; отдельной строкой — `store_error`, если он есть. Файла ещё нет → так и написать: появится после первого успешного ответа.
  - **«Файл сессии на диске»** (`gr.JSON`): сырое содержимое файла через `STORE.read_file(...)`. Перечитывается на каждом событии интерфейса — поллинга и автообновления, как и на дне 6, нет.
- **Подписи в переключателе агентов** дополняются `session_id`: `#2 · Базовый · s002 · 6 сообщ.`
- **`_view()` возвращает кортеж из 13 значений** вместо 11: новые значения добавляются **в конец** кортежа и в конец `VIEW_OUTPUTS` — порядок значений остаётся частью контракта всех обработчиков.

## 7. Технические требования

- **Новых зависимостей нет**: `json`, `pathlib`, `threading`, `datetime`, `os` — стандартная библиотека. `requirements.txt` не меняется.
- **Промпты, пресеты и параметры запросов не меняются вообще.** День 7 — про хранение, а не про поведение модели: `presets.py` сегодня не редактируется.
- `src/data/` добавляется в `src/.gitignore`: переписка — локальные данные пользователя, в репозиторий она не едет. В коммите дня не должно быть ни одного файла сессии.
- В `app.py` и `presets.py` по-прежнему нет ни `client.chat.completions.create`, ни создания `OpenAI(...)`; в `storage.py` их нет тем более.
- Замороженный `src/app_week1.py` не трогается: он не знает ни про агента, ни про хранилище и запускается как раньше (`./run.sh week1`).
- Приложение обязано подниматься при любом состоянии каталога данных: каталога нет, каталог пуст, в каталоге битый JSON, в каталоге посторонний файл.
- `README.md` дописывается под текущее состояние: сохранение истории, каталог данных, что происходит при перезапуске, переменная `TOOMANYRULES_DATA_DIR`.
- В конце дня — коммит и тег `day07`.

## 8. Что должно быть видно в видео

1. `ls src/data/sessions` (или отсутствие каталога) — истории нет. Запуск `./run.sh`, в панели: сессия `s001`, файла ещё нет.
2. Первый вопрос по правилам → ответ; в панели появился путь к файлу и его содержимое, в терминале — строка `сохранено s001: 2 сообщ. → …`. Рядом в терминале `cat src/data/sessions/s001.json`: тот же диалог, читаемым русским текстом.
3. Второй вопрос, ссылающийся на первый ответ → стек 4 сообщения, файл обновился.
4. **`Ctrl+C` в терминале** — процесс убит, приложение мертво. `./run.sh` снова; в логе старта видно, сколько сессий восстановлено.
5. **Обновление страницы: диалог на месте** — без единого нажатия, кнопки «восстановить» в интерфейсе нет. В панели: «восстановлено 4 сообщ. из `s001`».
6. **Вопрос, опирающийся на сказанное до перезапуска** («а что я спрашивал в самом начале?» / «а если …?») → корректный ответ; в метриках `prompt_tokens` заметно больше, чем был бы на пустом стеке, — вся история действительно ушла в модель.
7. Второй агент с другим пресетом, один вопрос ему, ещё один перезапуск → восстановлены оба, в переключателе видны обе сессии, стеки не перемешались.
8. «Сбросить диалог» → файл сессии исчез из каталога. «Удалить агент» → файл удалён, после перезапуска агент не возвращается.
9. Короткий устный вывод: контракт агента не менялся — день 6 объявил протокол `HistoryStore`, день 7 подставил в него реализацию; ту же точку позже займёт SQLite, когда появится VPS.

## 9. Критерии приёмки

- Есть `src/storage.py` с `JsonHistoryStore`, реализующим объявленный на дне 6 протокол (`load`/`save` по `session_id`). Сигнатуры протокола и публичный контракт `Agent` не изменились.
- Диалог → `Ctrl+C` → повторный запуск → открытая страница показывает тот же диалог **без действий пользователя**.
- Следующий после перезапуска вопрос отвечается **с учётом** доперезапускной истории: вопрос со ссылкой на прошлое сообщение получает осмысленный ответ, `prompt_tokens` соответствует полному стеку, а не одному вопросу.
- Файл `src/data/sessions/sNNN.json` содержит `version`, `session_id`, `preset`, отметки времени и `messages`; кириллица в файле читаема (`ensure_ascii=False`).
- Несколько агентов восстанавливаются все, каждый со своим стеком; переключатель показывает `session_id`; стеки не смешиваются.
- Пресет восстановлен по имени из `presets.py`; при неизвестном имени берётся пресет по умолчанию, приложение не падает, факт виден в логе.
- «Сбросить диалог» очищает стек и удаляет файл сессии; счётчики агента при этом сохраняются.
- «Удалить агент» убирает агента и его файл; после перезапуска он не восстанавливается; счётчики процесса не откатываются.
- Пустых файлов сессий в каталоге не появляется ни при каком сценарии (создал агента и не задал вопрос, сбросил диалог, перезапустил).
- Битый файл в каталоге: приложение стартует, эта сессия пропускается с предупреждением в лог, остальные восстанавливаются, битый файл не перезаписан.
- Ошибка записи на диск не роняет ход: ответ пользователю отдан, в панели и логе видна причина (проверяется, например, `chmod 500 src/data/sessions` — каталог перестаёт принимать запись).
- Каждое обращение к диску (загрузка, запись, удаление) залогировано; префикс логов агента содержит номер и `session_id`.
- `src/data/` в `.gitignore`, в коммите дня нет ни одного файла сессии.
- Дебаг-панель показывает `session_id`, путь к файлу, число восстановленных сообщений и сырое содержимое файла.
- `./run.sh week1` работает как раньше; `app_week1.py` не изменён.

## 10. Что сознательно НЕ делаем на этом шаге

- **Не берём SQLite** — решение зафиксировано в §2.1: он появится вместе с VPS и несколькими пользователями, в ту же точку протокола. Не пишем и «на всякий случай» второй реализации хранилища сегодня.
- **Не сжимаем, не суммаризируем и не обрезаем историю, не считаем бюджет контекста** — это дни 8-10. Восстановленный диалог уходит в модель целиком, даже если он длинный; `_build_messages()` сегодня не трогаем.
- **Не делаем пользовательского управления сессиями**: ни переименования, ни архива, ни поиска по истории, ни экспорта/импорта, ни корзины и отмены удаления, ни редактирования отдельных сообщений в файле из интерфейса. Переключатель агентов дня 6 остаётся единственным способом ходить между сессиями.
- **Не делаем многопользовательности и привязки сессии к вкладке браузера**: запуск локальный, каталог данных один. Две вкладки, работающие с одним агентом, — это один агент и один файл, как и было на дне 6.
- **Не синхронизируем два процесса** между собой: если нужен второй экземпляр (проверка, отладка), он поднимается с другим `TOOMANYRULES_DATA_DIR`. Межпроцессных блокировок и разрешения конфликтов не пишем.
- **Не пишем миграций схемы** — только поле `version` в файле. Формат ещё изменится на дне 8, и придумывать миграции до появления второй версии незачем.
- **Не сохраняем на диск конфиг агента и системный промпт** — только имя пресета: источник истины для промптов и параметров остаётся в коде.
- **Не сохраняем `reasoning_content`, метрики и счётчики** — ни за время жизни агента, ни за процесс. Восстанавливается контекст диалога, а не бухгалтерия: «потрачено» относится к запуску приложения и обнуляется вместе с ним.
- Не шифруем файлы и не прячем переписку — локальный каталог, локальный пользователь.
- Не добавляем стриминг, REST-сервис, RAG, инструменты/function calling и оркестрацию агентов — как и на дне 6, это дальше по программе.
- Не рефакторим `app_week1.py` под новую архитектуру и не приделываем сохранение истории к нему.
- Не пишем тестов и линтера: в проекте их нет, проверка ручная по сценариям §8.

Не расширяй объём дня сверх модуля `storage.py`, правок в `agent.py` из §5 и восстановления агентов в `app.py`.
