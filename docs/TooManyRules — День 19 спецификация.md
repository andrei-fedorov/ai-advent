# TooManyRules — спецификация дня 19

Тема: Композиция MCP-инструментов — «памятка к столу». Три инструмента сторожа FAQ выстраиваются в пайплайн: `faq_search` находит статьи в снимке, `faq_summarize` сжимает их в памятку моделью клиента через MCP sampling, `cheatsheet_save` сохраняет памятку в Markdown-файл. Цепочку по одной просьбе игрока ведёт агент. Данные между шагами передаются по ссылке, и код проверяет каждую передачу

## 1. Задание челленджа (день 19)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_19.txt`. Комментариев организатора к дню 19 на момент написания нет.

Ключевое из задания: **несколько MCP-инструментов** (в примере — поиск, сжатие, сохранение в файл) складываются в **пайплайн**: первый получает данные, второй обрабатывает, третий сохраняет результат. Проверить нужно две вещи: **цепочка выполняется автоматически** и **данные между инструментами передаются корректно**. Результат — автоматический пайплайн из нескольких MCP-инструментов; формат сдачи — **видео + код**.

Формат — «видео + код», поэтому **отдельного документа проверки нет** (правило дней 12, 16-18): проверка — в видео (§13), факты прогона — комментарием в коде (§8.4).

День 19 опирается на **день 18**: инструменты встают в сервер-сторож `src/faq_watch.py` и берут данные из его снимков FAQ в SQLite. Правила прошлых дней в силе:

- **LLM API вызывается только в `agent.py`**, клиентская часть SDK `mcp` — только в `mcp_client.py`. Сегодня сервер впервые пользуется моделью, и эти правила он не нарушает: модель ему даёт клиент (§2.4);
- **всё «про настолки» — в `presets.py`**, серверы про Too Many Bones не знают;
- **агент не знает про MCP**: инструменты и сэмплинг приходят к нему через протокол `ToolBox`;
- **решает модель**: код инструменты сам не вызывает (день 17);
- **на экране — текущий день, прошлые свёрнуты**;
- **абстракций под будущие дни не пишем**: три инструмента, одна цепочка.

**Задание дня 20 уже известно** (`tasks/AI Advent Challenge_20.txt`): несколько MCP-серверов, агент выбирает инструмент и сервер, длинный флоу через инструменты разных серверов. День 19 под него ничего не строит, но и не мешает ему. Из-за него два решения приняты сегодня так, а не иначе:

- **сэмплинг сервер получает только по явному разрешению** в своём описании (`McpServer.sampling`, §4.1). Если бы клиент объявлял sampling каждому серверу группы, чужой сервер, подключённый на дне 20, получил бы модель агента за наш счёт;
- **id `q…`/`s…` — ссылки внутри базы сторожа** (§2.3), и между серверами они не ходят. Цепочка дня 19 целиком живёт на одном сервере. Цепочки через несколько серверов — работа дня 20.

Числа в примерах — условные, если не сказано, что они замерены (§2.9).

## 2. Что делаем конкретно для TooManyRules

### 2.1. Пайплайн дня

Игрок просит: «Собери памятку к столу про яд и сохрани». Агент одним ходом выполняет три шага:

```
ask("Собери памятку к столу про яд (Poison) и сохрани в файл")
  раунд 1  модель → faq_search(query="poison", limit=5)            → id: q7 · 5 статей (снимок #12)
  раунд 2  модель → faq_summarize(search_id="q7", topic="Яд (Poison)")
                    сервер берёт тексты 5 статей из снимка #12 и просит модель у клиента (sampling)
                    клиент → агент → служебный вызов модели → 7 пунктов со ссылками   → id: s3 · текст памятки
  раунд 3  модель → cheatsheet_save(summary_id="s3")               → файл: src/data/cheatsheets/2026-09-26-cheatsheet-s3.md ✓
  раунд 4  модель → ответ игроку: памятка и путь к файлу
```

| Шаг | Инструмент | Получает | Отдаёт | Где данные |
| --- | --- | --- | --- | --- |
| получить | `faq_search` | английские ключевые слова | id поиска `q…` и список статей (номер, раздел, вопрос, что совпало) | последний удачный снимок сторожа |
| обработать | `faq_summarize` | id поиска и тему | id памятки `s…` и её текст | тексты статей того же снимка → модель клиента |
| сохранить | `cheatsheet_save` | id памятки и необязательное имя | путь к файлу, размер, проверка записи | Markdown-файл в `src/data/cheatsheets/` |

Продуктовый смысл: памятка — шпаргалка к игровому столу. В ней официальные разъяснения издателя по одной теме, коротко, по-русски, со ссылками на статьи. Её можно распечатать или открыть на телефоне во время партии. Пересказ из общих знаний модели здесь не годится: каждое правило в памятке — из статьи FAQ, и номер статьи стоит рядом.

### 2.2. Кто ведёт цепочку: модель

| Вариант | Цепочка | Почему нет / да |
| --- | --- | --- |
| код приложения вызывает три инструмента подряд | жёсткая | модель в цепочке не участвует — это скрипт, а не агент; и LLM всё равно нужен для сжатия |
| серверный инструмент-конвейер `cheatsheet_build(topic)` | жёсткая, внутри сервера | три шага становятся функциями одного инструмента, а не композицией MCP-инструментов |
| **модель через цикл раундов дня 17** | модель вызывает шаги по очереди и передаёт выход одного во вход следующего | **выбрано**: это и есть композиция инструментов агентом; цикл уже есть |

«Автоматически» значит: одна просьба игрока — вся цепочка в одном ходе, без вопросов между шагами. Порядок шагов модель узнаёт из описаний инструментов («шаг 1 / 2 / 3 памятки», §3.6). Шаги так устроены, что обойти порядок нельзя: `faq_summarize` принимает только id поиска, `cheatsheet_save` — только id памятки (§2.3).

Потолок `TOOL_MAX_ROUNDS` дня 17 — 4 раунда с инструментами. Цепочке нужно 3 раунда с вызовами и раунд ответа. Если модель сначала заглянет в `faq_questions` или повторит поиск, четырёх не хватит, поэтому **потолок поднимается до 6** (§8.2).

### 2.3. Как передаются данные: по ссылке

Если передавать данные **по значению**, модель несёт через свой контекст текст результата: вывод поиска кладёт во вход сжатия, текст памятки — во вход сохранения. На этом пути данные портятся тремя способами, и все три незаметны:

- **обрезка**: результат длиннее `TOOL_RESULT_MAX_CHARS` доходит до модели обрезанным, а дальше идёт уже обрезанный;
- **пересказ**: модель передаёт не тот текст, который получила, а свою версию — сокращённую, исправленную, переведённую;
- **выдумка**: на шаг сохранения может уйти текст, которого не выдавал ни один инструмент.

Поэтому данные передаются **по ссылке**. Каждый шаг кладёт результат в базу сервера и отдаёт короткий id: `q7` — результат поиска, `s3` — памятка. Модель передаёт следующему шагу только id. Сервер сам достаёт по нему данные — ровно те, которые записал. Ссылка понятна только серверу, который её выдал: другой сервер по `s3` ничего не найдёт. Поэтому все три шага — инструменты одного сервера, сторожа.

Корректность передачи проверяется кодом, на трёх уровнях:

| Где | Что проверяется | Что видно |
| --- | --- | --- |
| сервер, на входе шага | id существует и нужного вида (`q…` у сжатия, `s…` у сохранения); снимок, на котором искали, ещё в базе; все статьи поиска в нём есть; хеш памятки совпадает с записанным | ошибка инструмента с причиной: «это id памятки, а нужен id поиска (q…)» |
| сервер, на выходе шага | в памятке ссылки `[номер]` только на статьи этого поиска; файл после записи перечитан, и текст памятки в нём совпадает с записанным байт в байт | в ответе `faq_summarize` — «ссылки вне поиска: …», если есть; в ответе `cheatsheet_save` — «текст памятки s3 записан без изменений (sha … совпадает)» |
| приложение, по журналу хода | каждый id на входе шага был выдан выходом более раннего вызова этого же хода | строка «Цепочка» в панели: `q7 → faq_summarize ✓ · s3 → cheatsheet_save ✓` или ⚠️ (§7.2) |

Каждый шаг хранит, из чего он сделан: памятка — id поиска, файл — id памятки. Поэтому в файле памятки записана вся цепочка до снимка FAQ (§3.5).

### 2.4. Кто сжимает: модель клиента через MCP sampling

`faq_summarize` нужен LLM. Варианты:

| Вариант | Почему нет / да |
| --- | --- |
| сервер сам вызывает DeepSeek | серверу нужен ключ и SDK `openai`; второе место вызова LLM в проекте, со своим учётом денег, который панель не видит |
| сжатие без LLM (выдержки из статей) | «summarize» только по названию; по-русски памятку так не собрать |
| **MCP sampling: сервер просит модель у клиента** | **выбрано**: у сервера нет ни ключа, ни модели; вызов делает агент — единственное место вызова LLM, со своими счётчиками и ценой |

Sampling — возможность протокола. Сервер посреди `tools/call` просит клиента: «сгенерируй ответ на эти сообщения». Клиент решает, какой моделью и можно ли вообще, выполняет и возвращает текст. В эре 2026-07-28 это делается без встречного запроса от сервера. Сервер отвечает на `tools/call` результатом `InputRequiredResult` со своей просьбой. Клиент выполняет просьбу и повторяет `tools/call`, приложив ответ. Поэтому sampling работает и со stateless HTTP дня 18. В SDK v2 это выглядит так:

- **сервер**: параметр инструмента `Annotated[CreateMessageResult, Resolve(fn)]`, где `fn` возвращает `Sample(messages, max_tokens=…, system_prompt=…)`. SDK сам отвечает `InputRequiredResult`, а на повторе подставляет результат. В схему инструмента этот параметр не попадает: модель его не видит;
- **клиент**: `Client(url, sampling_callback=cb)`. Без `sampling_callback` клиент не объявляет возможность sampling, и сервер отказывает.

Цепочка вызовов: агент → `ToolBox.call(..., sample=…)` → `mcp_client` (`sampling_callback`, только если сервер разрешён для сэмплинга, §4.1) → функция агента → `_call_service_model()`. Сэмплинг — **шестая служебная работа** агента, со своими счётчиками `sampling_*` (§6). Сервер знает, что ответ пришёл от модели, и знает её имя (`CreateMessageResult.model`). Токенов и денег он не знает — их считает клиент.

### 2.5. Поиск

`faq_search` ищет в **последнем удачном снимке** сторожа (день 18, §2.5), а не на сайте. Сеть он не трогает и отвечает за миллисекунды, а результат воспроизводим: id поиска привязан к снимку.

- **По словам, не по смыслу.** Запрос — английские ключевые слова (FAQ английский; перевести тему игрока — работа модели, это сказано в описании). Слова запроса и статьи — `[a-z0-9']+` в нижнем регистре, от 3 букв, без короткого списка служебных слов. Слово запроса совпадает, если с него начинается слово статьи: `poison` находит `poisoned`. Оценка — 3 за каждое совпавшее слово запроса в вопросе плюс 1 за каждое в тексте. Статьи с нулевой оценкой не берутся. Порядок — по оценке, при равной — как на сайте. Проверено на снимке (§2.9).
- **Это не RAG**: ни эмбеддингов, ни индекса, ни автоматической подстановки найденного в запрос агента. Инструмент вызывает модель, а тексты статей уходят не в контекст агента, а в сэмплинг сжатия. RAG — неделя 5.
- Поиск `faq_questions` дня 17 не заменяет: для ответа на вопрос о правилах модель по-прежнему выбирает статью по списку.

### 2.6. Файл памятки

```markdown
# Памятка: Яд (Poison)

- Poison не складывается: счётчик ставится на значение последнего применённого эффекта. [33000210161]
- …

---

Источники — официальный FAQ издателя «Too Many Bones», снимок #12 от 25.09.2026 09:00:
- [33000210161](https://support.chiptheorygames.com/support/solutions/articles/33000210161) · Baddie Skills and Encounter Terms · Poison
- …

Собрано 26.09.2026 14:02 · поиск q7 («poison», 5 статей) → памятка s3 (модель deepseek-flash, sha 3f9a…) → этот файл
```

- **Заголовок, источники и строка происхождения пишет код**, из базы. Модель пишет только пункты. Ссылки на статьи в источниках — от сервера, а не от модели.
- Каталог — аргумент сервера `--out` (из `presets.py`: `src/data/cheatsheets/`, не в git). Имя — `<дата>-<имя>.md`. Имя берётся из параметра `name`, очищенного до `[a-z0-9-]`, не длиннее 40 знаков. Пусто после очистки — `cheatsheet-s<номер>`. Файл с таким именем уже есть — суффикс `-2`, `-3`. **Файлы не перезаписываются**, путь за пределы каталога невозможен: после очистки в имени нет ни `/`, ни `..`, и сервер ещё раз проверяет, что итоговый путь лежит внутри `--out`.

### 2.7. Где лежит и сколько живёт

| Что | Где живёт | Переживает |
| --- | --- | --- |
| результаты поиска, памятки, записи о сохранении | база сторожа (`src/data/faq_watch/faq_watch.sqlite3`), три новые таблицы (§3.7) | перезапуск сервера и приложения |
| файлы памяток | `src/data/cheatsheets/` | до удаления человеком |
| промежуточные сообщения хода (вызовы, результаты) | один ход (день 17) | — |
| id `q…`/`s…` в разговоре | только в тексте ответов модели, если она их назвала | как история |
| сэмплинг: токены и цена | счётчики агента и процесса, журнал ходов | как счётчики: на диск не едут |

**Формат файла сессии не меняется.** Память у цепочки — только в базе сервера. Поэтому «сохрани ещё и ту памятку» на следующем ходе работает, если модель назвала id в ответе.

### 2.8. Сколько это стоит

- **Сэмплинг** — служебный вызов модели на каждое `faq_summarize`. Вход — промпт сжатия и тексты статей (5 статей про Poison — 586 токенов, §2.9), выход — до 200 слов. Цена — у агента, в `sampling_*`.
- **Раунды основного запроса**: цепочка — 4 раунда вместо 1-3 дня 17; каждый следующий длиннее на результат шага. Текст памятки в результате `faq_summarize` модель видит — чтобы показать его игроку.
- **Схемы**: три новых инструмента — ещё ≈600-800 токенов в корзине `tools` каждого раунда. На дне 18 два инструмента сторожа по замеру стоили ≈466 токенов при ожидании 300-400, а описания и параметры у новых длиннее. Точное число — в замер.
- **Сайт** — ни одного запроса: все три шага работают по базе.

### 2.9. Что проверено до реализации

Проверено при написании (25-26.09.2026, прототипы во временном каталоге, в репозиторий ничего не попало). SDK mcp 2.2.0, Python 3.14.7.

- **Sampling поверх Streamable HTTP со `stateless_http=True`** — прототип. Сервер: инструмент `summarize(topic, sampled: Annotated[CreateMessageResult, Resolve(ask)])`, `ask` возвращает `Sample([SamplingMessage(role="user", content=TextContent(…))], max_tokens=120, system_prompt=…)` (`Resolve` и `Sample` — из `mcp.server.mcpserver`). Клиент: `Client(url, sampling_callback=cb)`, `cb` зовёт `deepseek-flash` через SDK `openai` и возвращает `CreateMessageResult(role="assistant", content=TextContent(…), model=…, stop_reason="endTurn")`. Результаты:
  - в `inputSchema` инструмента — только `topic`: параметр с `Resolve` модели не виден;
  - один вызов `call_tool` — **1,58 с**, ответ модели в результате инструмента, имя модели (`deepseek-flash`) сервер получил;
  - на сервере функция `ask` **выполнилась дважды** (первый раунд — просьба, второй — с ответом), тело инструмента — один раз. SDK требует, чтобы просьба на повторе была той же самой, поэтому `ask` должна быть детерминированной (§3.4);
  - **клиент без `sampling_callback`**: `call_tool` падает с `MCPError` — «Client did not declare the sampling capability required by resolver '…'». Это ошибка протокола, а не `isError` инструмента (§5.3).
- **Поиск по словам** (§2.5) — на полном снимке FAQ (82 статьи, прочитаны один раз функциями `faq_server.py`):
  - `poison stack` → первая «Poison» (33000210161), дальше статьи с poison в вопросе (Mulmesh, Tantrum, Duster);
  - `tink bots heal` → первая «Can Patches heal one of Tink's bots?» (33000210180, оценка 12);
  - `trover trove chest` → первая «How does Trover fit in the Trove Chest?»;
  - `engulf break` → первая 33000210162;
  - `initiative` → одна слабая статья. Поиск по словам находит только слова, и это будет видно в видео.
- **Сжатие** — промпт §3.6 на 5 статьях поиска `poison` через `deepseek-flash` без thinking: вход 1 594 символа, **586 / 200 токенов, 2,68 с**, `stop`. 7 пунктов по-русски, у каждого номер статьи из этих пяти; термины по-английски; ничего не добавлено от себя (сверено вручную с текстами статей).
- **Имена**: модулей и пакетов `cheatsheet` среди установленных нет (файла с таким именем и не будет — это имя инструмента).

Сверено с кодом дня 18 и по исходникам SDK 2.2.0 после реализации дня 18 (25.09.2026):

- **Сторож говорит на эре 2026-07-28** (`server/discover`, замер у `FAQ_WATCH`), поэтому сэмплинг идёт путём `InputRequiredResult`, а не встречным запросом сервера. Встречный запрос stateless HTTP не пережил бы.
- **Сбой сэмплинга на клиенте до сервера не доходит.** Если `sampling_callback` вернул `ErrorData`, клиент SDK прерывает цикл повторов и бросает `MCPError` у себя (`mcp/client/_input_required.py`, `_dispatch_all`). Второго раунда `tools/call` нет, тело инструмента не выполняется, сервер видит только первый раунд. Отказ «модель клиента не ответила» на сервере поэтому невозможен, и §3.3, §4.3, §6.2 это учитывают.
- **`ToolError` из функции `Resolve`** доходит до клиента так же, как из тела инструмента: `isError` и префикс «Error executing tool faq_summarize: » (`mcp/server/mcpserver/tools/base.py`, `Tool.run`).
- **Функция `Resolve` может принять `Context`**. На первом раунде у него `input_responses is None`, на повторе — ответ клиента. Так строка лога «просьба к модели клиента» пишется один раз (§3.8).
- **Поиск по словам** (§2.5) повторён на снимке базы автора (#6, 82 статьи): результаты совпали с перечисленными выше. Вопросы на сайте — как есть, чаще всего с «Q: » в начале. У статьи 33000210161 вопрос — просто «Poison».

**Не проверено**: весь пайплайн через агента и поведение `deepseek-flash` на трёх шагах подряд. Путь сбоя сэмплинга выведен из исходников, а не из прогона. Это прогон реализации (§12); расхождения — в замер.

### 3.5. Сохранение файла

1. Памятка из базы, проверка хеша.
2. Имя (§2.6), путь внутри `--out`.
3. Текст файла: заголовок, пункты памятки как есть, источники и строка происхождения (§2.6).
4. Запись: во временный файл в том же каталоге, затем `os.replace` — как атомарная запись хранилищ приложения. Имя проверяется на занятость до записи; гонок нет — сервер один.
5. Перечитать файл и проверить, что текст памятки в нём есть байт в байт. Нет — удалить файл и отказать.
6. Запись в базу: id памятки, путь, sha файла, размер.

## 4. Что меняется в `src/mcp_client.py`

### 4.1. Sampling у клиента

- **Сэмплинг разрешается серверу явно**: у `McpServer` новое поле в конце, `sampling: bool = False` (правило полей дня 18). Сейчас `True` только у `FAQ_WATCH` (§8.1). MCP оставляет решение клиенту, а сэмплинг — это модель и деньги агента. FAQ дня 17 его не просит, BGG дня 16 — чужой сервер, а на дне 20 серверов станет больше (§1).
- `call_tool(server, name, arguments, *, timeout_s, sampler=None)`. `Client(...)` получает `sampling_callback`, только если `sampler` задан **и** `server.sampling` истинно, — и только тогда объявляет возможность sampling. Иначе не объявляет: кнопки панели, каталоги и серверы без разрешения остаются без неё. Если `sampler` передан серверу без разрешения, он молча не используется: агент передаёт `sample` в каждый вызов и не знает, какой сервер что может.
- **`sampler` — обычная синхронная функция над словарями**, модуль по-прежнему не знает LLM:

  ```python
  # вход:  {"system": str, "messages": [{"role": "user" | "assistant", "text": str}], "max_tokens": int}
  # выход: {"ok": bool, "text": str, "model": str, "finish_reason": str, "error": str}
  ```

- `sampling_callback` переводит `CreateMessageRequestParams` в этот словарь и зовёт `sampler` через `anyio.to_thread.run_sync`: вызов модели синхронный и долгий, и цикл событий подключения он не блокирует. Поток не отменяется (`abandon_on_cancel` не задаётся): если потолок `fail_after` истёк во время вызова модели, подключение закроется после её ответа. Так сэмплинг, за который уже заплачено, попадает в счётчики агента, а ход не оставляет поток-сироту. Ответ переводится в `CreateMessageResult(role="assistant", content=TextContent(…), model=…, stop_reason="maxTokens" если finish_reason == "length", иначе "endTurn")`.
- **Отказ без вызова модели** — `ErrorData` с текстом: в просьбе есть не текст (картинка, аудио) — «клиент принимает только текст»; просьба с `tools` — «инструменты в сэмплинге не поддерживаются». `sampler` вернул `ok=False` — `ErrorData` с его `error`. Любой `ErrorData` SDK превращает в `MCPError` на стороне клиента, и до сервера он не доходит (§2.9, §4.3).
- `ToolCall` получает поле `samples: int = 0` — сколько просьб выполнено за вызов.
- Лог:

  ```
  [MCP watch] sampling/createMessage: 1 сообщение, 1 594 символа, max_tokens 1000 → 612 символов (deepseek-flash, endTurn)
  ```

### 4.2. `McpToolBox` и группа

- `McpToolBox.call(name, arguments, sample=None)` передаёт `sample` в `call_tool()` как `sampler`, а решает `server.sampling` (§4.1). `McpToolBoxGroup.call(...)` передаёт его серверу инструмента.
- **Потолок вызова — отдельно от потолка каталога**: `McpToolBox(server, *, timeout_s, call_timeout_s=None)`. `call()` берёт `call_timeout_s`, если он задан, иначе `timeout_s`; `catalog()` — всегда `timeout_s`. Вызов с сэмплингом ждёт модель, а каталог — нет. Общий потолок в 60 с на каждом ходе ждал бы минуту перед ответом, если сторож завис.
- Словарь ответа `call()` получает ключ `"samples"`.

### 4.3. Сбои

- **Клиент без sampling у инструмента, которому он нужен** — `MCPError` на `tools/call` (§2.9): стадия «вызов инструмента», текст ошибки SDK как есть. У агента `sample` есть всегда, и у сторожа сэмплинг разрешён, так что это путь ручных вызовов без `sampler` (REPL) или сервера без `sampling=True`.
- **Сбой сэмплинга на клиенте** (отказ клиента, `sampler` вернул `ok=False`) — тоже `MCPError` на клиенте, со стадией «вызов инструмента». Текст — `MCPError(<код>): <текст отказа>`. Второго раунда нет, тело инструмента не выполняется (§2.9). Модель агента получает его путём дня 17 для сбоев соединения: «Инструмент недоступен: сбой на стадии «вызов инструмента»: MCPError(…): …». Это честно: ответа инструмента нет.
- **Потолок `fail_after`** теперь покрывает и вызов модели внутри сэмплинга, поэтому у вызовов сторожа свой потолок `WATCH_CALL_TIMEOUT_S` (§8.2).

## 6. Что меняется в `src/agent.py`

### 6.1. Протокол `ToolBox`

`call(self, name: str, arguments: dict, sample: Callable[[dict], dict] | None = None) -> dict`. В докстринге — формат словарей `sample` (§4.1) и ключ `"samples"` ответа.

### 6.2. Сэмплинг — шестая служебная работа

Цикл раундов передаёт каждому `self._tools.call(...)` функцию `sample`: `_run_tool_call()` получает её новым параметром. Сейчас у него нет клиента OpenAI. Эта функция — замыкание хода над клиентом OpenAI и списком сэмплингов хода — зовёт `_run_sampling(client, request)`:

1. **Проверки клиента** (MCP оставляет решение за клиентом; `SAMPLING_MAX_CHARS`, `SAMPLING_MAX_TOKENS` — §8.2):
   - сообщения и системный промпт вместе длиннее `sampling_max_chars` — отказ «просьба длиннее N символов», модель не вызывается;
   - `max_tokens` просьбы больше `sampling_max_tokens` — берётся `sampling_max_tokens`, в лог — строка об урезании.
2. Сообщения: `system` (если есть) и сообщения просьбы как есть, по ролям.
3. `_call_service_model(client, messages, max_tokens)` — тот же вызов, что у всех служебных работ: модель агента, thinking выключен, ни температуры, ни `stop`.
4. `ServiceCall(kind="sampling", label="сэмплинг для <инструмент>", …)`. Общие счётчики агента и процесса — как у любого вызова (`_record_extra_call()`), и отдельно в счётчиках агента `sampling_calls`, `sampling_tokens`, `sampling_cost_usd` (`_record_sampling()`, правило дня 13: у каждой служебной работы своя цена). У счётчиков процесса разбивки по работам нет ни у одной служебной работы, и сэмплинг её не заводит.
5. Исключение API — не исключение наружу, а `{"ok": False, "error": "…"}`. До сервера такой сбой не доходит (§4.3): модель агента увидит «инструмент недоступен» с текстом сбоя, а памятки не будет. Ход не отменяется. Отказ по потолку из шага 1 идёт тем же путём.

Особенности этой работы по сравнению с остальными пятью:

- **Идёт внутри основного запроса, а не до него**: между раундами, внутри вызова инструмента. Служебный вызов по-прежнему не пишет в стек и не создаёт строку журнала. Во вход сэмплинга не попадает ничего из диалога — только просьба сервера. Сервер не видит историю, профиль, память и инварианты агента.
- **Замок**: `ask()` держит замок агента и ждёт `call()`. `sample` выполняется в другом потоке (`to_thread`, §4.1) и замка не берёт — стек в это время не меняется, ход ждёт. Счётчики меняются только из этого потока, пока ход стоит.
- **Обрезанный ответ** (`finish_reason="length"`) возвращается как есть, с `finish_reason`. Решает сервер: он такую памятку не записывает (§3.3).
- Промпт сэмплинга — от сервера. Агент его не меняет и не дописывает системный промпт проекта: это чужая задача с чужими данными (тексты FAQ), и ассистентом за столом модель здесь не выступает.

### 6.3. Ответ, журнал, лог

- `AgentReply` — поле в конце: `sampling_calls: tuple[ServiceCall, ...] = ()`.
- `ToolCallRecord` — поле в конце: `samples: int = 0`.
- `TurnStats` — поля в конце: `sampling_tokens: int = 0`, `sampling_cost_usd: float | None = None`.
- Счётчики агента (`_totals`) — `sampling_calls`, `sampling_tokens`, `sampling_cost_usd` рядом с `tracker_*` и `guard_*`. Счётчики процесса (`_process_stats`) — только общие, как у остальных служебных работ.
- Докстринг `ServiceCall` («сделанный до основного запроса») дополняется: сэмплинг — единственная служебная работа внутри основного запроса.
- Лог:

  ```
  [#3 Базовый · s003] сэмплинг для faq_summarize: 1 сообщ. + system, max_tokens 1000 — ок, 586/200 ток., $0.0002, 2.71 с
  ```

## 15. Что сознательно НЕ делаем на этом шаге

- **Не пишем конвейер кодом** — ни в приложении, ни инструментом-«всё-в-одном» на сервере: цепочку ведёт модель.
- **Не передаём данные по значению** между шагами и не принимаем текст памятки параметром `cheatsheet_save`: только id.
- **Не вызываем LLM на сервере** и не даём серверу ключа DeepSeek: сжатие — только сэмплингом через клиента.
- **Не спрашиваем человека перед каждым сэмплингом** (спецификация MCP это рекомендует клиентам с интерфейсом): просьбу о памятке игрок дал сам, а потолки клиента (§6.2) не дают серверу раздуть расход. Подтверждение в интерфейсе — отдельная тема.
- **Не поддерживаем в сэмплинге** картинки, аудио, инструменты, `include_context` и `model_preferences`: только текст и модель агента.
- **Не даём сэмплинг серверам по умолчанию** и не делаем переключателя в интерфейсе: разрешение — поле описания сервера в `presets.py`, сейчас только у сторожа.
- **Не строим цепочек через несколько серверов**, не передаём id между серверами и не меняем маршрутизацию группы дня 18: это день 20.
- **Не делаем RAG, эмбеддингов и индексов**, поиска по смыслу и перевода запроса кодом: поиск по словам, английские слова подбирает модель. RAG — неделя 5.
- **Не ищем на сайте** — только по снимкам сторожа; без снимков поиск честно отказывает.
- **Не делаем других форматов файла** (PDF, HTML, печать), чтения, списка, правки и удаления памяток инструментами или в интерфейсе: файл открывает человек.
- **Не показываем памятку в панели приложения** и не читаем её файл из приложения: приложение не трогает данные сервера; путь есть в ответе.
- **Не меняем инструменты дней 17 и 18**, системные промпты, служебные работы дней 9-15, формат файла сессии, `storage.py` и `tokens.py`.
- **Не оцениваем кодом качество памятки** (полноту, верность пересказа): сверяет человек по статьям. Код проверяет только передачу данных и ссылки на источники.
- **Не пишем отдельного документа проверки**: формат дня — видео + код; факты — в замере (§8.4).
- Не пишем тестов и линтера.

Не расширяй объём дня сверх инструментов, базы и промпта из §3, сэмплинга клиента из §4, шестой служебной работы из §6, блока дня 19 и перекладки аккордеонов из §7, параметров и сценария из §8, README и CLAUDE.md из §10.
