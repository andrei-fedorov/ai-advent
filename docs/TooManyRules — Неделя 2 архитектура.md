# TooManyRules — архитектура недели 2 (дни 6-10)

Документ фиксирует перестройку кодовой базы на границе недель 1 и 2. Спецификации дней 6-10 опираются на него и не повторяют этих решений.

## 1. Почему меняем подход

Неделя 1 («Основы LLM») состояла из **сравнительных экспериментов**: A vs B, четыре способа рассуждения, три температуры × три повтора, матрица 2×2. Каждый день давал самостоятельную витрину, которую нужно было видеть целиком и рядом с предыдущими — вкладка на день была для этого правильной формой.

Неделя 2 («База про агентов») устроена иначе: дни **наращивают одну и ту же сущность** — агент (день 6) → память между запусками (день 7) → сжатие контекста и работа с токенами (дни 8-10, по программе челленджа). Вкладка на день здесь дала бы пять почти одинаковых чатов, а день 7 вкладкой не показывается в принципе: его демонстрация — «убили процесс, запустили заново, диалог продолжается».

Поэтому на неделе 2:

- код недели 1 замораживается отдельным запускаемым артефактом;
- неделя 2 разрабатывается классически — один растущий `app.py`, коммит и тег на каждый день, возврат назад через git;
- роль «что нового сегодня» берёт на себя не вкладка, а **дебаг-панель**, которая прирастает вместе с агентом (день 6 — конфиг, стек, метрики; день 7 — файл истории и факт восстановления; дальше — сжатие и токены).

## 2. Заморозка недели 1

- `src/app.py` → `src/app_week1.py`. Дальше не редактируется; в шапке файла — комментарий, что это замороженный артефакт недели 1 (дни 1-5, вкладки).
- Файл **самодостаточен**: не импортирует новые модули недели 2 и ничего им не отдаёт. Дублирование системного промпта, констант и таблицы цен с новым кодом — осознанная цена заморозки: артефакт должен запускаться, даже когда новый код уедет далеко вперёд.
- Запуск: `./run.sh` — текущее приложение, `./run.sh week1` — артефакт недели 1 (единственное изменение в `run.sh`: необязательный аргумент выбирает файл запуска, по умолчанию `app.py`).
- Настоящий архив всё равно git: тег `day05` — состояние на конец недели 1. Файл-артефакт нужен для того, чтобы показать неделю 1 **не переключая ветки**, в том числе на видео.

## 3. Структура кода недели 2

| Файл | Назначение |
| --- | --- |
| `src/agent.py` | Сущность агента: `AgentConfig`, `AgentReply`, `Agent`, статистика. **Единственное место в проекте, где происходят вызовы LLM API.** Не знает ни про Gradio, ни про Too Many Bones |
| `src/presets.py` | Конфиги агентов TooManyRules: системный промпт проекта, модели, параметры, набор пресетов |
| `src/storage.py` | Появляется на дне 7: история диалога в JSON-файлах по сессиям (`src/data/sessions/`), загрузка и сохранение через протокол `HistoryStore` |
| `src/app.py` | Только интерфейс на Gradio: чат + дебаг-панель. LLM-логики не содержит |
| `src/app_week1.py` | Замороженный артефакт недели 1, вне графа импортов нового кода |

Направление зависимостей строго одностороннее: `app.py` → `presets.py` → `agent.py`, и `app.py` → `storage.py` → `agent.py` (протокол хранилища объявлен в `agent.py`). Циклов быть не должно; `agent.py` не импортирует ничего из проекта.

Что переносим из недели 1: `SYSTEM_PROMPT`, константы DeepSeek (`base_url`, модели, `extra_body` для `thinking`), таблицу цен и функцию оценки стоимости, паттерн логирования вызовов в stdout, и — как значения пресетов — ограничения дня 2 (`JSON`-промпт, `max_tokens`, `stop`) и параметры дней 4-5 (`temperature`, `pro` + `thinking`).

Что **не** переносим: вкладки, сравнительные функции (`compare_variants`, `run_day3`, `run_day4`, `run_day5`), валидацию JSON дня 2, подсветку минимумов дня 5, мета-промпт и консилиум дня 3. Всё это остаётся жить в `app_week1.py`.

## 4. Точки роста под известные и ожидаемые дни

Архитектура должна делать так, чтобы каждый следующий день менял **одно место**, а не расползался по коду:

- **День 7 (сохранение контекста, задание известно).** В `agent.py` объявляется протокол хранилища (`load`/`save` по `session_id`); агент принимает его необязательным параметром конструктора. День 6 работает с `None` (память процесса), день 7 добавляет реализацию в `storage.py` — **публичный контракт агента при этом не меняется**: подставляется реализация, а не переделывается агент. Подробности — `docs/TooManyRules — День 7 спецификация.md`.
- **День 8 (ожидаемо — сжатие контекста).** Сборка списка сообщений для запроса живёт в одном приватном методе агента. Сжатие/суммаризация подключается там, а не размазывается по вызовам.
- **День 9 (ожидаемо — работа с токенами).** `AgentReply` уже несёт `prompt`/`completion`/`total` токены и стоимость, агент уже копит их за время жизни. Бюджеты и лимиты надстраиваются над готовыми метриками.
- **Дальше (недели 4-7).** Агент ничего не знает про Gradio, поэтому его можно поднять за HTTP (REST-сервис, телеграм-бот) или переключить на локальную модель через `base_url` в конфиге, не трогая логику.

Абстракции под дни 8-10 заранее **не пишутся** — фиксируются только места, куда они встанут.

## 5. Конвенции недели

- В конце каждого дня — коммит и тег `day06`, `day07`, …: в таблицу челленджа идёт ссылка на тег, а не на «последний main», который к моменту проверки уже уедет вперёд.
- `README.md` описывает **текущее** состояние приложения плюс короткий раздел «неделя 1 — `app_week1.py`, запускается через `./run.sh week1`».
- На каждый день, как и раньше: спецификация в `docs/` и промпт исполнителю в `prompts/`.
- Дебаг-панель — обязательная часть каждого дня недели: то, что добавилось сегодня, должно быть в ней видно.

## 7. Открытые решения

- ~~**JSON или SQLite на дне 7.**~~ **Решено** в `docs/TooManyRules — День 7 спецификация.md` (§2.1): интерфейс хранилища + реализация на JSON-файлах, по файлу на сессию в `src/data/sessions/`. Для одного локального пользователя этого достаточно, и на видео это нагляднее (видно сам файл с `messages`). SQLite из общей спецификации проекта берём, когда появится VPS и несколько сессий/пользователей — протокол `HistoryStore` позволит подменить реализацию без переписывания агента.
- **Стриминг ответа.** Новый чат работает без стриминга: обычный вызов даёт полные метрики (время, токены, стоимость, `finish_reason`) на каждый ход, а они — главное содержимое дебаг-панели. Стриминг вернём, когда он станет нужен продукту, а не демонстрации.
