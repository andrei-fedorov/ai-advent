# TooManyRules — спецификация дня 26

Тема: запуск локальной LLM. Неделя 6 («Локальный ИИ») начинается с того, что модель работает на машине автора. В LM Studio поднимается локальная модель — для видео это Qwen3.5-2B (MLX, 4 бита, 1,75 ГБ), но приложение от неё не зависит. К модели обращаются через CLI (`lms chat`) и через OpenAI-совместимый HTTP API (`http://127.0.0.1:1234/v1`). Ассистент получает пресет **«Локальный»**: тот же агент, только другой `base_url`, и ключ не нужен. **Id модели приложение не хранит**: какую модель загрузить, человек решает в LM Studio, а приложение знает только адрес сервера. Какая модель ответила, оно узнаёт из ответа API и показывает в панели и логах. Кнопка «Проверить сервер» в блоке дня показывает, какая модель сейчас загружена. Три запроса разной сложности задаёт программа `./run.sh local`, и все они идут через агента. **Л1** — простой вопрос без игры. **Л2** — вопрос по правилам из общих знаний (К5). **Л3** — тот же вопрос с полным RAG дней 22–24: переписывание запроса, поиск, реранкер, ответ с цитатами и проверка формата. Поиск и реранкер у проекта локальные с дня 21, поэтому после дня 26 весь путь «вопрос → правила → ответ» может идти без интернета. Инструкции у пресета те же, что у пресетов DeepSeek: подстройки ассистента под локальную модель день не делает. На проверке до реализации (§2.5) Qwen3.5-2B на инструкциях дней 24–25 отвечала «Не знаю» даже при идеальной выдаче. Это результат дня, а не баг.

## 1. Задание челленджа (день 26)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_26.txt`. Комментариев организатора к дню 26 на момент написания нет.

Ключевое из задания: **установить и запустить любую локальную LLM** (Ollama, LM Studio, llama.cpp и т. п.). Проверить три вещи: **модель запускается локально**, **к ней можно обратиться через CLI или HTTP API**, **модель отвечает на простой запрос**. Сделать **минимум 3 запроса разной сложности**. Результат — запущенная локальная LLM, которая отвечает на запросы; формат сдачи — **видео + код**. Ничего «подстроить» под локальную модель задание не просит.

Формат «видео + код», результат — сам код и запущенная модель. Поэтому **отдельного документа проверки нет** (правило дней 12, 16, 24 и 25): проверка показывается в видео (§13), замер записывается комментарием у `LOCAL_QUESTIONS` в `presets.py` (§12).

Правила прошлых дней в силе:

- **LLM API вызывается только в `agent.py`**. Программа дня ходит к модели через `Agent.ask()`. Новый модуль `local_server.py` модель не вызывает: он только спрашивает сервер, какие модели у него есть и какая загружена (§4);
- **всё «про эту машину» — в `presets.py`**: адрес сервера, пресет, вопросы. `agent.py` не знает ни про LM Studio, ни про конкретную модель;
- **другой набор параметров модели — другой агент** (день 6): локальная модель — это пресет, а не переключатель на живом агенте;
- **код не оценивает ответы**: верно ли ответила модель, решает автор;
- **на экране — текущий день, прошлые свёрнуты**.

## 2. Что делаем конкретно для TooManyRules

### 2.1. Подготовка машины (делает человек)

Описывается в README (§8). Код LM Studio не ставит и не запускает, модели не скачивает и не загружает. Пример для модели видео:

```bash
lms get https://huggingface.co/lmstudio-community/Qwen3.5-2B-MLX-4bit
lms load qwen3.5-2b-mlx
lms server start
```

`lms ps` показывает загруженную модель, `lms server status` — «The server is running on port 1234». **Другую модель** загружают так же (`lms get`, `lms unload --all`, `lms load <id>`) или в окне LM Studio. Приложение и программу при этом перезапускать не нужно: следующий запрос уйдёт к новой модели. Загруженной стоит держать **одну LLM**: что LM Studio делает с запросом без id при нескольких загруженных, на проверке не выяснялось (§2.5), поэтому блок и программа об этом предупреждают (§4). Флаг `--context-length` движок MLX у LM Studio 0.4.25 игнорирует: Qwen3.5-2B загружается с контекстом 132 096 при любом значении флага (§2.5).

### 2.2. Три запроса

Данные — `presets.LOCAL_QUESTIONS` (§7), словари как у `RAG_CONTROL_QUESTIONS` плюс ключ `mode`:

| id | Сложность | Вопрос | Режим | Что проверяет |
| --- | --- | --- | --- | --- |
| Л1 | простой | «Привет! Ответь одной фразой: что ты умеешь?» | `без` | модель отвечает, первый токен приходит быстро, русский язык |
| Л2 | средний | К5 «Что происходит с гирлоком, когда он теряет последнюю фишку здоровья?» | `без` | знание предметной области из общих знаний: длинный ответ, на проверке — выдумка («бонусные очки») |
| Л3 | сложный | тот же К5 | `полный` | длинный запрос с выдержками, служебная работа (переписывание), строгий формат, проверка цитат и повтор формата |

Текст Л1 — предложение спецификации; автор может заменить его в `presets.py`. Ожидаемые источники Л3 — `sources` вопроса К5 (`Нокаут`, стр. 20; `Поднять гирлока`, стр. 22). Код сверяет только выдачу с ними, ответы оценивает автор.

### 2.3. Путь запроса

Путь у всех трёх один и тот же: свежий голый агент (`rag_eval.make_agent()`, §5) с пресетом «Локальный» → `Agent.ask()` → SDK `openai` → `POST http://127.0.0.1:1234/v1/chat/completions` с `model: "local"` → отвечает загруженная модель, её id приходит в ответе. У Л3 до основного вызова идут служебная работа переписывания (на той же локальной модели), поиск и реранкер. После вызова — проверка формата и, при нарушениях, один повтор (день 24). Ни одного обращения в интернет: поиск и реранкер берут модели из кэша Hugging Face (`allow_download=False`, день 22).

В приложении путь тот же: пресет «Локальный» в списке пресетов, флажок RAG выключен — Л2, включён — Л3. Служебные работы приложения (разбор памяти, переписывание, свёртка и т. д.) у этого пресета идут в ту же локальную модель: служебный вызов использует клиент агента (§3).

### 2.4. Что видно в панели и логах

«Последний вызов» показывает строку «Модель: `local` → ответила `qwen3.5-2b-mlx`» (§3.3, §6.2), время, токены по `usage`, цену «н/д». Бюджет контекста — «н/д» (§1.1). Лог хода пишет фактическую модель рядом с `model=local`, лог создания агента — адрес API (§3.4). Блок дня по кнопке показывает загруженную модель и её контекст (§6.2).

### 2.5. Что проверено до реализации (05.10.2026)

M1 Pro, 16 ГБ, macOS 15.7.7; LM Studio 0.4.25, движок `mlx-llm` 1.11.0; модель `qwen3.5-2b-mlx` (arch `qwen3_5`, MLX, 4bit, контекст до 262 144, загружена с 132 096, `parallel` 4). Скачивание — 1,75 ГБ; загрузка — 8,9 с (1,63 ГиБ). Индекс автора до и после проверок не менялся (md5 сверен).

**Сервер.**
- `GET /v1/models` отдаёт все скачанные модели (у нас три, вместе с bonsai-27b и эмбеддингом nomic), без признака загрузки.
- `GET /api/v0/models` (REST LM Studio) — те же модели с полями `type` (`llm`/`vlm`/`embeddings`), `state` (`loaded`/`not-loaded`), `arch`, `compatibility_type`, `quantization`, `max_context_length` и у загруженной — `loaded_context_length`. Это источник для «какая модель сейчас активна» (§4).

**Id модели в запросе.** При загруженной `qwen3.5-2b-mlx` запросы без поля `model`, с `"model": ""` и с `"model": "local"` все получили ответ этой модели, `model` ответа — `qwen3.5-2b-mlx`. Без загруженной модели — 400 «No models loaded. Please load a model in the developer page or use the 'lms load' command.». Агент отдаёт его как ошибку хода (§3.2), и текст сам подсказывает, что делать. **Не проверено**: какую модель LM Studio берёт для запроса с чужим id, если загружено несколько LLM. Для этого пришлось бы грузить вторую модель автора.

**Ответ API.**
- `POST /v1/chat/completions` отвечает в формате OpenAI: `usage` с `prompt_tokens`/`completion_tokens`, `completion_tokens_details.reasoning_tokens` = 0, у сообщения есть `reasoning_content` (пустая строка), `stats` пустой. Скорость и время до первого токена отдаёт только `POST /api/v0/chat/completions`: на Л2 — 100,9 ток/с, первый токен 0,19 с, генерация 4,6 с.

**Thinking и поле DeepSeek.**
- Запрос с `"thinking": {"type": "disabled"}` (так шлёт агент) принят, ответ тот же — поле игнорируется, 400 нет.
- `chat_template_kwargs.enable_thinking` (true и false) ничего не меняет: рассуждения нет, `reasoning_tokens` = 0. Включить thinking через API не удалось. Это граница дня (§15).

**CLI и ошибки.**
- `lms chat qwen3.5-2b-mlx -p "Сколько будет 17*3? Ответь одним числом." --stats` → «51», 204,7 ток/с, первый токен 0,41 с, 0,64 с всего.
- Переполнение контекста (≈140 тыс. токенов) — 400 «The number of tokens to keep from the initial prompt is greater than the context length…» за 0,6 с. Признак `"context length"` из `CONTEXT_OVERFLOW_MARKERS` (день 8) его узнаёт, правка не нужна.
- Сервер выключен (`lms server stop`): агент возвращает `ok=False` с текстом «Ошибка при обращении к DeepSeek API: Connection error.». Название провайдера в этой подписи неверно — правка §3.2.
- Ключ: текущий `_get_client()` требует `DEEPSEEK_API_KEY` и отправляет его локальному серверу. На проверке ключ был в `src/.env`, а сервер его не проверяет — правка §3.1.

**RAG на текущем коде — голый агент `rag_eval.make_agent()`, режим `полный`, Qwen3.5-2B.**

| Вопрос | Выдача (оценка реранкера) | Первый ответ | После повтора |
| --- | --- | --- | --- |
| К5 | Нокаут 0,998; Здоровье 0,955 | «I don't know. The rules you provided do not contain the answer…» — по-английски, без уточнения | «Не знаю» + уточняющий вопрос по-английски («What happens if a girdle…») |
| К8 | Простые и ценные трофеи 0,997; 8. Область трофеев 0,856; …0,108 | «Не знаю. В предоставленных выдержках … у гирлока есть только 4 места для трофеев…» — ответ найден, но начат с «Не знаю» | то же, нарушение осталось |
| К4 | Ловкость (ЛОВ) 0,939 | «Не знаю» | «Не знаю. В выдержках нет информации о ловкости» + три уточняющих вопроса |

Переписывание на локальной модели вернуло вопрос без изменений за 0,9–1,6 с, как и положено самостоятельному русскому вопросу (день 23). Поиск — как на DeepSeek. Загрузка e5 занимает 6–7 с, реранкера — 2 с, обе — один раз на процесс.

**Наблюдение для следующих дней — в код дня не идёт (§15).** С той же выдержкой «Ловкость (ЛОВ)» и инструкцией в две строки модель ответила верно и с номером [1]. С короткой инструкцией в четыре правила ответы на К5 и К8 верные, цитаты дословные, но номеров `[N]` после утверждений нет ни разу. С образцом ответа модель переписывала образец в ответ. Значит, модель отвечать по выдержкам умеет, а мешает ей объём и число правил инструкций дней 24–25 (≈1,3 тыс. токенов вместе с выдержками у К4).

### 2.6. Сколько это стоит

Деньги — «н/д» (§1.1). Время на M1 Pro по проверке: Л1 — меньше секунды. Л2 — ≈5 с (≈470 токенов ответа). Л3 — 4–17 с: первый поиск в процессе ждёт загрузку e5 и реранкера (≈9 с), основной вызов с повтором — 1,5–6 с, переписывание — ≈1 с.

### 2.7. Правки по ревью (06.10.2026)

- **Потолок ответа** — `max_tokens` = 2000 у пресета «Локальный» (§1.1, §7). `agent.py` не меняется: потолок конфига уже уходит и в основной запрос, и в раунд повтора формата.
- **Одно определение состояния сервера** — в `local_server.py` (§4): блок дня и программа больше не повторяют разбор и подписи друг друга, а подсказку `lms server start` дают по `ServerCheck.no_answer`, а не по началу текста ошибки.
- **Программа подсказывает `lms server start` только при «не отвечает»** (§5), как блок дня.
- **JSON без списка `data` на `/models` — сбой проверки** (§4), а не «сервер отвечает, моделей нет».
- Поведение для настоящего LM Studio не меняется.

## 3. Что меняется в `src/agent.py`

Минимум под не-DeepSeek сервер. Ход, служебные работы, RAG, проверка и повтор не меняются.

### 3.1. Ключ

`AgentConfig` получает поле `api_key_env: str | None = "DEEPSEEK_API_KEY"` — имя переменной окружения с ключом. В `_get_client()`:
- `None` — ключ не нужен: клиенту передаётся заглушка `"not-needed"` (SDK `openai` требует непустой `api_key`, LM Studio его не проверяет). Ключ DeepSeek на чужой сервер не уходит;
- строка — как сейчас, только из этой переменной. Нет значения → `RuntimeError`: для `DEEPSEEK_API_KEY` — с прежним `_NO_API_KEY_ERROR`, для другого имени — с общим текстом «Не задан <имя>…».

### 3.2. Подпись ошибки API

`_explain_api_error()` получает `base_url` агента. Подпись «Ошибка при обращении к DeepSeek API: …» остаётся только для `DEEPSEEK_BASE_URL`, иначе — «Ошибка при обращении к API <base_url>: …». Подсказки «запустите LM Studio» в агенте нет: агент не знает, что за сервер стоит по адресу. Подсказку дают блок дня (§6) и программа (§5). Ошибка «No models loaded…» подсказывает сама. Объяснение переполнения контекста (день 8) не меняется.

### 3.3. Фактическая модель

`AgentReply` получает поле `answered_model: str | None` (в конце, по умолчанию `None`) — `model` из ответа API последнего раунда основного запроса, как есть. `None` — ответа не было (сбой) или сервер поле не прислал.
- `AgentReply.model` остаётся моделью конфига. По ней, как и раньше, считаются цена и окно — для DeepSeek ничего не меняется, даже если DeepSeek называет в ответе модель иначе.
- `debug_state()["last_call"]` несёт оба поля. Панель (§6.2) показывает `answered_model`, если оно есть и отличается от `model`.
- Служебные вызовы (`ServiceCall`) фактическую модель не записывают: они идут к тому же серверу, что основной вызов.

### 3.4. Логи

- Строка «агент создан» дописывает `api=<base_url>`, если адрес не `DEEPSEEK_BASE_URL`. Тогда в stdout видно, что ход ушёл на локальный сервер.
- Строка хода `model=…` дописывает `→ <answered_model>`, если фактическая модель есть и отличается от модели конфига: `model=local → qwen3.5-2b-mlx`.
- Остальные строки не меняются: `cost=н/д` и бюджет «н/д» в них уже есть.

### 3.5. Что не трогаем

- `extra_body={"thinking": …}` уходит, как раньше, во всех трёх местах. LM Studio его игнорирует (§2.5). Поле провайдера в конфиг не выносим — это работа на день, когда появится сервер, который такое поле отвергнет.
- `PRICING_PER_M_TOKENS` и `tokens.CONTEXT_WINDOW_TOKENS` — без новых строк (§1.1).
- `reasoning_content` — прежний `getattr(...) or ""`.

## 4. Новый модуль `src/local_server.py`

Лист графа: из проекта не импортирует ничего, LLM не вызывает. Отвечает на вопрос «работает ли сервер и какая модель на нём сейчас загружена». Его берут `app.py` (кнопка блока дня) и программа дня — так приложение не импортирует программу. Имя проверено: модуля `local_server` нет ни в стандартной библиотеке, ни в пакетах venv.

- `ModelInfo` (frozen): `id`, `type`, `state` (`None`, если сервер не отдаёт состояние), `arch`, `format` (`compatibility_type`), `quantization`, `max_context`, `loaded_context`.
- `ServerCheck` (frozen): `ok`, `url`, `elapsed`, `error` (`""` при `ok`), `models: tuple[ModelInfo, ...]`, `extended: bool` (ответил ли REST LM Studio). Свойство `loaded` — загруженные языковые модели (`state == "loaded"`, тип не `embeddings`); при `extended=False` — пусто, состояние неизвестно.
- `check(base_url: str, timeout_s: float) -> ServerCheck` — **без исключений**, id модели не принимает:
  - `GET <base_url>/models` (OpenAI). Нет ответа, не JSON или JSON без списка `data` (на порту не OpenAI-совместимый сервер) → `ok=False` с причиной: «сервер не отвечает по <адрес>» для отказа соединения и таймаута (`ServerCheck.no_answer`), текст ошибки — для остального, в том числе обрыва посреди ответа.
  - Затем `GET <origin>/api/v0/models`, где `origin` — `base_url` без пути `/v1`. 404 или не JSON — не сбой: `extended=False`, модели — из первого ответа, `state` = `None`. Так модуль работает и с другим OpenAI-совместимым сервером, только без признака «загружена».
  - HTTP — `httpx` (уже в `requirements.txt`), таймаут — параметр (`presets.LOCAL_CHECK_TIMEOUT_S`, 3 с).
- Одно определение состояния сервера для блока и программы (правка по ревью): `ServerCheck.status` — один из шести видов (не отвечает, сбой, состояние неизвестно, модель не загружена, загружено несколько, загружена одна), `ServerCheck.llms` — языковые модели сервера, `ModelInfo.label` и `ModelInfo.context_text` — подписи модели и контекста. Вызывающие решают по ним, а не по тексту ошибки и не своими копиями.
- Логов у модуля нет — логируют вызывающие (блок и программа), как у `rag_answer.py`.

## 5. Новая программа `src/local_llm.py` — `./run.sh local`

Отдельная программа вне графа приложения, по образцу `rag_eval.py`. Импортирует `presets.py`, `agent.py`, `rag_search.py`, `embedder.py` (только `in_cache()`), `local_server.py` и `rag_eval.py` (`make_agent()`, `MODES` и мелкие помощники отчёта — ребро «программа → программа», как у `rag_dialog.py`). Логи — stdout, `[Локальная модель]`. Ключ DeepSeek не нужен.

**Аргументы:** `--only Л1,Л3` (латинская L принимается за Л), `--url <base_url>`, `--db <путь индекса>`, `--out <файл.md>`. Относительные пути — от `src/`, как у `rag-eval`. Аргумента модели нет: какая загружена, та и отвечает.

**Ход:**
1. Конфиг — `presets.PRESETS[presets.LOCAL_PRESET]`; `--url` заменяет `base_url` через `dataclasses.replace()`.
2. `local_server.check()`:
   - `ok=False` → отказ до запросов, код 2; подсказка `lms server start` — только когда сервер не отвечает (`no_answer`), как у блока дня (§6.2): чужому сервису на порту она не поможет;
   - `extended` и ни одной загруженной LLM → отказ, код 2: «модель не загружена — `lms load <id>`» и список id сервера;
   - загружено несколько LLM → предупреждение (§2.1) и продолжение;
   - `extended=False` → предупреждение «какая модель загружена, неизвестно» и продолжение.
3. Если в наборе есть вопрос с RAG — индекс (`RulesIndex.info()`) и реранкер в кэше (`embedder.in_cache()`). Нет → отказ до вызова модели, код 2. Это правило `rag_eval.py`.
4. Вопросы по очереди, на каждый — **свежий агент** `rag_eval.make_agent(config, name, index, mode)`; режим — из `question["mode"]` по `rag_eval.MODES`. Строка лога на вопрос: фактическая модель (`answered_model`), время, `prompt`/`completion`, ≈ток/с (`completion_tokens / elapsed`; это скорость с префиллом и раундами, а не чистая генерация — в отчёте так и подписано), у Л3 — переписывание, поиск, ожидаемые источники в выдаче, вид ответа, нарушения, повтор.
5. Отчёт Markdown — `presets.LOCAL_REPORT_DIR` (`src/data/local/`, вне git), имя по дате и времени, или `--out`.
   - Условия: дата, адрес, загруженные модели и их поля из `check()`, версия SDK `openai`, `temperature`, индекс.
   - Сводная таблица Л1–Л3: сложность, режим, **ответившая модель**, время, токены, ≈ток/с, у Л3 — выдача с оценками и найденность ожидаемых источников (`rag_search.sources_found()`), вид ответа, нарушения, повтор. Модель — по каждому вопросу, потому что её могут сменить в LM Studio посреди прогона.
   - Ответы дословно: у Л3 — первая попытка, если был повтор, и собранный ответ, как в разделе вопроса отчёта `rag-eval`.
   - Колонки оценки нет: ответы оценивает автор в видео.

**Коды выхода:** 0 — все вопросы прошли; 1 — сбой посреди прогона (ход `ok=False` или исключение), отчёт по пройденному; 2 — отказ до вызова модели; 130 — Ctrl+C, отчёт по пройденному. Это правила `rag_dialog.py`.

Сессий на диск программа не пишет, индекс только читает, модели не скачивает.

## 15. Что сознательно НЕ делаем на этом шаге

- **Не подстраиваем ассистента под локальную модель**: ни своих RAG-инструкций, ни промптов служебных работ, ни системного промпта, ни образцов ответа, ни своих чисел поиска. Что маленькая модель на инструкциях дней 24–25 отвечает «Не знаю», — результат дня; наблюдение про короткие инструкции (§2.5) — материал для следующих дней.

- **Не храним id локальной модели** и не выбираем её из приложения: ни списка моделей сервера в переключателе, ни `lms load` из кода, ни строки модели в `tokens.py` или таблице цен.
