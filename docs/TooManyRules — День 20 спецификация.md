# TooManyRules — спецификация дня 20

Тема: Orchestration MCP — три сервера, три назначения. У агента в одном каталоге инструменты трёх серверов: FAQ издателя (копия в SQLite + сайт), фанатская вики и файлы. Агент сам выбирает сервер и инструмент по описаниям и ведёт длинный флоу через несколько серверов одной просьбой игрока. Заодно FAQ переходит на сценарий автора «сначала копия, а если она пуста или устарела — сайт, копия докачивается в фоне», и сервер FAQ поднимает само приложение

## 1. Задание челленджа (день 20)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_20.txt`. Комментариев организатора к дню 20 на момент написания нет.

Ключевое из задания: **несколько MCP-серверов** зарегистрированы у агента. Агент **сам выбирает инструмент**, **маршрутизирует запросы** между серверами и **выполняет длинный флоу**. Проверить нужно сценарий, где работают **инструменты с разных серверов**, и **правильность выбора и порядка вызовов**. Результат — длинный флоу взаимодействия с несколькими MCP-серверами; формат сдачи — **видео + код**.

Формат — «видео + код», поэтому **отдельного документа проверки нет** (правило дней 12, 16-19): проверка — в видео (§15), факты прогона — комментарием в коде (§9.4).

День 20 опирается на дни 17-19: группу серверов `McpToolBoxGroup` (день 18), цикл раундов агента (день 17) и пайплайн памятки со сэмплингом (день 19). Правила прошлых дней в силе:

- **LLM API вызывается только в `agent.py`**, клиентская часть SDK `mcp` — только в `mcp_client.py`;
- **всё «про настолки» — в `presets.py`**, серверы про Too Many Bones не знают: адреса и имена приходят аргументами;
- **агент не знает про MCP**: инструменты приходят к нему через протокол `ToolBox`;
- **решает модель**: какой сервер и какой инструмент звать, код не выбирает (день 17);
- **описание инструмента — это промпт**; системные промпты пресетов не меняются (дни 17-19);
- **на экране — текущий день, прошлые свёрнуты**.

## 2. Что делаем конкретно для TooManyRules

### 2.1. Три сервера

| Сервер (`name`) | Программа | Транспорт | Кто запускает | Что знает | Инструменты |
| --- | --- | --- | --- | --- | --- |
| `watch` — FAQ издателя | `src/faq_watch.py` | Streamable HTTP, долгий процесс | приложение, если порт молчит; или человек | портал Freshdesk, одна категория — аргументами | `faq_search`, `faq_article`, `faq_summarize`, `faq_changes`, `faq_watch_schedule` |
| `wiki` — фанатская вики | `src/wiki_server.py`, новый | stdio, процесс на вызов | приложение, на каждый вызов | движок вики boardgamehub, одна вики — аргументами | `wiki_index`, `wiki_page` |
| `files` — файлы | `src/file_server.py`, новый | stdio, процесс на вызов | приложение, на каждый вызов | один каталог — аргументом | `save_markdown` |

Группа агента — эти три сервера в этом порядке (`watch+wiki+files`). Из группы уходит **`faq_server.py` дня 17**: у источника «FAQ издателя» теперь один сервер. `faq_server.py` остаётся: это библиотека чтения сайта (её импортирует `faq_watch.py`), отдельная программа и блок дня 17 в панели. BGG дня 16 — без изменений: только список по кнопке.

Сэмплинг по-прежнему разрешён только `watch` (`McpServer.sampling`, день 19): `wiki` и `files` модели агента не получают.

### 2.2. Длинный флоу дня

Игрок просит: «Готовлю партию за Тинка. Собери памятку: характеристики и стиль из вики, официальные уточнения по его ботам из FAQ издателя; сохрани как tink». Агент одним ходом:

```
ask("Готовлю партию за Тинка. Собери памятку … сохрани как tink")
  раунд 1  модель → wiki:  wiki_index(type="гирлоки")                  → строки «Тинк · geroi-tink · …»
  раунд 2  модель → wiki:  wiki_page(slug="geroi-tink")                → характеристики, стиль, текст
           модель → watch: faq_search(query="tink bot")                → id: q12 · источник: копия #27 · 4 статьи
  раунд 3  модель → watch: faq_article(article_id="33000210170")       → текст статьи (из копии)
           модель → watch: faq_article(article_id="33000210171")
  раунд 4  модель → files: save_markdown(name="tink", content="# Тинк …") → файл: src/data/cheatsheets/2026-09-27-tink.md ✓
  раунд 5  модель → ответ игроку: памятка и путь к файлу
```

Три сервера, пять-шесть вызовов, и порядок важен: данные — раньше сохранения, `faq_article` — по номерам, которые выдал `faq_search`. Вызовы одного раунда модель может делать параллельно (DeepSeek так делал уже на дне 17). Код цепочку не достраивает и не проверяет её «правильность»: какой путь выбрала модель, видно в панели (§8.2) и в логах трёх процессов.

### 2.3. Как агент выбирает сервер: по описаниям

Маршрутизацию держат **описания инструментов** (§3.6, §4.3, §5.3). Роутера в коде нет, системные промпты не меняются. Описание говорит, что за источник, на каком он языке, официальный ли, что в нём есть и когда его звать:

| Вопрос игрока | Куда | Почему |
| --- | --- | --- |
| Как работает правило, спорный случай, эррата | `watch`: `faq_search` → `faq_article` | официальные разъяснения издателя; английский — модель подбирает английские слова |
| Характеристики гирлока, состав коробки, кто такой плохиш или тиран, что делает навык, совместимость дополнений | `wiki`: `wiki_index` → `wiki_page` | справочник на русском, которого у издателя нет |
| Спорное правило, о котором пишут оба | оба; **при расхождении прав FAQ издателя** | вики — неофициальная, и сама об этом пишет на своей странице FAQ (§2.10); приоритет эрраты — §4 спецификации проекта |
| «Сохрани», «выгрузи в файл» | `files`: `save_markdown` последним | файл — результат, а не источник |
| Приветствие, вопрос о самом ассистенте | никуда | — |

Почему не иначе:

- **Не роутер в коде.** Выбор источника по смыслу вопроса — ровно то, что задание просит от агента. Код, который выбирает сервер ключевыми словами, делал бы работу модели хуже неё.
- **Не единый поиск «по всем источникам».** Один инструмент поверх трёх источников спрятал бы маршрутизацию внутрь сервера, и проверять было бы нечего.
- **Не строка в системном промпте.** Приоритет источников и «когда звать» — свойство инструментов: пока инструменты выключены переключателем, модели незачем о них знать. Правило дней 17-19 остаётся.

Выбор «копия или сайт» внутри FAQ модель **не делает**: его прячет сервер `watch` (§2.4). Для модели у FAQ одни и те же инструменты, а откуда пришли данные, видно по строке `источник:` ответа.

### 2.4. FAQ всегда доступен: копия и сайт

**Копия** — последний удачный снимок сторожа (день 18) в SQLite. **Хорошая** копия — удачный снимок есть и начат не раньше чем `--max-age-min` минут назад (по умолчанию 10 080 — неделя). Иначе копия **плохая**: пустая (удачных снимков нет — только неудачные попытки или ничего), или устаревшая. Снимок не бывает «наполовину»: неполный снимок пишется неудачной попыткой без статей (день 18), поэтому «неполная копия» — это копия без удачного снимка.

| Состояние | `faq_search`, `faq_article` отвечают | Фоном |
| --- | --- | --- |
| копия хорошая | **из копии**, как на дне 19 | ничего |
| копия плохая, сайт доступен | **с сайта** (§3.4) | запрос снимка (§2.5) |
| копия устаревшая, сайт недоступен | **из устаревшей копии**, с пометкой «сайт недоступен» | запрос снимка (он, скорее всего, тоже не удастся — повтор по §2.5) |
| копии нет, сайт недоступен | `ToolError`: «FAQ недоступен: сайт не отвечает (…), копии ещё нет» | запрос снимка |

Вторая строка ответов `faq_search` и первая — `faq_article` говорят, откуда данные (§3.5):

```
источник: копия — снимок #27 от 26.09.2026 22:47 (возраст 3 ч, порог 7 дн.)
источник: сайт — копия пуста, докачивается в фоне (снимок #1 начат 14:02)
источник: сайт — копия устарела (снимок #26 от 18.09.2026, порог 7 дн.), докачивается в фоне
источник: копия — снимок #26 от 18.09.2026 (устарела); сайт недоступен: ConnectError …
```

Так модель может честно сказать, насколько свежий ответ, а в видео видно, как первый вопрос идёт на сайт, а повтор — в копию (сценарий О1, §9.3).

### 2.5. Фоновая докачка: один исполнитель снимков

Снимки делает по-прежнему одна задача в `lifespan` сервера — планировщик дня 18. Теперь он **исполнитель снимков** с двумя источниками работы:

1. **Запрос снимка.** `faq_search` и `faq_article`, увидев плохую копию, ставят флаг «нужен снимок» и будят цикл (`wake`). Ответ инструмента снимка **не ждёт**: полный снимок — 89 запросов и ≈15 с (замер дня 18), а ответ с сайта — единицы секунд (§3.4).
2. **Расписание** — только если оно включено (§3.3). По умолчанию выключено.

Правила дня 18 остаются: снимки не перекрываются (цикл один), прерванный остановкой снимок в базу не попадает, повтор после неудачной попытки — не раньше `min(интервал, RETRY_MIN)`. При выключенном расписании интервалом для этой формулы считается `RETRY_MIN` (15 мин): иначе недоступный сайт опрашивался бы на каждом вопросе. Пока идёт снимок, новые запросы снимка ничего не делают — копия всё равно станет свежей. Запрос во время «паузы» после неудачи не запускает снимок раньше срока: пауза — вежливость к сайту, а ответ пользователю в это время всё равно идёт с сайта.

Сводку снимка сервер по-прежнему пишет в свой терминал — у автозапущенного сервера это терминал приложения (§2.6).

### 2.6. Автозапуск сервера FAQ

Фоновой докачке нужен процесс, который живёт дольше одного вызова: stdio-сервер `mcp_client` запускает на каждый вызов и закрывает сразу после ответа. Поэтому `watch` остаётся HTTP-сервером, а «FAQ доступен всегда» обеспечивает **автозапуск**: приложение само поднимает сервер, если его адрес молчит.

Это меняет правило дня 18 «сервер запускает не приложение, а человек». Ручной запуск остаётся: сервер, который уже отвечает по адресу, приложение использует как есть и не останавливает.

| Когда | Что делает `mcp_client` |
| --- | --- |
| старт приложения | адрес молчит — запустить сервер, дождаться, пока порт ответит (до `WATCH_AUTOSTART_WAIT_S`), и записать строку лога |
| перед каталогом каждого хода | та же проверка: сервер, упавший посреди сессии, поднимается снова. Не чаще раза в `AUTOSTART_RETRY_S` (60 с) — если сервер падает сразу (чужая база, занятый порт), он не перезапускается на каждом ходе |
| выход приложения | остановить **только то, что запустило само приложение**: SIGTERM, ждать до 5 с, потом SIGKILL |
| приложение убито без выхода | сервер сам замечает, что родителя нет, и останавливается (`--parent-pid`, §3.3) |

Подробности — §6.1: командная строка, окружение, свой экземпляр.

### 2.7. Вики: только удалённо

Вики `boardgamehub.ru/wiki/too-many-bones` — русскоязычный справочник фанатов: гирлоки с разбором стиля игры, плохиши, тираны, навыки, коробки, волны, совместимость дополнений и FAQ из чата сообщества. У издателя такого справочника нет, а FAQ издателя — на английском.

Почему только удалённо, а не в SQLite, как FAQ:

- **Объём не мешает** (≈334 страницы, ≈350 тыс. символов текста, §2.10), но **поиска по тексту вики сегодня не будет**. Поиск по словам без морфологии по-русски слабый: «боты» не находят «ботов». На неделе 5 (RAG) корпус вики всё равно придётся резать на чанки с метаданными и заводить эмбеддинги. Локальная база по словам сейчас — работа, которую через неделю выбросят.
- **Навигации по вики хватает.** У вики есть индексы по типам — таблицы «имя · роль/тип · волна · коробка» (§2.10). Модель выбирает строку и открывает страницу — тот же приём, что у FAQ на дне 17 (список → статья).
- **Сайт быстрый**: ≈0,2 с на страницу. Один вызов — один запрос.

### 2.8. Файлы: по значению

`save_markdown(name, content)` сохраняет **то, что передала модель**. Ссылка `s…` дня 19 понятна только серверу, который её выдал, и `files` по ней ничего не найдёт. Поэтому данные в сервер файлов идут **по значению** — ровно то, от чего день 19 уходил. Это записано прямо: гарантии «в файле ровно памятка s3» между разными серверами нет.

Что остаётся:

- **сервер файлов** проверяет свою часть: атомарная запись, без перезаписи, файл перечитан и совпадает с переданным байт в байт (код переносится из `cheatsheet_save`, §5.2);
- **панель** сверяет передачу по журналу хода: если в этом же ходе был `faq_summarize`, а `content` у `save_markdown` содержит его Markdown без изменений — ✓, иначе ⚠️ (§8.2). Это проверка «видно», а не «не даёт»: сохранение с ⚠️ не отменяется;
- **памятку по одному FAQ** по-прежнему собирает `faq_summarize` сэмплингом, а теперь ещё и отдаёт её готовым Markdown для сохранения (§3.5). **Памятку из нескольких источников** (FAQ + вики) пишет сама модель агента — сэмплинг сервера FAQ видит только статьи FAQ.

### 2.9. Сколько это стоит

- **Каталог хода**: три подключения вместо двух — `watch` по HTTP (≈0,02 с), `wiki` и `files` по stdio (≈0,5 с каждое, запуск процесса). Итого ≈1 с до первого раунда. Инструмент `faq_server` из каталога ушёл, так что stdio-процессов по-прежнему два.
- **Схемы**: пять инструментов `watch`, два `wiki`, один `files` — ≈1,5-2 тыс. токенов в корзине `tools` каждого раунда (оценка; на дне 18 четыре инструмента стоили ≈981). Точное число — в замер.
- **Раунды**: длинный флоу — 4-6 раундов. Потолок `TOOL_MAX_ROUNDS` поднимается с 6 до 8 (§9.2).
- **Сайт FAQ** при плохой копии: поиск — список вопросов (7 запросов) плюс тексты найденных статей (до `limit`, по умолчанию 5), статья — 1 запрос. Параллельно идёт фоновый снимок (89 запросов), так что в первые ≈15 с к сайту одновременно ходят до 8 запросов (по 4 у каждого клиента `Site`).
- **Сайт вики**: 1 запрос на вызов.

- **Размер текста**: плохиш, навык, тиран — 250-400 символов; гирлок — 8,7 тыс. (Бумер) и 12,6 тыс. (Тинк); коробка Undertow — 2,2 тыс.; FAQ вики — 3,6 тыс.; «Совместимость» — 2,4 тыс. Всего ≈350 тыс. символов. HTML — 82-101 КБ на страницу.
- **Время**: 0,18-0,39 с на страницу (6 замеров подряд).
- **Язык**: русский. Гирлоки названы по-русски (Бумер, Тинк), но slug — английский (`geroi-boomer`); плохиши — по-английски (Alpha Howl); навыки — по-русски (`navyk-iarost` — «Ярость»).
- **robots.txt** закрывает `/profile`, `/collection`, `/notifications`, `/login`, `/articles/drafts`, `/admin`, `/play-next/edit*` — `/wiki` открыт. В sitemap страниц вики нет. Поиска на сайте нет. Рендер серверный: текст есть в HTML.
- **FAQ вики** сам пишет, что он не официальный FAQ Chip Theory и при конфликте прав актуальная памятка или книга правил. На нём держится приоритет FAQ издателя (§2.3) и ожидание сценария О5.

**FAQ издателя** — база автора прочитана только на чтение (`mode=ro`), файл не менялся:

- статья 33000233634 «Is a Callous Baddie affected by True Dmg?»: «No» — Callous теряет HP только от урона кубиков атаки, иммунен к True Dmg (Bleed, Poison) и даже к Fatigue. На той же теме у вики — «Закалка: от чего защищает?» с «обычно не пробивают» и оговоркой про расхождения в старых русских памятках. Пара для сценария О5 (§9.3).

**Имена модулей**: `wiki_server` и `file_server` не совпадают ни с модулями стандартной библиотеки (там есть `fileinput`, `filecmp`), ни с пакетами venv (там есть `filelock`).

**Не проверено**: автозапуск и остановка сервера (в том числе при остановке превью-сервера), поиск по сайту и фоновый снимок одновременно, время ответа с сайта внутри вызова сторожа, выбор серверов моделью на длинном флоу. Это прогон реализации (§14); расхождения — в замер.

### 3.2. Копия и `--max-age-min`

- Новый аргумент `--max-age-min`, целое ≥ 1, по умолчанию 10 080 (неделя). Минуты, а не дни: для видео нужна устаревшая копия за пару минут (`--max-age-min 2`, §14).
- «Копия хорошая» — функция `copy_state(conn, now)`: последний удачный снимок, его возраст, порог, идёт ли снимок, срок следующей попытки. Её зовут `faq_search`, `faq_article` и `faq_changes` (для строки состояния); чистая часть — сравнение возраста с порогом — проверяется без базы.
- В строке старта сервера — порог: «копия считается свежей 7 дн. (--max-age-min 10080)».

### 3.3. Исполнитель снимков и расписание

- Цикл `scheduler()` дня 18 остаётся одной задачей в `lifespan`, но срок считается из двух источников: `refresh_requested` (флаг, поставленный инструментом) и расписание, если оно включено. Флаг снимается, когда снимок начат. Пауза после неудачи — `next_due()` дня 18; при выключенном расписании интервал в формуле — `RETRY_MIN`.
- **Расписание выключено по умолчанию.** В `settings` появляется ключ `schedule_enabled` (`"1"` / `"0"`). Базы дней 18-19, где его нет, читаются как «выключено», даже если там сохранён интервал: иначе у автора после обновления продолжились бы снимки по старому расписанию.
- Включают расписание явно: `--interval N` при запуске (включает и сохраняет, как на дне 18) или `faq_watch_schedule(N)` (включает и сохраняет). `faq_watch_schedule(0)` выключает и сохраняет. Схема параметра — `ge=0, le=10080`; значения 1-4 сервер отклоняет сам: «от 5 минут, или 0 — выключить».
- **`--parent-pid PID`** — новый необязательный аргумент. Сервер раз в тик цикла (`SCHEDULER_TICK_S`) сверяет `os.getppid()` с ним. Родитель сменился — сервер пишет строку лога и останавливается так же, как по Ctrl+C: идущий снимок в базу не попадает. Передаёт аргумент только автозапуск (§6.1); у ручного запуска его нет.
- Строка старта сервера говорит, что включено: «расписание выключено — снимки по запросу, когда копия пуста или старше порога» или «раз в 60 мин (из --interval)».

### 3.4. Поиск и статья с сайта

**Поиск.** `read_sections()` дня 18 (7 запросов, ≈3-4 с на сервере) даёт вопросы всех разделов. Слова запроса сравниваются **только с вопросами** — тексты статей на сайте ещё не прочитаны. Правила слов и веса — дня 19 (`_search_words()`, `_score_article()` с пустым текстом). Затем тексты первых `limit` найденных статей читаются `read_article()` параллельно (потолок `Site` — 4) и записываются в базу вместе с поиском (§3.7). Так `faq_summarize` по поиску с сайта работает тем же путём «по ссылке», что и по копии: функция `Resolve` детерминирована и сайт не трогает — она выполняется на каждом раунде просьбы (день 19, §3.4).

Ничего не нашлось — не ошибка (правило дня 19). Ответ: «по вопросам ничего не найдено; копия докачивается — через минуту поиск пойдёт и по текстам статей».

**Статья.** `read_article()` дня 18 — 1 запрос. В базу не пишется: копию обновит снимок.

**Сбой сайта** на поиске или статье при устаревшей копии — ответ из копии с пометкой (§2.4). При пустой копии — `ToolError` с текстом сбоя сайта.

### 3.7. База: версия 3

```sql
-- searches: run_id допускает NULL (поиск по сайту), новая колонка source
CREATE TABLE searches (id INTEGER PRIMARY KEY, created_at TEXT NOT NULL, run_id INTEGER REFERENCES runs(id),
                       source TEXT NOT NULL DEFAULT 'копия', query TEXT NOT NULL, limit_n INTEGER NOT NULL,
                       article_ids TEXT NOT NULL);
-- что поиск по сайту прочитал: по строке на найденную статью, тексты — в texts по хешу
CREATE TABLE search_articles (search_id INTEGER NOT NULL REFERENCES searches(id), position INTEGER NOT NULL,
                              article_id TEXT NOT NULL, section TEXT NOT NULL, question TEXT NOT NULL,
                              url TEXT NOT NULL, text_hash TEXT NOT NULL REFERENCES texts(hash),
                              PRIMARY KEY (search_id, position));
```

- **`user_version` — 3.** Сервер принимает 0 (создаёт всё), 1 (база дня 18: таблицы дня 19 и дня 20), 2 (база дня 19) и 3. Миграция 2 → 3 — одна транзакция: `searches` пересобирается (новая таблица, копия строк с `source='копия'`, старая удаляется, новая переименовывается — `ALTER TABLE` в SQLite `NOT NULL` не снимает), `search_articles` создаётся. - **Миграция односторонняя**: сервер с тега `day19` базу версии 3 не откроет (честный отказ дня 18). Для возврата к дню 19 нужна своя база (`--db`).
- `_search_articles()` дня 19 для поиска с `source='сайт'` читает `search_articles`, а не снимок; проверки передачи и тексты отказов дня 19 не меняются.

## 4. Новый `src/wiki_server.py`

### 4.1. Программа

- Отдельная программа, stdio, SDK v2 `MCPServer`, `structured_output=False`, `log_level="WARNING"` — как `faq_server.py`. Приложение запускает её процессом (`sys.executable`) на каждый вызов и не импортирует.
- Знает движок вики boardgamehub, но не Too Many Bones: аргументы `--base-url https://boardgamehub.ru`, `--wiki too-many-bones` (slug вики), `--wiki-name "Too Many Bones"` (для описаний инструментов).
- HTTP — `httpx`, `User-Agent` проекта, таймаут 10 с, один запрос на вызов. Разбор — дерево `Node`/`parse_html()` из `faq_server.py`: разбор HTML там общий, второго разбора в проекте не пишем. Это второе ребро между серверами (как `faq_watch.py` → `faq_server.py`), вне графа приложения; Freshdesk-часть `faq_server.py` вики не использует.
- Ожидаемые сбои — `ToolError` (день 17): сайт недоступен, 404, разметка не разобрана (что именно не найдено и где), неверный тип или slug. Логи — stderr, префикс `[Вики-сервер]`.
- Какие узлы HTML что содержат, исполнитель выясняет по живым страницам (§2.10 — что на странице есть); селекторы — константами вверху файла, как у `faq_server.py`.

```

Строка: имя · slug · Роль · Волна · Коробка.
Бумер · geroi-boomer · Дальний бой · 1-я волна, Too Many Bones · Too Many Bones
…
Страница записи — wiki_page(slug).
```

- `type` — slug типа или его русское имя, без учёта регистра («гирлоки», «girloki»). Неизвестный тип — `ToolError` со списком типов.
- `contains` — фильтр по подстроке в любой колонке, без учёта регистра. Строк больше `WIKI_INDEX_MAX_ROWS` (80) — первые 80 и «… ещё N — уточни contains». Плохишей 200: без фильтра ответ показывает 80 и просит уточнить.

**`wiki_page(slug)`**:

```
Страница: Тинк · Гирлоки · https://boardgamehub.ru/wiki/too-many-bones/geroi-tink
Здоровье: 3
Ловкость: 4
…
Текст:
Сборка ботов Тинка
…
✂️ Страница длиннее 9000 символов — продолжение по ссылке.
```

- `slug` — `[a-z0-9-]+`, без `too-many-bones/` и без адреса; префикс вики и полный адрес сервер срезает сам (модель может передать ссылку целиком). Проверяет сервер, а не схема — отказ понятным текстом (правило дня 19).
- Отбрасывается: путь `/wiki/…`, «История», «Нашли ошибку?», подпись автора, «Донат», «История правок», подписи к картинкам-кнопкам. Поля — строками «ключ: значение».
- Текст длиннее `WIKI_PAGE_MAX_CHARS` (9 000) — обрезан по границе абзаца с пометкой. Потолок ниже `TOOL_RESULT_MAX_CHARS` (12 000), чтобы пометку писал сервер, а не обрезка клиента: страница Тинка — 12,6 тыс. символов.
- Страница не из этой вики (редирект на другой путь) — `ToolError`.

## 6. Что меняется в `src/mcp_client.py`

### 6.1. Автозапуск HTTP-сервера

- **Поле описания** `McpServer.autostart: tuple[str, ...] = ()` — в конце, с умолчанием (правило полей дня 18). Командная строка процесса, которую задаёт `presets.py`; `()` — не запускать. Имеет смысл только у HTTP-сервера (`url`).
- **Функция `ensure_started(server, environ) -> AutostartStatus`**. `AutostartStatus` — что с сервером: `отвечает` (кто бы его ни запустил), `запущен приложением` (pid, время до ответа порта), `не запущен` (причина: автозапуска нет, адрес заменён без своей командной строки, процесс вышел с кодом N, порт не ответил за N с) и `пауза до …` (после неудачи).
  - Проверка «адрес молчит» — TCP-подключение к хосту и порту адреса, с таймаутом 0,5 с. Это не MCP-подключение: чужой сервер на порту «отвечает», и автозапуска не будет — сбой каталога покажет день 18.
  - Запуск — `subprocess.Popen(argv, env=<белый список>, stdin=DEVNULL)`, stdout и stderr наследуются: строки `[FAQ-сторож]` идут в терминал приложения. Окружение — тот же белый список `INHERITED_ENV`, что у stdio-серверов: ключ DeepSeek из `src/.env` процесс сервера не получает. Процесс остаётся в группе процессов приложения, поэтому Ctrl+C в терминале приложения доходит и до него.
  - Ждать ответа порта — до `wait_s` (параметр; из `presets.py` — `WATCH_AUTOSTART_WAIT_S`, 10 с), проверка раз в 0,1 с. Процесс вышел раньше — статус с кодом выхода (1 — порт занят, 2 — чужая база: коды дня 18).
  - После неудачного запуска следующий — не раньше `AUTOSTART_RETRY_S` (60 с).
- **Состояние модуля.** Реестр запущенных процессов по имени сервера и время последней попытки — первое состояние в `mcp_client.py`, который до сих пор его не держал (день 16: «состояния между вызовами нет»). Исключение осознанное: процесс, запущенный модулем, модуль и останавливает. Реестр — под замком: `ensure_started()` зовут и старт приложения, и каталоги ходов разных вкладок.
- **Остановка** — `atexit`: для каждого процесса из реестра SIGTERM, ожидание до 5 с, SIGKILL. Процессы, которые приложение не запускало, не трогаются. На случай, когда `atexit` не выполнится (SIGKILL приложения, SIGTERM без обработчика), сервер сам следит за родителем — аргумент `--parent-pid` в командной строке автозапуска (§3.3, §9.1).
- **`McpToolBox.catalog()`** у сервера с `autostart` сначала зовёт `ensure_started()`. Статус уходит в лог; сбой запуска каталог не отменяет — дальше сбой соединения, как на дне 18.
- **Свой экземпляр.** Если адрес заменён переменной (`url_env`), автозапуск — только при заданной переменной `TOOMANYRULES_FAQ_WATCH_ARGS`: её слова (`shlex.split`) дописываются к командной строке автозапуска, как аргументы `./run.sh faq-watch`, и позже заданный аргумент перекрывает прежний. Без неё — `не запущен: адрес заменён, своей командной строки нет`. Иначе экземпляр со своим адресом поднял бы сервер автора с базой автора. Порт командной строки (последний `--port`) должен совпасть с портом адреса — иначе `не запущен: --port N не совпадает с адресом`. Логика — в `resolve_autostart(server, environ)` (чистая функция, как `resolve_launch()`); имя переменной — поле `McpServer.autostart_env`.
- Лог:

  ```
  [MCP watch] автозапуск: адрес молчит — запускаю python faq_watch.py … --parent-pid 41235
  [MCP watch] автозапуск: порт ответил через 1.4 с, pid 41250
  [MCP watch] автозапуск: процесс вышел с кодом 2 — не запущен; следующая попытка не раньше 10:17
  [MCP watch] остановка: pid 41250 — SIGTERM, вышел через 0.3 с
  ```

### 6.2. Группа

- `McpToolBoxGroup.server_of(name) -> str` — имя сервера инструмента по карте маршрутов (или `""`). Для панели: колонка «сервер» (§8.2). Агенту не нужен.

## 14. Проверка: прогон

Отдельного документа нет (§1): проверка — в видео (§15), числа — в замере (§9.4).

1. **Свой экземпляр.** Приложение на своём порту с `TOOMANYRULES_DATA_DIR`; `TOOMANYRULES_FAQ_WATCH_URL` — адрес своего сторожа, `TOOMANYRULES_FAQ_WATCH_ARGS="--port <свой> --db <временная база>"` — автозапуск своего сторожа; `TOOMANYRULES_FILES_MCP_COMMAND` — сервер файлов со своим `--out`. Сторож автора на 8765, его база и его файлы не трогаются.
2. **Автозапуск.** Старт приложения — строка «запущен приложением», строки `[FAQ-сторож]` в терминале приложения, «копия: пусто · расписание выключено». Кнопка «Каталог группы» — восемь инструментов трёх серверов.
3. **О1** на пустой базе: `источник: сайт` у обоих вызовов, в терминале «снимок #1: начат (по запросу: копия пуста)» до ответа ассистента и «82 статьи» после. Повтор О1 — `источник: копия #1`.
4. **О2-О6**: строка «Маршрут», колонки «сервер» и «откуда»; О2 — открыть файл: данные вики и ссылки FAQ. Если модель выбрала `faq_summarize` — проверка передачи по значению (§8.2).
5. **Передача по значению** в REPL тем же `McpToolBox(FILES_MCP с своим --out)`: `save_markdown` с Markdown из `faq_summarize` — файл совпадает; с `content=""` — отказ.
6. **Устаревшая копия**: перезапуск своего сторожа с `--max-age-min 2`, подождать 2 мин после снимка — вопрос по FAQ идёт на сайт, в терминале «копия устарела (возраст …, порог 2 мин)».
7. **Сайт недоступен**: свой сторож с `--base-url https://nonexistent.invalid` — на пустой базе `ToolError` «FAQ недоступен…»; на копии с `--max-age-min 1` — ответ из копии с «сайт недоступен».
8. **Падение сервера**: `kill` своего сторожа — следующий ход поднимает его снова (строка автозапуска); сразу повторный `kill` — следующая попытка не раньше чем через 60 с.
9. **Выход приложения**: Ctrl+C — сторож остановился (`pgrep -fl faq_watch` — нет своего); остановка превью-сервера — сторож останавливается сам по `--parent-pid` в пределах тика.
10. **Расписание**: «Проверяй FAQ раз в час» → `faq_watch_schedule(60)`; «Больше не проверяй FAQ сам» → `faq_watch_schedule(0)`; после перезапуска сторожа — как сохранено.
11. `pgrep -fl "wiki_server|file_server"` — пусто. Замер — §9.4.

Если модель выбирает не тот сервер (вики для эрраты, FAQ для характеристик героя) или пропускает сохранение — это результат прогона, он виден в «Маршруте». Правка описаний допустима и записывается в комментарии у константы.

## 15. Что должно быть видно в видео

1. **Задача**: у агента три MCP-сервера — FAQ издателя, фанатская вики и файлы, — и он сам выбирает, куда идти.
2. **Серверы**: строка «Серверы» и «Каталог группы» — восемь инструментов, у каждого свой сервер; `watch` запущен приложением.
3. **О1 — FAQ всегда доступен**: пустая копия → ответ с сайта, в терминале — фоновый снимок; повтор — из копии.
4. **О2 — длинный флоу**: вики → FAQ → файл в одном ходе, строка «Маршрут» с тремя серверами, открыть файл.
5. **Выбор источника**: О3 — только вики, О4 — только FAQ, О5 — оба и приоритет официального FAQ, О6 — ни одного вызова.
6. **Порядок вызовов**: данные раньше сохранения, статья — по номеру из поиска; в «Маршруте» и в логах трёх процессов.
7. Короткий вывод: несколько серверов, выбор сервера моделью по описаниям, длинный флоу. Следующий шаг — неделя 5: RAG по правилам и корпусу вики.

## 17. Что сознательно НЕ делаем на этом шаге

- **Не делаем локальной копии вики** и поиска по её тексту: вики — только удалённо. Корпус вики, чанки и эмбеддинги — неделя 5 (RAG).
- **Не делаем RAG**: ни эмбеддингов, ни индекса, ни подстановки найденного в контекст агента кодом. Инструменты по-прежнему вызывает модель.
- **Не пишем роутер в коде** и не выбираем сервер ключевыми словами: сервер выбирает модель по описаниям.
- **Не делаем единого поиска по всем источникам** и не ставим сервер-агрегатор над другими серверами.
- **Не связываем серверы между собой по MCP** (сервер как клиент другого сервера) и не передаём id `q…`/`s…` между серверами.
- **Не отдаём модели выбор «копия или сайт»** и не делаем отдельного инструмента «обнови FAQ»: свежесть копии — забота сервера FAQ.
- **Не проверяем кодом «правильность» маршрута** и не отменяем сохранение с ⚠️: код показывает маршрут и передачу, суждение — за человеком.
- **Не меняем системные промпты** пресетов и промпты служебных работ; маршрутизация — только описаниями инструментов.
- **Не удаляем `faq_server.py`** и блок дня 17; не удаляем планировщик дня 18 — он выключен по умолчанию.
- **Не вызываем инструменты BGG**: сервер дня 16 — только список по кнопке, ключа BGG нет.
- **Не делаем других форматов файлов** (PDF), чтения, списка и удаления файлов инструментами; файл открывает человек.
- **Не делаем фоновой синхронизации по умолчанию** и не опрашиваем серверы из приложения: докачка — только по запросу, расписание — только по явной просьбе.
- **Не управляем другими процессами**: автозапуск — только сервер FAQ, только когда адрес молчит; чужой процесс на порту и сервер, запущенный человеком, приложение не трогает.
- **Не даём сэмплинг** `wiki` и `files`.
- **Не меняем `agent.py`**, формат файла сессии, `storage.py` и `tokens.py`.
- **Не оцениваем кодом качество ответов** и «лучший» источник: сверяет человек по статьям FAQ и страницам вики.
- **Не пишем отдельного документа проверки**: формат дня — видео + код; факты — в замере (§9.4).
- Не пишем тестов и линтера.

Не расширяй объём дня сверх изменений `faq_watch.py` из §3, двух новых серверов из §4-§5, автозапуска и методов группы из §6, блока дня 20 и перекладки аккордеонов из §8, серверов, параметров и сценария из §9, README, CLAUDE.md и §5 спецификации проекта из §10.
