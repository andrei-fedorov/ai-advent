## 2. Что делаем конкретно для TooManyRules

Берём один и тот же вопрос по правилам Too Many Bones и прогоняем его через DeepSeek API на 4 комбинациях «модель × режим рассуждения» — единственный провайдер, доступный по API на весь челлендж (см. общую спецификацию проекта, раздел 3).

Задание предлагает пример «слабая / средняя / сильная модель, например начало / середина / конец списка HuggingFace». В рамках единственного доступного провайдера (DeepSeek) это переносится на явную матрицу 2×2 по двум осям линейки DeepSeek V4:

|                    | thinking **off** | thinking **on** |
| ------------------ | ---------------- | ---------------- |
| **`deepseek-v4-flash`** | вариант 1 (самый слабый/дешёвый/быстрый) | вариант 2 |
| **`deepseek-v4-pro`**   | вариант 3 | вариант 4 (самый сильный — флагман + рассуждение) |

Режим `thinking` переключается параметром API, а не отдельным именем модели (см. раздел 3). Такая матрица нагляднее «просто трёх моделей»: видно раздельно эффект размера модели (flash vs pro) и эффект включения рассуждения (off vs on) — а не только суммарный эффект.

Используем тот же вопрос, что и в дне 4 (структура «факт + иллюстрация», чтобы было видно не только фактическую точность, но и стиль изложения):

```
Объясни как работает Отравление в Too Many Bones простыми словами, как будто
объясняешь новому игроку, и приведи короткий пример игровой ситуации,
описывающей это правило.
```

Один запуск сравнения — **4 обращения к API**, по одному на каждую ячейку матрицы. Повторы на ячейку не нужны — здесь сравниваются модель/режим, а не разброс ответов при фиксированных параметрах (в отличие от дня 4).

Системный промпт и вопрос не меняются между всеми четырьмя вызовами — переменные это только модель (`deepseek-v4-flash` / `deepseek-v4-pro`) и режим `thinking` (`off` / `on`).

## 3. Параметры запросов

- Системный промпт — `SYSTEM_PROMPT` из дня 1, без изменений.
- Вопрос — один и тот же во всех 4 вызовах (раздел 2).
- Модель — `deepseek-v4-flash` или `deepseek-v4-pro` (см. матрицу).
- Режим рассуждения переключается через `extra_body`, отдельно от имени модели:
  ```python
  # thinking off:
  extra_body={"thinking": {"type": "disabled"}}
  # thinking on (эффект рассуждения по умолчанию — "high"):
  extra_body={"thinking": {"type": "enabled"}}
  ```
- **`temperature`/`top_p`/`presence_penalty`/`frequency_penalty` не задаются ни в одном из 4 вызовов.** Задание дня 5 не упоминает эти параметры, так что они не обязательная переменная для сравнения; кроме того, в режиме `thinking: enabled` API их всё равно не поддерживает — единообразие проще всего сохранить, вообще нигде не задавая их и полагаясь на дефолты API.
- `max_tokens`/`stop` из дня 2 не задаются.
- На каждый вызов измеряется и сохраняется:
  - время ответа (замер в коде вокруг вызова API, в секундах);
  - количество токенов (`usage.prompt_tokens`, `usage.completion_tokens`, `usage.total_tokens` из ответа API — для вызовов с `thinking: enabled` `completion_tokens` включает и токены рассуждения, это нормально и не требует отдельного учёта);
  - оценочная стоимость вызова в долларах, посчитанная по цене за 1M токенов для конкретной модели (константы цены на вход/выход по `deepseek-v4-flash` и `deepseek-v4-pro` нужно взять с актуальной страницы цен DeepSeek — https://api-docs.deepseek.com/quick_start/pricing — на момент реализации).

## 4. Технические требования

- Тот же стек и файл (`src/app.py`), новая вкладка «День 5» добавляется по аналогии с днями 1-4 (`gr.Tab` внутри существующего `gr.Blocks`), остальные вкладки не трогаем.
- Один клик по кнопке делает все 4 вызова (порядок и синхронность выполнения не принципиальны) и логирует каждый вызов в stdout (модель, `thinking` on/off, `finish_reason`, время ответа, токены, длина и текст ответа) — тот же паттерн логирования, что в днях 2-4.
- Вывод — 4 подписанных блока (по одному на ячейку матрицы: модель + режим thinking), в каждом видно: текст ответа, время ответа, токены (prompt/completion/total), оценочную стоимость. Показывать сам текст рассуждения (`reasoning_content`) в интерфейсе необязательно — не входит в критерии приёмки, можно добавить по желанию, если это не увеличивает объём работы.
- Среди 4 вариантов зелёным цветом шрифта выделяется наименьшее значение отдельно по каждой из трёх измеренных метрик: время ответа, `total_tokens`, оценочная стоимость. Сравнение по каждой метрике независимое — победители по разным метрикам могут быть разными вариантами (например, самый быстрый не обязательно самый дешёвый по токенам). Красным/другим цветом худшие значения не выделяются — подсвечивается только минимум.
- Никакой автоматической метрики **качества** и никакой подсветки «лучшего по качеству» варианта кодом — сравнение качества делает автор вручную, глядя на 4 ответа (тот же принцип, что в днях 3-4). Подсветка минимума по времени/токенам/стоимости (пункт выше) не противоречит этому принципу: это не оценка качества, а простое сравнение уже вычисленных объективных чисел.
- API-ключ — по-прежнему только `DEEPSEEK_API_KEY` через `.env`, не коммитить. Новый провайдер API не добавляется.

## 5. Что должно быть видно в видео

1. Запуск скрипта, вкладка «День 5».
2. Все 4 ответа (flash/pro × thinking off/on) с ясно видными подписями модели и режима, временем ответа, токенами и стоимостью — с зелёной подсветкой наименьшего значения по каждой из трёх метрик.
3. Короткий устный вывод автора о различиях в качестве, скорости и ресурсоёмкости.

## 6. Критерии приёмки

- Один и тот же вопрос выполнен на всех 4 ячейках матрицы `deepseek-v4-flash`/`deepseek-v4-pro` × `thinking off`/`on`, при одинаковых остальных параметрах (системный промпт, вопрос; без `temperature`/`top_p`/penalty-параметров).
- Для каждого вызова показаны время ответа, количество токенов и оценочная стоимость.
- Наименьшее значение по каждой из трёх метрик (время, `total_tokens`, стоимость) выделено зелёным цветом шрифта — независимо по каждой метрике.
- Есть краткий словесный вывод о различиях в качестве/скорости/ресурсоёмкости (человеческое суждение, не автоматическая метрика).

## 7. Что сознательно НЕ делаем на этом шаге

- Не трогаем вкладки/промпты дней 1-4.
- Не задаём `temperature`/`top_p`/`presence_penalty`/`frequency_penalty` ни в одном из 4 вызовов.
- Не делаем повторов на ячейку матрицы (в отличие от дня 4) — здесь не оценивается разброс ответов одной конфигурации.
- Не считаем автоматическую метрику **качества** и не подсвечиваем «лучший по качеству» вариант кодом — эта оценка человеческая, как в днях 3-4. (Зелёная подсветка минимума по времени/токенам/стоимости — это не метрика качества, а сравнение уже измеренных чисел, см. §4 — это делать нужно.)
- Не используем устаревшие алиасы `deepseek-chat`/`deepseek-reasoner` для дня 5 — только явные `deepseek-v4-flash`/`deepseek-v4-pro` с переключением `thinking` через `extra_body`.
- Не добавляем новый провайдер API — остаёмся на DeepSeek, единственном провайдере с доступным ключом на весь челлендж.
- RAG / реальную базу правил — неделя 5 (по номеру недели, не путать с «днём 5» челленджа), точность ответов пока оценивается вручную по бумажной книге правил.

Не расширяй объём задания сверх сравнения матрицы 2×2 (модель × режим рассуждения) на одном и том же запросе.
