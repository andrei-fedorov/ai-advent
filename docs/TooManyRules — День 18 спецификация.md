# TooManyRules — спецификация дня 18

Тема: Планировщик и фоновые задачи — «сторож FAQ»: свой долгоживущий MCP-сервер по Streamable HTTP. По расписанию он снимает официальный FAQ издателя Too Many Bones в SQLite, после каждого снимка выдаёт сводку изменений, а по вызову инструмента отдаёт агрегированную сводку за период. Агент пользуется им наравне с инструментами дня 17

## 1. Задание челленджа (день 18)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_18.txt`. Комментариев организатора к дню 18 на момент написания нет.

Ключевое из задания: **MCP-инструмент с отложенным или периодическим выполнением**. Инструмент **сохраняет данные** (JSON или SQLite), **выполняется по расписанию** и **возвращает агрегированный результат**. Результат дня — агент, который **работает круглосуточно и периодически выдаёт сводку**. Формат сдачи — **видео + код**.

Формат — «видео + код» без «/ текст», поэтому **отдельного документа проверки у дня нет** (правило дней 12, 16 и 17): проверка показывается в видео (§13), факты реального прогона записываются комментарием в коде (§8.4).

День 18 — третий день недели 4 («MCP»). Правила прошлых дней в силе и здесь не повторяются:

- **внешний мир — за своим модулем**: LLM API вызывается только в `agent.py`, клиентскую часть SDK `mcp` импортирует только `mcp_client.py`, серверную — только отдельные программы-серверы (§3.1);
- **всё «про настолки» — в `presets.py`**: ни сервер, ни `mcp_client.py`, ни агент про Too Many Bones не знают;
- **агент не знает про MCP**: инструменты приходят к нему через протокол `ToolBox` (день 17);
- **на экране — текущий день, прошлые свёрнуты** (правило аккордеонов);
- **абстракций под будущие дни не пишем**: один новый сервер, два инструмента, одна задача по расписанию.

Все числа времени и токенов в примерах ниже — **условные, для иллюстрации формата**, если не сказано, что они замерены (§2.9). Настоящие берутся из прогона (§8.4).

## 2. Что делаем конкретно для TooManyRules

### 2.1. Что в продукте меняется со временем

Ассистент по правилам реактивен: вопрос → ответ. Во всём, чем он пользуется, со временем меняется только одно — **официальный FAQ издателя**. Издатель дописывает разъяснения и правит старые ответы, а это и есть эррата: место, где модель ошибается, и где правильный ответ однажды поменялся. Проверено при написании (§2.9): статья «How does the “Gearlocs Need Food Badly” Encounter work?» (33000210199) изменена на сайте **15.09.2026**, две статьи раздела Trover — в апреле 2026, самая старая — в 2017-м. FAQ живой, но меняется редко.

Поэтому «агент 24/7» дня — это **сторож FAQ**. Это сервер, который работает сам по себе, без приложения:

1. **по расписанию** (по умолчанию раз в сутки) снимает FAQ целиком — список вопросов и тексты всех статей — и **сохраняет снимок в SQLite**;
2. сравнивает снимок с прошлым удачным и **после каждого снимка выдаёт сводку**: какие статьи появились, изменились, переехали в другой раздел, пропали. Сводка пишется в лог сервера и в базу;
3. по вызову инструмента **отдаёт агрегированную сводку за период**: что сторож заметил за N дней, какие статьи по датам сайта изменены в этот период и в каком состоянии сам сторож;
4. по вызову второго инструмента **меняет расписание**. Инструмент возвращает ответ сразу, а работа, которую он запланировал, выполняется потом.

Агент получает оба инструмента вместе с `faq_questions` и `faq_article` дня 17. На «что нового в FAQ за месяц?» он зовёт сводку и пересказывает её по-русски со ссылками на статьи. На «проверяй FAQ раз в час» он меняет расписание.

Продуктовый смысл. Игрок узнаёт, что издатель изменил ответ, не перечитывая FAQ. А снимки в базе — это текст официальных разъяснений с историей правок. Сегодня агрегированный результат берётся из этой истории, а на днях 19 и 5-й недели это готовый корпус (§15).

### 2.2. Почему отдельный долгоживущий сервер по HTTP

Серверы дней 16-17 живут **одно подключение**. `mcp_client` запускает процесс по stdio, делает `tools/list` или `tools/call` и закрывает его. Если сервер так живёт секунды, работать по расписанию ему негде. Варианты:

| Где живёт расписание | Что получаем | Почему нет / да |
| --- | --- | --- |
| stdio-сервер по вызову + отдельный демон (cron, launchd) | инструменты читают базу, данные собирает чужой процесс | расписание оказывается вне MCP; «инструмент с периодическим выполнением» — только на словах |
| поток планировщика в процессе Gradio | ничего нового в транспорте | «24/7» только пока открыто приложение; приложение — интерфейс, а не служба |
| **отдельный MCP-сервер по Streamable HTTP с планировщиком внутри** | служба, которая работает без приложения и переживает его перезапуски; приложение подключается по адресу | **выбрано** |

Streamable HTTP — второй транспорт MCP после stdio: сервер слушает `http://127.0.0.1:8765/mcp`, клиент шлёт запросы JSON-RPC по HTTP. Для проекта это новое:

- сервер **запускает не приложение**, а человек (`./run.sh faq-watch`, §10). Приложение без сервера работает как на дне 17 (§6.3);
- у процесса сервера **долгая жизнь и своё состояние** — база и расписание. Подключения клиента при этом остаются короткими: одно подключение на вызов, как на днях 16-17;
- SDK v2 поддерживает это из коробки. Сервер — `MCPServer.run("streamable-http", …)` (под ним uvicorn и starlette, их уже ставит сам `mcp`). Клиент — тот же `Client`, только вместо `StdioServerParameters` ему передаётся адрес. Проверено прототипом (§2.9).

### 2.3. Инструменты сервера

| Инструмент | Параметры | Что возвращает | Запросов к сайту |
| --- | --- | --- | --- |
| `faq_changes` | `days`: integer, 1-365, по умолчанию 7 | агрегированную сводку за `days` дней. Состояние сторожа (расписание, снимки за период — удачные и сбои, последний и следующий снимок). Изменения, замеченные сторожем (сравнение соседних удачных снимков). Статьи, у которых дата изменения на сайте попадает в период (по последнему снимку) | 0 — только база |
| `faq_watch_schedule` | `interval_minutes`: integer, 5-10080 | новое расписание и время следующего снимка; интервал сохраняется в базе и переживает перезапуск сервера | 0 |

Почему именно так:

- **Агрегат — из базы, а не с сайта.** Вызов `faq_changes` в сеть не ходит и отвечает за миллисекунды. Сайт читает только планировщик. В этом смысл дня: работа идёт по расписанию, а инструмент отдаёт накопленное.
- **Два источника в сводке — и оба подписаны.** «Замечено сторожем» знает только то, что случилось после его первого снимка. «По датам сайта» — поле «Modified on» статьи (§2.9) — знает и о правках до первого снимка, но не говорит, что именно поменялось. Первое показывает работу сторожа, второе делает сводку полезной с первого дня. В ответе они не смешиваются: у каждого свой заголовок и своё «откуда известно».
- **Расписание меняет инструмент.** Это буквальное «инструмент с отложенным выполнением»: вызов возвращается сразу, а снимок по новому расписанию происходит потом, в фоне. Модель зовёт его только по прямой просьбе (описание, §3.7).
- **Кнопки «снять сейчас» нет.** Первый снимок сервер делает при старте с пустой базой, следующий — когда наступит срок. Внеочередной снимок получается, если сократить интервал: расписание пересчитывается от последнего удачного снимка, и если срок уже прошёл, снимок идёт сразу (§3.4). Отдельного инструмента для этого не нужно.

### 2.4. Расписание

- **Интервал — в минутах**, от `MIN_INTERVAL_MIN = 5` до `MAX_INTERVAL_MIN = 10080` (неделя), по умолчанию `DEFAULT_INTERVAL_MIN = 1440` (сутки). Нижняя граница — вежливость к чужому сайту: полный снимок — это 89 запросов (§2.9).
- **Кто задал интервал последним, тот и прав.** Значение хранится в базе. Явный `--interval` при запуске сервера перекрывает сохранённое и сохраняется сам. Вызов `faq_watch_schedule` тоже сохраняет. Без аргумента и без записи в базе действует умолчание. Поэтому просьба «проверяй раз в час» переживает перезапуск сервера, а `./run.sh faq-watch --interval 5` для видео действует, пока его не поменяют.
- **Следующий снимок считается от истории в базе, а не от старта процесса.** Удачных снимков нет — снимок сразу. Иначе — время последнего удачного плюс интервал. Если после него была неудачная попытка — время попытки плюс `min(интервал, RETRY_MIN = 15)`. Срок уже прошёл — снимок сразу. Поэтому перезапуск сервера расписание не сбивает: сервер, остановленный на ночь, утром снимет FAQ сразу, а перезапущенный через минуту подождёт свой срок.
- **Время — по стенным часам, а не по монотонным.** Планировщик спит не дольше `SCHEDULER_TICK_S = 60` секунд и каждый раз заново сверяет текущее время со сроком. На ноутбуке, который засыпал, иначе пропал бы снимок: во сне монотонные часы стоят, а срок по стенным уже прошёл.
- **Снимки не перекрываются**: планировщик — один цикл, следующий снимок начинается только после конца предыдущего.
- **Смена интервала будит планировщик**: он пересчитывает срок сразу, не дожидаясь конца своего сна.

### 2.5. Снимок и сравнение

Снимок — это всё, что нужно для сравнения: по каждой статье категории — номер, раздел, вопрос, дата изменения на сайте (как текст и разобранная), хеш текста ответа и его длина. Сами тексты хранятся отдельно, по хешу, без повторов: для 82 статей это ≈22 тыс. символов (§2.9), а от снимка к снимку тексты почти не меняются.

**Сравнивается только полный снимок.** Если хоть одна страница не прочиталась (сеть, 404, разметка) или у раздела прочитано не столько статей, сколько объявлено, снимок **неудачный**. Попытка записывается в базу со временем и причиной, но статьи не записываются, и ни с чем она не сравнивается. Иначе недочитанный раздел выглядел бы как «удалены 13 статей», и сводка стала бы ложной тревогой.

Сравнение нового удачного снимка с прошлым удачным даёт события четырёх видов:

| Вид | Когда |
| --- | --- |
| `новая` | номера статьи в прошлом снимке не было |
| `изменена` | тот же номер, другой вопрос или другой текст (хеш); в подробностях — что именно: вопрос было/стало, текст — строки разницы |
| `перенесена` | тот же номер, другой раздел (вопрос и текст могут совпадать) |
| `удалена` | номер был в прошлом снимке, в новом его нет |

У статьи может быть два события сразу («перенесена» и «изменена»). Одна смена даты «Modified on» без смены вопроса и текста событием не считается: сайт может переписать дату, не меняя ответа, и игроку это ничего не говорит. Дата при этом остаётся в снимке, и `faq_changes` показывает её в части «по датам сайта».

**У первого снимка сравнивать не с чем**: событий нет, в сводке снимка так и написано — «первый снимок: 82 статьи, база для сравнения».

### 2.6. «Периодически выдаёт сводку»: где её видно

| Где | Что | Когда |
| --- | --- | --- |
| терминал сервера | сводка снимка: сколько статей, запросов и секунд, события по видам и строка на каждое событие, время следующего снимка | после каждого снимка, сам — без приложения и без вопроса |
| база | попытка снимка (время, успех или причина сбоя, счётчики событий) и события | после каждого снимка |
| инструмент `faq_changes` | агрегат за период | по вызову: агент в чате или кнопка в панели |
| блок «Сторож FAQ (день 18)» в панели | тот же `faq_changes` кнопкой, со статусом подключения | по кнопке |

**Приложение не опрашивает сервер по таймеру**: в проекте нет поллинга, и `gr.Timer` сегодня не появляется (§15). Круглосуточно работает сервер, и сводку сам по себе он выдаёт в свой терминал. Приложение — окно, в котором можно спросить.

### 2.7. Где лежит и сколько живёт

| Что | Где живёт | Переживает |

### 2.8. Сколько это стоит

- **Сайт**: полный снимок — 89 запросов, ≈18 с при потолке 4 одновременных (§2.9). При интервале по умолчанию это 89 запросов в сутки. На нижней границе, 5 минут, выходит ≈18 запросов в минуту, поэтому 5 минут — режим для записи видео, а не для постоянной работы.
- **Токены**: схемы двух новых инструментов уходят в каждый раунд хода вместе со схемами дня 17 — корзина `tools` растёт (оценка при написании — ≈300-400 токенов сверх ≈495, точное число — в замер). Сводка за период — результат инструмента, его длину держит сервер (§3.6) и потолок `TOOL_RESULT_MAX_CHARS` дня 17.
- **Время хода**: каталог теперь — два подключения, stdio-сервер дня 17 (≈0,5 с) и HTTP-сервер (≈0,02-0,04 с). Вызов `faq_changes` — сотые доли секунды плюс подключение.
- **Модель**: служебных вызовов день не добавляет; сервер LLM не вызывает.

### 2.9. Что проверено до реализации

Проверено при написании спецификации (24-25.09.2026, прототипы во временном каталоге; в репозиторий ничего не попало). SDK mcp 2.2.0, Python 3.14.7, darwin/arm64.

- **Полный снимок сайта** — функциями `faq_server.py` дня 17 (`Site`, `_category_sections`, `_read_folder`, `body_text`) плюс чтение 82 статей: список — 7 запросов за 2,98 с, всё вместе — **89 запросов за 18,41 с**, 82 статьи, ≈22,3 тыс. символов текста ответов.
- **Дата изменения** есть только на странице статьи: `div.date-highlight` с текстом вида «Modified on: Tue, 13 Nov, 2018 at  8:35 AM» (два пробела перед часом — как на сайте). На страницах категории и раздела дат нет. Разбор `strptime("%a, %d %b, %Y at %I:%M %p")` после схлопывания пробелов прошёл для всех 82 статей. Самая старая — 16.10.2017 (33000210178), самые свежие — 01.04.2026 (33000314515, Trover), 06.04.2026 (33000314546, Trover), **15.09.2026 (33000210199, Specific Encounters, «Gearlocs Need Food Badly»)**. Часовой пояс портала на странице не указан.
- **HTTP-сервер на SDK** — прототип: `MCPServer(…, lifespan=…)` и `run("streamable-http", host="127.0.0.1", port=8765)`. Фоновая задача, запущенная в `lifespan` через `anyio` task group, **стартует один раз на процесс, а не на подключение**: в SDK v2 lifespan для Streamable HTTP открывает менеджер сессий (`streamable_http_manager.run()`). Три подключения подряд видели одну и ту же задачу. По Ctrl+C (SIGINT) lifespan закрылся штатно, задача отменилась, процесса не осталось.
- **Клиент** — `Client("http://127.0.0.1:8765/mcp")`: соединение за 0,02-0,035 с, **протокол 2026-07-28 через `server/discover`**, `tools/call` работает. С `stateless_http=True` — то же самое, lifespan по-прежнему один.
- **Сервер не запущен**: `Client(url)` падает за 0,02 с с `ExceptionGroup` → `httpx2.ConnectError: All connection attempts failed`. **`httpx2.ConnectError` — не `OSError`** (SDK ходит по HTTP через пакет `httpx2`, а не через `httpx`). Разбор сбоев `mcp_client` дня 16 его не знает и записал бы как неожиданную ошибку с трассировкой (§5.3).
- **Имена**: модуля `faq_watch` нет ни в стандартной библиотеке, ни среди установленных пакетов. Порт 8765 на машине автора свободен.

**Не проверено при написании**: настоящий сервер с базой и сравнением, группа инструментов у агента и интерфейс. Их прогон — часть реализации (§12). Расхождения с этим разделом записываются в замер как есть.

## 3. Новый сервер `src/faq_watch.py`

### 3.1. Что это за файл

- **Отдельная программа, а не модуль приложения**, как `faq_server.py`. Но её запускает не `mcp_client`, а человек: `./run.sh faq-watch` (§10). Приложение её не импортирует, в графе зависимостей приложения её нет.
- **Импортирует `faq_server.py`** — чтение сайта и разбор страниц (§4). Это единственное новое ребро, и оно между двумя серверами, вне графа приложения. `faq_server.py` при этом по-прежнему не импортирует ничего из проекта.
- **Серверную часть SDK `mcp`** импортируют теперь две программы: `faq_server.py` и `faq_watch.py`. Клиентскую — по-прежнему только `mcp_client.py`.
- **Единственное место работы с базой сторожа** (`sqlite3` из стандартной библиотеки). Правило «диск трогает только `storage.py`» — про приложение, а это отдельная программа со своими данными.
- **Знает портал Freshdesk, но не Too Many Bones**: адрес, категория, её имя и путь к базе приходят аргументами командной строки (§3.2). Слов «Too Many Bones» и «33000133540» в файле нет.
- **Строки — по-русски**: описания инструментов, тексты сводок и ошибок, логи. Вопросы и тексты FAQ остаются английскими.

### 3.3. Сервер и транспорт

```python
server = MCPServer(name="toomanyrules-faq-watch", version="1.0.0", log_level="WARNING", lifespan=scheduler_lifespan)
...
server.run("streamable-http", host="127.0.0.1", port=args.port, stateless_http=True)
```

- **`stateless_http=True`**: клиент подключается на один вызов, и серверу незачем держать сессии до таймаута простоя. Проверено, что так работает и эра 2026-07-28, и lifespan (§2.9).
- **Путь** — `/mcp` (по умолчанию SDK), адрес — только `127.0.0.1`. Защиту от DNS rebinding для localhost SDK включает сам.
- **`log_level="WARNING"`** — и SDK, и uvicorn: строки INFO каждого HTTP-запроса — шум. Свою строку «слушаю …» сервер пишет сам (§3.2).
- **Планировщик — в `lifespan`** (§3.4): вход открывает task group с циклом, выход отменяет её. Ctrl+C останавливает сервер штатно. Снимок, прерванный остановкой, в базу не попадает (§3.5) — в лог идёт строка «снимок прерван остановкой сервера».
- Инструменты — `@server.tool(…, structured_output=False)`, как на дне 17. Аннотации честные: у `faq_changes` — только чтение, повтор безопасен, мир закрытый (база, а не сайт); у `faq_watch_schedule` — запись, не разрушает, повтор с тем же значением безопасен (`idempotent_hint=True`), мир закрытый.

### 3.4. Планировщик

```python
async def scheduler(state):
    while True:
        due = state.next_due()                    # из базы, §2.4
        while now() < due and not state.wake.is_set():
            with anyio.move_on_after(min(SCHEDULER_TICK_S, seconds_until(due))):
                await state.wake.wait()
        state.wake = anyio.Event()                # сбросили «разбудить»
        if now() >= state.next_due():             # интервал мог смениться — пересчитать
            await run_snapshot(state)             # §3.5; исключений наружу не выпускает
```

- `next_due()` — чистая функция над последними попытками и интервалом (§2.4); её же зовёт `faq_changes`, чтобы показать «следующий снимок».
- `faq_watch_schedule` сохраняет интервал и вызывает `state.wake.set()`: планировщик просыпается и пересчитывает срок.
- Любое исключение внутри снимка — неудачная попытка с текстом причины (сбой сайта — текст `ToolError` из `faq_server`, ошибка в коде — имя исключения и трассировка в stderr). Цикл продолжается: сторож не падает от одного плохого снимка.

### 3.5. Снимок

1. `read_sections()` из `faq_server` (§4) — все разделы категории со всеми статьями, с проверкой имени категории.
2. Проверка полноты: у каждого раздела прочитано столько статей, сколько объявлено. Нет — неудачная попытка «неполный снимок: раздел Battle — на сайте 7, прочитано 6».
3. `read_article()` по каждой статье — параллельно, в пределах того же `Site` (потолок 4 одновременных запроса и счётчик запросов — дня 17). Номер статьи, раздел и вопрос берутся из списка, дата и текст — со страницы статьи. Проверка крошек (статья нашей категории) — как у `faq_article`.
4. Текст → `sha256` (первые 16 шестнадцатеричных знаков), длина; дата «Modified on» → текст и разобранное время (без часового пояса; не разобралась — только текст, это не сбой, а предупреждение в сводке снимка).
5. **Одна транзакция**: попытка, строки статей, новые тексты, события сравнения с прошлым удачным снимком (§2.5). До конца транзакции в базе от снимка нет ничего, поэтому прерванный снимок следов не оставляет.
6. Сводка снимка — в stderr (§3.8).

Неудачная попытка — строка в `runs` с `ok=0` и причиной, без статей и событий.

### 3.9. База

`sqlite3` из стандартной библиотеки, режим WAL: инструменты читают, пока снимок пишет. Одно соединение на операцию (`contextlib.closing`), запись снимка — одной транзакцией. Все операции — миллисекунды, поэтому они идут прямо в цикле событий, без потоков.

```sql
PRAGMA user_version = 1;
CREATE TABLE runs     (id INTEGER PRIMARY KEY, started_at TEXT NOT NULL, finished_at TEXT NOT NULL,
                       ok INTEGER NOT NULL, error TEXT NOT NULL DEFAULT '', articles INTEGER NOT NULL DEFAULT 0,
                       requests INTEGER NOT NULL DEFAULT 0, elapsed_s REAL NOT NULL);
CREATE TABLE texts    (hash TEXT PRIMARY KEY, text TEXT NOT NULL);
CREATE TABLE articles (run_id INTEGER NOT NULL REFERENCES runs(id), article_id TEXT NOT NULL,
                       section TEXT NOT NULL, question TEXT NOT NULL, modified_raw TEXT NOT NULL,
                       modified_at TEXT, text_hash TEXT NOT NULL REFERENCES texts(hash), chars INTEGER NOT NULL,
                       PRIMARY KEY (run_id, article_id));
CREATE TABLE changes  (run_id INTEGER NOT NULL REFERENCES runs(id), article_id TEXT NOT NULL,
                       kind TEXT NOT NULL, detail TEXT NOT NULL DEFAULT '');
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

- **Время** — ISO 8601 с часовым поясом машины (`datetime.now().astimezone()`), до секунд. `modified_at` — разобранная дата сайта без пояса или `NULL`.
- **`detail`** у события — JSON: хеши и длины текста было/стало, вопрос было/стало, раздел было/стало. Разницу строк `faq_changes` строит на лету по двум текстам из `texts`, в событии её не хранят.
- **Рост**: снимок раз в сутки — 82 строки в `articles` в сутки (≈30 тыс. в год), тексты не повторяются. Очистки старых снимков сегодня нет (§15).
- **Чужая или битая база не затирается** (правило `JsonLongTermStore` дня 11). `user_version` не 0 и не 1, или файл не открывается как SQLite — сервер пишет причину в stderr и завершается с ненулевым кодом, ничего не записав. Пустой файл или новый путь — схема создаётся.

## 4. Что меняется в `src/faq_server.py`

Чтение сайта выносится в публичные функции, которые берёт сторож. **Поведение инструментов дня 17 не меняется**: ответы `faq_questions` и `faq_article` — байт в байт прежние.

- `async def read_sections(site, config, section_filter="") -> tuple[list[Section], list[Section]]` — все разделы категории и выбранные фильтром, дочитанные по страницам. Это тело `questions()` до форматирования. `questions()` зовёт её.
- `@dataclass(frozen=True) class Article` — `id`, `question`, `section`, `url`, `modified` (текст «Modified on: …» со схлопнутыми пробелами; `""`, если блока нет), `text`.

- Новый маркер разметки `ARTICLE_MODIFIED = ("div", "date-highlight")`. Его отсутствие — не ошибка: `faq_article` дату не показывает, а сторож без даты пишет пустую строку.

## 5. Что меняется в `src/mcp_client.py`

Модуль остаётся листом графа и единственным местом импорта клиентской части SDK. Теперь он умеет второй транспорт и группу серверов для агента.

### 5.1. Сервер по адресу

`McpServer` получает два поля в конце, с умолчаниями (правило добавления полей дней 8-17):

```python
    url: str = ""                   # Streamable HTTP: адрес сервера; "" — stdio по command
    url_env: str = ""               # переменная окружения, целиком заменяющая url; "" — замены нет
```

- Сервер с `url` — это **HTTP-сервер, запущенный не приложением**: `command`, `command_env` и `env_keys` у него пустые. Окружение ему не передаётся — процесс уже живёт своей жизнью.
- `Launch` получает поле `transport: str = TRANSPORT_STDIO` (`TRANSPORT_STDIO = "stdio"`, `TRANSPORT_HTTP = "streamable-http"`). У HTTP-сервера `command_line` — итоговый адрес (для лога и панели), `origin` — «по умолчанию» или «из <url_env>», `argv` пуст.
- `resolve_launch()` для HTTP-сервера проверяет, что адрес начинается с `http://` или `https://` и в нём есть хост. Иначе — `error = "адрес не годится: …"`, сбой стадии «запуск» без подключения, как у неразбираемой командной строки. Пустая замена — нет замены; замена из пробелов — сбой (правило дня 16).

### 5.2. Подключение

`_run()` передаёт `Client` либо `StdioServerParameters` (как сейчас), либо строку адреса. `list_tools()`, `call_tool()`, `ToolListing`, `ToolCall` и `McpToolBox` работают с обоими транспортами без других изменений. Лог подключения показывает транспорт:

### 5.3. Сбои HTTP

- **Сервер не запущен** — стадия «соединение», текст «сервер не отвечает по адресу: ConnectError: All connection attempts failed». `httpx2.TransportError` (родитель `ConnectError`, таймаутов и обрывов чтения) добавляется в ожидаемые ошибки: без трассировки в логе и без перевода в «запуск» (§2.9). `mcp_client` импортирует `httpx2` — это HTTP-клиент самого SDK. Как запустить сервер, модуль не знает: подсказку показывает панель (§7.3).
- **Сервер завис** — общий потолок `fail_after`, «таймаут N с», как у stdio.
- **Ответ не MCP** (на порту чужой сервер) — `MCPError` или ошибка разбора от SDK, стадия «соединение», текст как есть.

### 5.4. Группа серверов для агента: `McpToolBoxGroup`

Агент дня 17 получает один `ToolBox`. Сегодня у него два сервера — FAQ по stdio и сторож по HTTP. Агент при этом не меняется (§6): группа сама отвечает протоколу `ToolBox`.

```python
class McpToolBoxGroup:
    """Несколько `McpToolBox` как один `ToolBox`: каталоги сливаются, вызов уходит серверу,
    который объявил инструмент в последнем каталоге."""

    def __init__(self, boxes: tuple[McpToolBox, ...]) -> None: ...

    @property
    def name(self) -> str: ...          # «faq+watch»

    def catalog(self) -> dict: ...      # §5.4
    def call(self, name: str, arguments: dict) -> dict: ...
```

- **`catalog()`**: каталоги серверов — по очереди, в порядке `boxes`. Инструменты сливаются в этом же порядке. Имя, уже встреченное у предыдущего сервера, пропускается, и об этом появляется предупреждение. Результат:
  - хоть один каталог получен — `ok=True`, инструменты полученных; сбои остальных — в новом необязательном ключе `"warning"`: «watch: сбой на стадии «соединение»: сервер не отвечает…»;
  - ни одного — `ok=False`, `error` — сбои всех через «; »;
  - `elapsed` — сумма.
- **`call()`**: сервер инструмента — по карте «имя → сервер» из последнего удачного каталога группы. Имени нет в карте — `{"ok": False, "error": "инструмента нет в каталоге группы", …}` без подключения (агент и так не отправляет имена вне каталога хода, это защита).
- **Карта — единственное состояние группы.** Она заменяется целиком в конце каждого `catalog()`, читается без замка. Агенты одного процесса видят один и тот же набор серверов, поэтому карты разных ходов совпадают.
- **Один сервер недоступен — ход идёт с инструментами остальных.** Сторож не запущен — у агента FAQ дня 17 и предупреждение в панели. Ни одного — ход без инструментов, как на дне 17.

## 6. Что меняется в `src/agent.py`

Одно: **предупреждение каталога**. В словаре, который возвращает `ToolBox.catalog()`, может быть необязательный ключ `"warning"` (§5.4). Если каталог получен и `warning` непустой:

- к `tools_note` дописывается « · ⚠️ <warning>» — это видно в блоке «Инструменты последнего хода»;
- в лог агента — `WARNING` «каталог получен не целиком: …».

Докстринг протокола `ToolBox` называет новый ключ. Больше в агенте ничего не меняется: цикл раундов, потолки, история, счётчики — как на дне 17. `McpToolBox` ключа `warning` не отдаёт никогда.

Скрипт стоит под `set -u`, а macOS запускает его системным bash 3.2 — проверить `./run.sh faq-watch` и без дополнительных аргументов.

## 12. Проверка: прогон

Отдельного документа нет (§1): проверка — в видео (§13), числа — в замере (§8.4). Сверяет человек.

1. **Свой экземпляр**: сторож — `./run.sh faq-watch --port 8766 --db <временный каталог>/faq_watch.sqlite3 --interval 5`. Приложение — `TOOMANYRULES_DATA_DIR=<временный каталог>/sessions`, `TOOMANYRULES_FAQ_WATCH_URL=http://127.0.0.1:8766/mcp`, свой порт Gradio (правило CLAUDE.md). Сторож автора на 8765 и его базу не трогать.
2. **Первый снимок при старте**: строка «слушаю …», снимок #1 — 82 статьи, ≈89 запросов, «первый снимок, база для сравнения», следующий — через 5 минут.
3. **Каталог по кнопке** в блоке дня 18: протокол 2026-07-28 через `server/discover`, два инструмента с параметрами и описаниями. Сводка кнопкой за 30 дней: состояние, «изменений нет» у сторожа, по датам сайта — 33000210199.
4. **Н1-Н4** в чате: вызовы и аргументы в блоке «Инструменты последнего хода» (теперь в блоке дня 18, §7.2), ответы, журнал ходов, строки агента, `mcp_client` и сервера.
5. **Периодичность**: дождаться второго снимка по расписанию. В терминале сервера появляется сводка снимка #2 с «изменений нет», а `faq_changes` показывает два удачных снимка.
6. **Имитация изменений — честно, как имитация**: остановить сторож и поправить **последний удачный** снимок в своей базе, чтобы следующий снимок увидел разницу с сайтом:

   ```bash
   sqlite3 <временный каталог>/faq_watch.sqlite3 "DELETE FROM articles WHERE run_id = (SELECT max(id) FROM runs WHERE ok = 1) AND article_id = '33000210180'"
   ```

   ```bash
   sqlite3 <временный каталог>/faq_watch.sqlite3 "UPDATE articles SET question = question || ' (старая формулировка)' WHERE run_id = (SELECT max(id) FROM runs WHERE ok = 1) AND article_id = '33000210161'"
   ```

   Снова запустить сторож с `--interval 5` и дождаться срока — не больше 5 минут от последнего удачного снимка. Следующий снимок даёт «новая · 33000210180» и «изменена · 33000210161 · вопрос: было … / стало …». Оба события видны в сводке снимка в терминале, в `faq_changes` в панели и в чате.
7. **Перезапуск сервера**: Ctrl+C во время снимка — снимок в базу не попал, в логе «прерван». Запуск без `--interval` — интервал из базы («из базы» в строке старта), срок — от последнего удачного снимка.
8. **Сбои**:
   - сторож не запущен — кнопки блока дня 18 дают стадию «соединение» и подсказку; ход агента идёт с инструментами FAQ, в заметке каталога — ⚠️ про `watch`;
   - порт занят вторым экземпляром — второй завершается с ошибкой;
   - база чужой версии (`sqlite3 … "PRAGMA user_version = 9"`) — сервер отказывается стартовать, файл не изменён;
   - сайт недоступен (`--base-url https://nonexistent.invalid` на своей базе) — неудачная попытка, повтор через `min(интервал, 15)` мин, сводка показывает сбой.
9. `pgrep -fl faq_server` и, после остановки сторожа, `pgrep -fl faq_watch` — пусто. Замер — комментарием у `FAQ_WATCH` (§8.4).

## 15. Что сознательно НЕ делаем на этом шаге

- **Не опрашиваем сервер из приложения по таймеру** (`gr.Timer`, фоновые потоки в Gradio): сводку сам по себе выдаёт сервер — в свой терминал; приложение спрашивает по кнопке и через агента.
- **Не шлём уведомлений** (MCP notifications, подписки на ресурсы, почта, мессенджеры, системные уведомления): сводка — в лог сервера и по запросу.
- **Не держим постоянного соединения** клиента с сервером и не используем сессии Streamable HTTP: одно подключение на вызов, сервер без состояния сессий.
- **Не запускаем сервер из приложения** и не делаем его системной службой (launchd, systemd, Docker): его запускает человек; развёртывание на VPS — отдельная тема.
- **Не открываем сервер наружу**: только `127.0.0.1`, без аутентификации и TLS.
- **Не делаем нескольких задач в планировщике**, cron-выражений, окон «не раньше 9 утра», внеочередного снимка отдельным инструментом и кнопок управления расписанием в панели.
- **Не зовём LLM на сервере**: сводка собирается кодом из базы; пересказывает её агент. Суммаризация моделью — тема дня 19.
- **Не делаем поиска по снимкам и памяток** — это день 19. Тексты статей хранятся, потому что по ним строится разница в сводке.
- **Не чистим старые снимки** и не делаем архивации, миграций схемы и экспорта базы.
- **Не показываем разницу текста целиком** и не делаем визуального сравнения версий статьи в панели: разница — строки в тексте сводки, с потолком.
- **Не отдаём агенту инструменты BoardGameGeek** и не добавляем другие источники (форум BGG) — один сторож одной категории FAQ.
- **Не меняем инструменты дня 17** и описания их параметров; не меняем системные промпты, служебные работы, формат файла сессии, `storage.py` и `tokens.py`.
- **Не оцениваем кодом качество пересказа сводки** — сверяет человек (§12).
- **Не пишем отдельного документа проверки**: формат дня — видео + код; факты прогона — в замере (§8.4).
- Не делаем RAG, эмбеддингов и индексов — это неделя 5. Не пишем тестов и линтера.

Не расширяй объём дня сверх сервера из §3, выноса чтения из §4, транспорта и группы из §5, предупреждения каталога из §6, блока и перекладки аккордеонов из §7, секции `presets.py` из §8, `run.sh`, README и CLAUDE.md из §10.
