# TooManyRules — AI\-ассистент по правилам Too Many Bones

Проект для AI Advent Challenge (9 поток)

## 1\. Идея и цели

TooManyRules — ассистент, который отвечает на вопросы по правилам настольной игры **Too Many Bones** (Chip Theory Games), опираясь на официальные правила, дополнения и эррата, а не на общие знания модели. Пользователь задаёт вопрос своими словами прямо во время партии — ассистент даёт точный ответ со ссылкой на источник (документ, раздел, страница), вместо того чтобы листать правила вручную.

Цели проекта:

- Углублённо освоить работу с LLM через API: промпт\-инжиниринг, агентов, контекст, MCP, RAG, локальные модели, автоматизацию — по программе AI Advent Challenge.
- Получить работающий инструмент для себя и своей игровой группы.
- Заложить архитектуру, которая может вырасти в открытый комьюнити\-сервис по всей линейке Chip Theory Games (Hoplomachus, Cloudspire) и, потенциально, за её пределы.
- Всё написание кода — силами AI\-ассистентов (Claude здесь выступает как архитектор/ревьюер спецификаций, код пишут другие, более простые ассистенты).

### Ограничение по процессу челленджа

Код самостоятельно не пишется — только AI\-ассистентами. Роль Claude в этом проекте: планирование, спецификации по каждому дню/неделе, ревью того, что сделали другие ассистенты. Каждый будний день организатор выдаёт новое задание; уже известные задания (дни 1\-17) учтены ниже, остальные будут поступать по ходу и встраиваться в этот план.

## 2\. Продукт: что делает MVP

- Пользователь пишет вопрос на русском или английском («можно ли использовать Fated Card после атаки?», «what happens when a Baddie dies on Adrenaline?»).
- Ассистент понимает, к какой игре/дополнению относится вопрос (по умолчанию — база Too Many Bones \+ подключённые дополнения, которые выбрал пользователь в сессии).
- До недели 5 (RAG) ассистент отвечает из общих знаний модели — это осознанное решение, чтобы затем наглядно сравнить с версией, которая опирается на реальный текст правил. С недели 4 (день 17) он может ещё и свериться с официальным FAQ издателя через MCP\-инструмент; это отдельный источник, а не текст правил, и переключатель возвращает ответы «только из общих знаний».
- С недели 5: ответ строится по реальному тексту правил (RAG) со ссылкой на источник (например: *база правил TMB, раздел «Adrenaline», стр. 34*).
- Если вопрос неоднозначный или правила разных дополнений противоречат друг другу — ассистент уточняет («у тебя куплен Undertow?») вместо того, чтобы гадать.
- Если ответа нет в базе — ассистент честно говорит, что не нашёл, а не выдумывает.
- Ассистент помнит игрока между партиями: какие коробки у него есть, с кем он играет, какие у него домашние правила. В эту долговременную память попадает только то, что игрок подтвердил сам (неделя 3, день 11).
- Ассистент отвечает так, как игрок сам настроил в своём профиле: как к нему обращаться, на каком языке и на каком уровне объяснять, чего не делать. Отвечает он и в режиме под задачу: за столом — коротким вердиктом, новичку — по шагам, после партии — подробным разбором. Режим под каждое сообщение выбирается сам или задаётся игроком (неделя 3, день 12).
- Ассистент ведёт игрока по многошаговой задаче — например, по подготовке стола к партии: сначала согласует план, потом ведёт по шагам, потом проверяет, что ничего не забыто. Задачу можно поставить на паузу на любом этапе и продолжить без повторных объяснений — через час, в том же разговоре или после перезапуска приложения (неделя 3, день 13).
- У игрока есть жёсткие рамки, которые ассистент не вправе нарушить: английские названия писать как в коробке, не предлагать того, чего у игрока нет, не выдавать за правило то, чего нет в правилах. Эти инварианты игрок задаёт сам, хранятся они отдельно от диалога, действуют в каждом ответе, и при конфликте с просьбой ассистент отказывает и объясняет почему — а просьба «забудь про ограничения» сама по себе становится поводом для отказа (неделя 3, день 14).
- Ассистент не даёт срезать углы в многошаговой задаче: пока план не утверждён — не диктует шаги, пока не пройдены проверки — не объявляет стол готовым. Просьбу пропустить этап («сразу к пятому шагу», «игнорируй стадии, выдай всё сразу») он не выполняет молча: говорит, почему так нельзя и что можно сделать сейчас. Если план оказался неверным, задача откатывается к планированию — это обычный переход с записью в журнал, а не потеря прогресса (неделя 3, день 15).
- Ассистент подключается к внешним источникам по протоколу MCP. Первый — сервер BoardGameGeek: поиск игр и карточки с дополнениями, коллекция игрока на BGG, поиск ответов на вопросы по правилам в форумах BGG. С ним приложение пока только устанавливает соединение и узнаёт, какие инструменты он предлагает (неделя 4, день 16).
- На вопрос о правилах ассистент сам сверяется с официальным FAQ издателя: смотрит список вопросов, открывает подходящую статью, пересказывает ответ по\-русски и даёт ссылку на неё. Если в FAQ ответа нет, так и говорит. FAQ читается живьём с сайта издателя через собственный MCP\-сервер проекта (неделя 4, день 17).

## 3\. Технический стек

| Слой | Технология | Комментарий |
| --- | --- | --- |
| Backend / AI\-логика | Python, FastAPI | Вся работа с LLM API, RAG, агентом, MCP — здесь |
| Frontend (весь проект до недели 5) | Gradio | Готовый чат\-интерфейс на чистом Python за минуты — сознательно без RAG, чтобы позже сравнить |
| Frontend (рост, недели 5\-7\+) | NiceGUI или тонкий HTML/JS (htmx) поверх FastAPI | Переход, если Gradio станет тесен — нужен кастомный вид, embeddable\-виджет |
| LLM API (облако) | DeepSeek API | Выбран как основной провайдер на весь челлендж |
| MCP (неделя 4) | Официальный Python SDK `mcp` v2 — и клиент, и свой сервер (`MCPServer`); серверы — отдельные процессы по stdio | bgg\-mcp (BoardGameGeek) — бинарник, собранный из тега v1.6.1, без Docker. Свой сервер FAQ издателя — Python\-программа в репозитории (httpx \+ `html.parser`). Клиентская часть SDK импортируется только модулем клиента, серверная — только своим сервером. Агент получает инструменты через протокол и вызывает их через function calling DeepSeek |
| Локальная LLM (неделя 6) | Ollama / llama.cpp с открытой моделью (Llama, Qwen, Mistral и т.п.) | Оффлайн\-режим для игры без интернета |
| Векторная база (RAG, неделя 5) | Chroma / FAISS (локально) на старте | Не требует внешней инфраструктуры, хватит для одной игры |
| Хранение сессий/контекста | JSON\-файлы по сессиям на локальном старте (день 7) — внутри них же рабочая память (день 11), состояние задачи (день 13) и инварианты сессии (день 14); рядом — отдельные файлы долговременной памяти (день 11), профиля пользователя (день 12) и постоянных инвариантов (день 14); SQLite — с появлением VPS и нескольких пользователей | Прячется за интерфейсами хранилищ (`HistoryStore`, `LongTermStore`, с дня 12 — хранилище профиля, с дня 14 — хранилище инвариантов), поэтому замена реализации не затрагивает ни логику агента, ни интерфейс. Пока один каталог данных — это один пользователь |
| Деплой | VPS (партнёр челленджа) | Уже есть по чек\-листу дня 0 |

Ключевое решение: **весь стек — Python**, включая интерфейс. Это осознанный выбор — рекомендация организатора «не знакомый стек» \+ то, что вся AI/RAG\-экосистема сосредоточена в Python, а не в JS.

Правило на весь проект: **начиная с дня 1 и до тех пор, пока не дойдём до заданий по RAG (предположительно неделя 5), интерфейс делаем на Gradio без RAG** — намеренно, чтобы позже наглядно показать разницу «модель отвечает из общих знаний» vs «модель отвечает по реальным правилам». Инструмент FAQ дня 17 это правило не нарушает: это вызов внешнего источника, а не поиск по тексту правил, и он выключается переключателем. Выключенный переключатель и даёт базу «из общих знаний» для сравнения на неделе 5.

Правило начиная с недели 2: **вся работа с LLM живёт в отдельном модуле\-агенте**, интерфейс не обращается к API напрямую. Именно это позже позволит поднять агента за HTTP (REST\-сервис, телеграм\-бот) или переключить его на локальную модель, не переписывая логику — см. `docs/TooManyRules — Неделя 2 архитектура.md`.

## 4\. Данные и источники правил

Материалы, которые уже есть в цифровом виде:

- Официальные PDF правил Too Many Bones (база \+ дополнения) — **на русском и на английском языке**.
- Официальный FAQ/errata с сайта Chip Theory Games или BoardGameGeek — **только на английском**. FAQ издателя лежит на портале поддержки (`support.chiptheorygames.com`, Freshdesk): по категории на игру, внутри — разделы и статьи «вопрос — ответ». У Too Many Bones на 22.09.2026 24 раздела и 82 вопроса; с дня 17 их читает свой MCP\-сервер. Игру нельзя опознавать по названию: в категории 20 Strong есть раздел «Too Many Bones» — это колода для другой игры.
- Обсуждения на форумах BGG — **только на английском**.
- Фанатская вики `boardgamehub.ru/wiki/too-many-bones` — **на русском**, неофициальная. Справочник по гирлокам (с разбором стиля игры), плохишам, тиранам, навыкам, коробкам, волнам и совместимости дополнений, плюс FAQ из чата сообщества. На 26.09.2026 ≈334 страницы и ≈350 тыс. символов текста; большая часть страниц — короткие карточки (250-400 символов), основной объём — страницы гирлоков. Поиска на сайте нет, есть индексы по типам. С дня 20 её читает свой MCP\-сервер, только удалённо.

Задача подготовки данных (входит в план недели 5, частично — раньше):

1. Собрать актуальные версии PDF правил (база \+ Undertow \+ Age of Tyranny \+ Splice & Dice \+ Unbreakable \+ другие релевантные материалы) в обеих языковых версиях, где они есть.
2. Разбить тексты на смысловые чанки (по разделам/подразделам, с сохранением метаданных: игра, дополнение, язык, номер страницы, раздел).
3. Отдельно проиндексировать FAQ/errata с пометкой «уточнение/исправление» — при конфликте с основным текстом правил приоритет у эррата. Поскольку FAQ/errata и обсуждения BGG — только на английском, для ответов на русском языке эту часть контента придётся либо переводить при индексации, либо переводить на лету при сборке ответа (решается на неделе 5). Там же решается, индексировать ли FAQ издателя или оставить его MCP\-инструментом. С дня 20 инструмент уже держит локальную копию FAQ в SQLite: копия свежая — ответ из неё, пустая или устаревшая — ответ с сайта, а копия докачивается в фоне. Индекс недели 5 может строиться поверх этой копии.
4. Заложить в схему данных структуру `publisher_id → game_id → expansion_id`, а не только `game_id`, с самого начала. Даже если пока данные только под Chip Theory Games / Too Many Bones, `publisher_id` стоит копейки заложить сейчас и обязателен, если в дальнейшем захочется подключить игры других издательств (не добавлять его сейчас означало бы миграцию всей схемы и переиндексацию, когда появится первая игра другого издателя).

Наличие официальных правил сразу на двух языках заметно снижает риск, о котором говорилось раньше: кросс\-язычным (RU↔EN) должен быть в основном только слой FAQ/errata/BGG, а не весь корпус. Фанатская вики — русскоязычная, но неофициальная: в корпусе недели 5 ей нужна пометка источника, а при конфликте прав официальный текст.

## 5\. Дорожная карта по неделям

Недели 1\-3 завершены (дни 1\-15), идёт неделя 4: дни 16\-20 реализованы. Архитектурные решения недели 2 (заморозка кода недели 1 отдельным артефактом, отказ от вкладок, раскладка модулей, конвенции) вынесены в отдельный документ: `docs/TooManyRules — Неделя 2 архитектура.md`. У недель 3 и 4 отдельных архитектурных документов нет — их решения записаны в спецификациях дней.

### Неделя 1 — Основы LLM (завершена, дни 1\-5)

MVP недели: минимальный, затем всё более контролируемый диалог с LLM по правилам Too Many Bones через Gradio\-интерфейс, без RAG (см. правило в разделе 3) — модель отвечает из общих знаний, с системным промптом «ты — TooManyRules, ассистент по правилам Too Many Bones».

**День 1** (известно): написать минимальный код — запрос в LLM (DeepSeek API) через API, получение ответа, вывод в CLI/Web. Реализация: Gradio\-чат \+ системный промпт, без RAG.

**День 2** (известно): один и тот же вопрос по правилам с разным уровнем контроля ответа — без ограничений / с явным форматом (например, структурированный JSON: `{rule: "...", note: "...", confidence: "..."}`) / с ограничением длины / со стоп\-условием. Сравнить ответы.

**День 3** (известно): одна задача по правилам (например, спорная игровая ситуация) решается четырьмя способами — прямой ответ / «рассуждай пошагово» / модель сама формулирует промпт для решения / «консилиум экспертов» (например: Rules Lawyer, Game Designer, Skeptic\-проверяющий). Сравнить точность.

**День 4** (известно): один и тот же вопрос по правилам выполняется при трёх значениях `temperature` (0 / 0.7 / 1.2), с несколькими повторами на каждое значение — чтобы сравнить точность, креативность и разнообразие ответов и сформулировать, для каких задач подходит каждая настройка.

**День 5** (известно): один и тот же вопрос по правилам прогоняется на матрице 2×2 «модель × режим рассуждения» (`deepseek\-v4\-flash` / `deepseek\-v4\-pro` × `thinking` off / on) с замером времени ответа, токенов и оценочной стоимости каждого вызова.

### Неделя 2 — База про агентов (завершена, дни 6\-10)

Тема недели по программе: реализация агента, сохранение контекста, сжатие контекста, работа с токенами. Здесь же — единственная за проект перестройка кодовой базы: код недели 1 замораживается запускаемым артефактом (`src/app_week1.py`), а неделя 2 разрабатывается классически — один растущий интерфейс без вкладок, коммит и тег на каждый день. Подробности — в `docs/TooManyRules — Неделя 2 архитектура.md`.

**День 6** (известно): вся работа с LLM выносится в отдельную сущность — агент со своим конфигом (системный промпт, модель, `temperature`, `max_tokens`, режим рассуждения), собственным стеком сообщений, подсчётом токенов и стоимости. Интерфейс становится только видом на состояние агента.

**День 7** (известно): сохранение контекста — история диалога пишется на диск и восстанавливается при перезапуске приложения, диалог продолжается так, будто агент не выключался.

**День 8** (известно): работа с токенами — агент считает токены текущего запроса, всей истории и ответа модели, показывает бюджет контекстного окна и рост токенов и стоимости по ходам диалога, а на переполнении показывает, что именно ломается. Ничего при этом не чинит: обрезка и сжатие — следующие дни.

**День 9** (известно): управление контекстом через сжатие истории — последние N сообщений уходят в модель как есть, всё, что старше, сворачивается в краткую сводку; сводка хранится отдельно от истории и подставляется в запрос вместо неё. Сравнивается расход токенов и качество ответов со сжатием и без. Для TooManyRules сводка держит ровно то, что нужно ассистенту по правилам через два часа партии: какая игра и какие дополнения обсуждаются, каким составом играют, какие правила уже разобрали и о чём договорились.

**День 10** (известно): три стратегии управления контекстом **без** summary и переключатель между ними — sliding window (только последние N сообщений), sticky facts (отдельный блок «ключ — значение» с целями, ограничениями и договорённостями, обновляемый после каждого сообщения пользователя) и ветки диалога (checkpoint, две независимые ветки, переключение между ними). Один и тот же сценарий прогоняется на каждой стратегии, сравниваются качество, устойчивость к потере деталей, расход токенов и удобство.

История диалога при этом остаётся полной и на диске, и в стеке агента: стратегия решает не что хранить, а что отправлять в модель. Именно поэтому одну и ту же переписку можно прогнать всеми стратегиями и сравнить — см. `docs/TooManyRules — День 9 спецификация.md`, §2.1.

Для TooManyRules сценарий сравнения — подготовка партии: игрок по ходу разговора называет состав, коробки, героев и тирана, договаривается, как трактовать спорное, и поправляет сказанное раньше, а контрольные вопросы спрашивают о том, что уже выпало из окна. Окно и факты встают в тот же протокол стратегий, что сводка дня 9, а ветки — нет: ветка — это отдельная сессия с копией общего начала истории («а если бы мы взяли другого тирана?»), и переключатель у неё свой. Результат сравнения — отдельный документ дня; см. `docs/TooManyRules — День 10 спецификация.md`.

### Неделя 3 — Оптимизация агента (state management, завершена, дни 11\-15)

Правила Too Many Bones с дополнениями — это сотни страниц, целиком в контекст не влезают. Сжатие истории диалога и стратегии контекста (сводка, окно, факты, ветки) закрываются ещё на неделе 2 — днями 9-10, поэтому неделя 3 строится поверх них. Первые дни недели — про состояние агента за пределами одного разговора: что он помнит об игроке и как под игрока подстраивается. Дальше — про состояние работы внутри разговора: задача как конечный автомат (день 13), ограничения, которые агент не вправе нарушать (день 14), и жёсткий контроль переходов между этапами задачи (день 15). Приоритизация релевантных разделов правил и токенный бюджет при нескольких подключённых дополнениях заданиями недели не стали — это вопросы недели 5 (RAG).

**День 11** (известно, реализован): модель памяти агента — три слоя, разведённых по времени жизни. Краткосрочная — разговор сессии; её урезают стратегии дней 9-10. Рабочая — данные текущей партии: цель, состав, герои, тиран, ограничения, договорённости; лежит в файле сессии, копируется в ветку и уходит со сбросом. Долговременная — игрок вообще: окружение (коллекция, игровая группа), решения (домашние правила) и знания (что игрок сообщил о правилах как проверенное); лежит отдельным файлом, общим для всех сессий. Что в какой слой, решает закрытая карта памяти, а не модель. Рабочую память служебный вызов «разбор памяти» пополняет перед каждым ответом, а в долговременную попадает только то, что человек подтвердил кнопкой. Проверка слоёв на сценарии из двух сессий — `docs/TooManyRules — День 11 проверка слоёв памяти.md`; см. `docs/TooManyRules — День 11 спецификация.md`.

**День 12** (известно, реализован): персонализация поверх модели памяти — профиль пользователя, который пишет сам пользователь, а не модель. У профиля общая часть (обращение, язык, уровень, ограничения) и режимы под задачи игрока — «За столом», «Учу новичка», «Разбор после партии» — со стилем, форматом, ограничениями и порядком ответа. В каждый запрос уходят общая часть и один режим; режим под сообщение выбирает роутер (служебный вызов модели) или сам пользователь. Профиль — не слой памяти и не пресет: пресет описывает вызов модели и задаётся разработчиком, память — то, что агент узнал из разговоров, профиль — то, как пользователь просит с ним работать. Поэтому формат ответов переезжает из долговременной памяти в профиль. Порядок ответа режима — место, куда на неделях 4-5 встанут настоящие шаги: инструменты MCP и поиск по правилам. См. `docs/TooManyRules — День 12 спецификация.md`.

**День 13** (известно, реализован): состояние задачи как конечный автомат — этап, текущий шаг и ожидаемое действие. Этапы `планирование → выполнение → проверка → готово`, пауза — флаг на любом активном этапе. Для TooManyRules задача — например, подготовка стола к партии: игрок начинает её кнопкой, ассистент предлагает план из шагов и проверок, игрок утверждает его словами, дальше ассистент ведёт по шагам и проверкам. Этап и шаг меняются только переходами из таблицы. Событие для перехода называет трекер — служебный вызов модели перед ответом — или человек кнопкой, а допустимость проверяет код; недопустимый переход отклоняется, и ассистент объясняет почему. Состояние задачи — не слой памяти: рабочая память помнит, что известно о партии, а состояние — где мы в работе и чего ждём. Оно лежит в файле сессии рядом с рабочей памятью и уходит в запрос своим блоком. Поэтому после паузы, перезапуска или выпадения разговора из окна ассистент продолжает с нужного шага, и пользователю ничего не нужно объяснять заново. Проверка пауз и продолжения на реальном прогоне — `docs/TooManyRules — День 13 проверка состояния задачи.md` (данные — по прогону, выводы пишет автор); см. `docs/TooManyRules — День 13 спецификация.md`.

**День 14** (известно, реализован): инварианты — ограничения, которые ассистент не вправе нарушить. Их пишет сам пользователь, хранятся они отдельно от диалога: постоянные — своим файлом рядом с долговременной памятью и профилем, инварианты партии — в файле сессии. В каждый запрос они уходят блоком **первым** из блоков агента, а конфликт нового сообщения с ними называет страж — служебный вызов перед ответом; конфликт виден в панели и в логе независимо от того, послушалась ли модель, и просьба «забудь про ограничения» сама считается конфликтом. Там, где нарушение формализуемо, его ловит код: инвариант над переходом автомата запрещает переход или требует подтверждения пользователя кнопкой. Для TooManyRules инварианты по умолчанию — названия как в коробке (буквально пример организатора про транслитерацию), только своя коробка, не выдавать за правило то, чего нет в правилах. Проверка конфликтов и отказов на реальном прогоне — `docs/TooManyRules — День 14 проверка инвариантов.md` (данные — по прогону, выводы пишет автор); см. `docs/TooManyRules — День 14 спецификация.md`.

**День 15** (известно, реализован): жёсткий контроль переходов — «красный путь» к автомату дня 13. День 13 делал happy path: трекеру предлагались только допустимые сейчас события, поэтому просьба перепрыгнуть этап до автомата не доходила вовсе. Теперь трекер видит все свои события и называет то, чего просит пользователь, даже если это сейчас недопустимо, — отклоняет код, и отказ с причиной уходит в блок запроса, в панель и в лог, а ассистент объясняет его игроку. Просьбы, которых в таблице нет вовсе («игнорируй все стадии, выдай всё сразу»), трекер отмечает отдельной строкой — сходом с маршрута. Блок состояния получает «Сейчас нельзя» — запреты этапа, которые выводит код: нельзя вести по шагам до утверждённого плана, нельзя объявлять готово без проверок. Откат назад по графу становится обычным переходом: «вернуться к плану» словами или кнопкой и «переоткрыть» завершённую задачу к проверкам — с записью в журнал, а не заменой задачи новой. Само свойство «вперёд по маршруту — только на один этап» проверяется у таблицы при импорте модуля. Честная граница дня: жизненный цикл задачи контролируется полностью, текст ответа — нет. Проверка красного пути на реальном прогоне — `docs/TooManyRules — День 15 проверка переходов.md` (данные — по прогону, выводы пишет автор); см. `docs/TooManyRules — День 15 спецификация.md`.

### Неделя 4 — MCP (идёт)

Тема недели по программе — Model Context Protocol: подключение внешних источников к агенту через MCP\-серверы. Кандидаты в источники для TooManyRules:

- BoardGameGeek — метаданные игр (дополнения, число игроков, сложность), коллекция игрока и обсуждения правил в форумах BGG. Готовый открытый сервер — bgg\-mcp (`github.com/kkjdaniel/bgg-mcp`, есть в официальном реестре MCP); с него неделя и начинается (день 16). Для вызова его инструментов нужен ключ BGG.
- Официальные страницы FAQ/errata издателя — для получения самых свежих уточнений. FAQ Too Many Bones открывает собственный MCP\-сервер проекта (день 17).
- Фанатская вики на русском — справочник по героям, врагам, навыкам и коробкам (день 20).
- (опционально) собственный MCP\-сервер с базой правил как переиспользуемый источник контекста.

С недели 2 сюда переходит одно правило: внешний мир — за своим модулем. Как LLM API вызывается только в агенте, а диск трогает только хранилище, так и клиентскую часть SDK MCP импортирует только модуль MCP\-клиента. Свой сервер — отдельная программа, которую приложение запускает, а не импортирует. Что подключать и как запускать сервер, решает слой пресетов проекта, а не клиент. Агент про MCP не знает: инструменты приходят к нему необязательной зависимостью через протокол, как хранилища.

**День 16** (известно, реализован): подключение MCP — клиент на официальном Python SDK (v2) сам запускает сервер BoardGameGeek (bgg\-mcp по stdio), устанавливает соединение, согласует версию протокола и получает список инструментов: поиск и карточки игр, коллекция, «горячее», цены, рекомендации, поиск по форумам правил и треды форума. Сервер — бинарник, собранный из тега v1.6.1; Docker не используется (выбор автора), и цена этого — отсутствие изоляции. bgg\-mcp — сервер старой эры протокола: соединение идёт рукопожатием `initialize` на версии 2025\-06\-18. Соединение и список видны в панели и в логе, сбои — со стадией, на которой оборвалось: запуск процесса, соединение, список. Агент инструментами не пользуется — по комментарию организатора на этом шаге достаточно получить список, — поэтому вызовов модели день не добавляет. Серверу передаётся только минимальное окружение и явно перечисленные переменные: ключ DeepSeek чужой процесс не получает. Ключ BGG для списка не нужен, а для вызова инструментов понадобится — BGG пускает к своему API только зарегистрированные приложения. Формат сдачи — видео \+ код, документа проверки нет; см. `docs/TooManyRules — День 16 спецификация.md`.

**День 17** (известно, реализован): первый инструмент MCP — свой MCP\-сервер вокруг официального FAQ издателя по Too Many Bones. Публичного API у портала нет, поэтому сервер читает его страницы. Инструментов два: список вопросов (с фильтром по разделу) и текст статьи по номеру; параметры описаны в схеме. Сервер читает только категорию Too Many Bones по её id, сверяет имя категории и отказывает статьям других игр — прежде всего 20 Strong, где есть раздел «Too Many Bones». Поиск сайта закрыт в robots.txt, поэтому подходящий вопрос выбирает сама модель по списку. Свой сервер на SDK v2 договаривается с клиентом уже по новой эре протокола — через `server/discover`, без рукопожатия. Агент получает каталог инструментов в каждом ходе и сам решает, звать ли их: ход становится циклом раундов «модель → вызовы инструментов → модель», финальный ответ пересказывает статью со ссылкой. В историю уходят только вопрос и ответ, формат файла сессии не меняется. Переключатель «Инструменты MCP в запросе» возвращает запрос дня 16. Формат сдачи — видео \+ код, документа проверки нет; см. `docs/TooManyRules — День 17 спецификация.md`.

**День 18** (известно, реализован): планировщик и фоновые задачи — сторож FAQ, свой долгоживущий MCP\-сервер по Streamable HTTP. По расписанию он снимает FAQ целиком в SQLite, сравнивает снимки и сам пишет сводку изменений в свой терминал. Инструменты отдают агенту сводку за период и меняют расписание. Агент получает инструменты двух серверов одной группой. Формат сдачи — видео \+ код; см. `docs/TooManyRules — День 18 спецификация.md`.

**День 19** (известно, реализован): композиция MCP\-инструментов — памятка к столу. Поиск по снимку сторожа, сжатие найденного в памятку и сохранение в Markdown\-файл выстраиваются в цепочку по одной просьбе игрока; цепочку ведёт модель. Данные между шагами идут по ссылке (id в базе сервера), а не текстом, и сервер проверяет каждую передачу. Сжимает модель агента по просьбе сервера — MCP sampling: у сервера нет ни ключа, ни модели. Формат сдачи — видео \+ код; см. `docs/TooManyRules — День 19 спецификация.md`.

**День 20** (известно, реализован): оркестрация MCP — у агента три сервера, по одному на источник или назначение: FAQ издателя, фанатская вики и файлы. Сервер и инструмент модель выбирает сама, по описаниям инструментов, и ведёт длинный флоу через несколько серверов одной просьбой. FAQ доступен всегда: свежая локальная копия — ответ из неё; пустая или устаревшая — ответ с сайта, а копия докачивается в фоне. Сервер FAQ поднимает само приложение, планировщик дня 18 выключен по умолчанию. Вики — только удалённо: локальный корпус вики — работа недели 5. Сохранение в файл уходит на отдельный сервер, и данные туда идут по значению. Формат сдачи — видео \+ код; см. `docs/TooManyRules — День 20 спецификация.md`.

### Неделя 5 — RAG (ядро продукта)

Полноценный RAG поверх подготовленной базы правил: эмбеддинги, векторный поиск, сборка ответа с обязательной ссылкой на источник (документ/раздел/страница). Здесь же решается вопрос перевода/кросс\-язычного поиска для англоязычного FAQ/errata\-слоя и судьба MCP\-инструмента FAQ: индекс поверх его локальной копии дня 20, живой инструмент или оба (см. раздел 4). В корпус входит и фанатская вики — с пометкой «неофициально». Сравнение «из общих знаний» vs «по правилам» идёт с выключенными инструментами MCP, иначе FAQ подмешивался бы в обе стороны. С этой недели интерфейс может перейти с чистого Gradio на более гибкое решение (см. раздел 3), если потребуется показывать источники и цитаты.

### Неделя 6 — Локальный ИИ

Оффлайн\-режим: локальная модель через Ollama/llama.cpp, работающая без интернета — органичный кейс для настолок (партии часто проходят без wifi — дома, в кафе, на турнирах). Тестируется офлайн\-версия RAG\-поиска (локальный векторный индекс \+ локальная модель).

### Неделя 7 — Пайплайн

Автоматизация: отслеживание обновлений официальных errata\-страниц, автообновление базы при выходе новых материалов, эскалация «модератору» (то есть тебе) вопросов, не покрытых базой правил.

### Advanced\-трек (после основного челленджа)

- **Code Assistance** — не касается напрямую продукта, но применимо к процессу разработки самого TooManyRules (агент, дольше работающий автономно над кодом).
- **FineTune** — дообучение/тюнинг модели под терминологию Too Many Bones и стиль игровых формулировок.
- **Security** — приватность и изоляция работы с пользовательскими данными, если проект откроется для комьюнити.

## 6\. Формат сдачи по дням

Ежедневно до 14:00 мск — новое задание от организатора. Результат каждого дня фиксируется в общей таблице челленджа в формате **видео \+ код**, ссылками в комментарии к своему слоту. Для этого проекта видео \= короткая демонстрация Gradio\-интерфейса с примером вопроса по Too Many Bones, код \= ссылка на тег соответствующего дня в репозитории (`day01`, `day02`, …): `main` к моменту проверки уже уезжает вперёд, а тег фиксирует ровно то состояние, которое показано в видео.

## 7\. Потенциал развития и монетизации

Не приоритет на старте, но заложен в архитектуру (в том числе через `publisher_id`, см. раздел 4):

- Freemium по играм: бесплатно на популярные позиции, комьюнити\-донаты (модель Patreon, распространена у настольщиков).
- Партнёрство с издателем: официальный «rules companion» к игре — есть прецеденты подобных интеграций у настольных издательств.
- Приложение/киоск для настольных кафе и турниров (в том числе офлайн\-режим с локальной моделью — неделя 6).
- Расширение на весь каталог Chip Theory Games (Hoplomachus, Cloudspire), затем — на игры других издательств и открытие для комьюнити (загрузка правил любых игр).

## 8\. Риски и открытые вопросы

- **Авторские права**\: PDF правил обычно доступны бесплатно для личного использования на сайте издателя, но публичное распространение текста при масштабировании требует отдельной проверки условий использования.
- **Точность — это весь смысл продукта**\: неверный ответ по правилам хуже, чем отсутствие ответа. RAG обязателен с недели 5, ответ должен явно указывать источник и степень уверенности. С дня 17 часть ответов опирается на FAQ издателя со ссылкой на статью, но выбирает статью и пересказывает её модель: неверно выбранная или неверно пересказанная статья выглядит так же убедительно, как верная. Проверяет её только человек, по ссылке.
- **Частичная кросс\-язычность**\: базовые правила есть на двух языках, а FAQ/errata и обсуждения BGG — только на английском. Решение (перевод этого слоя при индексации vs. кросс\-язычный эмбеддинг\-поиск) уточняется на неделе 5.
- **Объём контента**\: чем больше дополнений подключено одновременно, тем выше риск конфликтующих правок — требует продуманной приоритизации источников (эррата \> базовые правила) уже на неделе 2\-3.
- **Сведения об игроке**\: с недели 3 долговременная память и профиль пользователя хранят то, что игрок рассказал о себе, открытым текстом в локальных файлах — один каталог данных на одного пользователя. Для открытого сервиса нужны привязка памяти и профиля к пользователю (вместе с VPS и SQLite), изоляция пользователей друг от друга и решение, что из этого вообще можно хранить (Security\-трек).
- **Ложные переходы задачи**\: с недели 3 шаг задачи отмечается выполненным по словам пользователя, которые разбирает модель (день 13). Если трекер примет вопрос за «готово», шаг пропустится молча. Поэтому допустимые переходы ограничены таблицей, отказ виден, на сомнении трекер должен отвечать «событий нет», а к пропущенному шагу можно вернуться — с дня 15 ещё и к самому плану. Само состояние при этом сдвинуть нечем, кроме допустимого перехода, а попытка срезать угол видна в панели и в логе. Проверить, правильно ли шаг выполнен по правилам, до недели 5 нечем.
- **Порядок работы держится на модели, а маршрут — на коде**\: с дня 15 автомат не перепрыгнуть и не сломать никаким сообщением, но выполняет запреты этапа («не веди по шагам до утверждённого плана», «не объявляй готово без проверок») сам ассистент — код не читает его ответ. Поэтому ассистента можно уговорить рассказать лишнее; видно будет и уговор, и ответ, а насколько запреты держатся, показывает документ проверки дня.
- **Инвариант держится на модели везде, кроме переходов**\: с дня 14 ограничения пользователя уходят в каждый запрос отдельным блоком и конфликт с ними виден в панели и логе, но выполняет их сам ассистент — код не читает ответ и не проверяет, нарушен ли инвариант текстом. Формально проверяются только переходы автомата задачи. Поэтому результат дня — не гарантия, а видимость: насколько инварианты держатся, показывает документ проверки, и слабые формулировки правятся по нему.
- **Самоподтверждающиеся ошибки в памяти**\: утверждение модели о правилах, попавшее в долговременную память, уходило бы в каждый запрос каждой будущей сессии. Поэтому до RAG в долговременную память пишет только человек, а источник записи — только игрок (день 11). С недели 5 слой «знания о правилах» придётся сверять с реальным текстом правил.
- **Чужой MCP\-сервер**\: с недели 4 приложение само запускает чужую программу. Ей передаётся только минимальное окружение SDK и явно перечисленные переменные (ключ BGG), а версия закреплена тегом git, из которого собран бинарник. Изоляции от файлов приложения у бинарника нет — её дал бы Docker, от которого автор отказался (день 16). Описания инструментов bgg\-mcp пишет автор сервера: если они уйдут в запрос модели, это будет чужой текст в контексте, которому нельзя доверять как системному промпту. Аннотации инструментов — подсказки сервера, а не факт: у bgg\-mcp все инструменты помечены как разрушающие, хотя только читают.
- **Чужой текст в контексте**\: с дня 17 в запрос уходят результаты инструментов — текст страниц сайта издателя. Он идёт сообщением инструмента, а не системным, и не чистится от возможных инструкций внутри. Для FAQ издателя риск низкий, но с каждым новым источником (форумы BGG — уже текст любых пользователей) он растёт. Защита от инъекций через инструменты — отдельная тема (Security\-трек).
- **Разметка чужого сайта**\: у портала FAQ издателя нет открытого API, и свой сервер дня 17 читает его HTML. Смена вёрстки, переезд категории или защита от ботов ломают инструмент. Поэтому поломка должна быть видна, а не тиха: сервер сверяет имя категории, проверяет полноту разделов по объявленному числу статей и отвечает ошибкой, а не пустым списком. Сайт читается при каждом вызове, без кэша, — ход с инструментами заметно медленнее обычного.
- **Внешние зависимости недели 4**\: BGG пускает к своему XML API только зарегистрированные приложения — без ключа инструменты сервера не работают, а ключ выдают вручную и не сразу. Протокол MCP в 2026 году сменил эру (ревизия 2026\-07\-28 убрала рукопожатие), SDK — мажорную версию; клиент закреплён на SDK v2 и понимает обе эры, но большинство примеров в интернете написаны для v1 (в том числе `FastMCP`, который в v2 называется `MCPServer`). DeepSeek в режиме thinking по документации требует возвращать рассуждения всех прошлых ходов, если в запросе есть инструменты. История проекта их не хранит; на 22.09.2026 API принимает запрос и так, но это может измениться (день 17, §2.6 спецификации).
