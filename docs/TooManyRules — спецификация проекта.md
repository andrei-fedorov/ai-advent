# TooManyRules — AI\-ассистент по правилам Too Many Bones

Проект для AI Advent Challenge (9 поток)

## 1\. Идея и цели

TooManyRules — ассистент, который отвечает на вопросы по правилам настольной игры **Too Many Bones** (Chip Theory Games), опираясь на официальные правила, дополнения и эррата, а не на общие знания модели. Пользователь задаёт вопрос своими словами прямо во время партии — ассистент даёт точный ответ со ссылкой на источник (документ, раздел, страница), вместо того чтобы листать правила вручную.

Цели проекта:

- Углублённо освоить работу с LLM через API: промпт\-инжиниринг, агентов, контекст, MCP, RAG, локальные модели, автоматизацию — по программе AI Advent Challenge.
- Получить работающий инструмент для себя и своей игровой группы.
- Заложить архитектуру, которая может вырасти в открытый комьюнити\-сервис по всей линейке Chip Theory Games (Hoplomachus, Cloudspire) и, потенциально, за её пределы.
- Всё написание кода — силами AI\-ассистентов (Claude здесь выступает как архитектор/ревьюер спецификаций, код пишут другие, более простые ассистенты).

### Ограничение по процессу челленджа

Код самостоятельно не пишется — только AI\-ассистентами. Роль Claude в этом проекте: планирование, спецификации по каждому дню/неделе, ревью того, что сделали другие ассистенты. Каждый будний день организатор выдаёт новое задание; уже известные задания (дни 1\-7) учтены ниже, остальные будут поступать по ходу и встраиваться в этот план.

## 2\. Продукт: что делает MVP

- Пользователь пишет вопрос на русском или английском («можно ли использовать Fated Card после атаки?», «what happens when a Baddie dies on Adrenaline?»).
- Ассистент понимает, к какой игре/дополнению относится вопрос (по умолчанию — база Too Many Bones \+ подключённые дополнения, которые выбрал пользователь в сессии).
- До недели 5 (RAG) ассистент отвечает из общих знаний модели — это осознанное решение, чтобы затем наглядно сравнить с версией, которая опирается на реальный текст правил.
- С недели 5: ответ строится по реальному тексту правил (RAG) со ссылкой на источник (например: *база правил TMB, раздел «Adrenaline», стр. 34*).
- Если вопрос неоднозначный или правила разных дополнений противоречат друг другу — ассистент уточняет («у тебя куплен Undertow?») вместо того, чтобы гадать.
- Если ответа нет в базе — ассистент честно говорит, что не нашёл, а не выдумывает.

## 3\. Технический стек

| Слой | Технология | Комментарий |
| --- | --- | --- |
| Backend / AI\-логика | Python, FastAPI | Вся работа с LLM API, RAG, агентом, MCP — здесь |
| Frontend (весь проект до недели 5) | Gradio | Готовый чат\-интерфейс на чистом Python за минуты — сознательно без RAG, чтобы позже сравнить |
| Frontend (рост, недели 5\-7\+) | NiceGUI или тонкий HTML/JS (htmx) поверх FastAPI | Переход, если Gradio станет тесен — нужен кастомный вид, embeddable\-виджет |
| LLM API (облако) | DeepSeek API | Выбран как основной провайдер на весь челлендж |
| Локальная LLM (неделя 6) | Ollama / llama.cpp с открытой моделью (Llama, Qwen, Mistral и т.п.) | Оффлайн\-режим для игры без интернета |
| Векторная база (RAG, неделя 5) | Chroma / FAISS (локально) на старте | Не требует внешней инфраструктуры, хватит для одной игры |
| Хранение сессий/контекста | JSON\-файлы по сессиям на локальном старте (день 7), SQLite — с появлением VPS и нескольких пользователей | Прячется за интерфейсом хранилища (`HistoryStore`), поэтому замена реализации не затрагивает ни логику агента, ни интерфейс |
| Деплой | VPS (партнёр челленджа) | Уже есть по чек\-листу дня 0 |

Ключевое решение: **весь стек — Python**, включая интерфейс. Это осознанный выбор — рекомендация организатора «не знакомый стек» \+ то, что вся AI/RAG\-экосистема сосредоточена в Python, а не в JS.

Правило на весь проект: **начиная с дня 1 и до тех пор, пока не дойдём до заданий по RAG (предположительно неделя 5), интерфейс делаем на Gradio без RAG** — намеренно, чтобы позже наглядно показать разницу «модель отвечает из общих знаний» vs «модель отвечает по реальным правилам».

Правило начиная с недели 2: **вся работа с LLM живёт в отдельном модуле\-агенте**, интерфейс не обращается к API напрямую. Именно это позже позволит поднять агента за HTTP (REST\-сервис, телеграм\-бот) или переключить его на локальную модель, не переписывая логику — см. `docs/TooManyRules — Неделя 2 архитектура.md`.

## 4\. Данные и источники правил

Материалы, которые уже есть в цифровом виде:

- Официальные PDF правил Too Many Bones (база \+ дополнения) — **на русском и на английском языке**.
- Официальный FAQ/errata с сайта Chip Theory Games или BoardGameGeek — **только на английском**.
- Обсуждения на форумах BGG — **только на английском**.

Задача подготовки данных (входит в план недели 5, частично — раньше):

1. Собрать актуальные версии PDF правил (база \+ Undertow \+ Age of Tyranny \+ Splice & Dice \+ Unbreakable \+ другие релевантные материалы) в обеих языковых версиях, где они есть.
2. Разбить тексты на смысловые чанки (по разделам/подразделам, с сохранением метаданных: игра, дополнение, язык, номер страницы, раздел).
3. Отдельно проиндексировать FAQ/errata с пометкой «уточнение/исправление» — при конфликте с основным текстом правил приоритет у эррата. Поскольку FAQ/errata и обсуждения BGG — только на английском, для ответов на русском языке эту часть контента придётся либо переводить при индексации, либо переводить на лету при сборке ответа (решается на неделе 5).
4. Заложить в схему данных структуру `publisher_id → game_id → expansion_id`, а не только `game_id`, с самого начала. Даже если пока данные только под Chip Theory Games / Too Many Bones, `publisher_id` стоит копейки заложить сейчас и обязателен, если в дальнейшем захочется подключить игры других издательств (не добавлять его сейчас означало бы миграцию всей схемы и переиндексацию, когда появится первая игра другого издателя).

Наличие официальных правил сразу на двух языках заметно снижает риск, о котором говорилось раньше: кросс\-язычным (RU↔EN) должен быть в основном только слой FAQ/errata/BGG, а не весь корпус.

## 5\. Дорожная карта по неделям

Неделя 1 завершена (дни 1\-5), идёт неделя 2 — выданы задания дней 6 и 7. Архитектурные решения недели 2 (заморозка кода недели 1 отдельным артефактом, отказ от вкладок, раскладка модулей, конвенции) вынесены в отдельный документ: `docs/TooManyRules — Неделя 2 архитектура.md`.

### Неделя 1 — Основы LLM (завершена, дни 1\-5)

MVP недели: минимальный, затем всё более контролируемый диалог с LLM по правилам Too Many Bones через Gradio\-интерфейс, без RAG (см. правило в разделе 3) — модель отвечает из общих знаний, с системным промптом «ты — TooManyRules, ассистент по правилам Too Many Bones».

**День 1** (известно): написать минимальный код — запрос в LLM (DeepSeek API) через API, получение ответа, вывод в CLI/Web. Реализация: Gradio\-чат \+ системный промпт, без RAG.

**День 2** (известно): один и тот же вопрос по правилам с разным уровнем контроля ответа — без ограничений / с явным форматом (например, структурированный JSON: `{rule: "...", note: "...", confidence: "..."}`) / с ограничением длины / со стоп\-условием. Сравнить ответы.

**День 3** (известно): одна задача по правилам (например, спорная игровая ситуация) решается четырьмя способами — прямой ответ / «рассуждай пошагово» / модель сама формулирует промпт для решения / «консилиум экспертов» (например: Rules Lawyer, Game Designer, Skeptic\-проверяющий). Сравнить точность.

**День 4** (известно): один и тот же вопрос по правилам выполняется при трёх значениях `temperature` (0 / 0.7 / 1.2), с несколькими повторами на каждое значение — чтобы сравнить точность, креативность и разнообразие ответов и сформулировать, для каких задач подходит каждая настройка.

**День 5** (известно): один и тот же вопрос по правилам прогоняется на матрице 2×2 «модель × режим рассуждения» (`deepseek\-v4\-flash` / `deepseek\-v4\-pro` × `thinking` off / on) с замером времени ответа, токенов и оценочной стоимости каждого вызова.

### Неделя 2 — База про агентов (дни 6\-8 известны, дни 9\-10 — по мере поступления)

Тема недели по программе: реализация агента, сохранение контекста, сжатие контекста, работа с токенами. Здесь же — единственная за проект перестройка кодовой базы: код недели 1 замораживается запускаемым артефактом (`src/app_week1.py`), а неделя 2 разрабатывается классически — один растущий интерфейс без вкладок, коммит и тег на каждый день. Подробности — в `docs/TooManyRules — Неделя 2 архитектура.md`.

**День 6** (известно): вся работа с LLM выносится в отдельную сущность — агент со своим конфигом (системный промпт, модель, `temperature`, `max_tokens`, режим рассуждения), собственным стеком сообщений, подсчётом токенов и стоимости. Интерфейс становится только видом на состояние агента.

**День 7** (известно): сохранение контекста — история диалога пишется на диск и восстанавливается при перезапуске приложения, диалог продолжается так, будто агент не выключался.

**День 8** (известно): работа с токенами — агент считает токены текущего запроса, всей истории и ответа модели, показывает бюджет контекстного окна и рост токенов и стоимости по ходам диалога, а на переполнении показывает, что именно ломается. Ничего при этом не чинит: обрезка и сжатие — следующие дни.

**Дни 9\-10** (задания ещё не выданы): по программе недели — сжатие контекста и смежное. Для TooManyRules это ложится на продуктовую задачу: агент помнит, какая игра и какие дополнения выбраны в текущей сессии, задаёт уточняющие вопросы вместо того, чтобы гадать, и удерживает бюджет токенов при накоплении истории диалога.

### Неделя 3 — Оптимизация агента (state management)

Правила Too Many Bones с дополнениями — это сотни страниц, целиком в контекст не влезают. Ожидаемые задачи: сжатие/суммаризация истории диалога, приоритизация релевантных разделов, управление токенным бюджетом при одновременном подключении нескольких дополнений.

### Неделя 4 — MCP

Подключение внешних источников через MCP\-серверы:

- BoardGameGeek API — метаданные игр, ссылки на официальные обсуждения.
- Официальные страницы FAQ/errata издателя — для получения самых свежих уточнений.
- (опционально) собственный MCP\-сервер с базой правил как переиспользуемый источник контекста.

### Неделя 5 — RAG (ядро продукта)

Полноценный RAG поверх подготовленной базы правил: эмбеддинги, векторный поиск, сборка ответа с обязательной ссылкой на источник (документ/раздел/страница). Здесь же решается вопрос перевода/кросс\-язычного поиска для англоязычного FAQ/errata\-слоя. С этой недели интерфейс может перейти с чистого Gradio на более гибкое решение (см. раздел 3), если потребуется показывать источники и цитаты.

### Неделя 6 — Локальный ИИ

Оффлайн\-режим: локальная модель через Ollama/llama.cpp, работающая без интернета — органичный кейс для настолок (партии часто проходят без wifi — дома, в кафе, на турнирах). Тестируется офлайн\-версия RAG\-поиска (локальный векторный индекс \+ локальная модель).

### Неделя 7 — Пайплайн

Автоматизация: отслеживание обновлений официальных errata\-страниц, автообновление базы при выходе новых материалов, эскалация «модератору» (то есть тебе) вопросов, не покрытых базой правил.

### Advanced\-трек (после основного челленджа)

- **Code Assistance** — не касается напрямую продукта, но применимо к процессу разработки самого TooManyRules (агент, дольше работающий автономно над кодом).
- **FineTune** — дообучение/тюнинг модели под терминологию Too Many Bones и стиль игровых формулировок.
- **Security** — приватность и изоляция работы с пользовательскими данными, если проект откроется для комьюнити.

## 6\. Формат сдачи по дням

Ежедневно до 14:00 мск — новое задание от организатора. Результат каждого дня фиксируется в общей таблице челленджа в формате **видео \+ код**, ссылками в комментарии к своему слоту. Для этого проекта видео \= короткая демонстрация Gradio\-интерфейса с примером вопроса по Too Many Bones, код \= ссылка на тег соответствующего дня в репозитории (`day01`, `day02`, …): `main` к моменту проверки уже уезжает вперёд, а тег фиксирует ровно то состояние, которое показано в видео.

## 7\. Потенциал развития и монетизации

Не приоритет на старте, но заложен в архитектуру (в том числе через `publisher_id`, см. раздел 4):

- Freemium по играм: бесплатно на популярные позиции, комьюнити\-донаты (модель Patreon, распространена у настольщиков).
- Партнёрство с издателем: официальный «rules companion» к игре — есть прецеденты подобных интеграций у настольных издательств.
- Приложение/киоск для настольных кафе и турниров (в том числе офлайн\-режим с локальной моделью — неделя 6).
- Расширение на весь каталог Chip Theory Games (Hoplomachus, Cloudspire), затем — на игры других издательств и открытие для комьюнити (загрузка правил любых игр).

## 8\. Риски и открытые вопросы

- **Авторские права**\: PDF правил обычно доступны бесплатно для личного использования на сайте издателя, но публичное распространение текста при масштабировании требует отдельной проверки условий использования.
- **Точность — это весь смысл продукта**\: неверный ответ по правилам хуже, чем отсутствие ответа. RAG обязателен с недели 5, ответ должен явно указывать источник и степень уверенности.
- **Частичная кросс\-язычность**\: базовые правила есть на двух языках, а FAQ/errata и обсуждения BGG — только на английском. Решение (перевод этого слоя при индексации vs. кросс\-язычный эмбеддинг\-поиск) уточняется на неделе 5.
- **Объём контента**\: чем больше дополнений подключено одновременно, тем выше риск конфликтующих правок — требует продуманной приоритизации источников (эррата \> базовые правила) уже на неделе 2\-3.
