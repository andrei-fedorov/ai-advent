# TooManyRules — спецификация дня 30

Тема: локальная LLM как приватный сервис. Модель по-прежнему работает в LM Studio на Mac автора, но пользоваться ею теперь можно не только с этого Mac. Перед LM Studio встаёт своя программа — **сервис** `./run.sh service`. Он слушает домашнюю сеть, говорит на OpenAI-совместимом HTTP API и отдаёт страницу чата для браузера телефона. Сервис пускает только клиентов с ключом, ограничивает число запросов в минуту на клиента, отказывает запросам, которые не поместятся в окно модели, и ставит одновременные запросы в очередь: в модель идёт один запрос за раз, остальные ждут. Клиентов в видео два: телефон в домашнем Wi-Fi (страница чата) и приложение TooManyRules на Mac (пресет «Локальный» с адресом сервиса). Стабильность при нескольких запросах проверяет программа `./run.sh service-load`. Всё остаётся дома: модель — на Mac, разговор — в браузере телефона, сервис ничего не пишет на диск и не логирует тексты.

## 1. Задание челленджа (день 30)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_30.txt` и комментарии организатора из чата `tasks/AI Advent Challenge_30_comments.txt`.

Ключевое из задания: **развернуть локальную LLM как сервис** — на VPS или домашнем сервере, **с HTTP API** и **с возможностью чата**. Проверить: **доступ к модели по сети**, **стабильность при нескольких запросах**, **базовые ограничения** (rate limit, max context). Результат — приватный AI-сервис на базе локальной LLM; формат сдачи — **видео + код**.

Из комментариев организатора: ноутбук годится как домашний сервер, телефон — как клиент; желательно два устройства; суть — проверить связку «клиент — сервер»; мощная модель не нужна; одновременные запросы можно ставить в очередь — запрос, который ждёт, пока модель освободится, засчитывается.

Формат «видео + код», а проверка — «проверьте». Поэтому **отдельного документа проверки нет** (правило дней 12, 16, 24 и 25): проверка показывается в видео (§14), замер записывается комментарием у констант сервиса в `presets.py` (§13).

Правила прошлых дней в силе:

- **всё «про эту машину» — в `presets.py`**: адреса, порт, лимиты, вопросы нагрузки;
- **внешний мир — за своим модулем**, свой сервер — **отдельная программа**, которую запускает человек (дни 16–21);
- **LLM API вызывается только в `agent.py`**. Сервис модель от себя не вызывает: он пересылает чужой запрос, который собрал клиент, — это прокси, а не второй агент (§3.8);
- **код не управляет LM Studio**: не запускает сервер, не грузит и не выгружает модели (день 26);
- **код не оценивает ответы**.

## 2. Что делаем конкретно для TooManyRules

### 2.1. Схема

```
телефон (браузер, Wi-Fi) ──┐
приложение TooManyRules ───┼──► сервис :8800 ──► LM Studio 127.0.0.1:1234 ──► Qwen3.5-2B
./run.sh service-load ─────┘    ключ → лимит → контекст → очередь (1 в модели)
```

LM Studio остаётся на `127.0.0.1`: из сети к нему напрямую не попасть, только через сервис.

### 2.2. Подготовка машины (делает человек)

Описывается в README (§8).

1. LM Studio: `lms load qwen3.5-2b-mlx@4bit` и `lms server start` (день 29).
2. Ключи клиентов в `src/.env`. Ключ даёт `./run.sh service --new-key` (§3.2):
   
   ```
   TOOMANYRULES_SERVICE_KEYS=телефон:<ключ>:3,ноутбук:<ключ>
   ```
3. `./run.sh service`. При первом запуске macOS спросит, разрешить ли Python входящие подключения, — разрешить. Сервис печатает адрес в домашней сети.
4. Телефон — в том же Wi-Fi.
5. Приложение как клиент — §6.

### 2.3. Что значит «приватный»

- Модель и её ответы — на Mac автора; в интернет запросы не уходят.
- Пускают только по ключу; ключ у каждого клиента свой и отзывается удалением строки из `src/.env` и перезапуском сервиса.
- Сервис ничего не пишет на диск: ни разговоров, ни логов в файл. В логе (stdout) — имя клиента, время, токены и статус, но **не тексты вопросов и ответов**.
- История разговора страницы чата — в памяти вкладки браузера телефона; ключ — в `localStorage` этого браузера.
- Чего нет (§12): шифрования (HTTP без TLS — домашняя сеть считается доверенной) и доступа из интернета.

### 2.4. Проверка до реализации (11.10.2026)

M1 Pro, 16 ГБ; LM Studio 0.4 (тот же, что на дне 29); `qwen3.5-2b-mlx@4bit`, загрузка 8,8 с (1,63 ГиБ), окно загрузки 8 192 токена (`loaded_context_length`), `lms ps` — `PARALLEL 4`. Запросы — прямо в `POST /v1/chat/completions` LM Studio скриптом в scratchpad (`httpx`, `temperature` 0, `reasoning_effort` `"none"`). Перед проверкой сервер был выключен и модель не загружена — после проверки возвращено так же.

**Несколько запросов сразу — короткие вопросы** (≈25 токенов вопроса, до 300 ответа):

| Сразу | Все готовы за                     | Суммарно ток/с | Пик памяти процесса модели |
| ----- | --------------------------------- | -------------- | -------------------------- |
| 1     | 2,0 с (первый за процесс — 4,0 с) | ≈106           | 2,45 ГБ (в покое — 2,38)   |
| 2     | 3,4 с                             | ≈107           | 2,55 ГБ                    |
| 4     | 6,6 с                             | ≈127           | 2,87 ГБ                    |
| 6     | 8,7 с                             | ≈128           | 2,94 ГБ                    |
| 8     | 13,2 с                            | ≈130           | 2,94 ГБ                    |

LM Studio сам обрабатывает до четырёх запросов одновременно, остальные держит у себя в очереди; ошибок нет и при восьми. Ответы при t = 0 в пачке те же, что поодиночке (то же число токенов).

**Несколько запросов сразу — длинные** (≈3 570 токенов вопроса, как запрос с выдержками RAG, у каждого свой текст): один — 4,8 с; четыре сразу — **все четыре заканчиваются через ≈18,7 с**. Работа та же, что по очереди (4 × 4,8 с), но ждёт каждый всё время; с очередью первый получил бы ответ через ≈5 с, последний — через ≈19 с. Четыре запроса с одинаковым длинным началом — 5 с на все (кэш префикса, день 28); на реальных разных вопросах на это рассчитывать нельзя. Отсюда решение §1.1 — один запрос в модели.

**Окно контекста:**

- вопрос больше окна (≈10–20 тыс. токенов) — 400 за 0,05 с: «The number of tokens to keep from the initial prompt is greater than the context length. Try to load the model with a larger context length, or provide a shorter input»;
- **вопрос помещается, а вопрос + ответ — нет, LM Studio не отказывает**: 7 895 токенов вопроса + `max_tokens` 2000 — ответ 1 999 токенов (`length`), всего 9 894 > 8 192; 8 184 токена вопроса + 10 — тоже 200. Правило «вопрос + потолок ответа ≤ окно» должен держать сервис (§3.7).

**Оценка токенов.** `tokens.estimate_tokens()` на русском тексте этих запросов завышает ≈1,25× (4 452 против 3 568 по `usage`). Для отказа «не поместится» это безопасная сторона: сервис откажет чуть раньше, но не пропустит лишнего (§3.7, §12).

**Окружение.** FastAPI 0.141.1, uvicorn 0.52.4, starlette 1.6.0, httpx 0.28.1 уже в venv (их тянет Gradio); SDK `openai` 3.7.0. Имён `llm_service` и `service_load` нет ни в стандартной библиотеке, ни в пакетах venv. Homebrew на машине автора нет.

### 2.5. Почему без туннелей и VPS

Обсуждено с автором 09–11.10.2026, в код не идёт:

- **VPS** — подходящего нет, у других участников челленджа тоже возникли проблемы с этим;
- **Tailscale** — коммерческий: сервер координации и приложения для Apple закрыты;
- **NetBird** (открытый, WireGuard, посредник видит только шифр) — это VPN, и он конфликтует с VPN, который автору нужен на телефоне и на Mac;
- **zrok** (открытый туннель с бесплатным публичным сервером) — HTTPS заканчивается на сервере zrok, он видит переписку и ключ; к тому же регистрация у автора не прошла;
- **проброс порта на роутере** — нужен «белый» IP, и сервис стал бы виден всему интернету.

Остаётся домашняя сеть — для задания этого достаточно (§1.1). Сервис от способа доступа не зависит: он слушает порт, а туннель, если появится, настраивается снаружи без правки кода.

### 2.6. Сколько это стоит

Деньги — 0 (DeepSeek в сценарии не участвует). Время ответа — как у LM Studio на днях 26–29 плюс ожидание в очереди: короткий вопрос — ≈2 с, вопрос с выдержками RAG — ≈5 с, каждый следующий в очереди ждёт столько, сколько обрабатываются стоящие перед ним.

## 3. Новая программа `src/llm_service.py` — `./run.sh service`

Отдельная долгоживущая программа, как сервер FAQ дня 18: её запускает человек, приложение её не импортирует и не запускает, без неё приложение работает как на дне 29. HTTP — FastAPI + uvicorn (§2.4), в LM Studio — `httpx` (async). Из проекта импортирует `presets.py` (константы), `tokens.py` (оценка токенов), `local_server.py` (окно и id загруженной модели) и `agent.py` — только константу `CONTEXT_OVERFLOW_MARKERS` (§3.7); `Agent` сервис не создаёт. Логи — stdout, префикс `[Сервис]`. Имя проверено (§2.4).

### 3.1. Аргументы и старт

`./run.sh service [--host <адрес>] [--port <порт>] [--upstream <base_url>]`; умолчания — `presets.SERVICE_HOST` (`0.0.0.0`), `SERVICE_PORT` (8800), `SERVICE_UPSTREAM_URL` (`http://127.0.0.1:1234/v1`). `--new-key` — напечатать новый ключ (§3.2) и выйти.

При старте, до uvicorn:

1. Ключи (§3.2). Нет ни одного или строка не разбирается — отказ, код 2, с подсказкой формата и `--new-key`.
2. Порт свободен (как `_port_free()` сервера FAQ) — иначе отказ, код 2: «порт 8800 занят — сервис уже запущен?».
3. `--upstream` не указывает на сам сервис (тот же порт на `127.0.0.1`/`localhost`/`0.0.0.0`) — иначе отказ, код 2: запрос ходил бы по кругу.
4. `local_server.check(upstream)` — **не отказ**, а строка лога: модель и окно, «модель не загружена — `lms load …`» или «LM Studio не отвечает — `lms server start`». LM Studio можно поднять и после сервиса.
5. Строка «сервис запущен»: адреса (`http://127.0.0.1:8800` и адрес Mac в домашней сети — определяется UDP-сокетом без отправки пакетов; `--host 127.0.0.1` — только первый), клиенты (имена и лимиты, без ключей), очередь, потолки.

Адрес LM Studio — свой (`SERVICE_UPSTREAM_URL`, переменная `TOOMANYRULES_SERVICE_UPSTREAM`), а не `LOCAL_BASE_URL`: приложение-клиент получает адрес сервиса через `TOOMANYRULES_LOCAL_URL` (§6), и общая переменная замкнула бы сервис на себя.

### 3.2. Ключи клиентов

- Переменная `TOOMANYRULES_SERVICE_KEYS` (`presets.SERVICE_KEYS_ENV`) в `src/.env`: записи через запятую, запись — `имя:ключ` или `имя:ключ:лимит` (запросов в минуту для этого клиента; без него — `SERVICE_RATE_PER_MIN`).
- Проверка при старте: имя непустое и без `:`/`,`; имена и ключи не повторяются; ключ не короче `SERVICE_KEY_MIN_CHARS` (16); лимит — целое ≥ 1. Ошибка — отказ стартовать (§3.1) с номером записи, **без текста ключа**.
- `--new-key` печатает `secrets.token_urlsafe(24)` и строку-образец для `src/.env`.
- Сравнение — `hmac.compare_digest` по всем ключам. Ключ не попадает ни в лог, ни в ответы, ни в `/health`.
- Список ключей читается один раз при старте: новый клиент или отзыв ключа — перезапуск сервиса.

| `GET /health`               | нет  | JSON: `ok`, `model` (id загруженной или `null`), `context` (окно или `null`), `upstream` (`"ok"` / причина), `queue` (`active`, `waiting`, `max`), `limits` (`concurrency`, `rate_per_min`, `max_tokens`, `max_body_bytes`). Ни имён клиентов, ни ключей |

Прочие пути — 404. Ответ об ошибке — в форме OpenAI API: `{"error": {"message": "…", "type": "…", "code": "…"}}` (SDK `openai` показывает `message`); тексты — §9.

### 3.4. Путь `POST /v1/chat/completions`

Проверки — по порядку; первая не прошедшая даёт ответ:

| #   | Проверка                                                                                                                  | Отказ                                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1   | Ключ из `Authorization: Bearer`                                                                                           | 401 `invalid_api_key`                                                              |
| 2   | Размер тела ≤ `SERVICE_MAX_BODY_BYTES` (по `Content-Length` и по факту чтения)                                            | 413 `body_too_large`                                                               |
| 3   | JSON-объект; `messages` — непустой список, у каждого `role` и `content` — строка или список частей, где все части — текст | 400 `invalid_request`                                                              |
| 4   | `stream` не `true`                                                                                                        | 400 `stream_not_supported`                                                         |

Дальше — пересылка (§3.8). У ответа `200` — тело LM Studio как есть и заголовки `X-Service-Client` (имя клиента), `X-Queue-Wait` (секунды ожидания), `X-RateLimit-Remaining`.

Поле `model` и прочие поля запроса (`temperature`, `reasoning_effort`, `tools`, …) уходят как есть; меняется только `max_tokens` (§3.7). Заголовок `Authorization` клиента в LM Studio не уходит.

### 3.5. Очередь

- В модели одновременно не больше `SERVICE_CONCURRENCY` запросов (1); ждут не больше `SERVICE_QUEUE_MAX` (4); ждать — не дольше `SERVICE_QUEUE_TIMEOUT_S` (120 с). Порядок — по приходу (FIFO).
- Очередь общая на всех клиентов: запрос приложения ждёт за запросом телефона и наоборот.
- `Retry-After` у 503 — оценка: (ожидающих + 1) × среднее время последних ответов, не меньше 1 с; до первого ответа — 5 с.
- Очередь живёт в памяти процесса; перезапуск её обнуляет.

### 3.6. Лимит запросов

- Скользящее окно 60 с на клиента: учитывается каждый запрос с верным ключом, дошедший до шага 5 (§3.4) — в том числе тот, что потом получит отказ по контексту или очереди. Лимит — запись ключа или `SERVICE_RATE_PER_MIN` (10).
- Отказ — 429, `Retry-After` — секунд до выхода самого старого запроса из окна (округление вверх). Отказанный по лимиту запрос в окно не добавляется.
- Лимит — в памяти процесса; перезапуск обнуляет.
- SDK `openai` (приложение, §6) **сам повторяет** 429 и 503 до двух раз, с учётом `Retry-After`. В логе сервиса это видно как повторные запросы того же клиента; агент получает ошибку, только если не помогли и повторы.

### 3.7. Окно модели (max context)

- **Потолок ответа.** `max_tokens` запроса: нет или больше `SERVICE_MAX_TOKENS` (2000, как `LOCAL_MAX_TOKENS`) — ставится `SERVICE_MAX_TOKENS`; уменьшение — строка лога и заголовок `X-Max-Tokens-Capped`. Без потолка LM Studio генерирует до конца окна (§2.4).
- **Окно** — `loaded_context` загруженной модели из `local_server.check(upstream)`; результат кэшируется на `SERVICE_MODEL_REFRESH_S` (30 с) — модель могут сменить в LM Studio, не перезапуская сервис. Окна нет (модель не загружена, LM Studio не отвечает или не сообщает) — проверка пропускается, запрос идёт дальше (ответ LM Studio — §3.8).
- **Оценка вопроса** — `tokens.TOKENS_PER_REQUEST` + сумма по сообщениям (`tokens.TOKENS_PER_MESSAGE` + `tokens.estimate_tokens()` текста), та же эвристика, что в панели дня 8.
- **Правило:** оценка вопроса + потолок ответа ≤ окно. Иначе 400 `context_length_exceeded`: «Запрос не поместится в окно модели: ≈N токенов вопроса + M на ответ > W (окно `<id>`). Сократите текст или начните новый разговор.» Так ловится и случай, который LM Studio пропускает (§2.4).
- Оценка грубая (на русском завышает ≈1,25×, §2.4), поэтому есть и вторая линия: 400 LM Studio о контексте (признаки `agent.CONTEXT_OVERFLOW_MARKERS`, день 8) переводится в тот же `context_length_exceeded` с текстом LM Studio в конце.

### 3.8. Пересылка в LM Studio

- `POST <upstream>/chat/completions` через один `httpx.AsyncClient` на процесс, таймаут `SERVICE_UPSTREAM_TIMEOUT_S` (180 с), ключа нет (LM Studio его не проверяет).
- Ответ LM Studio 2xx — клиенту как есть (§3.4).
- 4xx/5xx LM Studio — клиенту тот же статус, тело в форме §3.3 с текстом LM Studio («No models loaded…» подсказывает `lms load` сама). «No models loaded» сбрасывает кэш окна.
- Нет соединения — 502 `upstream_unavailable`: «LM Studio не отвечает по <адрес> — `lms server start`»; таймаут — 504 `upstream_timeout`.
- Сервис не повторяет запрос в LM Studio и не меняет ответ.

### 3.9. Лог

Строка на каждый запрос к `/v1/*` (`/health` и `/` — без строк): время, клиент (или «без ключа» / «чужой ключ» и адрес отправителя), путь, статус, код отказа, ожидание в очереди, время в модели, `prompt`/`completion` токены по `usage`, модель ответа, «потолок ответа уменьшен N → M». **Без текстов вопросов и ответов и без ключей.** Строка лога очереди на изменение: «в модели 1, ждут 3». Access-лог uvicorn выключен — строки сервиса его заменяют.

### 3.10. Остановка

Ctrl+C — штатный выход uvicorn; SIGTERM — как Ctrl+C (`signal.default_int_handler`, правило сервера FAQ дня 20). Ожидающие в очереди получают обрыв соединения; на диске ничего не остаётся.

## 4. Страница чата `src/llm_service_chat.html`

Один HTML-файл без сборки и внешних библиотек: сервис читает его при старте и отдаёт на `/`. Работает в мобильном браузере (ширина телефона, крупный шрифт).

- Поле «Ключ» (`type=password`), сохраняется в `localStorage` браузера; кнопка «Забыть ключ».
- Лента сообщений и поле ввода; «Отправить» неактивна, пока ждём ответ; «Новый разговор» очищает ленту.
- История — в памяти страницы; каждый запрос отправляет её целиком (`messages`), сервис её не хранит. Запрос: `model: "local"`, `reasoning_effort: "none"`, без `max_tokens` (ставит сервис), без системного промпта.
- Под ответом — серой строкой: модель ответа, время, ожидание в очереди (`X-Queue-Wait`), токены.
- Ошибка — красной строкой с текстом `error.message` сервиса (там же секунды из `Retry-After`); сообщение пользователя при ошибке в историю не добавляется.
- Текст выводится как текст (`textContent`, перенос строк), без разметки и `innerHTML`.
- Внизу — строка состояния из `/health`: модель, окно, очередь; обновляется после каждого ответа.

## 12. Риски

- **HTTP без шифрования.** В домашней сети ключ и разговор идут открытым текстом; кто в той же сети и умеет перехватывать трафик, их увидит. Принято: сеть домашняя, данные — вопросы о правилах настольной игры. TLS — не на этом шаге (§16).
- **`0.0.0.0` — все сети Mac.** В кафе или в гостевом Wi-Fi сервис будет виден той сети (с ключом). Для такой сети — `--host 127.0.0.1` или не запускать сервис.
- **Оценка токенов грубая**: на русском сервис откажет раньше реального предела на ≈20 %, на тексте другого языка может пропустить — тогда отказывает LM Studio, и сервис переводит его ответ (§3.7). Точной токенизации у сервиса нет.
- **Одна генерация за раз**: при нагрузке ожидание растёт линейно; это решение (§1.1), а не ошибка. Параллель LM Studio включается `SERVICE_CONCURRENCY` до 4.
- **Перебор ключей** не ограничивается: ключ — 24 случайных байта, а 401 видны в логе.
- **Служебные работы приложения тратят лимит клиента** «ноутбук» (разбор памяти и др., §6). Лимит по умолчанию — 10 в минуту; SDK повторяет 429.

4. **Два клиента одновременно**: вопрос в приложении TooManyRules (через сервис) и на телефоне почти сразу — оба получают ответ; в логе сервиса второй ждал в очереди N с.
5. **Стабильность**: `./run.sh service-load` — запросы одновременно, очередь, 503 «очередь полна», 429; сервис жив, отчёт.
6. **Rate limit на телефоне**: у ключа телефона лимит 3 в минуту — четвёртый вопрос получает «повторите через S с».
7. **Max context**: длинный текст на телефоне — отказ с числами, следующий вопрос — ответ.
8. Короткий вывод автора: что значит «приватный» здесь и чего нет (HTTP без шифрования, только домашняя сеть).

- **Не выходим в интернет**: ни VPS, ни туннелей (NetBird, zrok, Tailscale, Cloudflare, ngrok), ни проброса портов (§2.5). Доступ — домашняя сеть.

- **Не отдаём наружу ассистента**: ни RAG, ни памяти, ни профиля через сервис; API ассистента — не этот шаг.

- **Не храним ничего на диске**: ни разговоров, ни статистики, ни логов в файл; ни базы, ни SQLite.
- **Не управляем LM Studio** из сервиса: ни запуска, ни загрузки и выгрузки моделей, ни выбора модели по полю `model`.
- **Не делаем точный подсчёт токенов** токенизатором модели — оценка `tokens.py` плюс ответ LM Studio.
- **Не меняем `agent.py`**, проверку ответа, тексты RAG, пресеты (кроме условного ключа) и раскладку аккордеонов приложения.
- **Не пишем телеграм-бот, мобильное приложение** и другие клиенты, кроме страницы чата.
- **Не защищаем от перебора ключей** и от DoS сверх лимита и очереди.
- **Не гоняем `rag-eval`, `rag-dialog`, `local` и `rag-compare` через сервис.**
- **Не пишем документ проверки** (§1). Не пишем тестов и линтера.
