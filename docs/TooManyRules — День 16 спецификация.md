# TooManyRules — спецификация дня 16

Тема: Подключение MCP — приложение само запускает MCP-сервер BoardGameGeek, устанавливает с ним соединение по протоколу MCP и выводит список его инструментов; агент инструментами пока не пользуется

## 1. Задание челленджа (день 16)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_16.txt` и комментарий организатора `tasks/AI Advent Challenge_16_comments.txt`.

Ключевое из задания: поставить MCP SDK или клиент (либо поднять MCP-сервер, если вариант локальный) и написать **минимальный код, который устанавливает MCP-соединение и получает от сервера список доступных инструментов**. Проверить две вещи: соединение устанавливается, список инструментов возвращается корректно. Результат — код, который подключается к MCP и выводит список инструментов; формат сдачи — **видео + код**.

Из комментария организатора: на этом шаге работать с MCP дальше не нужно — достаточно запросить список инструментов у любого общедоступного сервера. Это и есть граница дня: ни вызова инструментов, ни подключения к агенту (§12).

Формат — «видео + код» без «/ текст», а результат — сам код, поэтому **отдельного документа проверки у дня нет** (правило дня 12): проверка показывается в видео (§10), факты реального подключения записываются комментарием в коде (§3.3).

День 16 открывает неделю 4 («MCP»). Отдельного архитектурного документа у недели пока нет; этот документ опирается на правила прошлых недель и их не повторяет:

- **интерфейс — вид, а внешний мир — за своим модулем**: LLM API вызывается только в `agent.py`, диск трогает только `storage.py`. Сегодня появляется третий такой модуль: **SDK MCP импортирует только `mcp_client.py`**;
- **всё «про настолки» — в `presets.py`**: какой сервер и как его запускать, решает `presets.py`, а `mcp_client.py` про BoardGameGeek не знает — как `context.py` не знает, что сводка — про партию;
- **лист графа не импортирует ничего из проекта** (как `tokens.py` и `context.py`); новый модуль — лист;
- **каждое обращение к внешнему миру логируется** тем же форматом — как обращение к диску в `storage.py`;
- **на экране — текущий день, прошлые свёрнуты** (правило CLAUDE.md про аккордеоны);
- **абстракций под будущие дни не пишем**: сегодня один сервер и одно действие.

Все числа времени и токенов в примерах ниже — **условные, для иллюстрации формата**. Настоящие — по прогону (§3.3).

## 2. Что делаем конкретно для TooManyRules

По общей спецификации (§5, неделя 4) первый внешний источник проекта — BoardGameGeek: метаданные игр и обсуждения правил. Для него есть готовый открытый MCP-сервер — **bgg-mcp** (`github.com/kkjdaniel/bgg-mcp`, MIT, Go), зарегистрированный в официальном реестре MCP как `io.github.kkjdaniel/bgg-mcp`. День 16 к нему подключается и получает список его инструментов.

Шесть пунктов дня:

1. **`src/mcp_client.py`** — новый модуль: MCP-клиент на официальном Python SDK. Запускает stdio-сервер, согласует протокол, забирает список инструментов по всем страницам, закрывает соединение и отдаёт результат одним значением; каждый шаг пишет в лог (§4).
2. **`src/presets.py`** — описание сервера BoardGameGeek, потолок времени на подключение и замер реального подключения комментарием (§3).
3. **`src/app.py`** — блок «MCP: сервер BoardGameGeek (день 16)» наверху дебаг-панели: кнопка, статус соединения, таблица инструментов и ответ `tools/list` целиком; строка лога при старте; перекладка аккордеонов; шапка (§5).
4. **`src/requirements.txt`** — новая зависимость `mcp>=2.2,<3` (§2.5).
5. **`README.md`** — раздел про MCP и сборка сервера (§7, §8).
6. **`agent.py` и остальные модули не меняются** (§6): агент о MCP не знает.

Продуктовый смысл для TooManyRules. У ассистента появляется первый внешний источник, и сегодня приложение честно показывает только его **каталог** — что этот источник умеет. Из десяти инструментов bgg-mcp проекту ближе всего `bgg-rules` (поиск ответов на вопросы по правилам в форумах BGG — тот самый слой «обсуждения BGG» из §4 общей спецификации), `bgg-thread-details` (тред форума целиком), `bgg-search` и `bgg-details` (дополнения, число игроков, сложность) и `bgg-collection` (что стоит у игрока на полке — то, что день 11 держит в долговременной памяти со слов игрока). Пользоваться ими ассистент начнёт не сегодня.

Что из исходников важно знать заранее:

Аннотации — подсказки сервера, а не факт; таблица их не показывает, JSON ответа показывает как есть (§5.3).
- **Сервер называет себя `BGG MCP 1.6.0` и на теге 1.6.1**: номер зашит в `main.go`. Это не ошибка сборки.

### 2.2. Как запускается сервер: собранный бинарник

Сервер — отдельная программа, которую приложение запускает само, по нажатию кнопки: stdin и stdout процесса становятся каналом JSON-RPC. **Запускаем бинарник, собранный из исходников на теге v1.6.1**; Docker не используем.

| Что | Значение |
| --- | --- |
| Командная строка по умолчанию | `~/.local/bin/bgg-mcp -mode stdio` — в `presets.py` путь собирается из домашнего каталога (`Path.home()`) и уже абсолютный |
| Что поставить | Go ≥ 1.23 — только для сборки (§7.1); после сборки он не нужен |
| Запуск на каждое нажатие | десятки миллисекунд |
| Версия закреплена | тегом git, из которого собран |
| Изоляция | нет: процесс с правами пользователя |

**Почему бинарник, а не Docker.** README сервера рекомендует Docker, и в записи реестра пакет — образ `kdaniel/bgg-mcp:1.6.1`. Автор выбрал бинарник: Docker на машине нет, Go ставится за минуту, запуск — десятки миллисекунд вместо старта контейнера, и не нужно ни держать запущенный рантайм, ни заранее тянуть образ. **Цена — изоляция**: контейнер не дал бы чужому коду читать файлы приложения (`src/.env`, `src/data/`), а бинарник работает с правами пользователя. Окружение приложения — в том числе ключ DeepSeek — он при этом не получает: его отсекает белый список SDK (§2.6). Для сервера с открытыми исходниками, собранного из тега, это приемлемо.

**Почему тег v1.6.1**: последний помеченный; `main` новее, но тегом не помечен и может уехать, а версия в видео должна совпадать с версией в коде.

**Бинарник — только сборкой из клона на теге.** `go install github.com/kkjdaniel/bgg-mcp@latest` не работает: во всех тегах в `go.mod` опечатка в пути модуля (`kkjdanie`), исправленная только в непомеченном `main`. Порядок сборки — §7.1.

**Где лежит бинарник — соглашение, а не настройка кода.** Команда сборки кладёт его в `~/.local/bin/bgg-mcp`, и туда же смотрит командная строка по умолчанию: путь строится от домашнего каталога текущего пользователя, поэтому в коде нет ничего своего для конкретной машины, а в `src/.env` для обычного случая ничего не нужно. Если бинарник лежит в другом месте, переменная окружения `TOOMANYRULES_BGG_MCP_COMMAND` (обычно — строкой в `src/.env`) заменяет командную строку **целиком**; путь в ней — абсолютный (§4.3).

*При написании спецификации (22.09.2026) на машине автора не было ни Docker, ни Go; при реализации поставлен Go, сервер собран и замерен (§3.3).*

### 2.3. Что значит «установить соединение»: четыре шага

Каждое нажатие кнопки — одно полное подключение:

```
1. запуск процесса      ~/.local/bin/bgg-mcp -mode stdio
                        stdin/stdout — канал JSON-RPC, stderr — как есть в терминал приложения
2. согласование         → server/discover (версия 2026-07-28)
                        ← ошибка -32601: такого метода нет            — сервер старой эры, это норма
                        → initialize (клиент предлагает 2025-11-25)
                        ← 2025-06-18 · BGG MCP 1.6.0 · tools, resources, prompts, logging
                        → notifications/initialized                   ═ соединение установлено
3. список инструментов  → tools/list                ← 10 инструментов
                        (пришёл nextCursor → tools/list с курсором, пока курсор не кончится)
4. закрытие             stdin закрыт → сервер выходит
                        (SDK ждёт до 2 с, потом завершает процесс сам)
```

- **«Соединение установлено» — это шаги 1-2**: у клиента на руках имя и версия сервера, согласованная версия протокола и объявленные возможности. Именно это показывает первая строка статуса (§5.3) — проверка задания «соединение устанавливается».
- **«Список корректно возвращается» — это шаг 3 целиком**: все страницы, каждая разобрана SDK по схеме протокола (битый ответ до панели не дойдёт — будет сбой стадии), и ответ виден дословно рядом с таблицей.
- **Между нажатиями ничего не хранится**: ни процесса, ни сессии, ни списка. Долгоживущее соединение понадобится, когда инструменты начнут вызываться, — это решение следующих дней (§12).

### 2.4. Две эры протокола

Летом 2026 года у протокола MCP сменилась эра: **ревизия 2026-07-28 убрала рукопожатие**. До неё (версии по 2025-11-25) соединение открывалось `initialize`: клиент предлагает версию, сервер отвечает своей, клиент подтверждает. С 2026-07-28 клиент посылает один запрос `server/discover`, и сервер одним ответом сообщает версии, возможности и кто он.

Официальный Python SDK v2 умеет обе эры: `Client` по умолчанию (`mode="auto"`) сначала пробует `server/discover`, а на ошибку JSON-RPC откатывается к рукопожатию. bgg-mcp — сервер старой эры, поэтому соединение с ним всегда выглядит так, как на схеме §2.3: **проба не принята, рукопожатие `initialize`, протокол 2025-06-18**. Это не сбой, и панель с логом называют это прямо (§5.3, §4.7).

`mode` не закрепляем: следующий сервер недели может говорить уже на 2026-07-28 (например, свой, на SDK v2), и тот же клиент должен подключиться к нему без правок (§12).

### 2.5. Клиент: официальный Python SDK v2

`pip install mcp` с 28.07.2026 ставит **вторую мажорную версию SDK** (сейчас 2.2.0 от 07.09.2026; линия 1.x выходит отдельно), и её клиентский API другой, чем у v1. Большая часть примеров в интернете — v1 (`ClientSession` + `stdio_client` + `session.initialize()`); **их не копировать**. Требование в `requirements.txt` — `mcp>=2.2,<3`: верхняя граница — по совету самого SDK держать границу мажорной версии, нижняя — версия, на которой всё проверено (§2.9).

Что из SDK нужно дню:

| Что | Где в SDK v2 |
| --- | --- |
| описание stdio-сервера | `StdioServerParameters(command=…, args=[…], env={…})` |
| подключение и согласование | `async with Client(params) as client:` — вход в блок запускает процесс и согласует протокол, выход — закрывает. Пары `connect()`/`close()` нет, клиент одноразовый |
| что узнали при подключении | `client.server_info` (`name`, `version`; `None`, если сервер не назвался), `client.protocol_version`, `client.server_capabilities` (поля `tools`, `resources`, `prompts`, `logging`, … — `None`, если возможности нет), `client.instructions` |
| какой эрой договорились | `client.session.discover_result` — не `None` только при `server/discover` |
| список инструментов | `await client.list_tools(cursor=…)` → `ListToolsResult`: `.tools` (у каждого `name`, `title`, `description`, `input_schema`, `annotations`) и `.next_cursor`. **Постранично само не листает** — цикл по курсору пишет клиент |
| ответ в виде «как на проводе» | `result.model_dump(mode="json", by_alias=True, exclude_unset=True)` — ключи `inputSchema`, `nextCursor`, и только те поля, что прислал сервер. **Не `exclude_none`**: с ним модель SDK v2 дописывает поля эры 2026-07-28 со значениями по умолчанию (`ttlMs`, `cacheScope`, `resultType`), которых сервер старой эры не присылал (проверено, §2.9) |
| ошибки | `MCPError` (ошибка JSON-RPC: код и текст), `OSError` при запуске процесса; изнутри `async with` исключения приходят обёрнутыми в `ExceptionGroup` (§4.6) |

- **SDK асинхронный (anyio), проект синхронный.** Публичная функция модуля — обычная, внутри — `anyio.run()`. Gradio вызывает синхронные обработчики в рабочем потоке, где своего цикла событий нет, и `anyio.run()` там работает (проверено, §2.9). Обработчик остаётся обычной функцией с одним `return` — со спиннером ожидания, как все обработчики проекта.
- **Python 3.14** SDK поддерживает; с зависимостями проекта (`gradio`, `openai`, `python-dotenv`) он разрешается без конфликтов. Транзитивно SDK приносит `mcp-types`, `httpx2`, `jsonschema`, `pyjwt[crypto]` (а с ним `cryptography`), `sse-starlette` и `opentelemetry-api`; остальное (`anyio`, `pydantic`, `starlette`, `uvicorn`) уже стоит ради Gradio.
- **Кэш ответов SDK** (механизм эры 2026-07-28) на сервере старой эры не срабатывает, а клиент живёт одно нажатие — настраивать нечего.

### 2.6. Окружение сервера и ключ BGG

- **Процесс сервера не наследует окружение приложения.** SDK передаёт ему только белый список — `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER` — и то, что клиент перечислил явно. Ключ DeepSeek из `src/.env` до чужого сервера не доходит, и так и должно быть.
- **Явно передаются `BGG_API_KEY` и `BGG_USERNAME` — только если заданы** (непустые). Значения нигде не показываются и не логируются — только имена и «задан / не задан». Бинарник читает их прямо из своего окружения — больше ничего не нужно.
- **Для списка инструментов ключ не нужен.** Без ключа сервер создаёт клиент BGG без авторизации и отвечает на `tools/list` как обычно: список описан в коде сервера, в BGG за ним никто не ходит.
- **Для вызова инструментов ключ понадобится.** BGG с 2025 года пускает к XML API только зарегистрированные приложения и без токена отвечает 401. Ключ получают вручную на `boardgamegeek.com/applications`, и выдают его не сразу — **заявку стоит подать заранее**, к дню, когда инструменты начнут вызываться.
- `BGG_COOKIE` (альтернатива ключу из README сервера — строка с логином и паролем BGG) не передаём: ключ — рекомендованный путь, а пароль в окружении чужого процесса не нужен.

### 2.7. Где лежит и сколько живёт

**Ничего нового на диск не едет.**

| Что | Где живёт | Переживает |
| --- | --- | --- |
| описание сервера и потолок времени | `presets.py` | — (код) |
| замена командной строки, ключ и ник BGG | `src/.env` → окружение процесса при старте | перезапуск (это файл); **правка `.env` доезжает только после перезапуска** |
| результат подключения | выходы блока MCP в этой вкладке | ничего: перезагрузка страницы — блок снова пуст |
| процесс сервера | одно нажатие | — |
| лог подключения | stdout | — |

Результата подключения нет ни в файле сессии, ни в агенте, ни в checkpoint'е и ветке, ни в `_view()`: к диалогу MCP сегодня не относится вовсе.

### 2.8. Сколько это стоит

**Ни одного вызова модели**: подключение к MCP — не LLM, счётчики агента и процесса не двигаются. Цена — время: запуск процесса, согласование и список. Числа — в замер (§3.3).

Одно число статус показывает на будущее: **сколько токенов заняли бы описания и схемы всех инструментов**, если отдать их модели, — по оценке `tokens.py` (правило дня 8: оценка — не факт; факт придёт из `usage`, когда инструменты действительно уйдут в запрос). Сегодня в запрос не уходит ничего; число показывает, что MCP-инструменты не бесплатны: каждый добавляет свои токены к **каждому** запросу.

### 2.9. Что проверено до реализации

Проверено при написании спецификации (22.09.2026, во временном окружении; в репозиторий ничего не попало):

- **по исходникам** bgg-mcp v1.6.1 и mcp-go v0.43.2: список и параметры инструментов, запуск без ключа, ответ -32601 на неизвестный метод (в том числе до `initialize`), выбор версии протокола в `initialize`, сортировка инструментов, аннотации по умолчанию, объявляемые возможности;
- **SDK 2.2.0 на Python 3.14.7** — против эмулятора stdio-сервера, отвечающего так, как по исходникам отвечает mcp-go:
  - проба `server/discover` → -32601 → `initialize` (клиент предложил 2025-11-25) → протокол 2025-06-18, `discover_result is None`;
  - постраничный `tools/list` по `next_cursor` (три страницы → десять инструментов);
  - `model_dump(..., exclude_unset=True)` страницы отдаёт ровно поля ответа сервера (`nextCursor`, `tools`; у инструмента — `name`, `description`, `inputSchema`, `annotations`), а `exclude_none=True` дописывает `ttlMs`, `cacheScope` и `resultType`, которых сервер не присылал;
  - процесс сервера получил только белый список окружения и явно переданную переменную;
  - нет команды → `FileNotFoundError` сразу, без обёртки; процесс умер до рукопожатия → `ExceptionGroup` вокруг `MCPError(-32000, "Connection closed")`; процесс молчит → `TimeoutError` по потолку плюс до 2 с на закрытие;
  - три параллельных синхронных вызова через `anyio.to_thread.run_sync` из работающего цикла событий (так Gradio зовёт синхронные обработчики) — все три подключились;
  - SDK в штатном пути ничего не пишет в лог — строки подключения в stdout будут только наши;
- **зависимости**: `uv pip compile` для `requirements.txt` проекта плюс `mcp>=2.2,<3` на Python 3.14 разрешается без конфликтов.

**Не проверено при написании**: настоящий bgg-mcp — ни Docker, ни Go на машине тогда не было. Реальный прогон на собранном бинарнике — часть реализации (§9); расхождения с этим разделом записаны в замер как есть.

## 4. Новый модуль `src/mcp_client.py`

**Имя — `mcp_client.py`, а не `mcp.py`.** `mcp` — имя пакета SDK: файл `src/mcp.py` подменил бы его всему процессу, и `from mcp import Client` импортировал бы сам себя — та же ловушка, что `profile.py` на дне 12, только с установленным пакетом вместо модуля стандартной библиотеки. По той же причине не годится `mcp_types.py` — это модуль зависимости SDK. Модуля `mcp_client` нет ни в стандартной библиотеке, ни среди установленных пакетов (проверено).

### 4.1. Границы модуля

- **Единственное место, где импортируется SDK `mcp`.** Ни `app.py`, ни `presets.py` SDK не импортируют: интерфейс получает готовые типы модуля.
- **Лист графа**: из проекта не импортирует ничего; ни Gradio, ни Too Many Bones, ни BoardGameGeek, ни LLM. Что запускать — приходит параметром (`McpServer`).
- **Внешний мир — да**: модуль запускает процесс, говорит с ним по протоколу, читает окружение (замену командной строки и переменные для сервера) и **сам загружает `src/.env`** (`load_dotenv()` при импорте) — по правилу `agent.py`: модуль, который читает ключ, сам и подхватывает `.env`. Повторная загрузка безвредна: `load_dotenv()` не перезаписывает уже заданное.
- **Пишет в лог каждое подключение** (логгер `toomanyrules.mcp`) — как `storage.py` каждое обращение к диску (§4.7).
- **Публичный API синхронный**, асинхронность — только внутри.
- **Состояния между вызовами нет**: ни кэша, ни глобальных объектов, кроме констант и логгера. Две вкладки — два независимых подключения и два процесса; замков не нужно.

### 4.2. Константы и типы

```python

STAGE_CONNECT = "соединение"            # процесс есть, согласование не завершилось
STAGE_LIST = "список инструментов"      # соединение есть, списка нет

HANDSHAKE_INITIALIZE = "initialize"     # рукопожатие эры до 2026-07-28

SDK_VERSION: str                        # importlib.metadata.version("mcp") — для панели и лога

    enum: tuple[str, ...] = ()

    title: str                      # "" — сервер не прислал
    description: str
```

Тексты причин (пустая строка, неразбираемая строка, таймаут, сервер не объявил `tools`, повторившийся курсор) — константы модуля, нейтральные: слов «BoardGameGeek», «bgg» и «партия» в модуле нет.

### 4.3. Командная строка: `resolve_launch(server, environ) -> Launch`

Чистая функция: окружение приходит параметром, поэтому её зовут и подключение (с `os.environ`), и панель при построении, и строка лога при старте — и все трое видят одно и то же.

1. Если `server.command_env` задан и в окружении под этим именем непустая строка — берётся она, `origin = "из <имя переменной>"`; иначе — `server.command`, `origin = "по умолчанию"`. Строка из одних пробелов — непустая: это замена, и она даёт ошибку «пустая» (шаг 2), а не откат к умолчанию.
2. Строка разбирается `shlex.split()` (кавычки по правилам POSIX-шелла). Пустой результат или `ValueError` (незакрытая кавычка) — `error` с причиной и `argv = ()`. Тильда и переменные внутри строки не раскрываются — поэтому путь к бинарнику пишется абсолютным (в `presets.py` он уже абсолютный, §3.1; в замене — §7.2).
3. `env_set` / `env_missing` — `server.env_keys`, разложенные по тому, есть ли в окружении непустое значение.

### 4.4. Подключение: `list_tools(server, *, timeout_s) -> ToolListing`

Одна синхронная функция на всё подключение. **Исключений на ожидаемых сбоях не бросает**: любой сбой — это `ToolListing` со стадией и текстом (§4.6), чтобы интерфейсу не нужно было знать про типы ошибок SDK.

1. `launch = resolve_launch(server, os.environ)`. Ошибка разбора — сбой стадии «запуск» без запуска процесса.
2. Строка лога «подключение» (§4.7).
3. `StdioServerParameters(command=argv[0], args=list(argv[1:]), env={имя: значение для имён из launch.env_set})`.
4. `anyio.run()` асинхронной части; внутри весь путь закрыт одним `anyio.fail_after(timeout_s)`:

   ```python
   async def _connect_and_list(params, progress, timeout_s):
       with anyio.fail_after(timeout_s):
           async with Client(params) as client:          # запуск процесса + согласование (mode="auto")
               progress.connected(client)                # имя, версия, протокол, эра, возможности, instructions, connect_s
               if client.server_capabilities.tools is None:
                   raise _NoToolsError()                 # «сервер не объявил возможность tools» — tools/list не зовём
               cursor, seen = None, set()
               while True:
                   page = await client.list_tools(cursor=cursor)
                   progress.page(page)                   # инструменты + page.model_dump(mode="json", by_alias=True, exclude_unset=True)
                   cursor = page.next_cursor
                   if not cursor:
                       break
                   if cursor in seen:
                       raise _RepeatedCursorError(cursor)    # защита от бесконечного листания
                   seen.add(cursor)
       # выход из async with — закрытие: stdin, до 2 с ожидания, затем SDK завершает процесс сам
   ```

   `progress` — объект одного вызова (не модуля): он помнит текущую стадию и всё, что уже узнали, чтобы при сбое на списке в результате остались факты соединения. Эра — `HANDSHAKE_DISCOVER`, если `client.session.discover_result` не `None`, иначе `HANDSHAKE_INITIALIZE`. Возможности — имена полей `server_capabilities`, не равных `None`, в порядке полей модели SDK. `mode` клиента не задаётся (§2.4), `client_info` и `read_timeout_seconds` — тоже: общий потолок держит `fail_after`.
5. Исключения ловятся `except Exception`, а не `BaseException`: `KeyboardInterrupt` должен останавливать приложение, как раньше. Разбор — §4.6.
6. Строки лога: «соединение установлено» и «tools/list» — в момент события (их пишет `progress`, чтобы при зависании на списке в терминале уже было видно, что соединение есть), «соединение закрыто» или «сбой» — после выхода из `anyio.run()`. `total_s` считается там же — и при успехе, и при сбое.

### 4.5. Параметры инструмента: `tool_params(input_schema) -> tuple[McpParam, ...]`

Чистая функция над JSON Schema инструмента — то, что таблица показывает в колонке «параметры»:

- свойства — из `properties` **в том порядке, в каком пришли** (у bgg-mcp — по алфавиту); `properties` не словарь — параметров нет;
- `type` — строка как есть; список типов — через `|` (`string|null`); у `array` с `items.type` — `array[number]`; нет `type` — `""`;
- `enum` — значения строками, в порядке схемы;
- обязательность — по списку `required` верхнего уровня;
- вложенные объекты не разворачиваются: тип `object`, подробности — в JSON ответа (§5.3).

### 4.6. Сбои и стадии

Исключения SDK изнутри `async with` приходят обёрнутыми в `ExceptionGroup`, иногда вложенными; разбор берёт **первый лист** группы. Стадия — та, на которой был `progress`, с одним уточнением: `OSError` (нет файла, нет прав) на стадии «соединение» — это сбой **запуска** процесса. Кроме `TimeoutError`: в Python он подкласс `OSError`, но таймаут значит, что процесс запущен и молчит, — стадия остаётся «соединение» (поймано на прогоне).

| Что случилось | Стадия | Текст сбоя (пример) | Процесс |
| --- | --- | --- | --- |
| замена командной строки пустая или с незакрытой кавычкой | запуск | «командная строка не разбирается: No closing quotation» | не запускался |
| команды нет: бинарник не собран, неверный путь в замене, путь с тильдой | запуск | `FileNotFoundError: [Errno 2] No such file or directory: '/Users/…/.local/bin/bgg-mcp'` | не запустился |
| процесс завершился до конца согласования: сервер не понял флаги (`-mode nope`), упал на старте | соединение | `MCPError(-32000): Connection closed` | завершился |
| процесс молчит: это не MCP-сервер, завис | соединение | «таймаут 10 с» | завершён SDK |
| сервер не объявил `tools` | список инструментов | «сервер не объявил возможность tools» | закрыт |
| ошибка JSON-RPC на `tools/list`, процесс умер на списке, курсор повторился, таймаут на списке | список инструментов | `MCPError(…): …` / «курсор повторился: …» / «таймаут 10 с» | закрыт |

- `MCPError` пишется с кодом: `MCPError(-32000): Connection closed`; `TimeoutError` — словами «таймаут N с» (своего текста у него нет); остальное — `Тип: текст`.
- **Причину «Connection closed» знает только сервер**, и она — в его stderr, который идёт в терминал приложения как есть (у bgg-mcp с неверным флагом — «Invalid mode: nope. Use 'stdio' or 'http'»). Поэтому на стадии «соединение» статус добавляет подсказку: сообщение сервера — в терминале, над записью лога. stderr не перехватывается (§12).
- Исключение неожиданного типа (не `MCPError`, не `OSError`, не `TimeoutError` и не свои ошибки модуля) — тоже результат со сбоем, но в лог идёт с трассировкой: это, скорее всего, ошибка в коде, а не у сервера.

### 7.1. Сборка сервера

Строка в `src/.env` — путь **абсолютный** (тильда не раскрывается, §4.3):

```
TOOMANYRULES_BGG_MCP_COMMAND=/абсолютный/путь/bgg-mcp -mode stdio
```

Все новые строки необязательны:


Правка `.env` доезжает после перезапуска приложения. Для разовой проверки переменную удобнее задать в команде запуска — `load_dotenv()` уже заданное не перезаписывает:


### 7.4. Необязательная сверка: MCP Inspector

Независимый официальный клиент — чтобы показать, что список «корректный» не только в нашей панели. Нужен Node ≥ 22.19 (у автора — 24):

```bash
npx -y @modelcontextprotocol/inspector --cli "$HOME/.local/bin/bgg-mcp" -mode stdio -- --method tools/list
```

```bash
npx -y @modelcontextprotocol/inspector --cli "$HOME/.local/bin/bgg-mcp" -mode stdio -- --method initialize
```

В CLI-режиме Inspector v2 всё **до** `--` — команда сервера вместе с её флагами (`-mode stdio`), всё **после** — параметры самого Inspector. Первый вызов покажет те же десять имён, второй — имя сервера, версию протокола и возможности. Синтаксис — по документации Inspector 2.7; при написании спецификации команды не запускались.

## 8. Технические требования

- **Новая зависимость — одна**: `mcp>=2.2,<3` в `src/requirements.txt`. Остальные строки не меняются.
- **SDK `mcp` импортирует только `src/mcp_client.py`.** Вызовов LLM API вне `agent.py` не появляется; `agent.py` не меняется.
- **`mcp_client.py`** — лист графа: из проекта не импортирует ничего; ни Gradio, ни Too Many Bones, ни BoardGameGeek; публичный API синхронный; состояния между вызовами нет; каждое подключение логируется; значения переменных окружения не показываются и не логируются.
- **Граф зависимостей**: `app.py` → `presets.py` → `mcp_client.py`; `app.py` → `mcp_client.py` (подключение, описание запуска, версия SDK и белый список окружения). Остальное — как на дне 15. Циклов нет.
- **Приложение поднимается и работает без собранного сервера**: подключения при старте нет, сбой подключения — строка статуса и лога, а не исключение в обработчике. Чат, стратегии, память, профиль, задача и инварианты от блока MCP не зависят.
- Приложение обязано вести себя по §4.6 и §5.3:
  - без собранного бинарника или с неверным путём в замене (стадия «запуск»); с заменой на `bgg-mcp -mode nope` (стадия «соединение», сообщение сервера — в терминале); с пустой заменой и с незакрытой кавычкой (сбой без запуска процесса); с заменой на `sleep 100` (таймаут на стадии «соединение», процесс завершён);
  - с ключом BGG и без него — список один и тот же;
  - при нажатии в двух вкладках и при нажатии во время ответа модели в чате — подключения независимы, чат и панель агента не задеты;
  - после трёх нажатий подряд `pgrep -fl bgg-mcp` пуст.
- **Реальный прогон сделан** (§9), замер записан комментарием у `BGG_MCP` (§3.3).
- **Логи** — по §4.7 и §5.4.
- **`README.md`** дописывается под текущее состояние: заголовок «TooManyRules — день 16»; раздел про MCP — что подключаем и зачем, четыре шага соединения, две эры протокола, окружение сервера и ключ BGG, сборка сервера (§7), сверка Inspector и таблица «если не подключается»; строка `mcp_client.py` в «Структуре кода» и граф зависимостей; в «Запуске локально» — необязательный шаг про сборку сервера; спецификация дня 16 в списке документов.
- Замороженный `src/app_week1.py` не трогается.
- В конце дня — коммит и тег `day16`.

## 11. Критерии приёмки

- В `src/requirements.txt` добавлена `mcp>=2.2,<3`; `./run.sh` ставит её сам.
- Новый модуль `src/mcp_client.py`: единственное место импорта SDK `mcp`, лист графа, без Gradio и без знаний о BoardGameGeek; типы и функции §4.2-4.5; публичный API синхронный; состояния между вызовами нет.

## 12. Что сознательно НЕ делаем на этом шаге

- **Не вызываем инструменты** (`tools/call`) — ни кнопкой, ни из REPL, ни «для проверки ключа». Ключ BGG сегодня ничем не проверяется.
- **Не подключаем MCP к агенту**: список инструментов не уходит в запрос, нет function calling, модель не выбирает инструмент, `agent.py` не меняется. Как инструменты попадут в запрос и кто решает их вызвать — задание следующих дней.
- **Не запрашиваем ресурсы и промпты сервера** (`resources/list`, `prompts/list`) и не подписываемся на уведомления: возможности сервера только называются.
- **Не держим постоянного соединения**: ни сессии на процесс, ни пула, ни фонового потока с циклом событий. Каждое нажатие — полное подключение и закрытие.
- **Не храним результат**: ни на диске, ни в памяти процесса между нажатиями, ни в агенте, ни в файле сессии; нет кэша списка, кэш SDK не настраивается.
- **Не подключаемся при старте** приложения и не проверяем заранее, собран ли сервер: приложение поднимается без него.
- **Не делаем выбора сервера и редактора их конфигурации** в интерфейсе: сервер один, его описание — константа `presets.py`, замена командной строки — переменная окружения. Не читаем `mcp.json` / `claude_desktop_config.json`.
- **Не используем Docker** — ни как способ запуска, ни как запасной вариант: сервер — собранный бинарник (§2.2).
- **Не поднимаем свой MCP-сервер**, не используем HTTP-режим bgg-mcp, не подключаем удалённые серверы и Smithery, не делаем OAuth.
- **Не закрепляем версию протокола и режим согласования** (`mode`), не задаём `client_info` и отдельные таймауты запросов — работают значения SDK по умолчанию и общий потолок `MCP_TIMEOUT_S`.
- **Не перехватываем stderr сервера**: он идёт в терминал приложения как есть, панель на него ссылается.
- **Не оцениваем кодом «правильность» списка**: нет констант с ожидаемыми именами и числом, нет подсветки, нет сравнения с README сервера — сверяет человек (§9). Аннотации инструментов не интерпретируются.
- **Не переводим и не сокращаем описания инструментов** — они показываются так, как их прислал сервер.
- **Не передаём серверу `BGG_COOKIE`** и никаких переменных, кроме перечисленных в `BGG_MCP.env_keys`.
- **Не ставим Go из приложения** и не собираем сервер скриптом проекта: сборка — ручная, по README.
- **Не пишем отдельного документа проверки**: формат дня — видео + код; факты прогона — в замере.
- Не трогаем агента, формат файла сессии, `_view()` и замороженный `app_week1.py`; не пишем тестов и линтера.

Не расширяй объём дня сверх нового модуля из §4, секции `presets.py` из §3, блока и перекладки аккордеонов из §5, зависимости и README из §8.
