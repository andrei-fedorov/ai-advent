# TooManyRules — спецификация дня 22

Тема: первый RAG-запрос. Индекс правил дня 21 впервые работает на ассистента: перед ответом агент ищет в нём куски, ближайшие к вопросу игрока (нарезка «по структуре»), прикладывает их к вопросу выдержками со ссылками на документ, раздел и страницу и только потом зовёт модель. У агента два режима — с RAG и без, переключатель в чате. Сравнение режимов на 10 контрольных вопросах с ожиданиями и источниками делается двумя способами: программой из терминала (голый агент, два режима на каждый вопрос, отчёт) и вручную в приложении (полный ассистент). Качество ответов оценивает автор, код его не оценивает.

## 1. Задание челленджа (день 22)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_22.txt`. Комментариев организатора к дню 22 на момент написания нет.

Ключевое из задания: реализовать **цепочку «вопрос → поиск релевантных кусков → объединение с вопросом → запрос к LLM»** и **сравнить ответ модели без RAG и с RAG**. Усиление: **мини-набор из 10 контрольных вопросов** по своей базе; для каждого зафиксировать **ожидание** (что должно быть в ответе) и **какие источники должны быть использованы**. Результат — **агент с двумя режимами (с RAG / без RAG), 10 контрольных вопросов и сравнение качества**; формат сдачи — **видео + код**.

Сравнение — часть результата задания, поэтому кроме спецификации есть **документ сравнения** `docs/TooManyRules — День 22 сравнение ответов с RAG и без.md` (правило дней 10 и 21): числа и дословные ответы — по реальному прогону, оценку качества и выводы пишет автор (§11).

День 22 опирается на индекс дня 21 (`src/data/rag/index.sqlite3`, `embedder.py`) и на агента недель 2-4. Правила прошлых дней в силе:

- **LLM API вызывается только в `agent.py`** — программа сравнения тоже ходит к модели только через агента;
- **`sentence_transformers` импортируется только в `embedder.py`**, `pymupdf` — только в `rag_index.py`;
- **всё «про настолки» — в `presets.py`**: инструкция к выдержкам, контрольные вопросы, параметры поиска. Модули поиска про Too Many Bones не знают;
- **агент не знает, откуда берутся выдержки**: поиск приходит к нему через протокол, как инструменты через `ToolBox` (день 17);
- **код не оценивает качество ответов** и не называет «лучший» режим;
- **на экране — текущий день, прошлые свёрнуты**.

## 2. Что делаем конкретно для TooManyRules

### 2.1. Ход в режиме RAG

```
вопрос игрока
  1. служебные работы хода       свёртка, страж, разбор памяти, роутер, трекер — как на днях 9-15, по чистому вопросу
  2. поиск по индексу правил     вектор вопроса (query:) → близость со всеми кусками structural/ru → 5 ближайших
  3. каталог инструментов MCP    как на дне 17, если включены
  4. сборка запроса              системный промпт, блоки, история — как раньше;
                                 последнее сообщение = инструкция + выдержки [1]…[5] со ссылками + вопрос
  5. вызов модели                цикл раундов дня 17
  6. в историю                   только вопрос игрока и ответ — без выдержек
```

Поиск — работа кода, а не решение модели: в режиме RAG он идёт на **каждом** ходе, до вызова модели, как требует цепочка задания. Это не инструмент MCP и не служебный вызов LLM: модель не решает, искать ли, и не пишет запрос поиска. Вызовов LLM API в ходе RAG не добавляет — только токены выдержек в основном запросе.

### 2.2. Поиск: `structural`, русский, 5 ближайших, без порога

- **Стратегия** — `structural` (§1.1); **язык кусков** — `ru`: другого в индексе пока нет. Вопрос на английском ищется среди тех же русских кусков — модель многоязычная, одно пространство векторов (день 21, §2.6); определения языка вопроса нет (§19).
- **Запрос поиска — вопрос игрока как есть**: без истории, переписывания и расширения. Уточняющий вопрос («а если их двое?») найдёт плохо — это известное ограничение дня, оно видно в выдаче.
- **5 ближайших кусков** (`RAG_TOP_K`) перебором, как `--probe` дня 21: скалярное произведение нормированных векторов со всеми кусками стратегии и языка. Кусков — 190, поиск — доли миллисекунды, вектор вопроса — 0,01-0,4 с.
- **Порога близости нет.** У e5 близость лежит в узком коридоре: на предварительной проверке (§2.9) нерелевантный первый кусок вопроса вне корпуса набрал 0,828, а нужный кусок английского вопроса — 0,785. Порог, отрезающий первое, отрезал бы и второе. Выдача всегда полная; что из неё не относится к вопросу, решает модель по инструкции (§2.4).
- **Top-5 — стартовое значение, не подгонка под контрольные вопросы.** Предварительная проверка показала, что при 5 часть ожидаемых источников остаётся за бортом (К5, К6, К8, К9), а при 8 почти все попадают. Менять число — решение автора после прогона, с записью в замер; контрольный набор для оценки, а не для подбора параметров.

### 2.3. Куда встают выдержки: в сообщение с вопросом

Выдержки и инструкция к ним — **часть последнего сообщения `user` запроса**, перед текстом вопроса, а не ещё один `system`-блок за системным промптом:

1. **Так устроена цепочка задания** — «объединение с вопросом»: выдержки подобраны к этому вопросу и уходят вместе с ним.
2. **Текст документов — данные, а не указания разработчика.** `system` в проекте — голос разработчика (системный промпт, блоки инвариантов, профиля, памяти, задачи); выдержки из PDF туда не поднимаются.
3. **Изменчивое — в конец.** Выдержки меняются с каждым вопросом. Среди блоков сразу за системным промптом они сбивали бы кэшируемый префикс DeepSeek (кэш работает по совпадающему началу запроса) для всей истории на каждом ходе; в конце запроса префикс «системный промпт + блоки + история» остаётся прежним. Попадания в кэш видны в полях кэша «Последнего вызова» (день 8).
4. **История остаётся чистой.** В стек, файл сессии, checkpoint'ы и ветки идёт только вопрос игрока — правило дня 17 «в историю — только вопрос и финальный текст». Следующий ход старые выдержки не несёт: уточняющий вопрос видит прошлый ответ со ссылками, но не прошлые выдержки.
5. **Служебные работы выдержек не видят**: свёртка, страж, разбор памяти, роутер и трекер получают чистый вопрос (иначе разбор памяти записал бы правила из выдержек в рабочую память как «решения игрока»).

Вид последнего сообщения (заголовок и подпись вопроса — константы `agent.py`, инструкция — из `presets.py`, подписи выдержек — из метаданных кусков):

```
Выдержки из документов — найдено поиском по вопросу: 5

<инструкция RAG_INSTRUCTION, §2.4>

[1] Правила игры · Встречи · стр. 7
Встречи

Найдите карты роковых встреч, относящиеся к выбранному тирану (1–3 синие карты …

[2] Правила игры · • Колода встреч открытая: мне видны название и цвет следующей карты встречи, это нормально? · стр. 29
…

[5] Правила игры · Типы карт встреч · часть 1/2 · стр. 9
…

Вопрос:
Как собрать колоду встреч перед партией?
```

Близость в запрос не уходит — модели она не нужна и сбивала бы её к «первому месту»; она видна в панели, логе и отчёте. Поиск не удался или ничего не нашёл — последнее сообщение остаётся чистым вопросом, как без RAG, а сбой виден в панели и логе (§6.2).

### 2.4. Инструкция к выдержкам и ссылки на источник

Инструкция — `presets.RAG_INSTRUCTION`, черновик (правки по прогону — строкой в комментарии у константы, правило описаний инструментов дня 17):

```
Ниже — выдержки из русских правил базовой игры Too Many Bones (книга правил,
лист «Навыки злодеев и условия встреч», «Путеводитель гирлока»), найденные
поиском по вопросу игрока. Поиск ошибается: часть выдержек может не
относиться к вопросу, а нужного правила среди них может не оказаться.

- Отвечай по выдержкам. После каждого правила, взятого из них, укажи источник
  в скобках: документ, раздел и страница — например, (Правила игры,
  «Встречи», стр. 7). Номера выдержек игрок не видит — не ссылайся на них.
- Если в выдержках ответа нет или он неполный, прямо скажи об этом. То, что
  добавляешь из общих знаний об игре, помечай «(не из текста правил)».
- Выдержки, которые к вопросу не относятся, не пересказывай.
```

Системные промпты пресетов **не меняются**: режимы отличаются только последним сообщением, и сравнение идёт при одном и том же системном промпте. «Отвечай на том языке, на котором задан вопрос» из системного промпта остаётся в силе — английский вопрос получает английский ответ по русским выдержкам (К9).

Ссылку пишет модель — код её не проверяет (§19). **Ссылка наследует имя раздела куска**, а у части разделов книги заголовок в PDF — картинка (день 21, §2.9): правила трофеев лежат в разделе «Поражение в бою», врезка «Встречи — это…» — в «4. Фаза восстановления» 2/2, начало раздела «Злодеи» — в «8. Область трофеев». Страница в такой ссылке верна, имя раздела — нет. Это видно на К8 и записывается в документ сравнения, а не чинится в день 22.

### 2.5. Два режима агента

- **Переключатель «RAG: выдержки из правил в запросе»** — состояние агента, но не диалога (правило переключателей дней 11-17): на диск не едет, в checkpoint не входит; у нового, восстановленного агента и у ветки — **включён** (§1.1); сброс диалога его не трогает. Выключенный — поиска нет вовсе (ни загрузки модели, ни вектора вопроса), агент ведёт себя ровно как на дне 20.
- **Инструменты MCP — отдельный переключатель**, режимы RAG его не трогают. Для сравнения выключаются оба раза (§1.1); блок дня 22 напоминает об этом строкой, если инструменты включены.
- Остальное — профиль, инварианты, слои памяти, стратегия, задача — работает в обоих режимах одинаково.

### 2.7. Два прогона сравнения

| | Программа `./run.sh rag-eval` | Приложение, вручную |
| --- | --- | --- |
| Агент | **голый**: пресет `RAG_EVAL_PRESET` («Базовый»), только системный промпт — без хранилища, стратегий кроме «Всей истории», памяти, профиля, инвариантов, задачи и инструментов | **полный ассистент** как у игрока: пресет «Базовый», «Вся история», профиль, инварианты и слои памяти по умолчанию (свой каталог данных, §16) |

## 3. Новый `src/rag_search.py`

Поиск по индексу правил. Имя проверено: нет ни в стандартной библиотеке, ни среди установленных пакетов. Про Too Many Bones не знает: путь, стратегия, язык и число кусков — параметрами. LLM не вызывает; `sentence_transformers` не импортирует — вектор вопроса считает `embedder.py`.

### 3.1. Что внутри

- **Из `rag_index.py` переезжают** `SCHEMA_VERSION`, `TABLES`, `IndexFileError` и `check_index()`: версию схемы и проверку файла знают и тот, кто пишет индекс, и тот, кто его читает, — место им в модуле, который берут оба. Схема (DDL) и запись остаются в `rag_index.py`.
- **`Hit`** — кусок выдачи: `chunk_id`, `doc`, `lang`, `title`, `section`, `part`, `page_from`, `page_to`, `text`, `tokens` (токенизатором модели эмбеддингов, из индекса), `score`.
- **`RulesIndex(path, strategy, lang, top_k, allow_download=False)`**, один на процесс:
  - `name` — строка для лога: «structural/ru, top-5 · src/data/rag/index.sqlite3»;
  - `info()` — без модели: есть ли индекс, когда собран, какой моделью, сколько кусков стратегии и языка и всего; `{"ok", "error", ...}`. Для строки лога при старте и шапки блока дня 22;
  - `nearest(question, strategy=None, lang=None, top=None) -> list[Hit]` — ближайшие куски; бросает `RagError` с понятным текстом. Её берёт `--probe` дня 21 (обе стратегии, свой `top`);
  - `search(question) -> dict` — **протокол `Retriever` агента** (§6.1): те же ближайшие куски со стратегией, языком и `top_k` экземпляра, словарём, **без исключений**: `{"ok", "error", "elapsed", "load_s", "embed_s", "total", "hits": [словари Hit]}`.
- **`sources_found(hits, sources) -> list[int | None]`** — чистая функция: для каждого ожидаемого источника («документ, раздел, страница», §2.6) — место в выдаче или `None`. Её берут приложение (блок дня 22) и программа сравнения — одно определение «найден».

### 3.2. Загрузка и перечитывание

- **Куски индекса — в памяти процесса целиком** (≈300 строк, ≈1 МБ векторов): строки и матрица `float32`, фильтр по стратегии и языку — маской. Читается `mode=ro` — приложение индекс не меняет.
- **Индекс перечитывается, если файл сменился**: перед каждым поиском — `stat()` пути (время изменения, размер, inode). `./run.sh index` ставит новый файл через `os.replace()`, поэтому пересборка во время работы приложения подхватывается следующим вопросом (строка лога «индекс сменился — перечитан»).
- **Модель — та, что записана в `meta` индекса** (правило `--probe`): векторы разных моделей несравнимы. Расходится с `presets.RAG_EMBED_MODEL` — предупреждение в лог один раз.
- **Модель загружается при первом поиске**, не при создании: старт приложения не ждёт `torch`. Загрузку и её время видно в ответе `search()` (`load_s`).
- **`allow_download=False` у приложения и программы сравнения**: модели нет в кэше — сбой «модели … нет в кэше Hugging Face — сначала ./run.sh index (скачает ≈1,1 ГБ)», а не скачивание гигабайта посреди хода игрока. Индекс без модели в кэше бывает, только если кэш почистили.
- **Под замком**: перечитывание, загрузка модели и вектор вопроса — Gradio выполняет обработчики вкладок параллельно, а модель одна на процесс.

### 3.3. Сбои

`search()` не бросает; `ok=False` и текст — для лога и панели:

| Что | Текст (примерно) |
| --- | --- |
| файла нет | «индекса нет: src/data/rag/index.sqlite3 — сначала ./run.sh index» |
| чужой или битый файл | текст `IndexFileError` дня 21 с путём |
| нет кусков стратегии и языка | «в индексе нет кусков structural/ru» |
| модели нет в кэше | §3.2 |
| прочее | «поиск: <исключение>» — с трассировкой в лог |

## 6. Что меняется в `src/agent.py`

### 6.1. Зависимость `Retriever`

Новый протокол рядом с `ToolBox`, структурный — `rag_search.py` его не импортирует, агент не импортирует `rag_search.py`:

```python
class Retriever(Protocol):
    @property
    def name(self) -> str: ...        # для лога
    # {"ok", "error", "elapsed", "load_s", "embed_s", "total",
    #  "hits": [{"chunk_id", "doc", "title", "section", "part",
    #            "page_from", "page_to", "text", "tokens", "score"}]}
    def search(self, question: str) -> dict: ...
```

Конструктор — два параметра в конце, необязательные: `retriever: Retriever | None = None` (один на процесс, общий для агентов, как `ToolBox`) и `rag_instruction: str = ""` (настоящую передаёт `app.py` из `presets.py`, как лимиты инструментов). `retriever=None` — агент ведёт себя ровно как на дне 20. `fork()` передаёт ветке те же.

- `rag_in_request` (свойство) и **`set_rag_in_request(enabled) -> bool`** под `@_locked`, со строкой лога. Умолчание — включён, если есть `retriever` (§2.5).

### 6.2. Поиск в ходе

`_run_rag(user_message) -> RagRecord | None` — в `ask()` **после трекера и до каталога инструментов** (§2.1). Выключен или `retriever` нет — `None`, поиска нет. Иначе — `retriever.search()`, и:

- удачно и выдача не пуста — `hits` идут в сборку запроса;
- сбой или пустая выдача — **ход не отменяется**: запрос уходит без выдержек, в лог — WARNING, в ответ — запись со сбоем (правило каталога инструментов дня 17).

`RagRecord` (новый dataclass): `enabled`, `ok`, `error`, `elapsed`, `load_s`, `total`, `hits` (словари, как пришли), `message` (последнее сообщение запроса целиком, как ушло в модель; `""` — ушло без выдержек), `tokens` (оценка корзины `rag`).

### 6.3. Сборка запроса: `_with_rag()`

`_build_messages(..., rag_hits=None)` последним шагом зовёт **`_with_rag(messages, hits)`** — единственное место, где выдержки попадают в запрос: содержимое последнего сообщения заменяется на `часть RAG + вопрос` по виду §2.3. Порядок вызовов блоков не меняется: блоки встают за системный промпт, `_with_rag()` трогает только последнее сообщение.

- Подписи — константы агента: `RAG_HEADER` («Выдержки из документов»), `RAG_QUESTION_LABEL` («Вопрос:»); подпись выдержки — `[N] {title} · {section}[ · часть {part}] · стр. {a}[–{b}]`, затем текст куска. Про Too Many Bones агент не знает — всё, что про игру, в `rag_instruction` и в метаданных кусков.
- **Панель до вопроса выдержек не знает** — чистые методы не ищут (поиск грузит модель): предпросмотр запроса и «Бюджет контекста» — без части RAG, со строкой «выдержки подбираются по вопросу — до вопроса оценки нет». Факт хода — в «Последнем вызове» и блоке дня 22.
- **База сравнения «вся история»** в `ask()` собирается с той же частью RAG — экономия стратегии по-прежнему говорит только о стратегии (правило дня 11).

### 6.4. Счёт токенов: корзина `rag`

`_count_messages(messages, tools_json="", rag_text="")`: часть RAG приходит параметром — как схемы инструментов с дня 17, а не угадыванием по содержимому. Корзина `rag` — часть RAG, корзина `question` — ровно текст игрока; в сумме — всё последнее сообщение. `ask()` и панель ходят сюда же. Калибровка сравнивает оценку первого раунда с `prompt_tokens` — оба с выдержками.

### 6.5. Ответ, состояние, логи

- `AgentReply.rag: RagRecord | None` — в том числе у неудачного хода, если поиск успел пройти (правило раундов дня 17).
- `debug_state()["rag"]`: `available`, `enabled`, `name`, `last` (запись последнего хода).
- Лог — строка на ход, паттерн проекта:

```

[#3 Базовый · s003] RAG: выключен — поиска нет
```

Строка бюджета (`_log_budget`) получает корзину RAG.

## 8. Новая программа `src/rag_eval.py`

Прогон контрольных вопросов в двух режимах — отдельная программа, как `rag_index.py`: запускает человек, работает до конца. Импортирует `presets.py`, `agent.py`, `rag_search.py`; приложение её не импортирует. К модели ходит только через `Agent.ask()`. Сессий на диск не пишет (агенты без хранилища) — данные автора не трогает.

### 8.1. Командная строка

```
./run.sh rag-eval                    все 10 вопросов, пресет RAG_EVAL_PRESET, индекс presets.RAG_INDEX_DB
./run.sh rag-eval --only К1,К8       часть вопросов (номера из RAG_CONTROL_QUESTIONS)
./run.sh rag-eval --preset "Флагман + thinking"
./run.sh rag-eval --db <путь>        другой индекс
./run.sh rag-eval --out <файл.md>    куда писать отчёт (по умолчанию src/data/rag/eval/<дата-время>.md)
```

Ключ DeepSeek нужен (`src/.env`, как у приложения).

### 8.2. Прогон

1. Индекс — `RulesIndex(db, RAG_SEARCH_STRATEGY, RAG_SEARCH_LANG, RAG_TOP_K)`; `info()` не удался — отказ до первого вызова модели (код 2): сравнение без индекса бессмысленно.
2. На каждый вопрос — **два свежих агента одного конфига** (`Agent(PRESETS[preset], session_id="eval-К1-без", retriever=…, rag_instruction=RAG_INSTRUCTION)`): у первого `set_rag_in_request(False)`, у второго — включён. Всё остальное — `None` (§2.7). Порядок — без RAG, затем с RAG; по очереди, без параллельности.
3. Сбой хода — ошибка в отчёт вместо ответа, прогон идёт дальше. Ctrl+C — отчёт по пройденным вопросам с пометкой «прервано после К5», код 130.
4. Логи: строки агента (как в приложении) и свои — stdout, префикс `[RAG-прогон]`: вопрос, режим, время, токены, стоимость, ожидаемые источники в выдаче.

### 8.3. Отчёт

Markdown — готовый к переносу в §3 документа сравнения:

1. **Условия**: дата и время, пресет (модель, thinking), индекс (путь, когда собран, модель эмбеддингов, стратегия, язык, top-k), что инструментов, памяти и профиля у агентов нет.
2. **Сводная таблица**: № · ожидаемые источники в выдаче («2 из 2: места 1, 3» / «0 из 2» / «—») · `prompt_tokens` без → с · `completion_tokens` без → с · время без → с · стоимость без → с; строка итогов.
3. **По вопросу**: вопрос, что проверяет, ожидание, ожидаемые источники с местом в выдаче; таблица выдачи (место, близость, документ, раздел, часть, страницы, токены); **ответ без RAG** и **ответ с RAG** — дословно, цитатой, с метриками хода (время, токены, стоимость, `finish_reason`; у RAG — время поиска и токены выдержек).

Ни оценок, ни «✓» у ответов: «найден» относится только к выдаче. Раздел оценки в отчёте не заводится — он в документе сравнения и за автором.

## 19. Что сознательно НЕ делаем на этом шаге

- **Не делаем RAG инструментом**: ни MCP-сервера поиска по правилам, ни function calling «найди в правилах» — модель не решает, искать ли. Поиск — код, на каждом ходе в режиме RAG.

- **Не проверяем ссылки кодом**: есть ли названная страница среди выдержек, верен ли раздел — суждение автора.
