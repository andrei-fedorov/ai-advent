## 1. Задание челленджа (день 6)

Текст задания — платный контент челленджа, поэтому здесь не копируется. См. локально (не в git-репозитории): `tasks/AI Advent Challenge_06.txt`.

Ключевое из задания и уточнений организатора в чате: агент должен быть **отдельной сущностью, а не одним вызовом API**; логика запроса/ответа инкапсулирована в агенте; агент **сам** складывает стек сообщений и отправляет его в LLM; всё, что делалось на неделе 1 (системный промпт, температура, `max_tokens`, модель, режим рассуждения, подсчёт токенов), становится **конфигом** агента; в одном инстансе приложения должно быть можно поднять много агентов с разными конфигами.

Общие решения по неделе 2 (заморозка недели 1, отказ от вкладок, раскладка модулей, конвенции) описаны в `docs/TooManyRules — Неделя 2 архитектура.md` — этот документ их не повторяет и опирается на них.

## 2. Что делаем конкретно для TooManyRules

Три части, в этом порядке:

1. **Заморозка недели 1.** `src/app.py` переименовывается в `src/app_week1.py` без изменения кода (единственное допустимое изменение — комментарий в шапке о том, что это замороженный артефакт недели 1). `run.sh` получает необязательный аргумент: `./run.sh` запускает текущее приложение, `./run.sh week1` — артефакт.
2. **Агент.** Новый модуль `src/agent.py` — «коробка», внутри которой живёт вся работа с LLM: конфиг, стек сообщений, вызов API, замер времени, подсчёт токенов и стоимости, логирование, обработка ошибок. Наружу агент отдаёт только результат (`AgentReply`) и своё состояние для дебага. Конфиги агентов проекта — в `src/presets.py`.
3. **Новое приложение.** Новый `src/app.py` — одноэкранный интерфейс без вкладок: чат слева, дебаг-панель справа. Работает **только** через агента.

Приложение недели 2 начинается с чистого файла, а не правкой старого: из недели 1 переносится только то, что перечислено в разделе 3 архитектурного документа.

## 3. Сущность агента: `src/agent.py`

Модуль **не знает ничего про Too Many Bones и про Gradio** — ни промптов проекта, ни импортов из `app.py`/`presets.py`. Направление зависимости одно: `app.py` → `presets.py` → `agent.py`.

Контракт (сигнатуры фиксированы, детали реализации — на усмотрение исполнителя):

```python
@dataclass(frozen=True)
class AgentConfig:
    name: str                       # имя агента, попадает в логи и дебаг-панель
    system_prompt: str
    model: str = DEEPSEEK_MODEL     # дефолт — deepseek-v4-flash
    thinking: bool = False          # → extra_body={"thinking": {"type": "enabled"|"disabled"}}
    temperature: float | None = None
    top_p: float | None = None
    max_tokens: int | None = None
    stop: list[str] | None = None
    keep_history: bool = True       # ведёт ли агент стек сообщений между вызовами
    base_url: str = DEEPSEEK_BASE_URL   # задел на неделю 6 (локальная модель), сейчас дефолт

@dataclass(frozen=True)
class AgentReply:
    ok: bool
    text: str
    error: str | None
    finish_reason: str | None
    elapsed: float                  # секунды, замер вокруг вызова API
    prompt_tokens: int | None
    completion_tokens: int | None
    total_tokens: int | None
    cost_usd: float | None
    reasoning: str | None           # reasoning_content, если модель его вернула
    model: str
    agent_name: str

class HistoryStore(Protocol):
    """Точка подключения дня 7. На дне 6 реализаций нет."""
    def load(self, session_id: str) -> list[dict]: ...
    def save(self, session_id: str, messages: list[dict]) -> None: ...

class Agent:
    def __init__(
        self,
        config: AgentConfig,
        session_id: str = "default",
        store: HistoryStore | None = None,   # None → стек только в памяти процесса
    ) -> None: ...
    def ask(self, user_message: str) -> AgentReply: ...
    def reset(self) -> None: ...
    @property
    def history(self) -> list[dict]: ...      # копия стека, только user/assistant
    @property
    def number(self) -> int: ...              # порядковый номер агента в процессе (с 1)
    def debug_state(self) -> dict: ...        # конфиг + стек + метрики последнего вызова + статистика

# Уровень модуля: счётчики процесса и реестр созданных агентов
def process_stats() -> dict: ...
def agents() -> list[Agent]: ...              # все агенты процесса в порядке создания
def agent_by_number(number: int) -> Agent | None: ...
def delete_agent(number: int) -> bool: ...    # убрать агента из реестра
```

Требования к поведению:

- **Стек сообщений ведёт агент.** Системный промпт хранится в конфиге и подставляется первым сообщением при каждом вызове, но в самом стеке не лежит. Сборка `[system] + history + [новый user]` выполняется в **одном** приватном методе — это точка, куда на дне 8 встанет сжатие контекста. При успехе в стек дописывается пара «вопрос пользователя / ответ ассистента». Никакого сжатия, обрезания или лимита истории сейчас нет — в LLM уходит вся переписка целиком.
- **При ошибке стек не меняется** — ни сообщение пользователя, ни ответ не дописываются, чтобы повтор не задваивал историю.
- **`reasoning_content` в стек не попадает** — в историю кладётся только `content` ассистента (API не принимает reasoning обратно в контекст), сам reasoning отдаётся в `AgentReply.reasoning` для дебага.
- **`ask()` не бросает исключений** на ошибках API и на отсутствующем ключе — возвращает `AgentReply(ok=False, error=...)` с понятным текстом (для отсутствующего ключа — про `DEEPSEEK_API_KEY` и `.env`, как в неделе 1).
- **Параметры запроса берутся только из конфига.** У `ask()` нет аргументов, переопределяющих модель/температуру/лимиты: другой набор параметров — это другой агент, порождаемый через `dataclasses.replace(config, ...)`. Опциональные поля (`temperature`, `top_p`, `max_tokens`, `stop`) не передаются в API, если равны `None`.
- **Невалидная комбинация отсекается сразу:** `AgentConfig.__post_init__` бросает `ValueError`, если `thinking=True` вместе с заданными `temperature`/`top_p` — DeepSeek не поддерживает их в режиме рассуждения (ограничение уже описано в спецификации дня 5).
- **Хранилище — необязательная зависимость.** Если `store` передан, агент загружает историю на старте и сохраняет её после каждого успешного вызова; при `store=None` работает целиком в памяти. На дне 6 реализаций `HistoryStore` в проекте нет и `store` всегда `None` — протокол объявляется, чтобы день 7 подключился без переписывания агента.
- **Счётчики агента за время жизни:** число вызовов, число ошибок, суммарные `prompt`/`completion`/`total` токены и суммарная стоимость. `reset()` очищает **только стек сообщений**, счётчики не сбрасывает.
- **Счётчики процесса и реестр агентов:** состояние модульного уровня в `agent.py` — сколько агентов создано с момента старта приложения, сколько всего вызовов, токенов и денег, плюс список созданных агентов в порядке создания и доступ к агенту по порядковому номеру. Номер выдаётся при создании; по этому списку строится переключатель агентов в дебаг-панели. Агента можно убрать из реестра (`delete_agent`) — тогда живых агентов становится меньше, чем созданных: `agents_created` считает созданных за время работы и назад не откатывается, а число живых (`agents_alive`) считается по длине реестра. Номера удалённых агентов не переиспользуются — иначе в логах два разных агента выглядели бы одинаково. Это наглядный ответ на «один инстанс приложения — много агентов»: не только счётчик, но и сами инстансы, между которыми можно переключаться. Счётчики и реестр живут под одним `threading.Lock`: Gradio обрабатывает запросы в пуле потоков.
- **Стоимость** считается по таблице off-peak цен DeepSeek за 1M токенов (переносится из недели 1). При `thinking=on` `completion_tokens` включает токены рассуждения — отдельного учёта не требуется.
- **Логирование** каждого вызова в stdout тем же паттерном, что на неделе 1: номер и имя агента (`[#3 Базовый]` — с несколькими агентами одного пресета иначе не понять, кто отвечал), модель, `thinking on/off`, `finish_reason`, время, токены, стоимость, длина и текст ответа.

## 5. Технические требования

- Новых зависимостей нет: тот же `requirements.txt` (gradio, openai, python-dotenv), тот же запуск из `src/`, тот же `DEEPSEEK_API_KEY` из `src/.env`.
- **Никаких вкладок.** Один экран: слева чат (`gr.Chatbot` в формате сообщений — в Gradio 6 он единственный, аргумент `type="messages"` там удалён; поле ввода, кнопки «Отправить», «Сбросить диалог», «Новый агент» и «Удалить агент»), справа дебаг-панель. Выпадающий список пресетов — над чатом.
- **В `app.py` и `presets.py` нет ни одного `client.chat.completions.create` и не создаётся `OpenAI(...)`** — все обращения к API происходят внутри `agent.py`.
- **Интерфейс — только вид на стек агента.** Содержимое чата на каждом шаге рендерится из `agent.history`; Gradio не накапливает собственную копию переписки. Это прямая демонстрация того, что историей владеет агент, и это же понадобится на дне 7, когда история будет приходить из файла.
- **Активный агент — на сессию.** Экземпляр активного агента хранится в `gr.State` (у каждой открытой вкладки браузера свой). Глобального изменяемого «текущего агента» в модуле быть не должно. При этом сами созданные агенты лежат в реестре процесса (см. §3) — иначе предыдущий агент после смены пресета просто теряется, и «много агентов в одном процессе» подтверждается только счётчиком. Реестр держит агентов живыми до конца процесса: это осознанная цена демонстрации, а не продовый жизненный цикл.
- Смена пресета **порождает нового агента** с новым конфигом и пустым стеком, чат очищается, дебаг-панель и счётчик агентов процесса обновляются сразу — по событию **`select`** (выбор пункта человеком). Ни `change`, ни `input` не годятся: значение списка пресетов синхронизируется программно при переключении агента, а `change` срабатывает и на программное обновление; `input` же в Gradio 6.26 приходит на один выбор дважды. И то и другое рождает лишних агентов — проверено, оба списка слушают именно `select`. В тексте под списком прямо написать, что смена пресета начинает новый диалог.
- Кнопка **«Новый агент»** поднимает ещё один экземпляр с текущим пресетом. Сменой пресета двух агентов с одинаковым конфигом не получить, а именно два одинаковых агента с разными стеками нагляднее всего показывают, что инстансов несколько и переписка у каждого своя.
- Кнопка **«Удалить агент»** убирает активного агента из реестра процесса: он пропадает из переключателя, а интерфейс переходит на последнего из оставшихся (если реестр опустел — поднимает нового с текущим пресетом, экрана без активного агента не бывает). Счётчики процесса при этом **не откатываются**: потраченные токены и деньги остались потраченными, а «Агентов создано» считает созданных за сеанс. Живых агентов панель показывает отдельным числом рядом с ним.
- Удаление — это снятие с учёта, а не гарантированное уничтожение объекта: Python освободит агента, когда на него не останется ссылок (например, если тем же агентом занята другая вкладка браузера, он доживёт до её следующего действия). Такой агент показывается в её переключателе отдельным пунктом с пометкой «удалён», чтобы значение списка не осталось без варианта.
- Дебаг-панель показывает:
  - **выпадающий список агентов процесса** (номер, имя пресета, размер стека) — прямо над стеком сообщений. Выбор агента делает его активным: переключаются чат, стек, конфиг, метрики, счётчики за время жизни и список пресетов, и следующий вопрос уходит выбранному агенту. Список пересобирается на любом событии интерфейса — поллинга и автообновления нет;
  - конфиг текущего агента (`gr.JSON`, из `dataclasses.asdict`);
  - стек сообщений агента (`gr.JSON`) — видно, как он растёт с каждым ходом; номер агента, чьи сообщения показаны, стоит в подписи этого блока и в подписи чата;
  - метрики последнего вызова (`gr.Markdown`): время, `finish_reason`, токены `prompt`/`completion`/`total`, стоимость;
  - накопленное агентом за время жизни: вызовов, ошибок, токенов, стоимость;
  - счётчики процесса: сколько агентов создано в этом инстансе приложения, суммарные вызовы/токены/стоимость;
  - `reasoning_content` последнего вызова — в свёрнутом `gr.Accordion`, только когда он непустой.
- Ошибки (нет ключа, сбой API) показываются отдельной строкой статуса под чатом и в блоке метрик; стек сообщений при этом не меняется.
- `README.md` переписывается под текущее состояние: что делает приложение сейчас, плюс короткий раздел «неделя 1 — `app_week1.py`, запуск `./run.sh week1`».
- В конце дня — коммит и тег `day06`.

## 6. Что должно быть видно в видео

1. Запуск `./run.sh`: один экран, дебаг-панель с конфигом агента до первого вопроса.
2. Первый вопрос по правилам → ответ, метрики вызова (время, токены, стоимость).
3. **Второй вопрос, ссылающийся на первый ответ** («а если …?») → корректный ответ с учётом контекста, в дебаг-панели виден стек из 4+ сообщений. Это и есть демонстрация, что стек ведёт агент.
4. Кнопка «Сбросить диалог» → стек пуст, счётчики за время жизни агента сохранились.
5. Смена пресета (например, «Строгий JSON» или «Флагман + thinking») → в дебаг-панели новый конфиг, тот же вопрос даёт заметно другое поведение, счётчик агентов процесса вырос.
6. **«Новый агент» → вопрос второму агенту → переключение списком обратно на #1:** в чате и стеке снова первый диалог со своей историей, у второго агента — своя; счётчик агентов при переключении не растёт. Это и есть видимое доказательство, что инстансов несколько и живут они одновременно.
7. **«Удалить агент»** → агент пропал из списка, интерфейс переключился на оставшегося, «Агентов создано» не изменилось, а живых стало меньше.
8. `./run.sh week1` — вкладки недели 1 живы и работают как раньше.
9. Короткий устный вывод: агент — отдельная сущность, вся логика запроса/ответа и стек сообщений внутри неё, интерфейс — только вид; неделя 1 заморожена артефактом.

## 7. Критерии приёмки

- `src/app_week1.py` запускается через `./run.sh week1` и работает как раньше; его код не изменён (кроме комментария в шапке) и не импортируется новым кодом.
- Есть `src/agent.py` с `AgentConfig` / `AgentReply` / `Agent`; внутри агента инкапсулированы конфиг, стек сообщений, вызов API, замер времени, подсчёт токенов и стоимости, логирование и обработка ошибок.
- Новое приложение работает **только** через агента: в `app.py` и `presets.py` нет `chat.completions.create` и создания клиента `OpenAI`.
- Многоходовый диалог работает: второй вопрос отвечает с учётом первого, стек сообщений в дебаг-панели растёт на 2 сообщения за ход.
- `reset()` очищает стек, не сбрасывая накопленные счётчики агента.
- Смена пресета и кнопка «Новый агент» создают новый экземпляр агента в том же процессе; счётчик созданных агентов это подтверждает.
- Выпадающий список в дебаг-панели показывает всех агентов процесса; переключение показывает стек, конфиг и метрики выбранного агента и адресует ему следующий вопрос. Стеки агентов не смешиваются, а само переключение новых агентов не создаёт.
- «Удалить агент» убирает активного агента из списка и переводит интерфейс на оставшегося; счётчики процесса не откатываются, номер удалённого не переиспользуется.
- Ошибка API или отсутствие ключа не роняют интерфейс: показывается понятное сообщение, стек не портится.
- Каждый вызов агента залогирован в stdout (имя агента, модель, thinking, `finish_reason`, время, токены, стоимость, ответ).
- Объявлен протокол `HistoryStore`, агент принимает `store` и `session_id`; реализаций хранилища на дне 6 нет.

## 8. Что сознательно НЕ делаем на этом шаге
