# AGENTS.md

Правила для AI-агентов (Claude Code, Codex и других), которые работают в этом репозитории. Рядом лежит `CLAUDE.md` — символьная ссылка на этот файл (Claude Code читает `CLAUDE.md`); правится только `AGENTS.md`. В каталоге `week7/` действует ещё и `week7/AGENTS.md` (и так же `week7/CLAUDE.md` → `AGENTS.md`). Импорт `@AGENTS.md` вместо ссылки не годится: проверено 14.10.2026 на Claude Code 2.1.299 — при работе в `week7/` два одинаковых импорта в корне и в `week7/` склеиваются, и корневой `AGENTS.md` не загружается.

Язык репозитория — русский: README, спецификации, промпты, строки интерфейса и комментарии в коде пишутся по-русски. Новые файлы следуют этому же правилу.

## Что это за репозиторий

Проект автора для **AI Advent Challenge** — 7 недель, задание каждый будний день, результат дня — видео и код (тег `dayNN`).

- **Недели 1–6 (дни 1–30) — TooManyRules**, ассистент по правилам настолки Too Many Bones (Chip Theory Games): Gradio-приложение поверх DeepSeek API (SDK `openai` с `base_url` DeepSeek) с памятью, MCP, RAG по правилам и локальной моделью. Код — `src/`.
- **Неделя 7 (дни 31+) — `week7/`**: серия небольших продуктов (ассистент разработчика, AI-ревью PR, поддержка пользователей…), для которых TooManyRules — демо-проект.

Продуктовая ценность вторична по отношению к учебной: каждый день — это демонстрация одного приёма работы с LLM, а не шаг к «лучшему ассистенту».

## Процесс: спецификация → (промпт) → исполнитель

Ключевая особенность проекта (см. §1 спецификации проекта): **код пишет не Claude, а другие AI-ассистенты-исполнители.** Роль Claude — планирование, спецификации по дням и неделям и ревью того, что сделал исполнитель. Цикл дня:

1. Организатор выдаёт задание → оно ложится в `tasks/` (локально, вне git). Иногда рядом лежат комментарии организатора из чата — `tasks/AI Advent Challenge_NN_comments.txt`: спецификация их учитывает и так же не копирует.
2. Claude пишет спецификацию дня: `docs/TooManyRules — День N спецификация.md` (дни 1–30) или `week7/docs/День N спецификация.md` (неделя 7).
3. Если автор просит, Claude пишет `prompts/dayN-prompt.md` — роль-промпт исполнителю: что прочитать, в каком порядке работать, на что обратить внимание. Без просьбы автора промпт не пишется.
4. Исполнитель реализует по спецификации; Claude ревьюит.
5. Коммит + тег `dayNN` (в таблицу челленджа идёт ссылка на тег, а не на `main`). **Агенты сами не коммитят и не ставят теги без прямого разрешения автора** — ни `git commit`, ни `git tag`, ни push; разрешение на один коммит не распространяется на следующие. Закончив работу, агент оставляет изменения в рабочем дереве и сообщает, что готово к коммиту.

**Если ты исполнитель**: реализуй ровно спецификацию дня. Раздел «Что сознательно НЕ делаем на этом шаге» обязателен к соблюдению — он держит объём дня в рамках. Спецификация — живой документ: если по ходу реализации пришлось отступить от неё, отступление записывается в спецификацию, а не остаётся только в коде.

Прежде чем начинать писать код по запросу «сделай день N», уточни, нужна ли спецификация или реализация — по умолчанию в этом репозитории ожидается первое (для Claude).

Правило не абсолютное: автор может прямо попросить Claude написать код (так делались правки дня 6 после ревью). Порядок в этом случае тот же — **сначала документы, потом код**: спецификация дня остаётся живым документом и правится вместе с кодом, а `prompts/dayN-prompt.md`, если он был, уже отработан и не переписывается задним числом.

**README описывает только текущий день.** Делая новый день, замени в `README.md` описание предыдущего дня описанием нового (вводный абзац и раздел «… (день N)»); описания прошлых дней стираются — они живут в своих спецификациях. Кроме текущего дня в README остаются только инструкции по запуску и «Структура кода» — последняя всегда в самом конце. В дни недели 7 текущий день описывает `week7/README.md`, а корневой README ссылается на него (подробно — `week7/AGENTS.md`).

### Формат спецификации дня

Фиксированная структура, которую нужно сохранять у новых дней: задание челленджа → что делаем конкретно → промпты/параметры → технические требования → что должно быть видно в видео → критерии приёмки → **«Что сознательно НЕ делаем на этом шаге»**. Последний раздел обязателен и обязателен к соблюдению исполнителем.

Текст самих заданий — платный контент челленджа. `tasks/`, `theory/` и `.claude/` в `.gitignore`; спецификации **ссылаются** на `tasks/AI Advent Challenge_NN.txt` (номер дня двумя цифрами: `_09`, `_10`), но не копируют его текст. Не переноси содержимое `tasks/` в коммитимые файлы. `theory/` — лекции для автора; для спецификаций и разработки их читать не нужно.

Если сравнение или проверка — часть результата задания (дни 10, 11, 13–15, 21–23, 28, 29), кроме спецификации появляется ещё один документ дня — `… День N сравнение ….md` или `… проверка ….md`. Данные в нём (числа, дословные ответы) заполняются по реальному прогону, выводы и оценку качества пишет автор. Если задание только просит «проверьте», а результат — сам агент или код и формат — видео + код (дни 12, 16, 24, 25, 30, 31), отдельного документа нет: проверка показывается в видео, замеры записываются комментариями в коде.

## Команды

```bash
./run.sh                    # TooManyRules: приложение на http://127.0.0.1:7860
./run.sh <программа> [...]  # программы TooManyRules: week1, faq-watch, index, rag-eval, rag-dialog, local, rag-compare, service, service-load
./week7/run.sh <команда>    # продукты недели 7 — см. week7/AGENTS.md
```

Аргументы, отказы, коды выхода и что каждая программа пишет на диск — `docs/TooManyRules — архитектура кода.md`, раздел «Команды и программы». Python 3.14; у TooManyRules venv, `requirements.txt` и `.env` с `DEEPSEEK_API_KEY` — в `src/`, у недели 7 — свои в `week7/`.

## Общие правила

- **Тестов, линтера и сборки нет.** Проверка изменений — ручная: запустить, прогнать сценарий и посмотреть stdout, куда логируется каждый вызов API (модель, `finish_reason`, время, токены, стоимость). Логи — основной инструмент отладки; новые вызовы логируются тем же паттерном.
- **Код не оценивает качество ответов** и не подсвечивает «лучший» вариант — это суждение автора.
- **Внешний мир — за своим модулем**: одна внешняя библиотека (LLM API, MCP SDK, эмбеддинги, PDF) импортируется в одном модуле.
- **Имя нового модуля** проверяй на совпадение со стандартной библиотекой и установленными пакетами (`profile.py`, `mcp.py` подменили бы чужой модуль всему процессу).
- **Данные, сервисы и окружение автора не трогать**: свои прогоны — со своими каталогами данных, портами, `--db`, `--out`; LM Studio и серверы автора не останавливать и не перезапускать без вопроса. Конкретные правила для `src/` — архитектура кода, раздел «Свои прогоны»; для недели 7 — `week7/AGENTS.md`.
- **Абстракции под будущие дни заранее не пишутся**: задание следующего дня неизвестно.
