# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Язык репозитория — русский: README, спецификации, промпты, строки интерфейса и комментарии в коде пишутся по-русски. Новые файлы следуют этому же правилу.

## Что это за репозиторий

TooManyRules — ассистент по правилам настолки Too Many Bones (Chip Theory Games), который пишется как проект для **AI Advent Challenge** (7 недель, задание каждый будний день). Приложение — Gradio-интерфейс поверх DeepSeek API (через SDK `openai` с `base_url` DeepSeek). RAG сознательно не делается до недели 5: модель отвечает из общих знаний, чтобы позже наглядно сравнить.

Продуктовая ценность вторична по отношению к учебной: каждый день — это демонстрация одного приёма работы с LLM, а не шаг к «лучшему ассистенту».

## Процесс: спецификация → (промпт) → исполнитель

Ключевая особенность проекта (см. §1 общей спецификации): **код пишется не Claude, а другими, более простыми AI-ассистентами.** Роль Claude здесь — планирование, спецификации по дням/неделям и ревью того, что сделал исполнитель. Отсюда цикл дня:

1. Организатор выдаёт задание → оно ложится в `tasks/` (локально, вне git). Иногда рядом лежат комментарии организатора из чата — `tasks/AI Advent Challenge_NN_comments.txt`: спецификация их учитывает и так же не копирует.
2. Claude пишет `docs/TooManyRules — День N спецификация.md`.
3. Если автор просит, Claude пишет `prompts/dayN-prompt.md` — роль-промпт исполнителю: что прочитать, в каком порядке работать, на что обратить внимание. Дни 11-16 обошлись без промпта: не пиши его, пока о нём не попросили.
4. Исполнитель реализует; Claude ревьюит.
5. Коммит + тег `dayNN` (в таблицу челленджа идёт ссылка на тег, а не на `main`).

Прежде чем начинать писать код по запросу «сделай день N», уточни, нужна ли спецификация или реализация — по умолчанию в этом репозитории ожидается первое.

Правило не абсолютное: автор может прямо попросить Claude написать код (так делались правки дня 6 после ревью). Порядок в этом случае тот же — **сначала документы, потом код**: спецификация дня остаётся живым документом и правится вместе с кодом, а `prompts/dayN-prompt.md`, если он был, уже отработан и не переписывается задним числом.

### Формат спецификации дня

Фиксированная структура, которую нужно сохранять у новых дней: задание челленджа → что делаем конкретно для TooManyRules → промпты/параметры → технические требования → что должно быть видно в видео → критерии приёмки → **«Что сознательно НЕ делаем на этом шаге»**. Последний раздел обязателен и обязателен к соблюдению исполнителем: он держит объём дня в рамках.

Текст самих заданий — платный контент челленджа. `tasks/`, `theory/` и `.claude/` в `.gitignore`; спецификации **ссылаются** на `tasks/AI Advent Challenge_NN.txt` (номер дня двумя цифрами: `_09`, `_10`), но не копируют его текст. Не переноси содержимое `tasks/` в коммитимые файлы. `theory/` — лекции для автора; для спецификаций и разработки их читать не нужно.

Если сравнение или проверка — часть результата задания (день 10 — «+ сравнение результатов», дни 11, 13, 14 и 15 — формат «видео + код / текст»), кроме спецификации появляется ещё один документ дня — `docs/TooManyRules — День N сравнение ….md` или `… проверка ….md`. Данные в нём (числа, дословные ответы) заполняются по реальному прогону, выводы и оценку качества пишет автор. Если задание только просит «проверьте», а результат — сам агент или код и формат — видео + код (дни 12 и 16), отдельного документа нет: проверка показывается в видео, замеры (промптов на дне 12, реального подключения к MCP на дне 16) записываются комментариями в коде.

## Команды

```bash
./run.sh
```

`run.sh` сам создаёт `src/.venv`, ставит `src/requirements.txt` и запускает `src/app.py` на http://127.0.0.1:7860 (Gradio-дефолт). Необязательный аргумент выбирает, что запускать: `./run.sh week1` поднимает замороженный артефакт недели 1 (`app_week1.py`), `./run.sh faq-watch [аргументы]` (день 18; день 19 добавляет пайплайн памятки к столу тому же серверу) — сторож FAQ, отдельный MCP-сервер по Streamable HTTP, командной строкой из `presets.FAQ_WATCH_ARGV` с дописанными аргументами (`--interval 5`, `--port`, `--db`, `--out` перекрывают прежние); других значений нет. Всё живёт в `src/`, не в корне: там же venv, `requirements.txt` и `.env` с `DEEPSEEK_API_KEY` (не коммитится). Python 3.14 (`src/.python-version`).

Вручную:

```bash
cd src && source .venv/bin/activate && python app.py
```

Тестов, линтера и сборки в проекте нет. Проверка изменений — ручная: запустить приложение, прогнать сценарий и посмотреть stdout, куда логируется каждый вызов API (модель, `thinking`, `finish_reason`, время, токены, стоимость, текст ответа). Логи — основной инструмент отладки, добавляй их к новым вызовам тем же паттерном.

Для preview-сервера есть конфигурации `toomanyrules` и `toomanyrules-week1` в `.claude/launch.json` (обе на порту 7860). Если 7860 занят запущенным у автора приложением, не убивай его процесс: подними свой экземпляр на другом порту (`GRADIO_SERVER_PORT`) и верни `.claude/launch.json` в исходный вид, когда закончишь. Свой экземпляр поднимай и со своим каталогом данных — `TOOMANYRULES_DATA_DIR=<каталог>/sessions`: иначе он пишет в сессии автора (а вместе с ними — в рабочую память и, с дня 13, в состояние задачи), в его долговременную память и в его профиль (каталоги `memory`, `profile` и, с дня 14, `invariants` — соседи каталога сессий). Пути долговременной памяти и профиля печатаются в лог при старте — сверяй их до первого вопроса. С дня 18 свой экземпляр сторожа FAQ — свой порт (`--port`), своя база (`--db`) и `TOOMANYRULES_FAQ_WATCH_URL` у своего приложения; сторож автора на 8765 и его базу `src/data/faq_watch/` не останавливать и не трогать. С дня 19 к этому добавляется свой каталог памяток (`--out`): памятки автора в `src/data/cheatsheets/` не трогать — как и его базу сторожа.

Из `context.py` интерфейс не импортирует ничего: набор стратегий агенту выдаёт `presets.make_strategies()`, модель памяти — `presets.make_memory()`, роутер — `presets.make_router()`, автомат задачи — `presets.make_task_machine()`, книгу инвариантов — `presets.make_invariants()`, а панель рисует то, что вернул агент. Протоколы `HistoryStore`, `LongTermStore`, `ProfileStore`, `InvariantStore` и `ToolBox` (день 17) объявлены в `agent.py`, но `storage.py` и `mcp_client.py` их не импортируют — протоколы структурные. Протокол `ContextStrategy`, наоборот, объявлен в самом `context.py` вместе с типами, которые стратегия отдаёт агенту. `tokens.py`, `context.py` и `mcp_client.py` — листья графа: из проекта они не импортируют ничего; `memory.py`, `user_profile.py`, `task_state.py` и `invariants.py` зависят только от листа `context.py`.

Что важно знать про новый код:

- **На экране — текущий день; всё остальное свёрнуто.** Экран растёт каждый день, а в кадр видео должно попадать то, что показывает сегодняшний приём. Поэтому примеры и сценарии проверки прошлых дней лежат в закрытом аккордеоне «Примеры и сценарии прошлых дней (6, 10-15, 17-18)», а блоки дебаг-панели, не нужные для демонстрации текущего дня, — каждый в своём закрытом `gr.Accordion` с номером дня в заголовке («Конфиг агента», «Профиль и слои памяти (дни 11-12)», «Инварианты (день 14)» и редактор инвариантов, «Состояние задачи и маршрут (дни 13, 15)» с таблицей автомата внутри, «Память стратегии (дни 9-10)», «Заполнитель контекста (день 8)», «Счётчики процесса и таблицы ходов и агентов (дни 8, 10)», «Стек сообщений агента», «Файлы долговременной памяти, профиля и инвариантов (дни 11-12, 14)»; статичная таблица автомата собирается один раз при построении интерфейса). В кадре дня 19 развёрнут блок «Памятка к столу: пайплайн MCP (день 19)» наверху дебаг-панели (статичное описание пайплайна плюс «Инструменты последнего хода агента» — переехали сюда из блока дня 18, та же пара компонентов и выходов `_view()`), а сценарий дня стоит у поля ввода; блок «Сторож FAQ (день 18)» свёрнут под ним, блоки дней 17 и 16 — под ним же, сценарий дня 18 — в аккордеоне «Примеры и сценарии прошлых дней (6, 10-15, 17-18)». Ничего не удаляется и не выключается через `visible`: инструменты прошлых дней должны открываться одним кликом, а `_view()` и его выходы от сворачивания не меняются — компоненты внутри аккордеона остаются теми же выходами. **Делая новый день, переложи аккордеоны:** блоки и сценарий нового дня разверни в кадр, вчерашние — сверни.
- **Агентов в процессе много, и живут они дольше вкладки.** Смена пресета и кнопка «Новый агент» создают новый экземпляр; все они лежат в реестре `agent.py` (`agents()`, `agent_by_number()`, `delete_agent()`), а переключатель в дебаг-панели листает этот реестр. Активный агент при этом живёт в `gr.State`, то есть у вкладки браузера свой; глобального «текущего агента» в модуле нет.
- **Номера агентов монотонны и не переиспользуются.** Номер выдаётся при создании из счётчика `agents_created`; удаление агента (кнопка «Удалить агент») убирает его из реестра, но счётчики процесса не откатывает — потраченное осталось потраченным. Поэтому «создано» и «живых» (`agents_alive`, длина реестра) расходятся, и панель показывает оба числа.
- **Выпадающие списки слушают `select`, а не `change`/`input`.** `_view()` синхронизирует значения всех списков (пресет, стратегия, ветка, агент, checkpoint, «Профиль в запросе») на каждом событии, а `change` срабатывает и на программное обновление; `input` в Gradio 6.26 у `Dropdown` приходит на один выбор дважды. И то и другое рождало лишних агентов — проверено в логах; у списка стратегий `change` переключал бы стратегию сам по себе. Исключение — список «Checkpoint»: своего обработчика у него нет, это вход кнопки «Ветка от checkpoint'а». Все списки ещё и `filterable=False`, чтобы значение всегда совпадало с одним из пунктов. **У `gr.CheckboxGroup` («Слои памяти в запросе») и `gr.Checkbox` («Состояние задачи в запросе», «Инварианты в запросе», с дня 17 — «Инструменты MCP в запросе») событие другое — `input`**: у флажков оно приходит ровно один раз на клик и не приходит на обновление из `_view()` (проверено 16.09.2026 по сети и логу, комментарий у подписки). Группа «Кандидаты» своего обработчика не имеет — это вход кнопок «Сохранить в долговременную» и «Отклонить».
- **`_view()` возвращает кортеж фиксированной длины (сейчас 37), позиционно раскладывающийся в `VIEW_OUTPUTS`.** Порядок — часть контракта всех обработчиков; они возвращают одинаковый набор выходов, чтобы панель не расходилась с состоянием агента. Добавляешь элемент в панель — добавляй значение в конец кортежа и в конец списка выходов. **Осознанное исключение — редактор профиля (день 12): форма, а не вид.** Его поля в `_view()` не входят, иначе любое событие затирало бы несохранённую правку; у него свои выходы `PROFILE_EDITOR_OUTPUTS`, второй `demo.load` и обработчик списка «Режим для правки». **Второе такое исключение — редактор инвариантов (день 14):** свои выходы `INVARIANT_EDITOR_OUTPUTS`, загрузка формы — `load_event.then(...)` после `on_load` (пункты списка зависят от агента вкладки, которого к этому моменту ещё нет), список «Инвариант для правки» слушает `select` для выбора и `focus` для пересборки пунктов по книге активного агента; сохранение и удаление возвращают `COMMON_OUTPUTS + INVARIANT_EDITOR_OUTPUTS`. День 14 добавил в `_view()` три значения — переключатель, блок и файл инвариантов (спецификация называла два и 33: файл инвариантов оказался в `_view()` по тому же правилу, что файлы памяти и профиля, — он перечитывается на каждом событии). Необязательный `question` передаёт только обработчик кнопки «Набить контекст» — единственный случай, когда интерфейс сам знает содержимое поля ввода; поллинга и пересчёта по мере набора текста в проекте нет.
- **Агенты восстанавливаются один раз при старте процесса**, на импорте модуля `app.py` (`_restore_agents()` до `demo.launch()`), а не в `demo.load`: `demo.load` срабатывает на каждую открытую вкладку браузера и плодил бы копии сессий. Открытие страницы поэтому не создаёт агента, если реестр не пуст, — активным становится последний.
- **Пустых файлов сессий не бывает:** `save` с пустым списком удаляет файл, поэтому «Сбросить диалог» убирает сессию с диска, а `create_session()` только резервирует номер. Номера сессий, как и номера агентов, в пределах процесса не переиспользуются.
- **На диск едет история, имя пресета, память стратегий и рабочая память, но не конфиг:** системный промпт, модель и параметры берутся из `presets.py` при восстановлении. Сводка и рабочая память едут на диск потому, что они контекст. Токены, деньги, счётчики и журнал ходов не сохраняются вообще — восстанавливается контекст, а не бухгалтерия; кандидаты в долговременную память, положение «Слоёв памяти в запросе», «Профиля в запросе» и «Состояния задачи в запросе» и «Инвариантов в запросе», режим прошлого хода, последний отказ автомата, последний конфликт стража и ожидание подтверждения перехода не сохраняются тоже — это вопрос к человеку и инструменты проверки, а не диалог. Состояние задачи и её журнал переходов на диск едут — это контекст, а не бухгалтерия (день 13); сессионные инварианты едут тоже, в `context.invariants` (день 14), — постоянные лежат своим файлом. Профиль пользователя лежит своим файлом и к сессии не привязан. После перезапуска бюджет контекста сразу ненулевой, а журнал пуст: это ожидаемая картина, а не баг.
- **Оценка токенов до запроса считается по результату `_build_messages()`**, а не по стеку отдельно: «посчитали» и «отправили» не должны разъезжаться. Единственная точка разбора списка сообщений на части — `Agent._count_messages()`; и `ask()`, и `context_usage()` ходят туда. Разбор идёт по ролям: первое сообщение — системный промпт, последнее — вопрос, `system` между ними — блоки, и корзину блока решает начало текста: `user_profile.PROFILE_HEADER` — профиль, `memory.LONG_TERM_HEADER` — долговременная, `memory.WORKING_HEADER` — рабочая, `task_state.TASK_HEADER` — состояние задачи, `invariants.INVARIANT_HEADER` — инварианты, остальное — память стратегии. Поэтому заголовки блоков не должны начинаться одинаково. Оценка всегда показывается рядом с фактом из `usage` — до запроса точного числа не бывает, и в этом смысл дня 8; подгонять эвристику под последний ответ нельзя, систематическую разницу снимает коэффициент калибровки.
- **Журнал ходов (`TurnStats`) ведёт себя как счётчики агента, а не как стек сообщений:** `reset()` его не чистит (сброшен диалог, а не агент), запись добавляется только на успешный вызов. В таблице «Рост по ходам» это видно провалом `prompt` при продолжающей расти накопительной стоимости.
- **Переполненный запрос отправляется намеренно.** Проверок «а влезет ли» перед вызовом нет: предупреждение в панели и в логе есть, предохранителя нет. Стратегии дней 9-10 — способ до переполнения не доходить, а не проверка перед вызовом, и включаются они только переключателем стратегии.
- **Стратегия меняет запрос, а не память.** Стек сообщений агента и файл сессии всегда полные: сводка и факты живут отдельным полем рядом с историей, `covered` — индекс в историю, а не копия её куска. На этом держится сравнение стратегий на одном и том же диалоге — не подменяй сообщения сводкой в `_messages` и не удаляй их из файла.
- **Чистые методы и методы, меняющие память, разведены.** У стратегии `prepare()`, `build()` и `describe()` чистые, память меняет только `apply()`; у модели памяти чистые `describe()`, `prepare()` и `working_block()`, состояние меняют `apply()`, `take_candidates()`, `drop_candidates()`, `load()` и `reset()`. Чистые зовёт панель на каждый рендер (`debug_state()` → `ContextView`), поэтому служебная работа внутри `build()` или `_build_messages()` стоила бы денег на каждое движение в интерфейсе. Служебные вызовы делает только `ask()`, до основного. У фактов и у разбора памяти `prepare()` возвращает задачу почти всегда — это их штатное состояние, а не назревшее предупреждение.
- **Служебный вызов — настоящий вызов, но не ход.** Он считается в счётчиках агента и процесса наравне с обычными (поэтому `totals.calls` включает свёртки, обновления фактов, вызовы стража, разборы памяти, вызовы роутера и трекера), но не пишет в стек, не создаёт строку журнала и не затирает `_last_reply`. Сам вызов модели один на все служебные работы — `_call_service_model()` (`thinking` выключен, `max_tokens` из задачи, ни температуры, ни `stop`); работы вокруг него — `_run_context_task()`, `_run_invariant_guard()`, `_run_memory_task()`, `_run_route_task()` и `_run_task_tracker()`. Слова для лога и панели приходят от стратегии или модели памяти (`label`, `memory_label`, `last_update`): в текстах интерфейса нет слов, верных только для одной стратегии. Успех решает `apply() -> bool`, а не непустой текст. Сбой ход не отменяет: память не двигается, вызов повторится на следующем ходе. Обрезанный по `max_tokens` ответ (`finish_reason="length"`) применяется, но с предупреждением в логе и пометкой в панели — **кроме трекера задачи**: у него оборванный ответ не применяется вовсе (оборванный план хуже отсутствия перехода); у стража применяется — вердикт стоит первой строкой. **Цена у каждой работы своя:** `service_*` — только стратегии (рядом с их экономией), `memory_*` — только разбор памяти, который ничего не экономит, а добавляет, `route_*` — только роутер профиля, `tracker_*` — только трекер задачи, `guard_*` — только страж инвариантов, `sampling_*` — только сэмплинг. **Сэмплинг (день 19) — шестая служебная работа и единственное исключение из «до хода»:** она идёт не до основного запроса, а внутри него, между раундами цикла function calling — сервер просит модель через `ToolBox.call(..., sample=…)`, и за один ход таких просьб может быть несколько (не 0-1, как у остальных пяти). Разрешён только серверу с `McpServer.sampling=True` — MCP оставляет решение клиенту, а решение здесь принимает `presets.py`, а не сам агент.
- **Стратегия — состояние агента, а не поле `AgentConfig`.** Её переключают на живом агенте (`set_strategy()`), не теряя диалог: пресет создаёт нового агента, стратегия — нет. Экземпляры стратегий у каждого агента свои (`presets.make_strategies()`); память неактивных при переключении не чистится, `reset()` чистит память всех. Новый агент стартует на «Вся история», восстановленный берёт стратегию из файла.
- **Файл сессии — версия 2.** Рядом с `messages` лежит `context`: имя активной стратегии, память стратегий, с дня 10 — `checkpoints` и `branch`, с дня 11 — `working` (рабочая память) и снимок `working` в каждом checkpoint'е, с дня 13 — `task` (состояние задачи с журналом переходов) и его снимок в checkpoint'е, с дня 14 — `invariants` (сессионные инварианты) и их снимок в checkpoint'е (всё — только непустое). Для `storage.py` это непрозрачный словарь, и пишется он одной записью с историей. Файлы версии 1, файлы дня 10 без `working`, файлы дня 12 без `task` и файлы дня 13 без `invariants` читаются как есть, миграций нет. Мусор внутри `context` агент замечает сам — после `load()` сравнивает `dump()` с прочитанным, — потому что у `context.py`, `memory.py`, `task_state.py` и `invariants.py` логов нет. Пустая память в файл не пишется: `dump()` без памяти отдаёт `{}` у всех стратегий (у сводки — с дня 10, поэтому файлы дня 9 при чтении один раз предупреждают о «прочитанной не целиком» пустой сводке; это допустимо). У рабочей памяти покрытие без записей пишется: иначе разбор после перезапуска перечитал бы историю и заново предложил бы уже решённых кандидатов.
- **Длину сводки держит просьба в промпте (`SUMMARY_WORDS`), а `SUMMARY_MAX_TOKENS` — только страховка.** Лимит в предложениях длину не держал: модель соблюдает число предложений и растягивает каждое (замер — спецификация дня 9, §3.1). В сводке обязательны выводы по разобранным правилам, прежде всего поправки игрока: Too Many Bones модель знает плохо, и «правила она и так знает, достаточно перечня тем» для этого проекта неверно (§3.2). Меняешь промпт свёртки — проверь его на живом диалоге из нескольких свёрток подряд.
- **Факты — слияние построчных изменений, источник факта — игрок.** Ответ служебного вызова — только изменения `ключ: значение`, `ключ: удалить` или `нет изменений`; разбор (`context.parse_changes()`) срезает маркеры списка, выделение и кавычки, а `StickyFacts.apply()` сливает копию словаря, которая подменяет факты целиком (панель читает их без замков). Поправка игрока — новое значение ключа, а не `удалить`; образец формата в промпте — без кавычек и разметки, иначе модель повторяет разметку в ключах. Каждое правило `FACTS_PROMPT` закрывает сбой, пойманный на живом сценарии, — список в комментарии у промпта, замер — у `FACTS_MAX_TOKENS`. Меняешь промпт фактов — прогони сценарий §9.1 целиком: сбои видны на отдельных ходах и не повторяются на каждом прогоне.
- **Память разведена по времени жизни на три слоя (день 11).** Краткосрочная — разговор сессии: стек и память стратегий, урезает её стратегия. Рабочая — данные текущей партии: `context.working` файла сессии, пишется разбором сразу, копируется в ветку из снимка checkpoint'а, уходит со сбросом. Долговременная — игрок вообще: `src/data/memory/long_term.json`, одна на процесс и общая для всех агентов; сброс, удаление агента, новая сессия и ветка её не трогают. Сводка и факты — не отдельный слой, а способ отправить краткосрочную память короче.
- **Слой выбирает не модель, а карта памяти.** `MEMORY_MAP` в `presets.py` — закрытый список ключей со слоем, разделом и описанием; модель по описанию выбирает только ключ, ключ вне карты отклоняется и виден в логе и панели. Карта проверяется конструктором `AgentMemory` при импорте `presets.py`, а список ключей в `MEMORY_PROMPT` собирается из карты, а не пишется второй раз. Новый вид данных в памяти — это строка карты, а не надежда, что модель догадается.
- **В долговременную память пишет только человек.** Разбор относит к долговременной части карты не запись, а **кандидата**; в файл он попадает только по кнопке «Сохранить в долговременную» (`accept_candidates()`), и только после успешной записи уходит из кандидатов. Кандидат — вопрос к человеку: в запрос не уходит, на диск не пишется, в ветку не копируется, перезапуск не переживает. Не делай «уверенных» автосохранений и не отмечай кандидатов по умолчанию.
- **`JsonLongTermStore` читает файл один раз при создании**, дальше записи живут в памяти процесса. Каталог — `DATA_DIR.parent / "memory"`, сосед каталога сессий: экземпляр с другим `TOOMANYRULES_DATA_DIR` получает свою долговременную память. Битый файл не затирается (запись выключается, причина — в `error`); запись атомарная и под замком хранилища — оно общее для агентов; у каждой записи происхождение — сессия и время сохранения; пустая долговременная память файл не удаляет. Запись с ключом вне карты остаётся в файле и показывается в панели как «в файле, не используется», но в запрос и во вход разбора не уходит.
- **Переключатель «Слои памяти в запросе» меняет запрос, а не память** — правило стратегий дня 9: разбор идёт при любом положении, выключенный слой продолжает записываться. Краткосрочный слой переключателем не выключается. Положение — состояние агента, но не диалога: на диск не едет, в checkpoint не входит, у нового, восстановленного агента и у ветки включены оба слоя.
- **Порядок блоков в запросе — от устойчивого к изменчивому:** системный промпт, инварианты, профиль, долговременная память, рабочая, состояние задачи, память стратегии, хвост истории, вопрос. Блоки слоёв вставляет только `Agent._with_layers()`, блок профиля — только `Agent._with_profile()`, блок задачи — только `Agent._with_task()`, блок инвариантов — только `Agent._with_invariants()`; все вставки встают сразу за системным промптом, поэтому порядок вызовов обратен порядку блоков (`_with_task()` → `_with_layers()` → `_with_profile()` → `_with_invariants()`). Стратегии о слоях, профиле, задаче и инвариантах не знают. База сравнения «вся история» собирается с теми же блоками, поэтому экономия стратегии говорит только о стратегии.
- **Промпт разбора памяти — формат и уроки промпта фактов дня 10 плюс свои правила**, каждое из которых закрывает сбой живого прогона («вопрос игрока — не решение», «долговременное не переписывай в ключи партии», с дня 12 — «просьбы о форме ответа — не память») — список в комментарии у `MEMORY_PROMPT`, замер — у `MEMORY_MAX_TOKENS`. Меняешь промпт — прогони сценарий §9.1 дня 11 и сверь кандидатов с документом проверки дня 11.
- **Ветка — отдельная сессия и отдельный агент, а не стратегия.** `save_checkpoint()` фиксирует конец истории со снимком памяти всех стратегий и рабочей памяти; `fork()` собирает нового агента через параметр `seed` конструктора (тем же `_normalize_messages()`/`_load_context()`, что файл сессии), чтобы в реестр не попадал недособранный агент, и файл ветки пишется сразу. Ветка получает свежую модель памяти с рабочей памятью из снимка и то же хранилище долговременной памяти, что у родителя. Жива ли связь ветки с родителем, решает только `branch_parent()` — по `session_id`, id **и** времени checkpoint'а: после сброса родителя его новый `cp1` не тот же. Панель это правило не повторяет, а зовёт (`_live_branches()` в `app.py`). Семейство веток (`branch_family()`) считается по происхождению агентов реестра и у родителя не хранится. `reset()` чистит checkpoint'ы, происхождение и рабочую память вместе со стеком; у ветки `restored_messages` всегда 0.
- **Методы, меняющие агента, — под его замком.** `ask()`, `reset()`, `set_strategy()`, `save_checkpoint()`, `fork()`, `set_request_layers()`, `set_profile_choice()`, `accept_candidates()`, `reject_candidates()`, `start_task()`, `task_event()`, `set_task_in_request()`, `confirm_transition()`, `set_invariants_in_request()` и `set_session_invariants()` помечены `@_locked` (свой `RLock` у каждого агента): Gradio выполняет обработчики разных кнопок параллельно, и без замка checkpoint, нажатый во время ответа, снял бы память, обновлённую по вопросу, которого ещё нет в истории, а кандидат сменился бы новым разбором посреди решения человека. Чтение (`debug_state()`, `context_view()`, свойства) замка не берёт — рендер панели не ждёт ответа модели. Новый метод, который меняет стек, память или checkpoint'ы, — тоже под `@_locked`.
- **Имя модели — ключ сразу в двух таблицах:** `PRICING_PER_M_TOKENS` в `agent.py` и `CONTEXT_WINDOW_TOKENS` в `tokens.py`. Меняешь модель — правь обе, иначе стоимость и бюджет молча станут «н/д» (для модели вне таблиц это штатное поведение — задел под локальную модель недели 6, поэтому вслух ничего не сломается).
- **`gr.Chatbot` создаётся без `type="messages"`.** В `requirements.txt` стоит `gradio>=5`, а установлен 6.26, где этот аргумент удалён: формат сообщений там стал единственным. Не возвращай его обратно по старым примерам из недели 1.
- **Интерфейс не ведёт своей копии переписки, памяти и профиля:** чат на каждом шаге рендерится из `agent.history`, рабочая память и кандидаты — из `MemoryState`, долговременная — из записей хранилища, профиль, режим и переключатель — из `debug_state()["profile"]` (поля редактора профиля — форма, а не вид, см. выше). Ровно поэтому день 7 не потребовал переделки интерфейса: история приходит из файла в тот же `agent.history`.
- Логи агента идут с префиксом `[#3 Базовый · s003]` — номер и сессия обязательны, иначе несколько агентов одного пресета в stdout неразличимы, а «дошло ли до диска» не видно. Каждое обращение к диску логируется тем же паттерном; у хранилища долговременной памяти, общего для агентов, префикса агента нет — в его строках путь и сессия, чьё решение записано.
- **Обработчики намеренно не генераторы** (`on_send` здесь, `run_day5` в артефакте недели 1). Gradio показывает нормальный оверлей ожидания (спиннер + таймер) только для функций с одним `return`; у генератора вместо этого тонкая рамка без индикации.
- **Код нигде не оценивает качество ответов и не подсвечивает «лучший» вариант** — это ручное суждение автора по бумажной книге правил, явно исключённое из объёма в разделе «что сознательно НЕ делаем» каждой спецификации.
- Стоимость — оценка по off-peak-таблице `PRICING_PER_M_TOKENS` ($ за 1M токенов) и по цене входа без учёта кэша промпта; в пиковые часы ставки ×2. Таблица есть и в `agent.py`, и в `app_week1.py` — это следствие заморозки, а не рассинхрон, который надо чинить: `app_week1.py` остался и на старом имени модели, и на старых ценах.
- **Дешёвая модель переименована 11.09.2026:** `deepseek-v4-flash` (0.22/0.66) выведена из эксплуатации, вместо неё `deepseek-flash` — DeepSeek-V4.1-Flash по 0.15/0.60. Старое имя API ещё принимает и обслуживает той же моделью, но в таблицах проекта его нет. Флагман `deepseek-v4-pro` не изменился. Окно у обеих — 1 048 576 токенов (документация говорит «1M», сервер в ошибке о переполнении называет точное число; в таблице стоит число от сервера).

Из решений дня 11 дальше в силе всё, что перечислено выше про слои, карту, кандидатов и `JsonLongTermStore`, и ещё:

- **Модель памяти и хранилище долговременной памяти — необязательные зависимости агента**, как хранилище истории и стратегии: без них агент ведёт себя ровно как на дне 10. Экземпляр `AgentMemory` свой у каждого агента (`presets.make_memory()`), хранилище долговременной памяти одно на процесс. Этот же приём — «на агента фабрика из `presets.py`, на процесс один объект из `app.py`» — берут новые зависимости: на дне 12 так встали `make_router()` и `JsonProfileStore`.
- **Долговременная память и профиль — одни на каталог данных**: нескольких пользователей в одном процессе нет, привязка к пользователю — вместе с VPS и SQLite.

Из решений дня 12 (персонализация) дальше в силе:

- **Профиль пользователя — не слой памяти и не пресет.** Его пишет сам пользователь в редакторе, модель его не меняет и правок не предлагает; пресет по-прежнему — параметры вызова модели от разработчика. Профиль лежит в `src/data/profile/profile.json` (сосед `sessions` и `memory`), у него общая часть и режимы под задачи. Пока файла нет, действует `presets.DEFAULT_PROFILE`; после первого сохранения правка профиля по умолчанию в коде до сохранённого профиля уже не доезжает — это осознанно обратно правилу пресетов дня 7: профиль — работа пользователя. В запрос уходят общая часть и **один** режим, блоком сразу за системным промптом.
- **Режим выбирает роутер** — третья служебная работа через `_call_service_model()` со своими счётчиками `route_*`, — или сам пользователь переключателем «Профиль в запросе» (`авто` / режим / `выключен`). Сбой или неразобранный ответ роутера дают запасной режим и ход не отменяют. Положение переключателя и режим прошлого хода на диск не едут: у нового, восстановленного агента и у ветки — `авто`.
- **Профиль разбирается `parse_profile()` при каждом чтении**, кэша у агента нет; замечания разбора логируются один раз при старте процесса.
- **Модуль называется `user_profile.py`, а не `profile.py`**: `profile` — модуль стандартной библиотеки, и файл в `src/` подменил бы его всему процессу. Имя каждого нового модуля проверяй на совпадение с модулем стандартной библиотеки.
- **Ключ `формат ответов` ушёл из карты памяти в профиль** (формат режима «За столом»), раздел долговременной памяти `профиль` переименован в `окружение`. Старая запись `формат ответов` в `long_term.json` — запись вне карты: в панели «в файле, не используется», миграции нет.

Из решений дня 13 (состояние задачи) дальше в силе:

- **Состояние задачи — конечный автомат, а не слой памяти, не стратегия и не режим профиля.** Новый модуль `task_state.py` (ни сети, ни диска, ни логов, ни чтения часов, ни Too Many Bones; из проекта — только `context.py`). Этапы `планирование → выполнение → проверка → готово` и `отменена`; **пауза — флаг на активном этапе, а не этап**. Рабочая память помнит, что известно о партии, состояние задачи — где мы в работе и чего ждём; ни одно в другое не пишется.
- **Всё допустимое — таблица `TRANSITIONS`, этап и шаг модель не пишет никогда.** Трекер называет событие (с дня 15 — из всех своих событий с пометкой «можно сейчас» / «сейчас нельзя», допустимость решает код), код проверяет его по таблице и вычисляет следующее состояние. Недопустимое — отказ с причиной: он виден в логе и панели, а отказ трекера уходит ещё и в блок запроса этого хода, чтобы ассистент его объяснил. Не превращай таблицу в ветвления в агенте: на неё и на отказы встают день 14 (инвариант над переходом приходит в автомат параметром `TransitionGuard`, а не строкой таблицы) и день 15 (две новые строки отката и проверка свойств маршрута при импорте).
- **Трекер — четвёртая служебная работа через `_call_service_model()`**, счётчики `tracker_*`. В отличие от остальных служебных работ, **его обрезанный ответ не применяется**: оборванный ответ — это оборванный план. Трекер не вызывается без задачи, на конечном этапе, на ходе «Начать задачу» и **повторно на том месте истории, где его переход уже применён**: переход не идемпотентен, и повтор упавшего хода иначе отметил бы шаг дважды.
- **Начинает и отменяет задачу только человек — кнопками.** Сигнатура `ask()` не меняется: «Начать задачу с этим сообщением» зовёт `start_task()`, затем `ask()`. Одна задача на сессию; задача в работе новой не заменяется.
- **Состояние лежит в `context.task` файла сессии**, снимок — в checkpoint'е, копия — в ветке, сброс его чистит; `storage.py`, `memory.py`, `context.py` и `user_profile.py` не меняются. Журнал переходов едет на диск — это состояние: по нему считается «свежий» переход. Последний отказ, переключатель «Состояние задачи в запросе» и расход трекера на диск не едут.
- **Блок задачи — сразу за рабочей памятью, перед памятью стратегии.** Вставки идут `_with_task()` → `_with_layers()` → `_with_profile()`: каждая встаёт сразу за системным промптом, поэтому порядок вызовов обратен порядку блоков. На «готово» и «отменена» блок уходит только ходом сразу после перехода. Переключатель меняет запрос, трекер работает при любом положении. Корзина `task` в `RequestTokens`, заголовок `TASK_HEADER` начинается не так, как остальные.
- **`_view()` — 31 значение.** Таблица автомата в панели статична и в `_view()` не входит.
- **Формат дня «видео + код / текст»** — поэтому есть документ проверки `docs/TooManyRules — День 13 проверка состояния задачи.md`, по прогону сценария §9 на «Скользящем окне» с перезапуском и веткой без блока.

Из решений дня 14 (инварианты) дальше в силе:

- **Инвариант — не память, не профиль и не системный промпт.** Новый модуль `invariants.py` (ни сети, ни диска, ни логов, ни чтения часов, ни Too Many Bones; из проекта — только `context.py`; про `task_state.py` не знает). Инвариант — правило, которое ассистенту нельзя нарушить; память — что агент знает, профиль — как отвечать, системный промпт — работа разработчика. Пишет инварианты **только человек**, в редакторе: модель их не создаёт и не предлагает.
- **Две области и отдельное хранение.** `всегда` — `src/data/invariants/invariants.json` (`JsonInvariantStore`, копия `JsonProfileStore`, один файл на каталог данных); `сессия` — `context.invariants` файла сессии, со снимком в checkpoint'е, копией в ветку и очисткой сбросом. Номера (`П1`, `С1`) выдаются при сборке книги и ключом хранения не являются.
- **Страж — пятая служебная работа** через `_call_service_model()`, счётчики `guard_*`, идёт первым после свёртки стратегии. Он только называет конфликт нового сообщения с инвариантами; ход не отменяет и ничего не блокирует. Сомневается — `нет конфликта` (обратно правилу трекера: ложный отказ хуже пропущенного конфликта). Конфликт без номеров из книги и с номерами вне книги не применяется.
- **Блок инвариантов — первый из блоков агента**, сразу за системным промптом и перед профилем: `_with_task()` → `_with_layers()` → `_with_profile()` → `_with_invariants()`. Корзина `invariants` в `RequestTokens`, заголовок `INVARIANT_HEADER` начинается не так, как остальные четыре.
- **Где нарушение формализуемо, его ловит код.** Инвариант над переходом (`запрещён` / `с подтверждением`) приходит в `task_state.py` параметром `guards`; таблица `TRANSITIONS` не меняется. Запрет не обходится подтверждением — только выключением инварианта; ожидание подтверждения на диск не едет. В остальном инвариант держит модель, и это записано в спецификации прямым текстом — гарантии день не даёт, даёт видимость.
- **`_view()` — 34 значения** (переключатель, блок и файл инвариантов); редактор инвариантов — форма со своими выходами, как редактор профиля. Спецификация называла 33 — файл инвариантов оказался в `_view()` по правилу файлов памяти и профиля.
- **Подтверждённый переход трекера ведёт себя как кнопка человека для повторного вызова трекера.** Запись журнала остаётся с источником «трекер» и пометкой «подтверждено пользователем» в заметке (формат журнала не менялся), но `TaskMachine._tracker_status()` не считает её «уже учтённым переходом трекера»: иначе после подтверждения первой проверки трекер не разобрал бы следующее сообщение на том же месте истории, и вторая проверка не отметилась бы.
- **Страж сверяет номера с тем, что видел** — с действующими инвариантами без события. Названный выключенный инвариант или инвариант над переходом — «номер вне списка стража»: конфликт не применяется, номер виден в панели и в логе. Вердикт «нет конфликта» и отклонённый конфликт стирают только конфликт на том же месте истории (повтор упавшего хода), «последний конфликт» прежних ходов не трогают.
- **Правка инвариантов — сборка книги целиком.** Редактор собирает список, проверяет `invariants.validate()` и только потом пишет: постоянные — `JsonInvariantStore.save()`, сессионные — `Agent.set_session_invariants()` (под замком); смена области переносит инвариант, номер при этом меняется. До первого сообщения сессионные инварианты живут только в памяти агента: пустая история удаляет файл сессии — то же правило, что у рабочей памяти и задачи.
- **Формат дня «видео + код / текст»** — поэтому есть документ проверки `docs/TooManyRules — День 14 проверка инвариантов.md`, по прогону сценария §10 на «Скользящем окне» с веткой без блока и обоими режимами инварианта над переходом.
- **Замер и живой прогон дня 14** — комментарий у `GUARD_MAX_TOKENS` и `docs/TooManyRules — День 14 проверка инвариантов.md`: стратегия «Скользящее окно», прогон из REPL на временном каталоге данных. На прогоне страж не ошибся в вердикте ни разу; расхождение по номерам одно (Д1). В ветке без блока ассистент согласился переводить названия, хотя страж конфликт назвал, — выводы пишет автор.

Из решений дня 15 (жёсткий контроль переходов, «красный путь») дальше в силе:

- **Состояние не сдвинуть ничем, кроме допустимого перехода** — свойство кода (`TaskState` меняется только в `_transition()`), а не промпта. Трекер называет то, чего просит пользователь, даже если событие сейчас недопустимо: во вход идут все его события с пометкой «МОЖНО СЕЙЧАС» / «сейчас нельзя (причина)», причина берётся из `_rejection_reason()` — той же функции, что причины отказов, а пометка — из `_stage_paused_matches()`, которым считается `allowed()`. Второго определения допустимости в проекте нет. Правило «сомневаешься — `нет`» осталось и уточнено: оно про то, есть ли в сообщении событие, а не про то, допустимо ли оно. Это первая правка уже написанного промпта (`TASK_PROMPT`); каждое правило, добавленное по сбою живого прогона, — строка в комментарии у него (две: «без плана» — не «вернуться к плану», «план утверждён» без пунктов не бывает).
- **Сход с маршрута — отметка трекера, а не событие и не шестой служебный вызов.** Две необязательные строки ответа (`сход`, `чем`), закрытый список видов `OFF_ROUTE_KINDS` (`пропустить этап`, `игнорировать порядок`), разбирается независимо от события и только при разобранном ответе; вид вне списка молча игнорируется. Ничего в состоянии не меняет и ход не отменяет; строка «Сход с маршрута» в блоке — только при свежем (`off_route.messages == len(history)`), `OFF_ROUTE_INSTRUCTION` просит не выполнять просьбу в обход этапов и на планировании показать план заново (иначе после отказов план вышел бы из «последнего обмена» трекера, и «план утверждён» пришло бы без пунктов — живой прогон). Сход, последний отказ и счётчики красного пути (`rejected_total`, `off_route_total`) — память процесса, на диск не едут; `reset()` их обнуляет, `load()` не восстанавливает. Счётчики считают сообщения, а не попытки: тот же отказ (место истории + событие + источник) и тот же сход (место истории + вид) на том же месте истории заменяют прежний, а не добавляются — иначе повтор упавшего хода удваивал бы оба. Неразобранный ответ трекера сход не применяет, но свежий сход стирает: чужая строка от прежней попытки не должна уехать в запрос.
- **«Сейчас нельзя» — строка блока, которую выводит код** из этапа и флага паузы (`_forbidden_lines()`), плюс общая строка «этап и шаг меняет приложение; отменить, начать новую и переоткрыть — кнопкой». Заголовок `TASK_HEADER` не менял начала — он метка для `_count_messages()`. Цена больше, чем оценивала спецификация (≈80-124 токена вместо 25-40); числа — в документе проверки.
- **Откат назад по графу — две строки таблицы.** «вернуться к плану» (трекер и человек; с выполнения и проверки, не на паузе; стирает отметки и итоги шагов, план остаётся черновиком — «Прежний план (пересматривается…)», выполнение потом с шага 1) и «переоткрыть» (только человек, только с «готово», к проверке 1; отменённая задача не переоткрывается). `fire()` принимает оба наравне с паузой и отменой, кнопки подписаны на прежний `on_task_event`.
- **Маршрут проверяется при импорте, а `to_stages` — ещё и в момент перехода.** `Transition.to_stages` обязательно; `_validate_route()` проверяет пять свойств (вперёд по основному пути — не больше чем на один этап, достижимость, отсутствие тупиков, конечные этапы конечны). Строка с `Transition.same_stage` (пауза, продолжение) оставляет задачу на месте — её ребро идёт только в тот же этап, иначе проверка «планирование → проверка» ложно срабатывала бы на паузе. **`same_stage` объявляется, а не выводится из совпадения `stages` и `to_stages`**: у остальных строк `to_stages` читается как «в любой из этих этапов», и вывод по совпадению выводил такую строку из-под проверки прыжка целиком, а на правке, рассогласующей множества, ронял импорт с неверной причиной (правка по ревью дня 15). Проверка при импорте видит только таблицу, поэтому `_transition()` перед записью сверяет посчитанный этап с `to_stages` строки и при расхождении отказывает вместо перехода: «состояние не сдвинуть мимо таблицы» — свойство кода, а не двух согласованных между собой мест.
- **Границы дня соблюдены**: формат файла сессии, `storage.py`, `tokens.py`, `invariants.py`, `memory.py`, `context.py` и `user_profile.py` не менялись; `_view()` остался на 34 значениях; новых служебных вызовов и новых обработчиков интерфейса нет. Код по-прежнему не читает ответ ассистента: контролируется жизненный цикл задачи, а не текст ответа.
- **Формат дня «видео + код / текст»** — поэтому есть документ проверки `docs/TooManyRules — День 15 проверка переходов.md` по сценарию §9 (`ROUTE_SCENARIO`) на «Скользящем окне» с перезапуском, веткой без блока и обоими режимами инварианта над новым переходом; замер трекера дописан к комментарию у `TASK_MAX_TOKENS`. На прогоне трекер дважды (П1, П6) отметил сход без события — отказа автомата на них нет, состояние не сдвинулось; вход трекера подорожал на сотни токенов — выводы пишет автор.

Спецификация — `docs/TooManyRules — День 16 спецификация.md` (подключение MCP: соединение с MCP-сервером и список его инструментов). Отдельного архитектурного документа у недели 4 пока нет. Из решений дня 16 дальше в силе:

Сервер и на теге 1.6.1 называет себя `1.6.0`. Без собранного бинарника приложение поднимается, а блок MCP показывает сбой стадии «запуск»; `MCP_TIMEOUT_S` — 10 с.

День 15 сворачивается по правилу аккордеонов. Одна строка статуса — оценка токенов описаний инструментов (`tokens.estimate_tokens()`, считает `app.py`): в запрос сегодня не уходит ничего.

Замена командной строки из одних пробелов — это замена и сбой «пустая», а не откат к умолчанию; пустая переменная — замены нет.

- **Ожидаемый сбой сервера — `ToolError`**: только его текст доходит до клиента, SDK дописывает префикс «Error executing tool <имя>: » и ставит `isError`. Любое другое исключение — «Error executing tool …» без текста.
- **Инструменты — необязательная зависимость агента через протокол `ToolBox`** (реализация `mcp_client.McpToolBox`, один на процесс, как хранилища): без неё агент ведёт себя ровно как на дне 16. Агент про MCP не знает. Ветка получает тот же `ToolBox` и лимиты.
- **Каталог — в начале каждого хода, после всех служебных работ**, одно подключение; сбой каталога ход не отменяет — запрос уходит без `tools`. Переключатель «Инструменты MCP в запросе» (`set_tools_in_request()`, под замком) меняет запрос: выключено — ни каталога, ни корзины, ни параметра `tools`; у нового, восстановленного агента и у ветки — включено, на диск не едет.
- **Основной запрос хода — цикл раундов** «модель → вызовы → модель»: решает модель, код инструменты сам не вызывает. Раунд — настоящий вызов API, учитывается в счётчиках сразу (`_record_round()`), служебной работой не считается. Имя не из каталога и неразобранные аргументы на сервер не уходят; ответ `tool` — на каждый `tool_call_id`; результат длиннее `TOOL_RESULT_MAX_CHARS` обрезается с пометкой; после `TOOL_MAX_ROUNDS` раундов с вызовами — финальный с `tool_choice="none"`. Сбой API на раунде > 1 — ход неудачен целиком, стек не меняется, сделанные раунды и вызовы едут в ответ.
- **В историю — только вопрос и финальный текст.** `tool_calls` и результаты живут в пределах хода; формат файла сессии не менялся. `reasoning_content` раунда с `tool_calls` уходит обратно внутри хода (правило DeepSeek), между ходами история — только текст; `deepseek-v4-pro` с thinking это принимает (проверено).
- **Поля ответа меняют смысл один раз**: токены, стоимость, `elapsed` и кэш — суммы по раундам, `text` и `finish_reason` — последнего раунда, `request_tokens` — оценка первого. Калибровка и «оценка/факт» сравнивают оценку с `prompt_tokens` первого раунда (`TurnStats.first_prompt_tokens`), «ответ: оценка по тексту» — с `completion_tokens` последнего.
- **Корзина `tools` в `RequestTokens`** — схемы строкой JSON, те же, что параметр `tools`; сообщением не считаются (без `overhead`). Панель до вопроса считает её по каталогу прошлого хода (`_preview_tools_json()`): чистые методы в сеть не ходят.
- **`_view()` — 37 значений** (переключатель, «Инструменты последнего хода», JSON результатов). Каталог FAQ по кнопке — вне `_view()` (`FAQ_MCP_OUTPUTS`): функции блока дня 16 параметризованы сервером (`_mcp_server_md()`, `_mcp_status_md()`, `_mcp_list()` + два `functools.partial`). У `McpParam` появилось поле `description` — таблица FAQ показывает описания параметров, таблица BGG — как раньше.
- **Описания инструментов — это промпт**, системные промпты пресетов не менялись. Две правки описаний по живому прогону записаны комментариями у `QUESTIONS_DESCRIPTION` и `SECTION_DESCRIPTION`. Меняешь описание — прогони И1-И4 на `deepseek-flash`: модель зовёт инструменты не на каждом прогоне.
- **Формат дня «видео + код»** — документа проверки нет; замер реального прогона (82 вопроса / 24 раздела / 7 запросов, протокол 2026-07-28 через `server/discover`, ≈495 токенов схем, время вызовов, И1-И5, пресет с thinking, сбои, пустой `pgrep -fl faq_server`) записан комментарием у `FAQ_MCP` в `presets.py`.

## Неделя 4: день 18 реализован

Спецификация — `docs/TooManyRules — День 18 спецификация.md` (планировщик и фоновые задачи: сторож FAQ — свой долгоживущий MCP-сервер по Streamable HTTP со снимками FAQ в SQLite по расписанию). Из решений дня 18 дальше в силе:

- **Сторож — отдельная долгоживущая программа `src/faq_watch.py`, которую запускает человек** (`./run.sh faq-watch`), а не приложение и не `mcp_client`. Работает без приложения, переживает его перезапуски; приложение без сторожа работает как на дне 17. Командная строка — одна, `presets.FAQ_WATCH_ARGV`; `run.sh` дописывает к ней свои аргументы, и позже заданный перекрывает прежний (`argparse`). Окружение сервера — снятое до `import presets`: импорт подхватывает `src/.env`, и без этого ключи уехали бы в процесс сторожа (`os.execve`, правка по ревью). База — `src/data/faq_watch/faq_watch.sqlite3`, не по `TOOMANYRULES_DATA_DIR`: экземпляр сторожа отделяют порт и `--db`.
- **Транспорт — Streamable HTTP на `127.0.0.1`, `stateless_http=True`**; подключение клиента по-прежнему одно на вызов (`Client(url)`), процесс сервера — долгий. Планировщик — одна задача в `lifespan`: в SDK v2 для Streamable HTTP lifespan входит один раз на процесс, а не на подключение. Приложение сервер не опрашивает (ни `gr.Timer`, ни потоков): сводку каждого снимка сервер сам пишет в свой терминал.
- **Срок следующего снимка вычисляется из базы** (`next_due()` — чистая функция): удачных нет — сразу; иначе последний удачный + интервал; после неудачной попытки — её время + `min(интервал, RETRY_MIN)` (и без удачных тоже, иначе недоступный сайт опрашивался бы без передышки). Попытка, которую не удалось записать (база не приняла снимок, ошибка кода после чтения сайта), в `runs` не попадает — поэтому после неё сторож держит в памяти срок «не раньше» (сейчас + `min(интервал, RETRY_MIN)`), иначе перечитывал бы сайт каждую минуту (правка по ревью). Стенные часы, сон не дольше `SCHEDULER_TICK_S`; смена интервала будит планировщик; снимки не перекрываются. Интервал — в таблице `settings`: кто задал последним (`--interval` или `faq_watch_schedule`), тот и прав.
- **Сравнивается только полный снимок**; неполный или со сбоем сайта — строка `runs` с `ok=0` и причиной, без статей. Удачный снимок — одна транзакция (попытка, статьи, тексты по хешу, события); прерванный Ctrl+C в базу не попадает. События — `новая` / `изменена` / `перенесена` / `удалена`; одна смена даты «Modified on» событием не считается. Вопросы FAQ сами начинаются с «Q: » — своего префикса в строках нет.
- **Чужая или битая база не затирается**: `check_db()` читает в `mode=ro`, версия схемы (`PRAGMA user_version`) не 0 и не своя, не SQLite, версия 0 с чужими таблицами — отказ стартовать, файл не изменён. **Занятый порт проверяется до базы** (`_port_free()`, с `SO_REUSEADDR`, как uvicorn): uvicorn сообщает о занятом порте уже после входа в lifespan, и первый снимок успел бы начаться. Схема версии 1; день 19 добавляет таблицы миграцией 1 → 2.
- **`faq_changes` — только база**, два подписанных источника: «замечено сторожем» (события соседних снимков) и «по датам сайта» (последний снимок, граница — до суток: часовой пояс портала неизвестен). Потолки — `CHANGES_MAX_ITEMS`, `DIFF_MAX_LINES`, `DIFF_LINE_MAX_CHARS` (строка разницы — абзац статьи, длиннее — с «…») и общий бюджет ответа `CHANGES_MAX_CHARS` (меньше `TOOL_RESULT_MAX_CHARS` приложения: часть «по датам сайта» резервируется первой, события, которым не хватило места, идут без разницы или «не поместились»). Описания инструментов — промпт; правки по прогону — строкой в комментарии у констант.
- **`mcp_client.py` знает второй транспорт**: `McpServer.url`/`url_env` (у HTTP-сервера `command` пуст), `Launch.transport`, адрес проверяется `resolve_launch()` (иначе сбой «запуск» без подключения). HTTP SDK ходит через `httpx2`, его ошибки — не `OSError`: `httpx2.HTTPError` — в ожидаемых, `ConnectError` — «сервер не отвечает по адресу» на стадии «соединение», а не «запуск». Логгер `httpx2` приглушён до WARNING (строка на каждый POST — шум).
- **`McpToolBoxGroup` — несколько серверов как один `ToolBox`**: каталоги по очереди, дубль имени пропускается с предупреждением, сбой части серверов — необязательный ключ `warning` каталога, всех — `ok=False`. Вызов — по карте «имя → сервер» (единственное состояние группы), которую удачные каталоги только пополняют: иначе каталог хода другого агента, пока сторож лежит, выкинул бы из карты инструмент, законный по каталогу этого хода; имени нет — отказ без подключения. Агент дописывает `warning` к `tools_note` (« · ⚠️ …») и пишет WARNING в лог — больше в агенте ничего не менялось.
- **Блок «Сторож FAQ (день 18)» — снова вне `_view()`** (`WATCH_MCP_OUTPUTS`, `WATCH_DIGEST_OUTPUTS`, без `agent_state`): `_mcp_server_md()` / `_mcp_status_md()` знают HTTP-сервер (адрес вместо командной строки, подсказка `./run.sh faq-watch`, только когда сервер не отвечает по адресу — `mcp_client.is_no_answer()`; таймаут и чужой сервер на порту её не получают), сводка — `call_tool(FAQ_WATCH, "faq_changes", …)` дословно. «Инструменты последнего хода» переехали в этот блок, `_view()` — по-прежнему 37 значений.
- **Формат дня «видео + код»** — документа проверки нет; замер реального прогона (снимки, время, токены схем, Н1-Н4, имитация изменений, перезапуск, сбои) — комментарием у `FAQ_WATCH` в `presets.py`.

## Неделя 4: день 19 реализован

Спецификация — `docs/TooManyRules — День 19 спецификация.md` (композиция MCP-инструментов: памятка к столу — `faq_search` находит статьи в снимке сторожа, `faq_summarize` сжимает их в памятку моделью клиента через MCP sampling, `cheatsheet_save` сохраняет в Markdown-файл; цепочку по одной просьбе игрока ведёт агент, данные между шагами — по ссылке). Из решений дня 19 дальше в силе:

- **Три инструмента — на том же сервере, сторож (`src/faq_watch.py`), не новый.** Инструменты дня 18 (`faq_changes`, `faq_watch_schedule`) и планировщик не изменились. Версия сервера — `1.1.0`; новый аргумент командной строки — `--out` (каталог памяток, `presets.FAQ_CHEATSHEETS_DIR`, `src/data/cheatsheets/`, не в git; создаётся, если его нет).
- **Данные между шагами — по ссылке, не по значению.** Каждый шаг кладёт результат в базу и отдаёт короткий id (`q…` — поиск, `s…` — памятка); следующий шаг получает только id и сам достаёт данные из базы — ровно то, что записал предыдущий шаг. Так исключены три способа тихой порчи данных при передаче текстом: обрезка потолком результата, пересказ моделью своими словами, выдумка. Все три шага — на одном сервере: ссылка понятна только тому, кто её выдал.
- **Вид id проверяет сервер, а не JSON Schema.** Шаблон в схеме отсёк бы `"s3"` на входе `faq_summarize` ещё в SDK ошибкой валидации pydantic; сервер проверяет сам и отвечает понятным текстом («s3 — id памятки, а нужен id поиска (q…)») — модель по нему исправляется, а не гадает. Тот же приём — у `faq_summarize`/`cheatsheet_save`: снимок, на котором искали, пропал из базы, или в нём нет статьи — тот же отказ «повтори поиск» (снимки не удаляются, поэтому в обычном прогоне не встречается); хеш памятки в базе разошёлся с записанным при сжатии — «изменена после сжатия, сохранять не буду».
- **Поиск — по словам, не по смыслу, и только по последнему удачному снимку.** Токены — `[a-z0-9']+` в нижнем регистре, от 3 букв, без короткого списка служебных английских слов; слово запроса совпадает, если это начало слова статьи (`poison` находит `poisoned`). Оценка — 3 за совпадение в вопросе, 1 — в тексте; статьи с нулевой оценкой не берутся. Не RAG: ни эмбеддингов, ни индекса, ни автоматической подстановки найденного в контекст агента — тексты уходят только в сэмплинг сжатия.
- **Сэмплинг — шестая служебная работа агента, и единственная внутри основного запроса** (см. правило служебных вызовов выше). Сервер просит модель через `Annotated[CreateMessageResult, Resolve(fn)]` (SDK v2 сам ведёт цикл `InputRequiredResult`/повтор `tools/call` эры 2026-07-28 — сервер отвечает на первый раунд просьбой, на втором получает готовый результат; резолвер выполняется на каждом раунде, тело инструмента — один раз). Разрешение — поле `McpServer.sampling` (только у `FAQ_WATCH`; день 20 добавит серверов, и без явного разрешения чужой сервер получил бы модель агента за наш счёт). Клиент (`mcp_client.py`) переводит `CreateMessageRequestParams` в словарь и обратно, зовёт `sampler` через `anyio.to_thread.run_sync()` — вызов модели не блокирует цикл событий подключения, а `abandon_on_cancel` не выставляется намеренно: истёкший таймаут закрывает подключение только после ответа модели, а не обрывает уже оплаченный вызов.
- **Сбой сэмплинга на клиенте до сервера не доходит вовсе.** `sampler` вернул `{"ok": False, ...}` → `ErrorData` → SDK сам поднимает `MCPError` на стороне клиента и не шлёт второй `tools/call`; тело инструмента не выполняется, памятка не пишется. У агента это тот же путь, что сбой соединения (`TOOL_STATUS_UNAVAILABLE`) — «инструмент недоступен» с текстом сбоя.
- **`_run_tool_call()` передаёт `sample` в каждый вызов инструмента**, вне зависимости от того, умеет ли инструмент сэмплингом пользоваться — решает сервер, не агент. Каждая просьба сервера — отдельный `ServiceCall` (`kind="sampling"`), собирается через тот же `_call_service_model()`, что и остальные пять работ; все просьбы хода едут в `AgentReply.sampling_calls`. Обрезанный по `max_tokens` ответ (`finish_reason="length"`/`stop_reason="maxTokens"`) сервер не записывает — решение сервера, не агента (агент лишь возвращает ответ как есть). `finish_reason` в словаре `sample` — как у модели; перевод в `stop_reason` MCP — только в `mcp_client._stop_reason()`: агент словаря MCP не знает (правка по ревью). `ToolCallRecord.samples` агент считает по своим записям, а не по счётчику клиента (при таймауте посреди вызова модели они расходятся); отказ по `sampling_max_chars` — не вызов API и в счётчики не идёт.
- **Оборванная памятка не записывается** — то же правило, что у трекера задачи дня 13 (оборванный план/памятка хуже отсутствия результата); у стража инвариантов, для сравнения, оборванный ответ применяется — вердикт стоит первой строкой. У каждой служебной работы своё решение про обрезанный ответ, единого правила в проекте нет.
- **Файл памятки: заголовок, источники и строка происхождения пишет код, из базы** — модель пишет только пункты (уже проверенные на ссылки вне поиска). Путь — внутри `--out`, атомарная запись (временный файл + `os.replace()`), файлы не перезаписываются (совпадающее имя получает суффикс `-2`, `-3`), после записи файл перечитывается и текст памятки сверяется байт в байт — не совпало, файл удаляется, а не остаётся битым на диске.
- **`TOOL_MAX_ROUNDS` поднят с 4 до 6**: цепочке нужно 3 раунда с вызовами (поиск → сжатие → сохранение) плюс раунд ответа, 2 запасных — на `faq_questions` или повтор поиска. `WATCH_CALL_TIMEOUT_S` (60 с) — отдельный от `WATCH_TIMEOUT_S` (10 с) потолок именно вызова сторожа (`McpToolBox(..., call_timeout_s=…)`): вызов с сэмплингом ждёт ответа модели клиента, каталог — нет.
- **Блок «Памятка к столу (день 19)» — развёрнут наверху дебаг-панели**, «Инструменты последнего хода» переехали в него из блока дня 18 (те же компоненты и выходы `_view()` — по-прежнему 37 значений); строка «Цепочка» (какие id выданы и приняты каждым шагом хода — по журналу вызовов, без обращения к серверу) и колонка «сэмпл.» в таблице вызовов собираются внутри того же Markdown, новых выходов не добавляют. Сэмплинг — в «Последнем вызове», «Накоплено агентом» и в журнале ходов (`сэмпл. ток.`/`сэмпл. $`). Блок «Сторож FAQ (день 18)» свёрнут.
- **Модель решает, где остановиться** — код цепочку не достраивает: просьба «найди, но не сохраняй» доходит до `faq_search` (и, возможно, `faq_summarize`) и не доходит до `cheatsheet_save`; в панели это видно по строке «Цепочка», короче обычной или отсутствующей.
- **Формат дня «видео + код»** — документа проверки нет; замер реального прогона (протокол, схемы, П1-П3, число раундов вызовов, проверки передачи данных из §12 спецификации, сколько раз выполнился резолвер на вызов) — комментарием у `FAQ_WATCH` в `presets.py`. Прогон реализации подтвердил путь целиком на настоящем `deepseek-flash` (сэмплинг, полная цепочка из трёх инструментов, отказ без сохранения на «только найди»); числа на полном корпусе FAQ — шаг автора при записи видео.
